## §1 The fork

The cleared §14.9.8 per-server default-policy resolver returns, for every `(contract, step)`, a `SandboxDispatchDecision(tier=effective.sandbox_tier, …)` where `effective.sandbox_tier` is the surface-aware per-server default (`resolve_effective_sandbox_defaults`, §14.9.9 Reading A+: local-development → `TIER_1_PROCESS`). It does **not** compose the per-MCP-transport floor (ADR-D2 §1.3 — STDIO → Tier-3 microVM minimum) nor the remote-trust rows (C-AS-02 §2.3 rows 4-6 / C-AS-10 §10.1). The full `sandbox_tier_floor` lookup (U-AS-06) + the standalone `mcp_transport_floor` (U-AS-13) are **built in AS** but their RESOLVED tier never feeds dispatch:

- `mcp_transport_floor` is computed at registration (`mcp_host.py:106`) but only its `REFUSE` outcome is consumed (`:111`); the **RESOLVED** tier is discarded.
- The stage-5 dispatch resolver (`_build_default_policy_sandbox_resolver`) returns a CONSTANT; its `resolve(_contract, _step)` ignores both args.

The v1.43 §14.9.9 change-note **explicitly carved this out as a future arc**: *"The independent ADR-D2 §1.3 STDIO `tier-3-microvm` transport-floor … is NOT enforced by the §14.9.8 flat per-server-uniform MVP resolver this arc consumes — a bare STDIO local-development server resolves to `TIER_1_PROCESS`, below the §1.3 floor. That non-enforcement is the pre-existing §14.9.8 composition gap, carried forward and explicitly carved out at the §14.9.9 Scope boundary (distinct future arc)."* That future arc is **B6**. The §14.9.10 D4 (B2) re-affirms: the per-server-uniform→per-tool boundary is preserved, "per-tool sandbox granularity nests inside each host's resolver as the distinct future arc B6."

## §2 Resolution

### §2.1 Compose `mcp_transport_floor` (per-host), NOT `sandbox_tier_floor` (per-tool) — the function choice IS the Slice boundary

The stage-5 factory's **per-host** resolver/driver loop (Step 2b, `runtime_tool_dispatcher_factory.py`; per-host since B2/U-RT-130) composes the per-MCP-transport floor into each host's resolved tier:

```
floor = mcp_transport_floor(entry.transport, entry.trust_level, entry.blast_radius)   # U-AS-13
resolved_tier = tier_max(effective.sandbox_tier, floor.tier)                          # raise-only max()
```

**Why `mcp_transport_floor`, not `sandbox_tier_floor`** (advisor catch): `mcp_transport_floor(transport, trust_level, blast_radius)` is fed the **per-host** `MCPClientConfig.blast_radius` — ONE blast input per host ⇒ ONE tier per host ⇒ **per-server-uniform PRESERVED** (§14.9.8 scope honesty intact). Calling the full `sandbox_tier_floor(tool, …, contract.blast_radius_tier, …)` with the per-*tool* `contract.blast_radius_tier` would make the tier diverge per tool within a host → that silently pulls in the Slice-2 per-tool fork (rows 1-2 forcing + rows 7-10 per-tool blast) AND the coupled driver-granularity relaxation. `mcp_transport_floor` is exactly the per-host subset (STDIO row 3 + remote-trust rows 4-6), keyed on host-level properties (transport + trust + the per-host config blast). The two functions are semantically aligned on rows 3-6 (U-AS-06 AC5).

### §2.2 C10⊥C11 probe-resolved at ADR-D2 §1.3 in C10's favor — NO operator gate

The nameable cross-domain tension (§10.9 / §13.4): **C10** (action-safety / blast-radius — STDIO subprocess MCP has zero protocol-level auth; ADR-D2 §1.3 mandates a Tier-3 container minimum to prevent kernel-CVE-class escape) **⊥ C11** (operator-loop / local-deployment — out-of-box local-dev should work without a microVM substrate). **Probe (per `[[probe-resolves-fork-prescribed-council]]`): the cleared design already decided it.** ADR-D2 §Decision item 3: *"Per-MCP-transport sandbox-tier floor committing Tier 3 minimum for STDIO MCP transports **regardless of declared blast-radius**"* + §1.5 multiplicative `max()` composition ⟹ `max(local-dev-cell = Tier 1, STDIO-floor = Tier 3) = Tier 3` **even at local-development**. It is a **hard floor** — not overridable (§1.1 "Cell selection contract" permits operator override of the cell-*default* tier, but the transport-floor composes via `max()` on top, so a downward cell override cannot lower it below Tier 3). So enforcing the floor is **impl-to-cleared-ADR**, not a new decision; C10 already won at the ADR. Slice 1 therefore **fulfills** a committed mandate (sacrifices nothing) — the clean distinction from B4 Slice 4, which *relaxed* §14.5.3 (a committed-invariant sacrifice → operator's call). No AUQ.

### §2.3 `REFUSE` handled as a defensive raise (unreachable-by-construction)

`SandboxDispatchDecision.tier` is non-optional; `mcp_transport_floor` returns `REFUSE` (not a tier) for L0-remote. But L0-remote is **already refused at registration** (`materialize_mcp_stage` → `MCPServerRefusedError` at `mcp_host.py:111`; §14.9.10 D1 host materialization), so a host that survives to the stage-5 resolver loop can never be L0 → a resolver-level `REFUSE` is **unreachable-by-construction**. It is guarded by a defensive raise (`RT-FAIL-…` / `AssertionError`-class), not a returned decision — never a silent tier substitution.

### §2.4 Out-of-box behavioral change (named front-and-center, not gated)

Enforcing the floor **flips local-dev STDIO `TIER_1_PROCESS` → `TIER_3_MICROVM`** (and L2-remote → `TIER_4_FULL_VM`). Those hosts now require a configured `sandbox_driver` (microVM/VM) or **bootstrap fail-closes** with `RT-FAIL-SANDBOX-DRIVER-UNAVAILABLE` (§14.9.9 FR-2(i)). This is the most common MCP setup (STDIO subprocess servers), so it is a real out-of-box change — but it is the **cleared ADR-D2 §1.3 mandate**, and the §14.9.9 fail-loud floor makes it **safe** (a STDIO server never *silently* under-sandboxes at Tier 1; it either runs at Tier 3 or refuses to boot). This is documented in the PR + checkpoint, not surfaced as a blocking AUQ (pre-authorized + impl-to-cleared-ADR).

## §3 Test cascade (as-built; verified at HEAD)

STDIO + no-`sandbox_driver` host configs that run through the stage-5 factory fail-close at bootstrap once the floor is enforced. The cascade was **sized empirically** (advisor-directed) — the full `harness-runtime` suite was run pre/post and each break traced. Actual disposition:

- **Factory tests** (`test_u_rt_75_runtime_tool_dispatcher_factory`, 4 breaks): the 2 STDIO helpers (`_config_with_server`, `_bare_server_config`) gain a tier-3 `sandbox_driver` config (the driver OBJECT constructs without docker; only `call_tool` shells out) so bootstrap succeeds; the 3 resolver/emitter tests assert the floored TIER_3 + the floor-aware reason; the 2 driver tests were repurposed to the B6 reality (STDIO bare → fail-loud; STDIO + driver → gVisor at TIER_3). The pure TIER_1-in-process / TIER_2-Docker driver-registry coverage stays in `test_sandbox_tier_driver_selection.py` (direct `_select_tool_execution_driver` calls, floor-independent).
- **`test_u_rt_86_mcp_client_external_server_e2e` (the H_T-AS-2 / H_T-CP-18 retirement evidence): UNAFFECTED — verified ran-and-passed at HEAD (2 passed, NOT skipped).** It dispatches via the `MCPClientHost.call_tool` path directly, NOT through the stage-5 FR-2 driver-selection factory, so the floor never hits it. `ToolContract` is still enforced at dispatch regardless of tier → the retirement evidence is preserved (it was never about the sandbox tier).
- **In-process-STDIO dispatch e2e (`test_r100_ac2_tool_step_via_api_run` + `test_r_cl_p3_live_multi_tier_api_run`×3): SKIPPED with B6 reasons.** These run a real in-process STDIO echo subprocess via `api.run` and relied on STDIO dispatching at TIER_1 — the **pre-B6 gap** ADR-D2 §1.3 forbids. At TIER_3 the dispatch routes to a container runner (not the in-process echo), so they cannot run substrate-free; converting them to container-gated would duplicate `test_r410_container_tool_execution_e2e`. They are skipped (preserved intact), tool-completion-at-the-mandated-tier covered by the Docker-gated R-410, and the DEFAULT-LANE restoration registered as `B-MCP-HOST-REMOTE-TRANSPORT` (a remote L1 RO server would resolve to TIER_1 and restore a substrate-free api.run tool-completion e2e — blocked today by the host-factory `_VALID_TRANSPORTS` rejecting the granular remote enum).
- **New tests** (`test_sandbox_tier_driver_selection.py::compose_transport_floor` suite — the primary floor-logic coverage): STDIO local-dev TIER_1 → TIER_3 (+ gvisor/runsc + floor-aware reason); STDIO self-hosted TIER_2 → TIER_3; remote L2 → TIER_4; remote L1 RO → unchanged TIER_1 (+ per-server-default reason retained); minimum_tier unchanged under the floor; operator tech-override survives the raise; remote L0 → defensive raise. Plus the factory-level contrast tests above.

**Coverage note (advisor-flagged, surfaced honestly):** gating the in-process e2e removes the only DEFAULT-LANE proof that `api.run` *completes* a tool workflow. Within B6's scope this is an accepted loss (the in-process config was ADR-forbidden); the floor behavior is proven at factory + unit level and R-410 proves container completion. Full default-lane restoration is `B-MCP-HOST-REMOTE-TRANSPORT`. **If "STDIO MCP tools cannot run in-process even at local-development" is too strict for the out-of-box story, that is an ADR-D2 §1.3 revision via design back-flow — operator's call (surfaced at the checkpoint; does not block this arc).**
