The engine-resume firing is gated on the **presence of a pause record** (`RuntimeEngineRecoveryLoop.has_pause_record`, a pure non-emitting substrate read), **NOT** on the F2 step prefix (`resume_at > 0`) and **NOT** on resume validity. This was sharpened by decorrelated out-of-family Codex review across **four rounds**; the correctness story has three load-bearing parts:

1. **Presence-not-`resume_at` gate (Codex round-2 [P2]):** gating on `resume_at > 0` was wrong in **both** directions — (a) it fired a spurious `cp.resume-attempted = ABORT_SNAPSHOT_CORRUPTED` for an ordinary step-prefix crash recovery with no engine pause, and (b) it silently never resumed an engine pause captured **before** step 0 (resume_at==0). The presence check is the sole gate; `RESUMPTION` fires when resuming a committed step prefix OR a present engine pause.
2. **Presence-not-validity + fail-closed (Codex round-3 [P1-r3-a/b]):** the gate's earlier form (`has_captured_pause`) used the resume *outcome* (validity) as a presence proxy — so a present-but-**corrupt** snapshot was misread as *absent*, silently skipping the resume (losing the abort record AND resuming past unrecoverable state). The root fix renames the gate to `has_pause_record` (**true presence** — file exists & non-empty, corrupt or not) and the driver **fails the run closed** on any aborting `ResumeOutcomeKind` (`ABORT_SNAPSHOT_CORRUPTED` → `CP_FAIL_PAUSE_SNAPSHOT_CORRUPTION`; `ABORT_REVALIDATION_FAILED` → `CP_FAIL_RESUME_MATERIAL_DIFF_DETECTED`), mirroring the cleared workflow-layer `if not resume_result.resumed: return FAILED` precedent. Both fail-classes are pre-existing C-CP-26 §26.5 constants (no new contract — X-AL-3-clean); the `cp.resume-attempted` entry the fire emits is the durable audit record of the abort.
3. **Run-scoped storage key (Codex round-4 [P2]):** the WAL pause record and the F2 replay prefix are two halves of one resumption mechanism, so they must share a scope. The F2 prefix is run-scoped (`run_idempotency_key` includes `run_id`); the pause record was keyed by `workflow_id` only — so a fresh run of the same `workflow_id` (different `run_id`) would pick up an earlier run's lingering record, and a lingering *corrupt* record would fail-close **every** future run of that `workflow_id` (a permanent DoS). The fix run-scopes the durable **storage key** to `(workflow_id, run_id)` (a collision-free SHA-256, computed in `RuntimeEngineRecoveryLoop`), while the **ledger** entries keep the plain `workflow_id` (the audit reads `wf-X`, matching the `workflow.envelope` `workflow.id`). Resume reuses the same `run_id`, so a different `run_id` is by construction a new execution — run-scoping isolates fresh runs without ever breaking a real resume. The capture + resume branches compose the key identically.

**Residual (retention hygiene, not a correctness gap):** with run-scoping, an abandoned run's segment file lingers on disk under its own run-scoped key (gitignored runtime state under `.harness/engine-recovery-segments/`). It can never be matched by a different run, so it is a disk-retention concern, not a correctness leak — deliberately not bundled into this arc (a separate retention/compaction refinement).

## §2 — Finding 1 (recorded-not-gated, O-CP-4 / E-impl-1 precedent): the CP/IS-level resume_at is degenerate-vs-save-point; the genuine WAL_SEGMENT capability is the durable substrate + loop firing

Exactly as EVENT_SOURCED_REPLAY at E-impl-1 (`.harness/r-fs-1-e-impl-1-finding.md` §2), the WAL_SEGMENT **resume_at computation** (`_determine_segment_replay_resume_at` → `_determine_resume_at`, the F2 idempotency-key prefix) is **behaviorally identical to save-point skip-prefix** at the CP/IS level. The §8.1 `segment_replay` "per-segment dedup" manifests as the F2 idempotency-key join (a re-materialized segment's key already resolves to an entry → not re-applied); the "replay from WAL segments" manifests as the prefix not being re-dispatched. This is the **same accepted bar** save-point + EVENT_SOURCED_REPLAY already carry.

**The distinction that makes E-impl-2 NOT a built-but-vacuous trap** (unlike a degenerate resume_at alone): WAL_SEGMENT delivers a **genuine new capability** save-point lacks — the **durable WAL segment-log substrate (U-RT-121)** + the **engine-layer recovery-loop firing in production (U-CP-95 + U-RT-122)** → `cp.pause-captured`/`cp.resume-attempted` land against a crash-survivable store with **distinct engine-layer action_ids**, proven **by execution** (not grep). That IS the R-CXA-2 CP→IS engine-layer producer seam going live (its first real driver). "Who reads `cp.pause-captured`?" — the entry landing with the distinct engine-layer action_id IS the producer seam; OD ingestion is the standing downstream D6 pattern (the same accepted bar as all CP→IS emission).

The genuine **cached-output / output-carrying-event-history** refinement (§8.1 "cached … replayed") remains the registered **`B-ENGINE-OUTPUT-REPLAY`** + **B-INTERSTEP** build arcs (shared with EVENT_SOURCED_REPLAY) — not this unit's burden, not a silent defer.

## §3 — Finding 2 (Class-3 plan-AC-vs-precedent reconciliation): `resumption.is_replay` rides the standing-deferred L9 OTel layer — bare RESUMPTION emitted, no span-attr producer

U-CP-94's functional AC mentions post-resumption `step.boundary` spans carrying `resumption.is_replay: bool` (§8.3 item 2). Per the **E-impl-1 precedent** (`.harness/r-fs-1-e-impl-1-finding.md` §4) and the U-CP-93 `_IN_SCOPE` comment, `resumption.kind`/`resumption.is_replay` are the **standing-deferred L9 OTel-span layer shared across all engine classes**: the driver emits bare `WorkflowEventClass.RESUMPTION` (CP emits typed events; OD/runtime ingests + populates span attributes — the D6 pattern). There is **no CP-side producer for the span attribute**, so WAL_SEGMENT mirrors EVENT_SOURCED_REPLAY: bare RESUMPTION, **no test asserts a span attribute that has no producer**, and minting a WAL-only span producer would diverge from the cross-engine-class consistency (X-AL-3-adjacent). Recorded here as the same disposition as E-impl-1 — Class-3, recorded-not-gated.
