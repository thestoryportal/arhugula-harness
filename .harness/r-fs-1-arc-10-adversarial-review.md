The linear sibling `_append_step_ledger_entry` populates it from `ctx.procedural_tier_snapshot_resolver` (the R-003 producer-site lift, PR #137). The R-003 lift is a **landed invariant** realized across multiple CP producer sites today: `pause_resume_protocol.py:812/899/1003`, `sibling_ledger_entry_composition.py:158`, `per_step_override_evaluator.py:295`, and the linear driver append. ## Findings considered and rejected (transparency)

- **R-1 (Timestamp policy = spec contradiction → HALT-route?) — REJECTED.** The impl's reasoning is sound. CP §25.12 (`Spec_Control_Plane_v1_32.md:75-83`) constrains append *order* ("serialized through the single writer in deterministic declaration order … NOT completion order"); it says nothing about timestamp *values*. IS §5.4 + the IS writer are silent on values beyond the non-decreasing invariant (`state_ledger_write.py:221-227`). The canonical reading — timestamp = ledger-append event, consistent with the linear path's `datetime.now(UTC)` at append (`workflow_driver.py:1579`) — is coherent. A fan-out is one barrier-drain persist event; a single shared fan-out timestamp is trivially monotonic. **No §2.7.6 fork.** (Footgun residue captured as F1-02.)
- **R-2 (Terminal idempotency-key collision — the arc-9 dedup defect class) — REJECTED (provably distinct).** Independently recomputed `sha256(run_idempotency_key, step_index, branch_path)`: step `branch_path = f"{pa}:{bi}"` (`bi` an int) never ends in `:terminal`; terminal `branch_path = f"{pa}:{bi}:terminal"` always does → preimages byte-distinct → keys differ regardless of `step_index`. Verified for same-branch, cross-branch (`b1:terminal` vs all `b11` steps), and nested fan-out (`pa = ...:branch:0:step:7`). The IS writer dedups **solely** on `idempotency_key` (`state_ledger_write.py:218`), so distinctness is the right and sufficient guard. Test `test_terminal_idempotency_key_distinct_from_all_step_keys` exercises it. Sound.
- **R-3 (Terminal `WriteKey.step_id` collision) — REJECTED (non-issue).** `append_ledger_entry` reads `write_key.idempotency_key` only (the equality check `:212-215`); `thread_id`/`step_id` are never consulted in the dedup/persist path (IS §7.5 reading-iii — write-args, not persisted). So terminal `step_id = f"{bi}:terminal"` cannot affect dedup or persistence. Sound.
- **R-4 (Append-only / no-mutation — is the terminal disposition a genuine fresh append?) — REJECTED (sound, e2e-proven).** The terminal entry is a fresh `EntryPayload` with its own distinct `action_id` (`{pa}:branch:{bi}:terminal`) + distinct idempotency key, buffered as the branch's last entry and drained through the real writer (never a re-hash of a prior entry). `test_terminal_entry_is_fresh_append_not_mutation` reads back N step + 1 terminal entries and asserts `verify_chain == VALID` (which would FAIL on any re-hashed prior entry). Matches IS §5.4 append-only invariant (`Spec_Information_Substrate_v1.md:503`) + runtime §2.2 item 3 (`Spec_Harness_Runtime_v1.md:2096`).
- **R-5 (Test rigor — recording fake vs real writer?) — REJECTED (real writer).** `_RealLedgerWriter.append` routes every buffered `(payload, write_key)` through the REAL `append_ledger_entry` (`test_...cadence.py:104-105`), exercising dedup + zero-tolerance monotonicity + hash-chain + JSONL persistence, then re-reads via `read_ledger` and `verify_chain`. `results` records each `WriteResult` so a silent `IDEMPOTENT_NOOP` drop is observable (`assert all(r is WriteResult.APPENDED ...)`). The scrambled-completion determinism test drives REAL `asyncio` concurrency (`asyncio.as_completed`) and asserts completion-order ≠ branch-index-order before draining. Not a fake.
- **R-6 (Scope-fencing — does the impl decide the disposition, usurping U-CP-85?) — REJECTED (clean).** `terminal_status` is a caller-supplied param (`compose_branch_metadata(..., terminal_status=...)`, `workflow_driver_types.py:392-395`); the helpers persist what they are handed. U-CP-85's cascade logic decides *which*. The `Literal["cancelled","completed","timed_out"]` forecloses `failed` per IS §5.4 (`Spec_Information_Substrate_v1.md:487`) + CP §25.15.2 obl. 4 — `test_ran_and_errored_branch_terminal_is_completed` proves the ran-and-errored→`completed` rule. Sound.
- **R-7 (Linear `_append_step_ledger_entry` behavioral change?) — REJECTED (byte-identical).** The diff (`git show 5ede2d2`) touches `_append_step_ledger_entry` not at all; `branch_metadata` defaults to the carrier's `None` (`state_ledger_entry_schema.py:132`), so linear entries are unchanged. (The `procedural_tier_snapshot_ref` asymmetry is the branch helpers *omitting* what the linear path keeps — F1-01 — not a change to the linear path.)
- **R-8 (X-AL-3 anti-extension — does the impl introduce an unauthorized contract/field/value-set?) — REJECTED.** No new IS field (`BranchMetadata` is U-IS-19, arc #7), no new value-set (`{cancelled, completed, timed_out}` is IS §5.4-committed), no new contract. The `action_id`/`branch_path`/terminal-path string shapes are CP-side write-arg composition (CP §25.16 authorizes branch-scoped key composition; `:terminal` suffix is a producer-cadence detail the spec explicitly defers to B1-spec-2). Phase-7 impl posture, `harness-cp/src` + tests only → X-AL-3 trivially clean.
- **R-9 (Nested-fan-out global `action_id` uniqueness) — REJECTED.** `compose_branch_terminal_action_id` = `{parent_action_id}:branch:{bi}:terminal`; `parent_action_id` is the spawning step's globally-unique `action_id` (which under nesting is itself a branch-step `action_id`), so the shape composes recursively unique at every depth (IS §5.4, `Spec_Information_Substrate_v1.md:485`). `:terminal` cannot collide with any `:step:{int}` suffix. Sound.
- **R-10 (Integration AC "Verified at B1-impl-N" — honest deferral?) — REJECTED (honest, and partially over-delivered).** The plan marks the integration AC (persisted-branch-causality reconstruction) "Verified at B1-impl-N" (`Implementation_Plan_Control_Plane_v2_32.md:155`). `test_branch_entries_round_trip_real_writer` *already* reads back `(parent_action_id, branch_index)` + discriminating `terminal_status` through the real writer + `verify_chain` — so the integration AC is partially satisfied *now*, not silently punted.
