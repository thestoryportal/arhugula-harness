## Recommended design (one paragraph, committal)

C1 specifies handoff contract: the operator-facing correlation identity is a **deterministic, domain-separated digest over the branch child context's `(parent_idempotency_key, branch_index, placement.position)`** — call it `escalation_instance_id` — **plus the plain `branch_index` ordinal**, both riding as NEW Optional (`None`-default) fields on `HITLEscalationBrief`, minted at the single already-factored escalation choke point `RuntimeHITLGateComposer._escalate_to_secondary_channel` (`hitl_gate_composer.py:1259`), threaded outward on the webhook via the existing brief adapter and threaded *inward* to the operator's pause snapshot by copying it off `HITLPauseRequestedSignal.brief` (the signal already carries the brief — `hitl_gate_composer.py:1336-1339`) into `PreDispatchGateOwningBranchResumeState` — so the SAME identity appears at both ends of the correlation with ONE mint site. The webhook delivery idempotency key gains the same discriminator as a suffix when `branch_index is not None` (linear path byte-unchanged), because without that, branch-distinct payloads still collide at every dedup layer. The identity is deliberately **correlation-only, structurally not an address**: it is not run_id-shaped, cannot collide with a `hitl_responses` key, and a mistaken paste of it into `hitl_responses` falls through to the safe INERT re-pause. Property 1's key shape untouched (constraint 1 ✓); the internal `f"{snapshot_run_id}:pre-dispatch-gate:{branch_index}"` string never crosses the boundary — only a one-way projection of the same basis does (constraint 2 ✓); available strictly pre-dispatch (constraint 4 ✓); the 2+-concurrent story is stated honestly below, not relabeled away (constraint 3 ✓).

## Identity shape + minting site (grounded, file:line)

**(a) The branch-distinct, pre-dispatch-available quantity.** Grounded in the actual call path, the winning basis is already fully composed before any child run exists:

- `StepExecutionContext.branch_index` (`workflow_driver_types.py:298`) — set at branch-spawn by `compose_branch_child_context` (`workflow_driver_types.py:586-648`, spawn site `workflow_driver.py:8351`). Branch-distinct by construction; property 6's own discriminator.
- `StepExecutionContext.parent_idempotency_key` — inherited verbatim by every peer branch (`workflow_driver_types.py:630-633`), so branch-*shared*, but **run-instance-distinct**: it is `_compute_step_idempotency_key(run_idempotency_key, step_index)` where `run_idempotency_key = sha256(run_id, workflow_id, *extras)` (`workflow_driver.py:646-665, 668-694, 3312`). The spawning invocation's own `run_id` is folded in — this is exactly the recursion-proof property the B-39 keying-defect note proved `branch_path`/`parent_action_id` lack (`pause_resume_protocol_types.py:1352-1388`: two peer branches dispatching the same `child_workflow_id` have byte-identical internal `action_id`/`branch_path`, but distinct run-lineage keys).

The composite `(parent_idempotency_key, branch_index, placement.position)` is therefore: branch-distinct among peers (ordinal), instance-distinct under recursion and repeated same-manifest dispatch (run_id folded in), distinct across two gates on one branch (placement — a pre-dispatch owner can be `PRE_ACTION` on an `INFERENCE_STEP`/`TOOL_STEP`, not only `SUB_AGENT_BOUNDARY`, per the round-5-corrected resume guard at `workflow_driver.py:8089-8105`), and tree-wide unique — the same uniqueness argument spec v1.108 §1.1(d)'s codex round forced onto the *internal* identity, satisfied here by the same (run-instance × ordinal) basis. Critically it exists **before dispatch**: it is an *input* to `compose_child_run_id_seed`, not an output of dispatch — so it covers `PURE_PATTERN_NO_ENGINE`, where the child run_id is a uuid minted only at dispatch (round-7 narrowing, charter constraint 4).

Rejected alternatives: **bare `branch_index`** — fails tree-wide uniqueness (two barriers' "branch 0" collide; the exact §1.1(d) collision codex flagged for the internal identity applies unchanged externally). **Parent `run_id` + ordinal, exposed raw** — the right *basis* but the wrong *exposure*: raw run_id on the brief invites the operator to key `hitl_responses` by the parent run's id, and since a resumed run consults `hitl_response_for(run_id)` with *its own* run_id (`workflow_driver_types.py:569-572`), a parent-run_id key is not inert noise — it is a live misattribution path. That is direct pressure on §1.1(b); the one-way digest forecloses it structurally. Also run_id is not currently in composer scope, so it would cost new threading the digest basis doesn't need. **Fresh per-escalation uuid** — fails the C1 lifecycle tests outright: a resume-forward re-fire of the still-unresolved gate would mint a *new* identity, presenting one logical checkpoint as a stream of distinct requests; duplicate-suppression and operator continuity both break. Deterministic minting is load-bearing, not aesthetic.

**Minting site.** C1 places the mint at `_escalate_to_secondary_channel` (`hitl_gate_composer.py:1259-1339`) — the U-RT-119-factored single body both escalation routes (§14.8.8.1 step-4-bis durable-async at `:2033` and §14.8.9 timeout dispatch at `:2165`) already share. One mint site, zero new choke points. Correction to the charter's grounding pack worth recording: the helper's own parameter list today carries only `tenant_id` from the context — but **both callers hold the full `step_context`** (they read `step_context.tenant_id` at `:2039`/`:2171`), so the threading is a private-helper parameter widening (pass `step_context`, or `branch_index` + `parent_idempotency_key`), not a Protocol or driver change. No `StepExecutionContext` field additions, no driver-side changes to mint.

## Carrier + threading path

C1 specifies handoff contract — three carriers, each with a distinct job:

1. **`HITLEscalationBrief` gains two Optional fields** (`validator_framework_types.py:134-151`): `escalation_instance_id: str | None = None`, `branch_index: int | None = None`. Optional-with-None-default per falsified premise (ii) — the frozen model's existing constructors (the validator-framework path constructs briefs too) stay valid; linear/non-fan-out escalations carry `None` and are byte-identical to today. The brief is the right primary carrier because it is *both* the webhook projection source (`deliver_webhook_for_brief(durable_brief, ...)`, `:1328-1330`) *and* the signal payload (`HITLPauseRequestedSignal(brief=durable_brief, ...)`, `:1336-1339`) — one field addition feeds both directions. Webhook-payload-only enrichment was the tempting smaller carrier; C1 rejects it because it severs the inbound half: the driver would have no channel to echo the identity into the snapshot.
2. **Snapshot echo**: the driver, catching `HITLPauseRequestedSignal` at the fan-out barrier and recording `PreDispatchGateOwningBranchResumeState(branch_index, step_id, step_kind, child_workflow_id)`, copies `signal.brief.escalation_instance_id` into that record (additive Optional field; rides under the §1.3a drop-when-empty hash-strip convention already authorized for this carrier family). This closes the correlation loop: the webhook request and the operator-visible pause state carry the **same** identity, joined by equality, with no recomputation and no second mint site. Without the echo, the identity is distinct-but-orphaned — the operator can tell requests apart but cannot tie either to a snapshot row across runs (the brief's `parent_action_id` is workflow-scoped, not run-scoped). This is a follow-on spec-leg item (a property-6-adjacent carrier addition), flagged as such, not silently absorbed.
3. **Idempotency-key composition**: `compose_hitl_action_id` (`hitl_gate_composer.py:428-440`) → append the discriminator when branch context is present: `hitl:{parent_action_id}:{placement}:{escalation_instance_id-or-branch-qualifier}`; `None` branch → today's shape byte-exact. This mirrors the §25.16 `branch_path` precedent (`workflow_driver.py:668-694` — same problem, same fix, one layer down: N peers must not collapse under key-only dedup). The `hitl:` prefix is preserved — it is the OD audit-trace discriminator (CXA v2.9 §0.3 8-prefix table); only the suffix grows. Without this carrier change the brief fields are moot: a dedup layer keying on today's byte-identical `hitl:{parent_action_id}:{placement}` will suppress peer B's delivery as a replay of peer A's, and the operator never sees the second request at all.

**What this does NOT do to B-39 addressing** (constraints 1+2): `hitl_responses` stays exclusively `child_run_id`-keyed; the digest is not a valid key there and never becomes one; pre-dispatch owners still resolve ONLY via property-4/6 sole-membership uniform fallback. The identity's operator-facing semantics are: *"this names the request; it does not address the response."* The separate, narrower original-B-71 half — exposing an **already-dispatched** child's real `run_id` on that child's own internal-gate escalations so the operator can build a `hitl_responses` key — is compatible with this design (same brief, a third Optional field) but is an addressing-capability exposure, which is C10's call, not mine (seam question 3).

## 2+-concurrent story

Property 6(c) is unamended by this design and should be stated to the operator, not papered over. With distinct identities the operator experience becomes: **N distinguishable, stably-identified requests; collectively parked**. Concretely: (1) each of the N pre-dispatch escalations arrives as a distinct webhook request (distinct payload *and* distinct idempotency key — today the operator receives byte-identical requests, or possibly only one, dedup-suppressed); (2) each re-pause/re-fire cycle re-presents the *same* `escalation_instance_id` per branch — the operator sees "still request X," never a phantom new request; (3) resolution remains serialized by contract: the operator addresses run_id-keyable (already-dispatched) peers via `hitl_responses` first; when exactly one unaddressed gate-owner remains, the sole-membership uniform fallback delivers (`workflow_driver.py:8340-8350`); while 2+ remain and ≥1 is pre-dispatch, **every member re-pauses INERT** — the §1.1(c) accepted liveness limit. The escalation payload should say so when the composer can know it (the honest wording is C11's surface — consultant seam).

Does the design create pressure to violate §1.1(b)? It *surfaces* pre-existing pressure — an operator who can distinguish two requests will want to answer them distinctly — but it does not *yield* to it: the identity is one-way, non-run_id-shaped, and a misdirected `hitl_responses` entry keyed by it simply never matches → INERT re-pause (property 4's safe failure), never misattribution. The stable external identity is also exactly the handle a *future*, properly-specified property-6 extension (a uniform-response *target selector* riding a new resume-context field — NOT `hitl_responses`) would key by; C1's position is to **register that as a follow-on B-\***, not design it here — it is an observable contract change to a cleared mechanism and routes through its own spec leg (X-AL-3).

## Failure modes + mitigations (C1 domain)

- **Resume-forward re-fire** (an unresolved pre-dispatch gate re-fires every resume cycle — the confirmed B-72 behavior, v1.108 change-note): deterministic mint basis → identical identity + identical idempotency key on every re-fire → dedup layers correctly classify it as the same logical request. Mitigated by construction; the uuid alternative fails exactly here. Whether re-delivery should *refresh* (reminder semantics) vs stay suppressed is C9's knob, flagged not decided.
- **Digest-input instability across resume**: basis = `run_id` (snapshot-preserved: the sole-membership comparison at `workflow_driver.py:8346-8349` equates the resume frame's `run_id` with the snapshot-derived eligible identity — it could never succeed otherwise), the fan-out step's static `step_index`, and the manifest-ordinal `branch_index` → stable across pause/resume cycles.
- **Ordinal instability / manifest edits**: `branch_index` derives from static manifest order and the resume validator identity-guards it loudly — bounds, disjointness, `step_id`, captured `step_kind`, `child_workflow_id` all checked, material edits **rejected** not silently re-bound (`workflow_driver.py:8071-8118`). The ordinal is stable-or-rejected. Residual: an edit swapping two byte-identical steps is undetectable — and also semantically inert.
- **Webhook transport retries** re-deliver an identical payload under an identical key — safe under any idempotent consumer; unchanged from today's contract (C9 owns retry posture; `WebhookDeliveryExhaustedError` propagation unchanged, `:1287-1288`).
- **Two-mint-site drift** (webhook says X, snapshot says Y): foreclosed by minting once at the composer and threading the *value* inward on the existing `HITLPauseRequestedSignal.brief` channel — the signal is the already-specified control-transfer contract between composer and driver; no parallel plumbing.
- **Cross-cutting pre-checks** (standing C1 obligations): *cost* — a few hundred bytes per escalation payload/snapshot record; negligible, no fan-out multiplier concern. *Observability* — the mint point is a natural span-attribute site (`hitl.escalation.instance_id` on the `hitl.invocation.*` family); C7 to specify, flagged per the charter's observability note. *Reliability* — failure surface unchanged (delivery exhaustion, pause, signal); the new fields are Optional and inert on every legacy path.

## What I need C10 to answer (the seam questions)

1. **Projection strength**: is a domain-separated SHA-256 digest over `(parent_idempotency_key, branch_index, placement)` acceptable as the external handle, or does C10 require decoupling from key-derivation material entirely (the raw `parent_idempotency_key` feeds `compose_child_run_id_seed` — does a one-way digest with a distinct domain prefix sufficiently sever that lineage)?
2. **Snapshot echo**: any blast-radius objection to the same identity living durably in the operator-visible pause snapshot (it becomes a persistent correlation handle across the run's paused lifetime)?
3. **The addressing half**: for *already-dispatched* children's internal-gate escalations, may a real `hitl_responses`-keyable `run_id` transit the webhook channel at all — or must addressing keys only ever be read from the snapshot the operator directly holds, keeping the external channel correlation-only? My design works under either answer; the brief's field set differs.
4. **Replay semantics of the widened idempotency key**: does branch-distinctness weaken any replay/spoof property C10 currently derives from the coarser byte-identical key (N distinct keys where one existed)?
