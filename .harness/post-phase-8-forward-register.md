### B-1 · Layered capability-aware routing activation `⚖️ council-eligible`
- **Current state (empirically verified this session).** Provider construction is **live** — all 3 adapters (`AnthropicAdapter` / `OpenAIAdapter` / `OllamaAdapter`) built at bootstrap stage-3a (`providers.py`). The retry/breaker/**fallback-chain dispatch** (`C-RT-16`, `lifecycle/retry_breaker_fallback.py`) **is wired** at the stage-5 `StepDispatcher` and iterates fallback candidates (primary → same-family → cross-family → terminal) with `advance_or_raise` on per-candidate exhaustion. **But the layered routing-*selection* path is a stub:** `routing_core_surface.infer()` raises `NotImplementedError` (`routing_core_surface.py:83`/`:97`), and `layered_routing_strategy.route()` has **zero non-test callers** (verified). So *which provider to use* is taken statically from the manifest `model_binding`, not from capability-aware layered routing.
- **What this means for the harness.** Provider plumbing + failure-time fallback exist; **capability-aware provider *selection* is not active.** Combined with B-2, the multi-provider machinery is present but **unexercised at MVP**.
- **Close-out steps.** (1) Implement the `infer()` composition seam to invoke `layered_routing_strategy.route()` (declarative-layer first) before provider dispatch (CP spec C-CP-02); (2) bind per-layer time-budgets (C-CP-03 `LayerBudget`); (3) implement capability-shortfall fallback (C-CP-04 + ADR-F1 §Consequences(c)) — fall to a capable provider *before* the step fails when the primary lacks a required capability (e.g. extended-thinking).
- **`⚖️ Council (C5 ⊥ C9 ⊥ capability-preservation).`** Designing the routing-selection policy is a genuine tension: **cost** (cheapest-deterministic-first) vs **reliability/recovery** (when to fall back / breaker thresholds) vs **capability-preservation** (don't route a thinking-required step to a non-thinking model to save cost). Convene a dyad (cost-voice + reliability-voice) when this arc opens.

### B-39 · Nested paused-child HITL-response ROUTING (per-child operator response delivery) *(split from B-32 after a same-session Codex review found the first routing attempt had 3 real defects; not shipped)*
- **What it is.** Two or more concurrently-paused peer/nested children (PARALLELIZATION `asyncio.TaskGroup`, or nested ORCHESTRATOR_WORKERS/HIERARCHICAL_DELEGATION recursion) share ONE run-level `ctx.resume_context_holder`. Delivering each paused child its OWN correct operator HITL response — without one child silently starving another, and without a later unrelated resume accidentally reusing a stale response — is unresolved.
- **Current state.** A first attempt built `ResumeContext.hitl_responses: dict[str, HITLResult]` keyed by the paused child's `workflow_id` (mirroring the existing `effect_fence_resolutions` per-branch pattern), consumed via non-destructive `peek()` + keyed lookup at the runtime HITL gate composer's resume Step-0. It was mutation-probed (reverting broke the composer-level routing test) and passed the full workspace suite — but out-of-family Codex review caught 3 real defects before it shipped, all confirmed correct on direct inspection:
  1. **Never one-shot-consumes.** `peek()` is non-destructive by design (that's what avoids the original race), but nothing ever clears a KEYED entry once delivered — a LATER, unrelated HITL-composed step sharing the same `workflow_id` (e.g. the same child dispatched again, or coincidentally reused) would silently reuse the stale response instead of requiring a fresh operator gate.
  2. **`workflow_id` is not branch-unique.** Fan-out siblings can legitimately dispatch the SAME `child_workflow_id` — the runtime already uses `branch_path` (§25.16 idempotency-key composition, `compose_branch_path`) specifically to disambiguate this case. A map keyed only by `workflow_id` collapses two such paused siblings onto one entry, so both would receive the SAME operator decision.
  3. **The delivery mechanism itself is unresolved, not just the map shape.** `execute_workflow` / `child_workflow_runner` currently accept NO `resume_context` parameter at all (only `pause_snapshot_input`) — there is no existing plumbing that threads a resolved per-child value into a recursive child's OWN internal re-entry. `effect_fence_resolution`'s per-branch pattern (the thing this attempt mirrored) resolves PARENT-side and threads a single resolved value onto the CHILD's `StepExecutionContext` — but that field is consumed by TOOL-step dispatch code within the SAME step, not by a recursive child's OWN composer at a deeper recursion level. So the "mirror the effect-fence shape" premise this attempt started from does not actually carry through to the recursive-child case; the threading path needs its own design, not just a differently-keyed map.
  The attempt was fully reverted (not shipped) rather than landed with known defects.
- **Close-out steps.** Design constraints for the next attempt, per the 3 findings above: (a) key by something branch-unique — `branch_path` or an equivalent derived child-run identity, not `workflow_id` alone; (b) delivery must be genuinely one-shot per key without a destructive whole-holder clear racing concurrent siblings — `peek()` alone is insufficient once true one-shot semantics are required per key; (c) work out the actual threading mechanism first (how does a resolved per-child value reach that child's OWN recursive re-entry, given `execute_workflow` has no `resume_context` parameter today) — the map shape is the easy part. **Council:** not yet re-evaluated — the original C7/C8-HITL-fidelity-vs-C1/C5-orchestration-correctness framing may not even be the right lens once a concrete delivery mechanism is proposed (per this register's own `[[probe-resolves-fork-prescribed-council]]` discipline: ground the mechanism first, then decide if a real value-tension remains). Not urgent — open when a real multi-child concurrent-HITL-pause scenario is confirmed reachable in a live deployment (today's fixtures/tests do not exercise it in production; the B-32 fixtures that DO exercise nested pauses use plain branch-failure pauses, not HITL gates).
