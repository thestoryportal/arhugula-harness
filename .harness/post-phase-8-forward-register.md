### B-1 · Layered capability-aware routing activation `⚖️ council-eligible`
- **Current state (empirically verified this session).** Provider construction is **live** — all 3 adapters (`AnthropicAdapter` / `OpenAIAdapter` / `OllamaAdapter`) built at bootstrap stage-3a (`providers.py`). The retry/breaker/**fallback-chain dispatch** (`C-RT-16`, `lifecycle/retry_breaker_fallback.py`) **is wired** at the stage-5 `StepDispatcher` and iterates fallback candidates (primary → same-family → cross-family → terminal) with `advance_or_raise` on per-candidate exhaustion. **But the layered routing-*selection* path is a stub:** `routing_core_surface.infer()` raises `NotImplementedError` (`routing_core_surface.py:83`/`:97`), and `layered_routing_strategy.route()` has **zero non-test callers** (verified). So *which provider to use* is taken statically from the manifest `model_binding`, not from capability-aware layered routing.
- **What this means for the harness.** Provider plumbing + failure-time fallback exist; **capability-aware provider *selection* is not active.** Combined with B-2, the multi-provider machinery is present but **unexercised at MVP**.
- **Close-out steps.** (1) Implement the `infer()` composition seam to invoke `layered_routing_strategy.route()` (declarative-layer first) before provider dispatch (CP spec C-CP-02); (2) bind per-layer time-budgets (C-CP-03 `LayerBudget`); (3) implement capability-shortfall fallback (C-CP-04 + ADR-F1 §Consequences(c)) — fall to a capable provider *before* the step fails when the primary lacks a required capability (e.g. extended-thinking).
- **`⚖️ Council (C5 ⊥ C9 ⊥ capability-preservation).`** Designing the routing-selection policy is a genuine tension: **cost** (cheapest-deterministic-first) vs **reliability/recovery** (when to fall back / breaker thresholds) vs **capability-preservation** (don't route a thinking-required step to a non-thinking model to save cost). Convene a dyad (cost-voice + reliability-voice) when this arc opens.

### B-46 · Cross-process ledger lock has a first-write TOCTOU on lazy sidecar provisioning *(surfaced at B-40's own PR, out-of-family Codex round 4 + advisor(), 2026-07-15; CLOSED 2026-07-18 — PR #1052)*

- **What it is.** `harness_is.cross_process_ledger_lock`'s lock sidecar (B-40) is provisioned lazily by whichever writer touches a ledger first. ### B-68 · Protected result store's opportunistic GC can race a concurrent in-flight publication under a short TTL *(registered at the B-65-A impl arc, out-of-family Codex round 11 [P2], 2026-07-22; CLOSED 2026-07-25 -- in-process synchronization scope; cross-process residual split to B-73)*

- **What it is.** `write_once()` captures `_StoredEnvelope.written_at` via `time.time()` BEFORE serialization/encryption/`_publish_atomic`'s fsync+`os.link` commit — a real, non-instantaneous gap. A CONCURRENT sweep (a different in-process opportunistic call from another request, or the bootstrap/shutdown-half sweep from a co-resident process sharing the same store directory) that runs during that gap decrypts the envelope, computes `current_time - written_at`, and — if the deployment-configured `ttl_seconds` (operator-settable, `gt=0.0`, no floor) is shorter than the write's own encrypt+fsync latency — can judge the just-published entry already expired and unlink it before `write_once()` even returns. The caller then holds a "live-looking" `composite_key` whose first `read()` raises an unhandled `FileNotFoundError` instead of the typed `ProtectedStoreCrossTenantError`/`ProtectedStoreTamperError` refusals the store otherwise guarantees.
- **Fix landed (2026-07-25, branch `b68-protected-result-store-gc-race-mtime-authority`, 5 rounds of out-of-family Codex review).** (1) `gc_sweep()`'s age authority switched from the pre-publish `_StoredEnvelope.written_at` field to the committed entry file's own filesystem mtime, explicitly refreshed via `os.utime` + its own fsync AFTER the durable `os.link` commit — closing the original timing gap. (2) A process-wide `threading.Lock` registry keyed by the store root's RESOLVED path (`_root_locks`, module-level, not per-instance) now serializes `_publish_atomic`'s entire publish critical section against `gc_sweep`'s entire scan — closing same-process races, including a co-resident concurrent-INSTANCE race (e.g. across bootstrap/resume cycles) the original registration did not anticipate; the lock key uses the root's filesystem identity (`(st_dev, st_ino)`, falling back to the resolved path only before the directory exists) so filesystem-equivalent path aliases (e.g. a `..`-containing spelling, or a case-folded spelling on a case-insensitive volume) share the same lock, and the temp-file's full lifetime (creation through the post-commit mtime-refresh fsync) is inside the lock so a sweep cannot reclaim an in-flight temp file mid-publish. (3) `read()` degrades a missing entry to a typed `ProtectedStoreEntryNotFoundError(FileNotFoundError)` — the optional interim hardening this row's close_out named — instead of a raw `FileNotFoundError`. Each fix is witnessed by a deterministic (non-flaky, mechanism-level) mutation-probed test: reverting the fix makes the corresponding test fail; restoring it passes. 10 new tests added across all rounds; full `harness-runtime` + `harness-cp` suites green.
- **Frequency correction (merge-gate round-1 concurrency lens, PR #1078, 2026-07-22).** Independently confirmed the race is real and reachable via genuine multi-threading, and sharpened this writeup's own framing: `shutdown()` step 5b fires `gc_sweep()` UNCONDITIONALLY once per `run()`/`resume()` call, with no interval throttle — unlike the in-write opportunistic trigger's `_OPPORTUNISTIC_GC_INTERVAL_SECONDS = 300.0` gate. On a daemon serving many concurrent short-lived workflow runs against the SAME shared store instance, concurrent-sweep frequency is materially higher than a reading based only on the 300s opportunistic throttle would suggest — the fix above closes the race regardless of frequency for the same-process case.
- **Residual split out (round 5 convergence check).** Out-of-family Codex round 5 confirmed the in-process fix is sound but restated the SAME cross-PROCESS gap this row's fix comments always disclosed ("a genuinely separate OS process sharing the store directory remains an open residual, registered, not silently assumed closed") — two co-resident daemon PROCESSES each hold their own independent `_root_locks` registry, so a `threading.Lock` alone cannot exclude them. Not a defect introduced by this fix; split to **B-73** as its own registered row rather than expanding this arc's scope, per the terminal register discipline (B-64/B-67 precedents).
- **Council: no** — narrow TTL-dependent race with a documented reachability precondition; the in-process fix was a known primitive (a resolved-path-keyed lock), not a judgment call.

### B-74 · Protected result store's mtime-based GC age authority can under-report publish time below a filesystem's timestamp granularity *(surfaced at the B-68 impl arc, out-of-family Codex round 7 [P2], 2026-07-25)*

### B-76 · Protected result store's lock-key registry can fail open on a transient stat() failure during root-identity resolution *(surfaced at the B-68 impl arc, out-of-family Codex round 8 [P2], 2026-07-25)*

### B-77 · Protected result store's mtime refresh is not durable atomically with the publish commit, leaving a crash window where a recovered entry looks pre-aged *(surfaced at the B-68 impl arc, out-of-family Codex round 8 [P2], 2026-07-25)*

- **What it is.** `_publish_atomic` makes the entry durable in two separate steps: the `os.link` commit + its directory fsync (durability step 1), THEN a separate `os.utime` mtime refresh + its own fsync (durability step 2). The NEXT process's bootstrap sweep, reading this crash-recovered entry, would then see the OLD (potentially already-TTL-exceeded) mtime and could immediately reclaim an entry that in fact just barely finished publishing before the crash.
- **Current state.** Registered, not built. This is a variant of round 1's original bug, but scoped to the crash-recovery path specifically (not the live-concurrent-thread path round 2-7 closed) — a narrower reachability precondition (needs a crash at a specific ~2-syscall-wide instant, not just concurrent access) with the same root cause (mtime refresh is not atomic with the commit that makes the entry durable and visible).

Alternatively, treat any post-crash entry with a mtime predating the entry's OWN prior directory-fsync-only durability marker as needing a decrypt-based fallback age check (mirroring the existing undecryptable-entry fallback) rather than trusting a possibly-pre-refresh mtime unconditionally. Witness with a test that simulates a crash between the `os.link` commit and the `os.utime` refresh (e.g. via a monkeypatched `os.utime` that raises once) and asserts a subsequent bootstrap-style sweep does not reclaim the crash-recovered entry immediately.
- **Council: no** — narrow crash-window durability-ordering gap; the fix (atomic age-stamp-with-commit, or a fallback age check) is a known pattern, not an open design question.
