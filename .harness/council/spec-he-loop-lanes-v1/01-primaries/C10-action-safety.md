# E1 A1 — C10 action-safety / blast-radius (primary, independent, blind)

## Position on spine tensions

**T1 — C-HE-07 supersedes R-19.** **ACCEPT the supersession.** C10 authored R-19 on the premise "Permission-guard classifies an already-constructed command's blast radius; it is not a workflow-ordering engine." Verified at HEAD, that premise is false and was already false when R-19 was written: `_safe_worktree_remove_wrapper` (`permission-guard.sh:184-198`) already denies the raw worktree-removal verb (`:57-65`) and allows only a wrapper (`safe-worktree-remove.sh`, called at `:288-289`) that itself enforces a mutex ordering — the exact shape C-HE-07 proposes for merge. R-19's calling-code-only fix (C-HE-06 §1) closes the cooperative path but leaves a residual gap R-19 did not price: any Bash tool call reaching permission-guard outside ship-pr's Python (a stray agent-issued `gh pr merge`, a lane that improvises) is auto-allowed today with zero lease check (`gh pr merge 268 --squash --delete-branch` → allow, `test_permission_guard.sh:168-169`). Under N≥2 that is the split-brain merge this spec exists to prevent. C-HE-07 is the correct belt-and-suspenders fence.

**T6 — OPEN-branch single re-issue vs "never invoked twice".** **ACCEPT as worded.** Invariant binds only on the MERGED branch; the OPEN branch's one re-issue per reconcile pass is safe because `gh pr merge --match-head-commit <sha>` is idempotent server-side (a merged PR cannot re-merge; the pinned head_sha cannot land a different tree). No falsifying scenario found.

**T7 — C-HE-31 §3/§4 siting + promotion/demotion.** **RECONCILE.** Siting rule (stable boundary only, never blocking `PostToolUse` per-edit) is the right asymmetric gating. Promotion bar (20-arc zero-FP replay) well-calibrated. But §4's demotion clause is a silent weakening of a gate with no emission requirement. Reconciled wording: "...is demoted to advisory automatically; the demotion event MUST itself emit a C-HE-24 finding row (`producer=lanes_verify` or equivalent, `finding_type=gate_demotion`, `severity=warn`) naming the check and the triggering rejected-finding count, and the rolling 20-arc window MUST be evaluated at a named, recurring site (`just lanes-verify` or CI)."

**T8 — C-HE-08 both fences vs terminating-refresh path.** **ACCEPT, contingent on the §4 tiebreaker testing the load-bearing parameter.** Context list verified byte-exact against the 12 live "— blocking" job names. `enforce_admins: true` correctly closes the false-confidence gap raised at R-20 and composes with the `gh api -X` loop-mode deny (`:396`). Addition: `strict: true` is the parameter most likely to interact badly with the terminating-refresh cadence; §4's tiebreaker should explicitly assert that a refresh PR branched from a since-superseded `main` either fast-forwards cleanly or is caught pre-merge, not just that some refresh PR run succeeds once.
