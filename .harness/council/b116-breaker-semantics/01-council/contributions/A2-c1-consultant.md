## (1) C9's "no C1 topology change is implied" — half true, and the half that is false is the one the dead-half-open finding creates

C9 is right that **no code path in the advance mechanism changes** under either reading: `record_failure` at `:1028` and the advance at `:733` are sequential and independent; the guard he and C11 price touches only the former. [HIGH]

He is wrong that the **topology semantics** are untouched. The breaker pre-check at `:674-683` is not telemetry — it is a *topology gate* that deletes a candidate slot from the chain for the duration of the run. With `attempt_half_open()` at **zero call sites** (re-verified this session across `harness-{runtime,cp,od,core}/src` — the only hits are `retry_breaker.py:51,201,289`, i.e. docstrings plus the definition), OPEN is absorbing, so reading (I) makes a breaker trip an **irreversible candidate-set deletion**. Probe C's end state is a declared N-candidate fallback chain that has silently become a **null topology**: every subsequent dispatch walks N slots, emits N `retry.skipped` events, does zero work, and exhausts. That is a terminal state **no canonical artifact declares** — a termination-criterion gap in my own scope, not C9's. **C1 terminates on: candidate exhaustion within a dispatch (`RetryBreakerFallbackExhaustedError`, `:899`) and first terminal step failure within a run — never on "all candidates permanently ineligible," which is a state the design never named.** [HIGH]

**The amplifier neither primary named.** C9 argues from the *fault's* candidate-independence; I add the chain's half: **`_advance_or_exhaust` is the multiplier.** One candidate-independent fault is charged **N times per dispatch**, N = chain length (Probe B: three breakers, one dispatch). So under (I), **lengthening the fallback chain to improve resilience makes the misconfiguration harm strictly worse and trips the whole chain sooner.** A topology decision (add a candidate) inverts into a reliability regression. That inversion is a C1-domain argument for (II) that stands independently of C9's information-content argument and C11's operator-recoverability argument. [HIGH]

## (3) C9's honest counter-argument — falsified at HEAD, and (I) does not buy what it claims

C9's "(II) yields unbounded full-chain traversals … forever, with nothing accumulating to stop it." The orchestration layer already stops it, at three levels, all verified this session:

- **Within a candidate:** `RetryPolicy.max_attempts=3` (`:131,943`) — moot for fail-fast, which does not retry.
- **Within a dispatch:** chain length N, then terminal `RetryBreakerFallbackExhaustedError` (`:899`).
- **Within a run:** the first failed step returns `RunStatus.FAILED` with `terminal_step_index` (`workflow_driver.py:5564-5572`) — the linear run **stops**. Fan-out topologies "halt the fan-out on the first branch/worker failure" (`:9531`, `:13952`). Evaluator-optimizer is capped at `_DEFAULT_EVALUATOR_OPTIMIZER_MAX_ITERATIONS = 3` (`:10555`), and a dispatch exception inside it is terminal (`:11457`), not a re-iteration. [HIGH]

For a **candidate-independent** fault the bound is therefore **one step**: it fires on the first dispatch and the driver terminates the run. No shipped topology survives a step failure and re-dispatches it. What genuinely repeats is *across operator-initiated runs* — and **(I) does not bound that either**, because breaker state is in-memory per-process (C11's §4.1.27 fact, and it resets every run). So (I)'s claimed advantage — "at least it converges" — exists only inside one long-lived process doing many dispatches, and *there* the same latch that converges also permanently deletes healthy candidates. The trade is not "converge vs grind"; it is **"converge by disabling the chain vs terminate the step, which the driver already does."** C9's counter-argument is the strongest thing in either primary and it does not survive the driver's own terminality. [HIGH]

**HITL.** I concur with C11's (d) — **C1 places no HITL checkpoint on this path** — but on independent grounds, and with a flag: fail-fast tags `retry.fail_class = PERMANENT_FAIL_EXIT` (`:1024-1027`), and C-CP-21 §21.1 routes `permanent-fail-exit` *directly to the validator-escalation HITL placement*. That taxonomy is **validator**-side; the dispatcher borrows the label for a span attribute while the exception propagates to a plain step failure. **The escalation the attribute names is not the escalation the topology performs.** That is a real placement/label divergence, it is not this fork's business, and it must not be quietly used as evidence that "an escalation path exists." [MODERATE]
