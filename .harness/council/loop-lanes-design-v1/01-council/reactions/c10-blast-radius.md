## 1. Ruling on Open Decision #5 — protect `main`

**Yes. Minimal protection now (restrict direct pushes, require a PR), and I found a second, worse gap while grounding this that raises the stakes.**

Applying the four-tier taxonomy: a write to `main` is the highest-blast-radius surface in the whole workspace — it keys the §12.2.1 fixed point, the roadmap hash, and (per E26, settled) `committed_arc_ids()`'s correctness for every other lane. That makes it `write-unbounded` by the artifact's own definition ("scope exceeds bounded scope... monetary actions above threshold"-class consequence), not `write-bounded-reversible`. Per §4.1(e) of my own posture (cross-deployment trust transitions are gate-mandatory because they're low-frequency and un-gated leakage is high-cost), server-side protection on `main` is the textbook case — it costs nothing on the capability axis (C4↔C10 Layer-3 tension resolves to near-zero cost here) because every *legitimate* write path already goes through `gh pr merge` (`ship-pr/SKILL.md:190-221` — CONFIRMED read this session: it verifies `state=MERGED`, `baseRefName`, and post-merge CI before even branch-deleting). Minimal protection blocks nothing the tooling actually does; it only closes a door nothing legitimate uses.

**Grounded this session, independently:** `gh api .../branches/main --jq '{name,protected}'` → `{"name":"main","protected":false}`; `gh api .../rulesets` → `[]`. Confirms the artifact's claim, third verification.

**What I found that changes the calculus:** the client-side gate has the identical gap. `tools/hooks/permission-guard.sh:427` (CONFIRMED, read in full this session) allowlists bare `push` in the loop-mode safe-Bash-prefix set with **no destination-branch check** — only the deny-list at `:321` catches `--force`/`--force-with-lease`/`-f`. A plain `git push origin main` (or `git push` while checked out on local `main`), with no chaining, passes `_bash_args_safe` and auto-allows in loop mode. So today, at N=1, with `main` unprotected server-side, a loop-mode session's ordinary non-force push is **one auto-approved tool call away from landing unreviewed content on `main`** — no PR, no CI, no merge-gate. This is squarely my domain (per-tool gate level for the `push` verb is currently `open`; it should be `gate-on-write` when the target is `main`) and none of C1/C3/C8 named it. Branch protection is the cheap fix for *both* halves at once: it makes the server reject the push regardless of what the client-side hook auto-approved, which is exactly the "defense in depth" property currently absent everywhere in this design.

**What breaks:** nothing in the documented flow (PR + `gh pr merge`). What it does foreclose: item 20's raw `PATCH /git/refs` mechanism as specified (see §2) and any hand-run `git push origin main` an operator or agent might use as a shortcut during debugging — both should be foreclosed, so that's a feature, not a cost.

## 2. Ruling on the raw-ref-push bypass (item 20)

**Never acceptable as currently specified; conditionally acceptable only as a bridge, contingent on Decision #5 landing first.**

Item 20's own blocking reason (squash commit has one parent, breaks GitHub ancestry-based auto-close, `ship-pr/SKILL.md:191` hard-aborts on non-MERGED state) is a correctness defect, not mine to rule on. My question is narrower and independent: **is it ever acceptable, trust-boundary-wise, to move `main`'s ref via a mechanism GitHub never witnessed?**

No, as specified. A non-force `PATCH /git/refs` is a content-blind CAS — it proves only "the ref hadn't moved since I last checked," never "the content I'm pushing passed CI or review." Every safety property C5/C4 (E45/E46, settled) discussed rests entirely on the *local coordinator process* having built that squash commit correctly. That is exactly the "zero GitHub-side defense in depth" framing C5 flagged and handed to me — it's the `write-unbounded`-with-no-preventive-layer combination FM-E exists to catch. C5's own Window 1/Window 2 split (E45) is correct: Window 1 (stale local evidence, no adversary) is closeable today with a `git merge-tree` byte-compare immediately pre-push; Window 2 (a genuine race against a concurrent writer) is not closeable without a server-side witness — and there currently isn't one, because `main` isn't protected at all (§1).

**Conditional path, if this is ever revived:** branch protection lands first (§1) *and* the coordinator posts a verifiable commit-status to GitHub for the exact tree-SHA it's about to push, with a required status check bound to it, before the `PATCH` fires — that gives GitHub an actual assertion to enforce against, turning the local recompute into something the server can reject rather than something only the coordinator's own good behavior guarantees. Absent that, this stays in Blocked permanently, not just until the ancestry bug is fixed — the ancestry bug and the trust-boundary gap are two independent reasons to keep it blocked, and only one of the two council legs (C4/C5) named the second.
