## 1. The spine tension: is the evidence gate coherent?

**Position: the gate is coherent on the safety axis and incoherent on the decision-rule axis. The sharp counter-argument as posed is answerable, but only because of a sequencing fact the artifact states but never uses to defuse it.**

CONFIRMED — `HARNESS-LOOP-AND-LANES-DESIGN-v1.md:118` headers Phase 0 explicitly *"correctness. Ungated by lane count"*, and `:83` states L-4: *"Sequence: fix defects → gather evidence → only then build machinery."* Phase 0 items 4–9 fix X3–X8 unconditionally before Phase 1 (which contains O1 at `:158-159` and the ≥3-pilot bar at `:163-164`) runs at all. That means by construction, when a pilot lane actually executes, the *known* concurrency defects (split-brain ledger, the duplicate-append race, the ABA takeover, the loop-marker split) are already closed. **The ≥3-pilot bar does not require "knowingly running the unsafe configuration"** for any defect already on the X1–X8 list — those are gone before pilots start. The operator's sharp counter-argument, read literally, presupposes O1 and the pilots are the *only* safety check; they are not — Phase 0 is.

Where it breaks: the artifact never says what happens if O1 is RED for something **not** on the X1–X8 list — a genuinely new defect surfacing only at real 4-worktree scale (subprocess timing, `gh`/CI concurrency, a git ref-lock interaction Phase 0's fixes didn't anticipate). Items 11 and 13 are listed as co-equal Phase-1 bullets, not "O1 first, pilots contingent on a GREEN verdict." That's a genuine gap, and it's exactly the shape of error C8 exists to catch: **two different eval instruments answering two different questions, presented as one gate.**

- **O1** (`:158-159`) is a targeted diagnostic probe of one named defect class (X6-adjacent, `hook_project_dir()` collision) — a single technical repro with a binary outcome. It is NOT a statistical claim; it needs no holdout, no counterfactual baseline. It's closer to a mutation-probe than an eval.
- **The ≥3-pilot bar** (`:163-164`, citing `two-lane/SKILL.md:140-142`) is a *different* instrument. Grounded — CONFIRMED at `.claude/skills/two-lane/SKILL.md:140-142`: *"Follow-on orchestration is registered only after ≥3 manual pilot runs surface a named recurring pain."* That gate was designed by the two-lane recipe to answer **"is orchestration machinery (spawner, lock, dedup) worth building"** — a Husain Stage-1/2 (manual-review → categorize) instrument for a *build-tooling* decision, not a safety-of-N=4 decision. The artifact imports this bar wholesale into the 4-lane context without re-scoping it, which is how "≥3 pilots" ends up misread as "3 more chances to hit an unsafe race."

**My ruling:** decouple explicitly. (1) Safety is settled by Phase 0, unconditionally, before any lane count runs — restate this as the answer to Open Decision #3, don't leave it open. (2) The ≥3-pilot bar governs *only* whether Phase 2 (items 15–19: mechanization, dedup, lease-file widening, shadow trial) is worth building — rename/re-scope it as such so it stops reading as a re-litigation of the N=4 mandate. (3) Add the one missing decision rule: **a RED O1 (or any pilot surfacing a defect not in the X1–X8/19-failure-mode inventory) routes back to Phase-0-shaped fix-first, not through the remaining pilot count.** Without that explicit branch, the plan is silently assuming pilots never find anything new — an assumption the plan's own "19 named, ~0 detections" admission (`:236`) makes hard to credit.

## 2. Is AC#2 (restated, §6) sufficient?

**Partially — and the honest answer requires naming a boundary I should recuse from, not paper over.**

AC#2's two probes (`:206-217`) are deterministic correctness proofs about a specific race (claim/takeover + queue-release timing), not population-level claims over a corpus. Per my own skill's C5↔C8 discriminator (*"a per-call decision the harness routes on, or a population-level claim about a corpus/holdout"* → the former is C5's), **AC#2 is C5-shaped, not C8-shaped.** I'm not the right voice to certify its sufficiency as a mechanism — that's mutation-probe/validator discipline. What I *can* certify, from the eval-methodology seat:

- Probe (b) is CONFIRMED accurate by code inspection: `committed_arc_ids()` at `tools/arc_metrics.py:697-716` returns `set()` on either a `LEDGER.relative_to(REPO)` `ValueError` (line ~707) or a `git show` `AbortError` (line ~712). **Precision gap the artifact doesn't surface:** these are two different early-return branches with two different meanings — one says "ledger isn't even in this repo," the other says "ledger's in the repo but merged history doesn't have it yet (no `origin/main`, or unmerged)." Probe (b)'s stated framing (*"a fresh `tmp_path` has no `origin/main`"*) implies it's exercising the **second** branch — which only happens if the test harness keeps `LEDGER` relative to `REPO` while pointing `REPO` itself at the fresh `tmp_path` git checkout. If the harness instead monkeypatches `LEDGER` to a bare `tmp_path/arc-metrics.jsonl` (the pattern the *existing* 46 tests use — confirmed at `tools/test_arc_metrics.py`, e.g. lines 588-589), it hits the **first** branch instead and never touches the `git show`/merged-history logic that's the actual thing under test. This is a one-line fixture-construction risk, not a design flaw, but it should be named before someone builds probe (b) against the wrong branch and gets a false GREEN.
- Probe (a) — "barrier-gated in-process thread sweep enumerating reachable interleavings" — introduces a genuinely NEW test technique to this file. CONFIRMED: all 46 existing `# mutation-probe:`-annotated tests in `tools/test_arc_metrics.py` (verified count: 46 matches) simulate concurrency via `monkeypatch` sequencing, not real threads — e.g. `test_a_claimed_arc_is_skipped_by_a_concurrent_drain` (`:587`) fakes a peer's prior drain by mutating state before the call, not by running two threads. Zero actual `threading`/`concurrent.futures`/barrier usage anywhere in the file (grep CONFIRMED empty). This means probe (a) isn't "one more mutation-probe test" — it's a new capability with its own failure surface. Institutional memory (`multiprocess-fork-plus-threading-lock-deadlock.md`) records this exact workspace has hit lock/fork deadlocks in concurrency-test code before; that's a reason to budget probe (a) real implementation risk, not treat it as equivalent effort to the other 45.
- Neither probe states what N (lane count) the interleaving sweep needs to cover. "≥2 simulated lanes" is argued as sufficient by the rename-based claim mechanism being inherently pairwise (only one winner regardless of contender count), but the artifact doesn't say this — it should, since the operator mandate is N=4 and a reader shouldn't have to re-derive why 2 generalizes.

**What's missing from AC#2 that's genuinely mine:** a post-fix trace-driven check. AC#2 is a pre-deploy regression proof (Husain Stage 3/4-shaped: automate + align on synthetic interleavings); it has no Stage-1 equivalent verifying the fix holds under *real* `git`/`gh` subprocess latency once lanes actually run — an in-process thread sweep can't reproduce that. Phase 0 item 9's split-brain CI check (`jq '.arc_id' | sort | uniq -d` on every merge, `:150-151`) is exactly this drift check, already in the plan — but the artifact never ties it back to AC#2 as its production-side complement. State that linkage explicitly: AC#2 = pre-deploy proof, item 9 = its trace-driven regression detector.
