## C2 — Context Engineering & Attention Budget Architect (PRIMARY)

### The frame: the harness violates its own read contract at Tier-1

My domain spec gives me the sharpest possible as-is-vs-intended frame, and it is in my own lane, so I lead with it. **C-IS-07 §7.2 (the C2-pole read contract)** mandates that durable state is read into context **Selective / Bounded / Navigation-primitive-mediated / Read-into-dynamic-suffix**, and it *explicitly precludes "direct full-file `cat`-style reads."* That contract was written for the harness's *own* runtime state-ledger reads — but it is the harness's stated discipline for how at-rest durable substrate (C3) should enter a working context (C2). 

`CLAUDE.md` — the agent's Tier-1 "system prompt," re-read **every turn** — does the exact opposite. It is a **341,611-byte (~334KB) full-file dump into the static prefix**, and **§2 (Canonical artifact pointers) alone is 277,298 bytes = 81% of the file**. Three table *cells* are the bulk of it: the CP-spec pointer cell (line 80) is **55,152 bytes**, the OD-spec pointer cell (line 81) is **52,801 bytes**, the CXA pointer cell (line 92) is **55,238 bytes** — ~163KB across three cells that should each be a one-line pointer ("consult the canonical spec at vN"). The harness ships a Selective/Bounded/navigation-mediated read contract for its runtime and then force-loads the entire delta-version provenance ledger into its own re-attended-every-turn prefix. This is C-IS-07 §7.2's anti-pattern instantiated at the most expensive prompt position in the system. [HIGH — byte counts measured this session; C-IS-07 §7.2 verbatim]

This validates operator hunch #1 ("CLAUDE.md bloated/unfocused") but reframes the *why*: the problem is not header count or line count. The problem is **what altitude the content sits at and where it lives in the prompt**. §1 (framing) is 6,079 bytes; §10 (operating principles) is 13,971 bytes; §12 (roadmap) is 14,677 bytes — those are healthy. The disease is concentrated: across-turn *provenance* (C3's at-rest concern — version-history change-notes) has been pasted into a within-turn *pointer table* (C2's concern).

### The cost mechanism: this is FM-D/FM-H cache-detonation, not just "a big file"

The load-bearing C2 claim — the one no other voice will make — is the *cache* mechanism. **C2 places no commitment on "the file is big"; C2 commits on the static/dynamic split and cache discipline.** Per research §2.3 + §2.2.5 ("compaction-after-cache invalidates everything; the prompt-cache prefix hash changes; next request is a full cache write"), the static prefix earns its keep only if it is **stable across turns**. 

The §2 cells are the opposite of stable. The workspace's *own discipline* mandates editing them on nearly every spec/plan PR — I count **20 occurrences of "+ workspace `CLAUDE.md` row bump"-class phrasing inside CLAUDE.md itself**. Every CP-spec, OD-spec, runtime-spec, CXA, or plan PR rewrites a §2 cell. So the 334KB static prefix is **invalidated continuously across the entire project history** → a recurring full cache *write* (1.25× base input price per Anthropic caching, research §2.3) on a ~334KB prefix, every spec PR. The intended cache-efficiency capability (amortize via 0.10× cache reads on a warm stable prefix) is **structurally defeated**: a prefix that's rewritten every PR can never warm. [HIGH on the design-level claim — the cache-discipline rule (frequently-edited content must not sit in the re-attended prefix) holds regardless of the literal `cache_control` placement Claude Code uses; the recurring-edit mechanism is verified from CLAUDE.md's own text.]

**The damning contrast — the harness already knows how to budget context.** The *hooks* are tightly token-budgeted: `session-start.sh` documents "Total preamble overhead at session start: under 50 tokens worst case"; `prompt-context.sh` injects ~17 tokens (`[roadmap] next=…`); the per-prompt injectors are <50 tokens each. The harness can do disciplined, bounded, JIT context injection — and does, at the hook layer. It simply does not apply that discipline to its own Tier-1 file. The fix is not novel engineering; it is applying the harness's existing context-budgeting posture to CLAUDE.md.

### Altitude diagnosis (research §2.2.2 — Anthropic "right altitude")

CLAUDE.md conflates three altitudes that research §2.2.2 keeps separate:
1. **Operating instructions** ("the Goldilocks zone — heuristic-with-examples"): §11 posture, §12 loop discipline, §13/§14 conventions, the locked rules (never-halt, defer-and-continue, prefer-free-ollama, paid/secret/destructive deny-list). *This is correct altitude and belongs in the prefix.*
2. **Navigation anchors** (pointers to where canonical content lives): §2's *job* — but it's been inflated from pointers into the content itself.
3. **Provenance / audit trail** (version-by-version change history): the §2 cell bodies. **This is C3's durable-store surface and does not belong in the within-turn prefix at all** — it belongs at rest (git history + the design-substrate files themselves already hold it verbatim per the delta-only-preserve convention).

The fix is **altitude extraction**: keep (1) in the prefix; reduce (2) to genuine one-line pointers + a generated index; evict (3) to the durable store (where it already redundantly lives). C2 sets system-prompt altitude at **heuristic-with-operating-rules-plus-navigation-anchors; NOT embedded-provenance-history** (research §2.2.2 Goldilocks framing).

### Folder architecture as interpretable context (research §2.2.3 — "emergent behavior on metadata signals")

Operator hunches #2/#3/#4 are real and they are *my* lens because **folder architecture is JIT-navigation infrastructure** — research §2.2.2/§2.2.3 names "folder hierarchies, naming conventions" as the metadata signals the agent navigates by, and the JIT decision rule (§2.2.3) presumes "navigation primitives exist (filesystem, index, schema)." The current architecture *degrades* those signals:

- **No single-source-of-truth pointer (hunch #3, confirmed).** `design-substrate/` holds **29 CP-spec copies (v1.2→v1.30), 31 CP-plan copies, 19 CXA copies (v2.1→v2.19), 7 Workflow copies (v1.8→v1.14)**, flat, with **no `Project_Workflow.md` / `Cross_Axis_Composition_Document.md` SSOT pointer**. The agent cannot navigate to "the canonical Workflow doc" — it must *know* the version, which is why §2's cells got inflated to carry the version inline. The bloat and the missing-pointer are the *same defect*: absent navigation infrastructure forces canonical content into the prefix.
- **No AGENTS.md / ARCHITECTURE.md / WORKFLOW.md / HOOKS.md (hunches #4/#5, confirmed absent).** These are the canonical top-level navigation anchors a fresh context lands on. Their absence means orientation lives nowhere *but* the 334KB CLAUDE.md — a self-reinforcing bloat loop.

Crucially — and this keeps me in-lane — **the 29 versions existing on disk is fine and intended** (git-as-state + delta-only-preserve-verbatim is a C3 durable-store convention; I do **not** recommend deleting them, that's C3's at-rest surface and a locked convention). The defect is purely (a) no SSOT pointer so canonical is undiscoverable, and (b) provenance force-loaded into the prefix. My fix is **navigation + altitude extraction**, never retention.

### MEMORY.md: over-cap is a measurement success, not a context-engineering failure

The durable memory index (C3's store) is the **read-seam source** for what semantic memory enters context — so I have a co-primary stake on the *loading* side. **MEMORY.md is 27,051 bytes against a 24,400-byte cap, with 169 topic files** — and the system-reminder this very session reports it was **"only partially loaded."** That partial-load is an *observable context-rot signal* (research §2.2.5 — content silently dropped from the attended window). 

But note the bright spot for my eval-ability obligation: **the cap is already hook-enforced** — `loop-gc.sh:56` and `session-end-cleanup.sh:53` both flag `> 24400B`. This is the *precedent that proves the fix-pattern works*: a context artifact under an automated byte-budget with a surfacing hook. CLAUDE.md has no equivalent budget — and should. The MEMORY.md *retention/compaction policy* (what to keep, when to delete, how to compact) is **C3's at-rest surface — I defer the policy to C3** and own only the loading-into-context discipline (index entries must be short, one-line, navigation-anchor altitude per the global memory hygiene rule; the bloat is index lines carrying detail that belongs in `memory/<slug>.md` bodies, JIT-loaded).

### Hook machinery (hunch #5): well-budgeted JIT injectors, undocumented as a whole

The hook system is, from my lens, **the harness's best context-engineering asset and its most under-documented one**. `UserPromptSubmit` runs three JIT dynamic-suffix injectors every turn (`prompt-context` roadmap orientation + `skill-activation-check` + `prompt-lint`); `SessionStart` runs the §12.1 roadmap audit; `PreCompact`/`PostCompact` checkpoint-and-reinject is *exactly* the research §2.2.3 compaction-with-durable-handoff pattern; `StatusLine` context-recovery. These are correctly bounded and correctly placed in the dynamic suffix (not the static prefix). The only context-layer gap is **interpretability** — there is no `HOOKS.md` synthesizing the lifecycle, so this machinery is invisible to a fresh context and to the operator. That's a navigation-anchor gap, not a budget gap. (Span emission from hooks → C7; the loop-autonomy *policy* → defer to the relevant control voice. I own only "are these injectors budgeted and correctly placed in the prompt": yes.)
