## 1 — The gap, stated precisely

`ToolContract.is_deterministic_inhouse` (`harness-as/src/harness_as/tool_contract.py:96`, default `False`) is a plain self-declared boolean — this, not `ToolMetadata`, is the actual declaration site (`ToolMetadata` at `sandbox_tier_floor.py:54` is a *downstream* carrier, constructed at `resolve_per_tool_sandbox_defaults` from `contract.is_deterministic_inhouse`, `harness-runtime/.../sandbox_defaults.py:243-246` — corrected across two review passes: `ToolMetadata` was wrongly attributed to `ToolContract` in the first draft; the constructing function was then wrongly cited as `resolve_effective_sandbox_defaults`, which only computes surface-level defaults and never receives a `ToolContract`, at a second pass). Nothing in the authority chain (`ADR-F4.md`, `ADR-D2.md` §1.5.1, `Spec_Action_Surface_v1.md`, the AS plan) specifies *how* the claim it encodes — "this tool is locally-authored and behaves deterministically" — gets verified. It is set by whoever writes the tool-registration code, or by an operator-declared per-MCP-server default (`MCPClientConfig.default_is_deterministic_inhouse`, `harness-runtime/src/harness_runtime/types.py:758`). No code-signing, sandboxed dry-run, HITL approval, or cryptographic attestation exists today. This is a genuine authority-chain silence, not a contradiction between artifacts — hence a design-gap exploration, not a tension resolution.

**A second, sharper gap underneath the first (surfaced on review, not in the first draft): "deterministic" itself is undefined here.** The field's docstring conflates *provenance* ("locally-authored, in-house") with *behavior* ("deterministic") — these are different properties. Determinism is not a property of code in isolation; it is relative to a fixed input, a fixed initial state, a fixed environment (dependency versions, OS, concurrency), and a stated notion of observational equivalence (identical stdout? identical side-effect trace? identical wall-clock-independent output only?). None of the candidates in §6 can be scoped correctly — including deciding what "verifying" the flag even means — until this definition exists. This is itself a candidate deliverable: a short definitional note (which inputs/state/environment dimensions are held fixed, which are allowed to vary, what "equivalent" means for a given tool's output shape) should precede any of Candidates A/B/C/D, not follow them.

## 2 — Five-axis decomposition

| Axis | Engagement |
|---|---|
| **Action surface (AS)** | Primary — `ToolContract`, `sandbox_tier_floor()`, `GateLevel` all live here. |
| **Operational discipline (OD)** | Secondary — any attestation record is an audit-ledger entry; a verification *process* (if HITL-gated) touches the HITL palette. |
| **Control plane (CP)** | Engaged for Candidate C, not marginal — an operator-attestation flow (registration, approval, renewal, revocation) is CP's own "HITL placement" surface, even though the resulting decision is *recorded* by OD. Corrected on review from an initial "marginal" mis-scoping. |
| **Information substrate (IS)** | Engaged for Candidate A, not marginal — a content-hash pin is only a trust anchor if the *expected* digest is durably stored somewhere the code being checked cannot itself rewrite; that durable, tamper-resistant anchor is an IS-axis concern (state-ledger entry or equivalent), not incidental to AS. Corrected on review from an initial "marginal" mis-scoping. |
| **Deployment surface** | Marginal — a heavier mechanism (sandboxed dry-run, static analysis) has real per-deployment-surface cost/availability implications (e.g., not every deployment surface can afford a dry-run sandbox at tool-registration time). |

## 3 — Probabilistic/deterministic boundary placement

**The claim itself ("this code is deterministic") is fundamentally a deterministic-side question** — determinism is a property of code, not of an LLM's judgment about the code. Any candidate mechanism that asks an LLM to *judge* whether a tool is deterministic (e.g., "have Claude read the source and decide") places a deterministic-side reliability property on the probabilistic side — the exact antipattern `CLAUDE.md`'s boundary discipline flags. This immediately rules out one class of "verification" that might otherwise seem cheap (LLM-graded code review as the attestation mechanism) as the *sole* gate — it can inform a human decision, but should not itself be the deterministic floor.

## 4 — Existing architectural precedent (grounds the candidates below)

Four load-bearing precedents already exist in this codebase. **This section's claims were sharpened on review — the first draft overstated how directly each precedent transfers; the corrected, more precise readings follow.**

1. **ADR-F4's `max()` composition + T-perm-1 (C4 capability ↔ C10 gating) — precedent applies with an important asymmetry, not directly.** `assigned_tier = max(contract.minimum_tier, blast_radius_floor, mcp_server_trust_tier_floor, operator_policy_floor)`. `minimum_tier` is a self-declared field too, but it is **monotone-safe inside `max()`**: a false-low `minimum_tier` cannot lower the *other* operands, so an incorrect self-declaration is bounded by whichever floor is actually strictest. `is_deterministic_inhouse`, under B-25's Reading B or C, does not work the same way — it would select a *less restrictive branch* inside `sandbox_tier_floor()` itself, i.e. it lowers the floor `max()` composes over, not just one input among several independent ones. That is a stronger, risk-reducing exemption, and ADR-F4 does not establish that this *kind* of self-declared exemption is safe to leave unverified — the precedent bounds a different failure shape than the one at stake here.
2. **ADR-F5's structure-not-content fingerprint pattern — the pattern *shape* is reusable, the specific guarantee is not.** `outputs_hash = SHA-256(canonicalize_concat(secret.name, secret.scope, secret.last_rotated_at))` (`Spec_Action_Surface_v1.md` §8.1, C-AS-08) proves *which named secret scope/version participated in an audit event* — it does not prove, and was never designed to prove, the identity, dependency set, or build provenance of executable code. The reusable part is narrower than the first draft claimed: "a deterministic hash feeding an audit-ledger field, computed at a well-defined boundary" is a good shape to imitate for Candidate A; "this already proves code identity" is not established by F5 and should not be implied.
3. **A closer, previously-missed AS-axis precedent: C-AS-14's `mcp.primitive.signature.sha256`.** `Spec_Action_Surface_v1.md` §14.3 already defines a per-primitive content-addressable hash — `sha256` over the tool's name + input/output schema (`runtime_tool_dispatcher.py:_compute_primitive_signature_hash`) — emitted for tool-poisoning detection at every MCP dispatch. This is a nearer existing precedent for Candidate A than C-AS-08: it already hashes a *tool's* identity-relevant shape, in production, today. It is still a **schema-shape** hash (name + I/O schema), not a full source/dependency/build hash — Candidate A would need to state explicitly why this existing surface is insufficient (it hashes shape, not implementation) and whether it should be extended rather than parallel-built.
4. **ADR-D2's `operator_policy_floor` — supplies an authorization-and-audit precedent, not a ready-made attestation lifecycle.** The existing mechanism ("the operator asserts an override; it's captured in the audit ledger with persona-tier cryptographic shape per D5 §1.4; it is structurally *prohibited* at multi-tenant-compliance cells") establishes *how this workspace lets an operator assert something risk-affecting, with accountability and persona-tier bounds*. It does not, by itself, supply registration/renewal/revocation machinery for a *different* kind of claim (tool determinism vs. a sandbox-tier downgrade) — Candidate C would need to build that lifecycle by analogy to D2's audit shape, not assume D2 already provides it "almost entirely as-is."

**Every candidate below answers "how does the flag get verified." None of them ask "should the flag exist at all."** That is a real gap in a first draft of this memo, caught on review: B-25 is still open, and its own Reading A ("the field never gates anything — row 7 keys purely on `blast_radius_tier`") is a live candidate there. **So this is not two independent questions (producer-side verification vs. consumer-side floor value) — it is mostly a dependency, consumer gates producer, with one caveat sharpened on review:**

- **If B-25 resolves to Reading A** (the field gates nothing): the most defensible disposition for *this specific field, in its current role as a sandbox-tier input,* is **Candidate 0 — deprecate/remove it**, not build a verification mechanism for an input nothing consumes. This is presented as the honest default under Reading A, not as the uniquely forced conclusion — B-25's own text only goes as far as "arguably," and the fork doc separately notes removal has a larger footprint than it first appears (it touches `tool_contract.py`, `types.py`, and `mcp_client_host_factory.py`, all production-threaded).
- **A caveat review surfaced:** code/artifact-identity integrity, tool-poisoning detection, and reproducibility/replay-testing are all things a content-hash mechanism (Candidate A) or a schema-signature extension (§4 item 3) could still deliver value for, *independent of whether this specific sandbox-tier field survives B-25*. If the operator or another consumer wants that value, it should be scoped and justified on its own terms — not smuggled in as "leftover infrastructure" from a determinism-floor mechanism whose original consumer got removed.
- **If B-25 resolves to Reading B or C** (the field does gate something — a one-tier bump or a forcing tier): the field is load-bearing, and Candidates A/C below become worth pursuing on the floor-verification grounds this memo was originally scoped around.

**This memo's candidate shortlist in §6 is therefore conditional on B-25's resolution for the floor-verification framing specifically — not a claim that hash-pinning/schema-signature work has zero value under Reading A.** Read the candidates below with that distinction in mind.

## 6 — Candidate mechanisms (conditional on B-25 ≠ Reading A — see §5)

### Candidate 0 — Deprecate/remove the field (the honest disposition under B-25 Reading A)

**What it does.** If B-25 resolves to "the field never gates anything," remove `is_deterministic_inhouse` from `ToolContract` and `MCPClientConfig.default_is_deterministic_inhouse` from the runtime threading, per the fork doc's own Reading A framing. No verification mechanism is worth building for a field that influences nothing.

**Composition.** A deletion, not an addition. Removes rather than extends the `max()` formula's input surface (the formula itself is unaffected either way, since the field was never actually read). Note per §5's caveat: this is a deletion of *this field's role as a sandbox-tier input*, not necessarily a claim that no future mechanism should ever hash/attest tool identity for a different purpose.

**Value.** Removes a misleading surface: a field with a docstring implying it gates a security decision, when it demonstrably doesn't, is worse than no field — it invites exactly the kind of false confidence the original B-24/B-25 grounding pass exists to catch.

**Cost.** Low — mechanical removal, though it touches production-threaded code (`tool_contract.py`, `types.py`, `mcp_client_host_factory.py`) so needs the same X-AL-3 back-flow discipline as any other design-substrate-adjacent change.

### Candidate A — Content-hash pinning (structural, no semantic verification)

**What it does.** At tool-contract registration, compute a content hash of the tool's source/definition — extending C-AS-14's already-production `mcp.primitive.signature.sha256` from a name+I/O-schema hash to something closer to a full-source/dependency hash, rather than inventing a parallel mechanism — and store the *expected* digest in a durable, tamper-resistant IS-axis anchor (not just "alongside" the flag in the same mutable record a compromised or careless registration could rewrite together). On every subsequent load, recompute the hash; a mismatch either fails registration or auto-demotes `is_deterministic_inhouse` to `False` for that load. **This verifies "the code hasn't silently changed since someone asserted determinism" — it does NOT verify the original assertion was true.**

**Composition.** Primarily AS-axis (the hash computation, extending C-AS-14), but genuinely touches IS (the durable expected-digest anchor — see §2's corrected assignment) and a minimal OD touch (an audit-ledger entry recording hash + assertion timestamp). Feeds the existing `max()` formula unchanged — no new floor, just a stronger guarantee behind the existing `True` value.

**Value.** Closes the *drift* failure mode (a tool that was true when reviewed can't silently become false-but-still-`True`-flagged after a code change slips in) — but not unconditionally: because other `max()` operands (blast-radius floor, trust-tier floor, `operator_policy_floor`) can still raise the *effective* composed tier above what this field alone would select, "Tier 1 forever" overstates the exposure — the field's own bad value is bounded by whatever else is composing into `max()`. Does **not** close the *original assertion was never checked* failure mode. Also genuinely unresolved, not just a detail: what "the tool's source/definition" even means for a remote MCP-hosted tool (mutable server-side, not locally hashable the same way), a containerized tool, or a tool with transitive dependencies not captured by hashing the registration-time definition alone — this needs to be scoped per deployment-surface/tool-transport shape, not assumed uniform.

**Cost.** Low-to-moderate, revised up from "low" on review — the durable-anchor and cross-transport-shape questions above are real design work, not implementation detail. Still reuses an already-implemented pattern (C-AS-14) rather than inventing one.

### Candidate B — Static/structural determinism linting (partial semantic verification)

**What it does.** At registration, run a deterministic static-analysis pass over the tool's declared implementation (banned syscalls/imports — no network, no wall-clock reads, no unseeded randomness, no filesystem writes outside a declared scope) and only permit `is_deterministic_inhouse=True` to be set if the pass is clean. Mirrors the existing GUARDRAIL-class carve-outs noted at `harness-as/CLAUDE.md` §5.2 (project-authored components against upstream ABCs) — this would be another project-authored, deterministic (not LLM-graded) checker.

**Composition.** AS-axis, registration-time gate. The check result is itself deterministic-side (a linter, not an LLM judgment) — satisfies §3's boundary discipline. Feeds the `True`/`False` value into the same unchanged `max()` formula.

**Value.** Meaningfully raises confidence that `True` reflects a real property, not just an assertion — catches the common failure class (a tool that reads the clock, hits the network, or uses unseeded randomness is definitionally not "deterministic," and this is mechanically checkable without semantic understanding of *what* the tool does).

**Cost.** Moderate, and the ceiling on what it actually catches is lower than "partial verification" implies. Requires authoring + maintaining a project-authored static analyzer (another GUARDRAIL-class component, per the existing carve-out discipline). Two real gaps surfaced on review, beyond the already-stated "clean-primitives-only non-determinism" gap: (1) banned-import/syscall lists are bypassable through wrappers, dynamic imports, native extensions, subprocess calls, or delegating to a remote service — a determined or careless tool author routes around the linter, not just an accidental one; (2) the check conflates *effect use* with *non-determinism* — reading a clock value and discarding it is not observably non-deterministic, while a genuine data race can be non-deterministic without touching any banned primitive at all. This candidate should be scoped as "catches the sloppy/accidental case," not "meaningfully raises confidence" against an adversarial or subtle one.

### Candidate C — Operator-attestation with audit-ledger accountability (HITL, reuses `operator_policy_floor` shape)

**What it does.** Setting `is_deterministic_inhouse=True` for a tool requires an explicit operator action (not a code-author's silent default) — modeled identically to `operator_policy_floor`'s existing shape: an operator-initiated override, captured in the audit ledger with persona-tier cryptographic shape per D5 §1.4, and — following the D2 precedent verbatim — **structurally prohibited (or requiring a stronger gate) at multi-tenant-compliance persona cells**, exactly as `operator_policy_floor` already is.

**Composition.** Reuses OD's existing audit-ledger + persona-tier *shape* by analogy, but building the actual registration/approval/renewal/revocation lifecycle is real CP-axis work (per §2's corrected assignment) — D2 supplies the pattern to imitate, not a drop-in mechanism. No new floor in the `max()` — this changes *who can set the input*, not the composition formula.

**Value.** This is **accountability, not verification** — a distinction sharpened on review. It closes "a silent code-author default with no one on the hook" and replaces it with "a named operator asserted this, on this date, under this persona tier." It does **not** establish that the underlying claim (the tool actually behaves deterministically) was ever true — an operator can attest to a false claim exactly as easily as a code author can silently default one. T-perm-1 (the permanent C4↔C10 tension) is not "closed" by this candidate for this field, as an earlier draft overstated — it's given a real audit trail, which is a genuine but narrower win.

**Cost.** Low-to-moderate. No new mechanism to build; mostly a registration-flow policy change + wiring the existing D5 §1.4 audit shape onto this specific field. The recurring cost is operator burden — every new deterministic in-house tool now needs an explicit sign-off step, which is friction the operator absorbs directly (this is the nameable tension in §7 below).

### Candidate D — Sandboxed behavioral verification (full semantic verification; NOT recommended to pursue now)

**What it does.** Actually execute the tool N times in an isolated sandbox with varied-but-controlled inputs and diff the outputs/side-effect traces for determinism, before permitting the flag.

**Composition.** Would require new CP-axis surface (a verification workflow/step) and new IS-axis surface (durable storage of verification runs/results) beyond the AS-axis field itself — this is the only candidate that meaningfully spreads outside AS+OD.

**Value.** The candidate that verifies closest to the *actual claim* (behavioral determinism) rather than a proxy for it — but "full semantic verification" overstates what finite sampled execution can establish: no finite number of runs proves determinism for an arbitrary program, and a valid test design requires *repeating the identical input/state case* under controlled environmental perturbation, not just comparing outputs across varied inputs (varied-input comparison, as an earlier draft implied, is not a valid determinism test at all). Best framed as "highest assurance among cheap-to-state options, still fundamentally a sampling argument, not a proof."

**Cost.** High, and open-ended: what counts as a sufficient set of repeated-identical-case trials, what to do about intentional (and legitimate) non-input-driven variance (e.g., a tool sorting a dict whose iteration order is stable-but-implementation-detail-dependent), and how this composes with the sandbox tier the *verification run itself* needs. The bootstrapping problem is real but not fully fundamental, as an earlier draft implied — an untrusted candidate can be run at the strongest available tier for its verification pass, before any lower-tier eligibility is granted from that pass's result; the remaining cost is designing a valid, non-trivial test protocol, not an unsolvable circularity. Still a full new design surface, not a bounded extension.

## 7 — Nameable cross-domain tension (surfaced, not resolved)

**C4 (tool-contract semantics / capability introspection) ⊥ C10 (blast-radius conservatism) ⊥ operator-loop-burden (a third, non-council-labeled axis worth naming explicitly).**

- C4 wants the contract surface to stay expressive and low-friction — a boolean flag is cheap, and burdening every tool registration with mandatory linting or sandboxed verification (Candidates B/D) taxes every tool author, including the overwhelming majority who are being honest.
- C10 wants the claim to actually mean something before it's allowed to influence a security-relevant tier decision — a silently-trusted, unverified boolean is exactly the "capability erasure" failure ADR-F4 itself warns about in principle, even if the specific row-7 blast-radius gating happens to bound the practical damage today (per B-25's own finding, this bounding is itself unclear/contradictory).
- **Operator-loop-burden** is the third, easily-missed axis: Candidate C (operator attestation) directly trades C10 assurance for a recurring operator action on every new deterministic in-house tool — worth naming as its own concern rather than folding it silently into C4, since it's a burden on the *human*, not on the *contract's expressiveness*.

Per §10.9's nameable-tension discriminator, this is council-eligible (a dyadic C4⊥C10 convening, possibly with the operator-burden concern voiced as a third input rather than a full third seat) **if and when the operator wants to commit to building any of B/C/D**. It is not council-eligible yet, because nothing is being decided in this memo — see §8.

## 8 — Recommendation

**Candidate A (content-hash pinning, extending C-AS-14 rather than parallel-building) and Candidate C (operator-attestation via the `operator_policy_floor` audit shape) are the ones worth further design-phase investment.** They compose (A bounds silent drift after an assertion is made; C makes the assertion itself accountable), but — corrected on review — **they do not jointly "verify determinism."** Neither establishes that the original claim was ever true; A proves the code hasn't silently changed since assertion, C proves a named human is on the hook for the assertion. Both are worth pursuing precisely because they're honest about that limit and reuse existing machinery (C-AS-14's hash pattern; D5 §1.4's audit shape; the unchanged `max()` formula) rather than inventing new primitives — but "closes both failure modes B-25 named as risks" overstated what they deliver; they reduce risk on two specific sub-modes (drift, unaccountability), not the harder "is the claim true" question. **Before scoping either, the definitional gap in §1 (what does "deterministic" mean — which inputs/state/environment are fixed, what counts as equivalent output) needs a short answer; without it, neither A nor C has a well-defined target to check against.**

**Candidate B (static linting) is a reasonable follow-on, with a lower ceiling than "meaningful" implies** — it catches sloppy/accidental non-determinism through banned primitives, not adversarial or subtle cases (bypassable via wrappers/native code/subprocess/remote calls; conflates effect-use with actual non-determinism). Still worth layering on after A+C if the operator judges the residual gap worth a GUARDRAIL-class linter's maintenance cost — just scoped honestly as a floor-raiser against carelessness, not a determinism check.

**Candidate D (sandboxed behavioral verification) is premature — YAGNI given the field currently has zero behaviorally-effective consumers** (the value is threaded through to `ToolMetadata` at every dispatch, per `sandbox_defaults.py:245`, but per B-25's own core finding, the composed floor never actually branches on it — a corrected phrasing from an earlier "zero production callers" draft, which understated that the value *is* threaded, just not consumed for a decision). D is the only candidate that spreads outside AS+OD into CP/IS, the only one whose scope is genuinely open-ended, and — though its bootstrapping problem is less fundamental than first drafted (strongest-tier-first verification runs sidestep the literal circularity) — still real, closed-ended-engineering-resistant design work. Per the workspace's own standing discipline against building speculative infrastructure ahead of a real, demonstrated consumer (the B-19/B-42/B-30/B-44 pattern), this stays a **named, not built** option unless a real tool population and a real incident/near-miss make the case concretely.

**Sequencing, softened from the first draft's stronger claim:** B-25's resolution determines whether *this field, as a sandbox-tier input,* is worth verifying at all — if Reading A, Candidate 0 (deprecate the field in that role) is the honest default, though not the only permissible reading of B-25's own hedged "arguably." Independent of B-25, if the operator or another consumer wants tool-identity integrity, drift detection, or reproducibility for its own sake, that is a separately-scoped extension of the existing C-AS-14 signature-hash surface, not a producer-side companion to this specific field. **Concretely: B-25 first; then, only if the operator wants to proceed on the sandbox-tier-floor framing, a Class 1 fork doc for Candidate A and/or C, which must open by stating the working definition of "deterministic" from §1 before specifying any mechanism.**
