## §1 The fork

B4 Slice 3 makes a **per-step** prompt take effect: an operator annotates a specific workflow step with a `prompt_version_sha`, and that step's dispatch injects the corresponding store-resolved content as the provider system prompt at the §14.5.2 translate seam, taking precedence over the per-role (Slice 1, #616) and run-level-default prompts. The per-step **model** override already exists (`StepOverride.model_binding`, C-CP-06 §6.1); per-step **prompt** is the Slice-3 increment.

Two questions surfaced at arc-open grounding (HEAD `a4ee004`):

**(Q1) Where does the per-step prompt binding live?** Adding a field to the cleared `StepOverride` schema is an X-AL-3 design-substrate extension. CP spec **v1.27 §2(d)** is explicit: `StepOverride` + `WorkflowManifestEntry` field extension follows **"X-AL-3 explicit-extension discipline"** (mirror precedents: v1.20 `default_gate_level`, v1.22 `tenant_id`, v1.34 webhook-ctor binding-lift arcs). The v1.2 baseline `// ... additional per-workload fields` extension clause sits inside the `WorkflowManifestEntry {}` block (that is how `entry_version` grew at plan v2.12 with no spec bump) — it does **not** cover the `StepOverride` sub-record. So Slice 3 owes a real CP spec §6.x amendment (this fork + clearance + bundled-absorption — the #616 pattern). Under FULL-SPEC the back-flow is pre-authorized but must be **authored**, not silently absorbed.

**(Q2) Must the per-step prompt enter the run-level §5.2 procedural-tier hash?** §14.5.2 states the coherence invariant: *"the §5.2 procedural-tier hash cannot report 'unchanged' while injected content changes."* Slice 1 (#616) brought the per-**role** catalog into §5.2 (`prompt_selection_manifest_sha`) because `per_role_bindings` is **run-level config** (on `RuntimeConfig.prompt_selection_manifest`). A per-**step** override is a different provenance **scope**: it lives on the per-workflow `WorkflowManifestEntry.per_step_overrides`, which is **not** on the runtime `HarnessContext` the §5.2 resolver reads (`run_bootstrap` does not receive `manifest_entry` — `api.py:547`). So the question is whether per-step coherence is satisfied by the run-level §5.2 hash or by step-level ledger provenance.

## §2 Resolution

### §2.1 Q1 — surface: `StepOverride` (Route A), not `PromptSelectionManifest` (Route B)

| Route | Mechanism | Assessment |
|---|---|---|
| **A — `StepOverride.prompt_version_sha` (CP §6.1)** | Add an optional `version_sha` field to the per-step override record, alongside the existing `model_binding`/`engine_class`/`hitl_placement`. | **CHOSEN.** This is the surface §14.5.3 *names* as the B4 deliverable ("the per-step override surface … R-FS-1 child-arc B4"). It sits in the per-step customization family. `step_id` is correctly **workflow-scoped** (a `StepOverride` belongs to one `WorkflowManifestEntry`). The dispatcher already receives `binding: StepEffectiveBinding` (`llm_dispatch.py:434`), so the override threads cleanly. |
| **B — `PromptSelectionManifest.per_step_overrides` (CP §29)** | Add a `dict[StepID, str]` mirroring `per_role_bindings`/`per_workload_overrides`; coherence-free (already hashed via `prompt_selection_manifest_sha`). | **Rejected.** `per_role_bindings`/`per_workload_overrides` key on **categories** (role, workload — cross-workflow, correctly run-level in `RuntimeConfig`); a `step_id` is an **instance inside a specific workflow**. Putting `step_id`s into a run-level selection manifest breaks the abstraction level and is a **Track-B reuse hazard** the moment one `PromptSelectionManifest` is shared across workflows (step-id collision). "Mirror `per_workload_overrides` exactly" is a false parallel — a step is not a category. The free-hash advantage does not buy past the abstraction cost. (advisor-surfaced.) |

### §2.2 Q2 — provenance scope: the WIRED per-step override state-ledger entry, not §5.2 (Route A-clean)

The decisive empirical finding overturned a stale v1.27 reading. CP spec v1.27 §16.5.6 says `emit_override_state_ledger_entry` "is currently ABSENT at HEAD (no production caller)." **That is stale vs HEAD `a4ee004`:** the composer is now WIRED at `workflow_driver.py:1913-1930` — gated on `binding.override_applied`, it emits a per-step override state-ledger entry whose idempotency_key hashes **`post_override_step_config = binding.model_dump(mode="json")`** (line 1927), i.e. the *whole* `StepEffectiveBinding`.

| Route | Mechanism | Assessment |
|---|---|---|
| **A-hashed — §5.2 5th component** | Thread `manifest_entry`'s per-step prompt bindings onto `HarnessContext` + add a `per_step_prompt_bindings_sha` §5.2 component (the #616 shape applied to per-step). | **Rejected.** Forces step-level (per-workflow) data into the run-level procedural-tier hash + a NEW `HarnessContext` carrier `run_bootstrap` does not currently receive — the exact impl-ahead-of-spec carrier drift advisor flagged at #616. Higher blast radius (IS spec + new carrier) for no provenance gain over A-clean. |
| **A-clean — step-level override-ledger provenance** | Add `prompt_version_sha` to `StepEffectiveBinding`; the already-WIRED override state-ledger entry's `binding.model_dump(mode="json")` then automatically includes it → its idempotency_key changes when the per-step prompt flips → **live, audit-grade, step-level provenance**. §5.2 run-level hash **unchanged**. | **CHOSEN.** Correct **scope**: a per-step override is step-scoped; its provenance belongs at the per-step override ledger entry (which *also* carries `procedural_tier_snapshot_ref` — run-level base + step-level delta together fully capture the step's effective prompt). This follows the per-step **MODEL** override precedent (model override → override-ledger entry, never §5.2). The §14.5.2 line-3078 invariant is **run-level** (active prompt + run-level selection catalog) and stays satisfied; per-step deviation is captured one layer down at the correct scope. **No IS-spec change, no new carrier.** |

**Why coherent.** A per-step prompt flip ⟹ different `StepEffectiveBinding.prompt_version_sha` ⟹ different `binding.model_dump` ⟹ different override-entry idempotency_key ⟹ a distinct hash-chained ledger entry. The `version_sha` is content-derived (`== prompt_version_sha(content)`, IS §5.2 v1.6 derive-invariant) and the store is content-addressed, so the recorded sha pins exact injected content. No injected-content change is invisible to provenance.

### §2.3 Runtime mechanism (impl-discretion per §14.5.3)

§14.5.3 defers "the per-step override surface" to **implementation discretion**, so the runtime dispatch mechanism is impl-discretion (documented, not a second fork): dispatch precedence **per-step (`binding.prompt_version_sha`) > per-role (`per_role_system_prompts[role]`) > run-level default (`active_system_prompt`)**. The per-step sha resolves to content via a bootstrap-built `prompt_versions_by_sha` map (from `ctx.prompt_manifest.versions`); **fail-loud** if the sha is not an authored store member (`RT-FAIL-PROMPT-SELECTION-UNAUTHORED`, mirroring the per-role path) and **binding-tier governance parity** (`RT-FAIL-PROMPT-VERSION-UNAPPROVED` when the **deployment** persona tier (`config.persona_tier` / the dispatcher's `self.persona_tier` — NOT the per-workflow `binding.persona_tier`; a SOLO-manifest workflow must not downgrade a binding-tier deployment's governance, the Codex-caught P1) requires approval and the sha is unapproved — closing the gap where a per-step override could otherwise bypass the OD C-OD-34 governance the per-role/default paths enforce). The §14.5.2 `RT-FAIL-PROMPT-INJECTION-CONFLICT` precedence applies to the per-step-injected prompt unchanged.

Codex (out-of-family, decorrelated diff review) caught a real **[P1] governance bypass** advisor + I missed: the per-step governance check keyed on the per-workflow `binding.persona_tier` rather than the **deployment** tier (`config.persona_tier` / the dispatcher's `self.persona_tier`).
