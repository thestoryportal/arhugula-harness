## Class 1 findings (blocking)

### F1-01 — Drain-time re-stamping inverts across CONCURRENT SIBLING sub-agent drains; the central invariant is false for the topology's core case AND untested there

- **Location:** `harness-cp/src/harness_cp/workflow_driver.py:625` (`drain_timestamp = datetime.now(UTC)` captured *before* the append loop / *outside* the writer lock) + the `drain_branch_buffers` docstring claim at `:615` ("Stamping at append makes physical-append-order == timestamp-order **by construction**") + the module-level note at `:2050-2058`.
- **Defect:** The "by construction" monotonicity claim holds only for **causally-ordered** drains (within-level: orchestrator drain-call A before workers drain-call B; single-path recursion: one child drains during the barrier, parent drains after). It is **false for two or more `SUB_AGENT_DISPATCH` sibling workers at the same level** — which is the *core* use case of recursive bounded fan-out (cap 3 → a node with multiple internal-node children). Each sibling child runs its own `execute_workflow` on a concurrent `to_thread`/executor thread and calls `drain_branch_buffers` **independently against the shared `ctx.ledger_writer`**. `drain_branch_buffers` captures ONE `drain_timestamp = now()` **before** the loop and **outside** `real_writer.append`'s lock. So two siblings capture two independent timestamps in one order, but the writer lock can serialize their physical appends in the *other* order. Sibling Y (captured a later ts) can win the lock and append first; sibling X (captured an earlier ts) then appends second → `entry.timestamp < prior.timestamp` → **`NonMonotonicTimestampError`** on the zero-tolerance writer (`state_ledger_write.py:223`, `_CLOCK_SKEW_TOLERANCE = timedelta(0)`).
- **Evidence (verified by execution, three escalating probes):**
  1. *Writer-level:* appending a later-ts entry then an earlier-ts entry to the real writer → `NonMonotonicTimestampError` raised, only 1 entry persisted. (The writer does exactly what the diff relies on it NOT needing to do for the buffered path.)
  2. *Production driver path, forced inversion:* a hierarchical parent with **two** sub-agent workers each recursing into a child, on `_RealLedgerWriter`, with a descending `wd.datetime.now()` (models the race) → the run raises `NonMonotonicTimestampError` through the real writer.
  3. *Realistic timing, NO clock patching:* two real threads, real monotonic `datetime.now()`, with a non-trivial capture→append window (which production drains genuinely have — sort, `model_copy`, JSONL serialize, fsync, and the child's *own nested drain work*): sibling A captures T1 first, is descheduled mid-work; sibling B captures T2>T1, wins the lock, appends; A appends T1<T2 → **`NonMonotonicTimestampError`** raised deterministically. (A 4000-iteration tight-window stress showed 0 natural inversions — i.e. it's timing-sensitive when the capture→append window is sub-microsecond — but the realistic-window probe makes it deterministic. `datetime.now()` is wall-clock, not monotonic, so an NTP step-back is an additional trigger.)
- **Verification-shape gap (SKILL.md checklist item 7 — `[[verification-shape-sharpened-grep-vs-e2e]]`):** every multi-worker hierarchical test uses `_RecordingLedger`, which has **no monotonicity check**. The only two `_RealLedgerWriter` tests (`test_hierarchical_delegation_live_real_ledger_chain_valid_at_depth:806` and `..._with_linear_child:832`) each use exactly **one** `_sub_agent_worker("sub", ...)`. So the zero-tolerance invariant — the load-bearing claim of Part 2 — is exercised against the real writer **only for single sub-agent recursion**, never for the concurrent-sibling case where it breaks. The diff even adds `..._with_linear_child` as "the advisor's trap, guarded" — but that trap is the *cross-level* (parent-vs-child) inversion, a different and easier case than the *sibling-vs-sibling* concurrent one.
- **Why this isn't caught today:** the runtime sync/async-bridge deadlock (Part 4) currently *masks* this — the real runtime can't reach concurrent sub-agent recursion at all. So the hole is latent behind the deadlock and behind the test-double.
- **Discriminator (§4.1):** (a) — affects substantive content of the current-phase artifact; resolution is self-contained to `workflow_driver.py` (+ a test). Does NOT trigger (b)/(c): no upstream artifact is wrong (§25.12 only mandates branch-index append *order*; §25.18 explicitly defers the timestamp mechanism to impl-discretion). Classified **blocking** because the invariant is false in the topology's central case and is the diff's headline correctness claim.
- **Resolution path (shape, not authored fix):** make the drain timestamp non-decreasing across concurrent appends to the shared writer — capture/assign the timestamp **inside** the writer's append critical section (so physical-append-order genuinely == timestamp-order), OR have the single writer stamp at append, OR make the drain-timestamp monotonic against the writer's last-persisted timestamp under the lock. Then add a `_RealLedgerWriter` test with **two concurrent sub-agent siblings each recursing** (the missing coverage), forcing the capture→append-order inversion, asserting `verify_chain` VALID. Update the `drain_branch_buffers` docstring's "by construction" claim to state the actual mechanism that makes it true.

### F3-02 — No recursion-DEPTH guard (only fan-out WIDTH is capped)

- **Location:** `harness-cp/src/harness_cp/workflow_driver.py:3537` (`_execute_hierarchical_delegation` caps `worker_count` per level) + the docstring's "scope-bounded recursion."
- **Observation:** The cap bounds fan-out *width* (≤3 direct children per parent) but nothing bounds recursion *depth*. "Scope-bounded recursion" (topology_pattern.py:76 / §25.11) is satisfied in practice because depth is bounded by the finite manifest tree, but a deeply-nested hand-authored manifest (or, post-deadlock-fix, a self-referential child manifest) would blow the Python recursion/stack via the synchronous `child_workflow_runner` re-entry. §25.18 defers recursion shape to impl-discretion, so this is defensible — but a depth ceiling (mirroring the width cap) would be the symmetric, cheap hardening.
- **Discriminator:** (a) — substantive but defensible-as-deferred. Informational; note for the operator, not a blocker.

### F3-03 — A child declaring `ORCHESTRATOR_WORKERS` escapes the cap (documented as intentional — confirm it's wanted)

- **Location:** `harness-cp/src/harness_cp/workflow_driver.py:2240-2241` (`_HIERARCHICAL_DELEGATION_FANOUT_CAP` docstring: "a child declaring `ORCHESTRATOR_WORKERS` re-enters the uncapped strategy — by design").
- **Observation:** The cap is a property of the HIERARCHICAL_DELEGATION pattern; a `SUB_AGENT_DISPATCH` worker whose child manifest declares `ORCHESTRATOR_WORKERS` recurses into the *uncapped* strategy. The docstring calls this intentional and it is spec-defensible (the cap is per-pattern; §25.11 names the cap only on the HIERARCHICAL row). Flagging it so the operator confirms that an escape-the-cap-by-declaring-a-sibling-topology path under a hierarchical root is the desired semantic, not an oversight. (Admissibility still gates the child's topology×workload, so it's not unbounded.)
- **Discriminator:** (a) — substantive design semantic, documented. Informational; confirm-don't-fix.
