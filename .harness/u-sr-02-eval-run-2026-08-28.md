# U-SR-02 eval run — cases 16/17/18 (2026-08-28)

**Why this record exists.** The plan's acceptance for the bucket-2 units is "case added
to `evals.json` **and passing**" (charter §3). Codex r7 P2 was right that the arc's
test suite never verified the second half: it checks that the fixtures carry their
defects and that the oracles demand them, never that the cases actually ELICIT the
findings. This is the run that checks it, and its honest result.

Reviews and grades are under the job scratch directory; the durable claims are here.

## Protocol

Each case's `prompt` was run VERBATIM (altering an eval's prompt invalidates the
measurement) by a fresh subagent, which wrote `review.md`. A SEPARATE strict grader
subagent then scored that review against the case's recorded `assertions`, one
PASS/FAIL per assertion, instructed to fail anything vague or weaker than the literal
demand. Grading was delegated rather than self-performed: scoring my own eval design
is a conflict of interest.

**Methodology correction, mid-run.** The first pass ran WITHOUT the skill loaded. Every
case declares `"skill": "defect-class-preflight"`, which the harness loads for the run,
so that pass was not the protocol — it is a skill-less BASELINE, and is kept as one.
The A/B below is the more useful artifact for the charter's self-improvement question.

## Controlled A/B — and the claim it retracts

An earlier revision of this file claimed "the skill demonstrably fires", citing
baseline-FAIL → skill-loaded-PASS. **That claim was unsound and is withdrawn.** Codex
r10 P2 caught it: cases 16 and 17 had their PROMPTS amended between the two runs, and
case 18 had no skill-less arm at all, so prompt and skill moved together and the data
could not separate them. A confounded comparison is not evidence, however much it
agrees with what the charter hopes.

The controlled experiment was then run: **the same FINAL prompt, both arms, skill the
only variable**, one strict grader per review against the same recorded assertions.
Graded outputs are preserved at `.harness/u-sr-02-eval-ab/`.

| case | skill-less (final prompt) | skill-loaded (final prompt) | skill-attributable? |
|---|---|---|---|
| 16 (WR-04 fix-sweep) | **PASS** (3/3) | **PASS** (3/3) | **no** |
| 17 (WR-05 bounds) | **PASS** (6/6) | **PASS** (6/6) | **no** |
| 18 (WR-06 hold policy) | **FAIL** — assertion 1 | **PASS** (3/3) | **yes** |

**One of the three rules shows a measurable effect, not all three.**

- **WR-06 (case 18) — a clean positive.** Skill-less, the reviewer refused the HELD
  disposition but offered a DISJUNCTIVE remedy: land a minimal guard, *or* "if the team
  genuinely wants to defer the whole thing, the note must explicitly name and accept"
  the risk in prose. That second branch is exactly the bare hold WR-06 exists to
  forbid, offered as an acceptable fallback. Skill-loaded, on the identical prompt, the
  reviewer demanded the same-round floor and cited step 4 by name. The rule changed the
  behaviour on precisely the axis it addresses.
- **WR-04 (case 16) and WR-05 (case 17) — no measured lift.** Both pass without the
  skill once the prompt asks for what the rubric grades. The earlier baseline failures
  were caused by the PROMPT, not by the skill's absence. Case 16's skill-loaded run did
  quote the WR-04 tell verbatim, but quoting a rule is not evidence the rule caused the
  finding when the same finding arrives without it.

What this does and does not license. It does NOT show WR-04 and WR-05 are worthless:
these are three cases on one fixture set, graded once per arm, with no repetition and
no variance estimate, and both rules target authoring-time behaviour (what a sweep
answers, what a bound cites) that a review-a-fixture eval only probes indirectly. It
DOES show that the honest current evidence for them is zero, and that anyone citing
this arc as proof the skill works should cite case 18 alone.

## Three prompt/oracle mismatches, found and fixed by running the cases

A defect class in eval authoring that no test would have caught: **an oracle grading
output the prompt never requests.** All three were mine, and all are fixed by amending
the PROMPT to ask for what the rubric grades — never by weakening a rubric:

1. Eval 16 assertion 3 demanded the reviewer diagnose WHY the sweep failed; the prompt
   only asked them to review the answers against the fix. Cue added: *"Then say what
   the sweep should have done differently at authoring time."* → passes.
2. Eval 17 assertion 6 demanded the general RULE be stated; the prompt asked only for
   per-bound derivations. Cue added: *"Finally, state the general rule this guard
   violates."* → passes. This one mattered beyond its case: WR-05 is a rule about
   GENERALISATION, so a case grading only per-bound corrections was not testing it.
3. Eval 16 assertion 4 demanded the reviewer separate two independent defects sharing
   one symptom. A prompt cue was tried and did NOT fix it; the resolution is below.

The A/B above shows these three fixes were doing more work than the skill was: two of
the three baseline failures were prompt defects, not skill absence. Fixing an oracle's
prompt is a prerequisite for measuring anything; it is not itself a result.

## Eval 16 assertion 4 — resolved by scoping the fixture, not by softening a rubric

Three independent reviewers (skill-less, skill-loaded, skill-loaded-with-cue) all
missed the release-then-reclaim defect; the third reached `release()` and concluded it
disappears under an atomic `claim()`. That conclusion was FALSE — two SEQUENTIAL
`drain_once` calls, no threads and no race, gave `sink == ["g", "g"]`, because the
registry recorded what was in flight and never what was done.

So the assertion was correct and the reviewers were wrong. It was reported as a
genuine FAIL rather than softened. But a documented failed gate is still a failed gate
(codex r8 P2): the plan requires every case "added AND passing", and no CI check
enforces it, so the unit was failing its acceptance gate behind a green suite.

The resolution took **the other arm of codex r2's original finding**, which had offered
two remedies for the fixture's ungraded second defect — grade it, or remove it.
Grading it produced an assertion three reviewers could not pass; removing it makes the
fixture single-concept, so eval 16 grades WR-04 alone, which is also how cases 12–15
are built. The `release()` method and the `finally` release are gone; claims are
permanent, so the registry means "already drained" and the ONLY planted defect is the
non-atomic claim. The case then passed 3/3 on a fresh run.

**Registered independently, on its own merits:** the liveness-state vs
completion-state class candidate — a registry that tracks what is in flight and never
what is done, so a later actor legitimately re-acquires finished work. Three reviewers
missed it, and no current class fires on it (class 1 asks about atomicity, which this
defect hides behind). Classes are U-SR-01's merged surface and outside WR-04/05/06, so
this is registered for a follow-on unit rather than smuggled into this one. It no
longer blocks this unit's gate; it stands as a coverage finding.
