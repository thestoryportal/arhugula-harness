# C10 blast-radius verdict — U-1 slice-1 frozen-tool-superset visibility change (2026-07-09)

*Council voice C10 (Action Safety & Blast Radius) adjudication of the C4⊥C10 tension surfaced at `.harness/u1-cache-breakpoint-slice1-design.md` §"CRITICAL open question". Genuine dedicated-voice pass (C10 was NOT a voice in the original U-1 C4/C2/C6 design). Resolves the impl-blocking Option A vs Option B decision. Probe-resolved per §10.9 discipline: council surfaces, primary sources decide.*

## VERDICT: **A-with-conditions** (Option A is the posture-consistent choice for slice 1)

Slice 1 SHOULD send the full frozen tool superset per step with per-step selection on `tool_choice`, gated by the conditions below. Option B (preserve per-step wire-subsetting) is NOT required — no committed contract forbids A, and refusing A purely to minimize wire visibility when execution is already gated is the over-gating failure mode (FM-F, SKILL §86), inverting the committed maximal-action-surface posture (Persona §5; s13 §4.1).

## The load-bearing distinction: SELECTION ⊆ REGISTRY, and every registry tool is execution-gated — `payload.tools` is visibility-only TODAY

The sharper claim (stronger than "visibility ≠ execution"): the wire `tools[]` array does NOT scope execution in the current harness. Execution scope is registry-scoped and already decoupled from the wire array, so Option A relaxes NO execution-scoping gate. Grounded empirically:

- **The harness dispatches a TOOL_STEP by `step_payload["tool_id"]`, resolved against the REGISTRY — never against `payload.tools`.** `RuntimeToolDispatcher` (`runtime_tool_dispatcher.py:769-814`) reads `step.step_payload["tool_id"]`, routes it via the stage-5 `routing_index` to the owning host, and calls `host.tool_registry.get(tool_id)`. A `tool_id` in no host's registry raises `RT-FAIL-TOOL-CONTRACT-UNKNOWN` (:796,814). **There is no `payload.tools`-membership check in the dispatch path.** The per-step wire tool array (`n` → `kwargs["tools"] = list(n)` in `llm_dispatch.py`) is what the model SEES at an INFERENCE_STEP; the actual tool EXECUTION is a separate registry-keyed TOOL_STEP dispatch. So `payload.tools` is a **visibility/steering** surface today, not an execution-scoping gate. This is the knockout: the model could already only cause execution of a registry-resident tool, whatever the wire array showed — A changes the *visible/selectable* set, not the *dispatchable* set.
- **Every registry tool is execution-gated regardless of which step selects it.** `step_blast_radius.py` + `step_mcp_trust_tier.py` + `effect_fence.py` + `RuntimeToolDispatcher` all resolve the `tool_id` against the `ToolRegistry` (`ctx.mcp_client_hosts[*].tool_registry`) / `ctx.tool_contracts` and apply `max()`-floor gating + the sandbox-tier floor (`:829-843`) + the effect-fence. An unresolvable/unregistered tool RAISES `StepBlastRadiusResolutionError` (fail-safe: an unclassifiable action gates, never auto-approves — `step_blast_radius.py:29-33,121-126`). Wire visibility is **not an input** to any gate. The blast-radius boundary is the sandbox/trust/registry EXECUTION gate — A leaves it fully intact.

The committed containment boundary across every relevant contract is **capability/execution + sandbox containment**, never model-context tool visibility.
- **ADR-D2 §1.4 / :135 frames the boundary as capability + containment, explicitly NOT visibility.** Sub-agent registry-downgrade "*removes capability* (sub-agent cannot invoke a tool)"; sandbox-monotonicity "*constrains containment*." The blast-radius axis is `sandbox_tier_floor(tool, deployment_surface, blast_radius_tier, mcp_transport, mcp_server)` — five EXECUTION-time inputs, zero visibility inputs.
- **The committed prompt-injection mitigation is architectural-cut-of-leg, not tool-count minimization** (ADR-F5 §iii; ADR-D2 Alt-3; Cluster 4 §2.3.2 [HIGH]). Filter/surface-minimization tops out ~97% and is rejected as insufficient; the committed cut is sandbox network-egress restriction + secret-passthrough contract + per-tool `required_secrets` allowlist. None of these depend on how many tools are *visible* in context.

## Grounding on the three required axes

### 1. No committed contract requires least-privilege tool VISIBILITY per step

Verified by raw dir-arg grep across all 295 `design-substrate/` files (the initial `*.md`-glob greps mangled to false-negatives — rtk `rg-flag-and-paren-mangling`; re-run raw per §14.3):

- `least.privilege` → **only** ADR-D4 §1.5 Rationale + Alt-7: principle-of-least-privilege at the **TOPOLOGY layer** = sub-agent registry inheritance/downgrade (removing *invoke capability*), NOT model-context minimization.
- `visib` → **only** operator-observability surfaces (span sampling, audit `operator_readable`, `VisibilitySurface` for IS path-classes). Zero hits framing model-context tool minimization as a containment property.
- `per.privilege | privilege.tier` → ADR-D3 `frozen_tool_superset_per_privilege_tier` (the slice-3 partition — see conditions) + D4 §1.5 privilege inheritance. Neither commits per-STEP wire-visibility minimization at top-level dispatch.
- JIT / progressive-disclosure → only skill-BUILD timing (Project_Workflow, Phase_7_Kickoff), never tool-context loading. Note C2 (JIT-triggers owner per SKILL §52) WAS a voice in the U-1 pass and converged on full-superset emission — the visibility owner effectively pre-cleared it.

**Finding: no committed decision is violated by A.** Visibility ≠ execution; the blast-radius boundary is the sandbox/trust/registry EXECUTION gate, which A leaves fully intact.

### 2. Multi-tenant / persona-tier: no cross-tenant/cross-privilege leak forbidden at the committed posture

- Persona is a **bridging-arc**: sole operator with direct host access at design-time; multi-tenant binding is FUTURE-state (Persona §1, §2.1, and every `tenant` hit is "at multi-tenant **binding**" — Open Question #10 "Tenant isolation specifics… Bound WHEN multi-tenant deployment design begins"). Tenant-isolation is explicitly a deferred, not-yet-committed surface.
- At the committed tiers (solo-developer / self-hosted-server), all registered tools already belong to the single operator's own trust domain — full-superset visibility to a single-operator model leaks no cross-tenant tool *existence*, because there is one tenant.
- ADR-D3 already anticipates the multi-privilege refinement: the sub-agent breakpoint is `[sub_agent_system_prompt + role_prompt + frozen_tool_superset_per_privilege_tier]` — the superset is PARTITIONED per privilege tier at the sub-agent boundary. This is the committed home for cross-privilege visibility partitioning, and the design correctly defers it to slice 3.

**Finding: no committed persona/deployment posture forbids A at solo-developer + self-hosted tiers.**

### 3. Prompt-injection / selection surface: the selectable set widens to the registry, but the DISPATCHABLE set was already registry-scoped

Framing correction (per decorrelated review): the change is **selection-scope**, not pure visibility — with `tool_choice: auto`/`any`, the model can *select* (and thus name for dispatch) a registered tool the step's `payload.tools` did not declare. Whether a dispatch can be *initiated* is a C10 blast-radius question, so this is squarely in-lane. But it does not widen the *executable* surface, because:

- **Selection ⊆ registry = the already-dispatchable set.** Per axis-1 above, the harness TOOL_STEP dispatch never validated against `payload.tools` — it resolves `tool_id` against the registry. The wire superset IS the registry union (`runtime_tool_dispatcher_factory.py:269` cross-host union under the RT-FAIL-MCP-TOOL-NAME-COLLISION guarantee). So the frozen superset exposes exactly the set of validly-dispatchable tools — it adds NO tool the harness couldn't already have dispatched. The selectable set rises to equal the dispatchable set; the dispatchable set is unchanged.
- **Every selectable/dispatchable tool is per-tool gated** — a tool an injection names still must clear `blast_radius_floor` + `mcp_server_trust_floor` + sandbox-tier floor + effect_fence to EXECUTE. The committed mitigation (architectural cut, MCP trust-tier, per-tool gate) operates on execution, not context membership.
- MCP supply-chain integrity (the one heavy preventive layer, s13 §4.1(d)) is a per-SERVER trust-tier property, unaffected by per-step wire visibility.

**Finding: the selection/injection-surface delta is immaterial at slice-1 scope — selection ⊆ registry ⊆ the already-execution-gated set; it does not justify Option B's complexity.**

## Conditions / guardrails for A (C10 sign-off is conditional on these)

1. **Single-privilege-tier / top-level dispatch only.** Slice 1 is single-threaded-linear (no sub-agents), so this is satisfied structurally. But the frozen superset MUST emit only on top-level (non-downgraded) dispatch. **Rationale (the C10-lane condition the C4/C2 pass missed, SKILL §51):** D4 §1.5 enforces sub-agent downgrade via `sub_agent_tool_registry` — external-irreversible is **REMOVE (sub-agent registry omits the tool)**, external-reversible is DOWNGRADE_TO_ASK. Because that downgrade is a **registry/execution** mechanism (the omitted tool cannot dispatch — the gates key on registry membership), applying a parent-scoped full superset to a downgraded sub-agent's wire context would make the model *see* tools its registry has REMOVED. That is still not an execution capability leak (the removed tool cannot dispatch), but it defeats the topology-layer least-privilege intent and re-surfaces the exact tools D4 §1.5 deliberately hid from the sub-agent. The committed fix is ADR-D3's `frozen_tool_superset_per_privilege_tier` (slice 3). Until slice 3 lands, the superset must be computed from the DISPATCH-scoped registry, so a sub-agent dispatch naturally gets its downgraded registry's union — never the parent's.
2. **Fail-safe if a downgraded/sub-agent dispatch ever reaches the frozen-superset path before slice 3.** The superset computation (`runtime_tool_dispatcher_factory.py`) must derive the union from the dispatch's OWN resolved registry (`ctx.mcp_client_hosts[*].tool_registry` scoped to the dispatch), NOT a captured parent-scoped set — so per-privilege-tier partitioning is correct-by-construction once slice 3's sub-agent registries exist. If the impl instead captures a single global union, register a guard that the frozen-superset emit is skipped (falls back to `payload.tools`) on any SUB_AGENT_DISPATCH-originated step until slice 3.
3. **Slice-3 per-privilege-tier partitioning remains REQUIRED before multi-tenant binding** — already the design's registered slice-3 item (`frozen_tool_superset_per_privilege_tier` + sub_agent breakpoint). This verdict does NOT clear multi-tenant; it clears solo-developer + self-hosted single-privilege-tier slice-1.
4. **Deterministic-order + ≥4096-tok non-vacuity gates** (already in the design §"Slice-1 implementation" 2/4) stand — orthogonal to blast-radius but load-bearing for no-silent-failure (a nondeterministic order is a silent cache miss).
5. **No dispatcher-side step-scope check is required (empirically resolved, NOT assumed).** The `RuntimeToolDispatcher` already dispatches by registry-resolved `step_payload["tool_id"]` with no `payload.tools`-membership validation (`runtime_tool_dispatcher.py:769-814`), so `tool_choice`-steered selection over the superset relaxes NO existing execution-scoping gate — the harness never had one at the wire-array level. Had the dispatch instead validated `tool_use ∈ payload.tools`, this condition would REQUIRE preserving that dispatcher-side check while sending the superset only on the wire (cache-stable prefix + `tool_choice` steer, dispatcher still rejects an out-of-step-scope tool). That branch does not apply — but if a future arc introduces a step-scope dispatch gate, the frozen-superset path must preserve it.

## Net

A is not merely *permitted* — it is the posture-CONSISTENT choice: maximal-action-surface with reactive containment (execution-gated, richly audited) is the committed C10 discipline, and Option B would be reflexive over-gating (FM-F) that minimizes a wire-visibility surface no committed contract treats as a containment boundary. The impl is unblocked for slice 1 at single-privilege-tier top-level dispatch under conditions 1-4.
