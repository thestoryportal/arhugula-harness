# Clearance — `Spec_Information_Substrate v1.8`

v1.8 is the **IS-side carrier of R-FS-1 arc #4 (B1-spec-1b)** — the coordinated IS amendment that CP spec v1.32 §25.13 forward-references (Route Y). It adds the **`branch_metadata` D-derivative sidecar** to `StateLedgerEntry` — the persisted carrier for the fan-out branch causality + per-branch terminal disposition the CP non-linear-topology `WorkflowDriver` composes. This is a **design-substrate-only** amendment; **no code lands** here (the carrier impl is a later arc, B1-impl-N).

**What changed.** One additive amendment — a NEW §5.4 sub-section under C-IS-05 — plus the Status-block Revision row, the v1.7→v1.8 Change-note, and the `harness-is/CLAUDE.md` §1.2 pointer bump:

1. **`branch_metadata: BranchMetadata | None`** — the optional **8th** field on `StateLedgerEntry` / `EntryPayload` (alongside the §5.1 7th field `procedural_tier_snapshot_ref`). `BranchMetadata` = `{parent_action_id: Identifier, branch_index: int ≥ 0, terminal_status: {cancelled, completed, timed_out} | None}`. `None` at every entry outside a fan-out branch (the `SINGLE_THREADED_LINEAR` path, bootstrap, non-branch steps — **every pre-v1.8 entry**).
2. **Producer-supplied, not resolver-derived** — the CP `WorkflowDriver` composes it (CP spec v1.32 §25.11 / §25.13 / §25.15); unlike §5.1, there is **no §5.2-analogue resolver contract**.
3. **Two carrier invariants:** (a) **append-only** — `terminal_status` is set at the branch's *terminal entry* written fresh at branch-termination, NEVER by mutating an already-written entry (mutation would re-hash a persisted entry and break the §6.3 chain); (b) **dispatch-boundary disposition, not step-outcome** — a ran-and-errored branch is `completed` (step-outcome lives at the step entry per CP §25.15.2 obl. 3), which is why the value set has no `failed`.

**Why "zero §6 / forward-only" is true.** `branch_metadata` is payload content (tamper-evident per §6.5 when non-`None`), but the §6 construction *discipline* is unchanged: the canonical payload includes the sidecar when non-`None` and **omits it when `None`** — the established §5.1 pattern (`entry_hash.py` `canonicalize` includes a sidecar field only `if … is not None`). Every pre-v1.8 entry carries `branch_metadata = None`, so it canonicalizes **byte-identically** to a v1.8 `None`-sidecar entry — ZERO breaking change for the existing chain; forward-only, no historical-entry migration.

**The cross-spec reconciliation (and why it is NOT a halt).** Three existing CP-axis disposition vocabularies overlap the new `terminal_status`: `SubAgentResultStatus` `{completed, failed, cascade-cancelled}` (C-CP-14 §14.2 span attribute), `CascadeDecisionAtFanoutClose` `{completed, cascade-cancelled, paused-on-failure}` (C-CP-15 §15.2 fanout-close primitive), `RunStatus` `{SUCCESS, DRAINED, FAILED, PARTIAL, PAUSED}` (C-CP-25 §25.2 run-level). §5.4 documents the relationship **descriptively**: these are distinct token sets on **distinct carriers** (no two are the same field on the same object → no shared comparison column → no collision). The distinctness is by carrier-segregation, NOT token-disjointness — `completed` is even carried with a *different* meaning on `SubAgentResultStatus` (success) than on `terminal_status` (dispatch-boundary), and `RunStatus` does not use `completed` at all. The committed value set is coherent + buildable → no Class-1 halt. The **reciprocal CP-side cross-reference** (CP spec v1.32 §25.13/§25.15 commits the value set without pointing back at these sibling enums) is flagged a **Class 3 informational** doc-coordination item, foldable into a future CP touch (e.g. B1-spec-2 / B1-plan).

**Carve-outs for Phase 7 / downstream consumers.**
- **Carrier-home is deferred to B1-impl-N** — `harness-core` (shared) vs `harness-is` (with the entry shape), exactly as §5.1 deferred resolver residence. The **one hard constraint:** NOT `harness-cp` — the IS axis is consumer-most-upstream with **0 outbound cross-axis edges** (harness-is §1.1 / CXA §2.2), so IS cannot import from CP; CP consumes the entry shape from IS via the established CP→IS direction.
- **Write-cadence is deferred to B1-spec-2** — *which* entry carries the non-`None` `terminal_status` (a dedicated branch-terminal marker entry vs. the branch's last step entry) and *which* entries carry `branch_metadata` at all (every branch step vs. spawn + terminal) are producer/runtime concerns (CP spec v1.32 §25.18).
- **`branch_path` is NOT in this sidecar** — it is the CP-side §25.16 *idempotency-key* composition detail; `(parent_action_id, branch_index)` is the persisted causality key (`action_id` is globally unique, so it is unique even under nested fan-out).
- **§5 six-field shape / §5.1 sidecar / §5.2 recipe / §5.3 store / §6 hash-chain / §7 read-write / §10 seam exports are PRESERVED VERBATIM.** No new CXA export seam (the sidecar travels the existing §10.1 entry-shape export).
