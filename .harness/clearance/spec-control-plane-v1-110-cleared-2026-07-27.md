# Clearance — `Spec_Control_Plane_v1_110` (co-designed B-79/B-80 spec leg)

Adds TWO new additive CONTRACT properties to `Spec_Control_Plane_v1_106.md` §1.2's HITL delivery mechanism family (C-CP-26 §26.8.1) and its sibling effect-fence-resolution mechanism (`Spec_Control_Plane_v1_107.md` §1):

**Property 7 (closes `B-79`).** A resumed branch's HITL-relevant gate configuration (its applicable `HITLPlacement` set + `removed_placements` override) MUST be validated as unchanged between pause-capture time and resume time, at the fan-out closure's pre-dispatch-gate-owning delivery site, the LINEAR `resume_at` site, the `EVALUATOR_OPTIMIZER` site, and the `DECENTRALIZED_HANDOFF` site (all 3 sequential sites carry no per-step identity check of any kind today — round-2 codex out-of-family review caught EO/DH's initial omission; both mirror LINEAR's mechanism EXACTLY per their own inline comments and share the identical gap), and — impl discretion, not required — `RuntimeHITLGateComposer`'s Step 0. A mismatch MUST reject the resume as a material diff, fail closed, reported through the SAME `RunResult.fail_class` path `_resume_body_mismatch` already uses. §1.3a authorizes one new additive field on `PreDispatchGateOwningBranchResumeState` (drop-when-empty/`None` hash-strip scoped, mirroring the `v1.108` precedent) plus a net-new carrier at the LINEAR/EO/DH sites (one shared or 3 distinct, impl discretion).

A dyadic council convening (C10 + C1) ran the mandatory probe-first check BEFORE deliberation and falsified this row's own registered premise — Runtime-owned persona/engine-class placement-resolution logic is NOT opaque to `harness-cp` for the scenario in scope; `step_context.hitl_placements` (via `fold_step_hitl_placements`) and `StepEffectiveBinding.removed_placements` are both CP-native folds already available at pause-capture time, so no new cross-axis seam is needed. A TENSION over hash scope (narrow `.position`-only vs. the full 4-field `HITLPlacement` tuple) was probe-resolved in favor of the broader hash at zero extra cost (`HITLPlacement` is itself a frozen 4-field model already inside the same tuple). Every load-bearing claim in the convening's recommendation was independently re-verified against current HEAD at this spec's authoring time (`pause_resume_protocol_types.py:208-252`, `hitl_placement.py`, `workflow_driver_types.py`, `per_step_override_evaluator.py`, `hitl_gate_composer.py:1684-1762`), not merely trusted.

**Out-of-family `just codex-review-uncommitted` caught 3 real defects across 2 rounds, before merge.** (a) [P1] round 1: the first draft ALSO authorized the new field on `PausedChildBranchResumeState` (`B-21`/`B-31`) — confirmed WRONG by direct read (`workflow_driver.py:8016-8058`): that carrier only forwards `child_resume_snapshot` to a recursively-dispatched child's own, separate `execute_workflow()` call, and never itself constructs a `HITLDeliveryCell` (`workflow_driver.py:8036-8045` confirms delivery-cell construction is gated on `branch_index in _recovered_pre_dispatch_gate_owning` — a DIFFERENT carrier). Authorizing a placement-identity hash there would not close any real gap and would incorrectly reject a valid resume on an unrelated parent-placement change; fixed by scoping §1.3a's authorization to `PreDispatchGateOwningBranchResumeState` only (a recursively-dispatched child's own gate identity is independently covered by this same property applying at the child's own `execute_workflow()` invocation). (b) [P2] round 1: §1.1(c) originally claimed the rejection mirrors a C-CP-20 audit-ledger reporting path — confirmed WRONG by direct read: `_resume_body_mismatch`'s existing mismatch handling returns `RunResult(status=FAILED, fail_class=...)` directly, with no audit-ledger emission at all; fixed to require only that same reporting shape, not a new audit-ledger requirement. (c) [P1] round 2: property 7's scope entirely OMITTED the `EVALUATOR_OPTIMIZER` (`workflow_driver.py:10789-10806`) and `DECENTRALIZED_HANDOFF` (`workflow_driver.py:14803-14820`) delivery-cell construction sites, both landed later by the `B-78` impl leg (PR #1117) and confirmed by their own inline comments to mirror the LINEAR mechanism EXACTLY — fixed by extending §1.1(d)/§1.2/§1.3a's scope to cover all 3 sequential sites uniformly.

**Property 8 (closes `B-80`).** The effect-fence-abort HITL-delivery suppression guard MUST be computed against the true root of the resume tree, mirroring the ALREADY-SHIPPED `compute_hitl_uniform_fallback_eligible_run_id`/`compute_effect_fence_uniform_fallback_eligible_key` root-computed, thread-down-unchanged discipline — a pure computed value, no `§1.3a`-style durable-carrier authorization needed (confirmed at this spec's authoring: `compute_effect_fence_uniform_fallback_eligible_key`, `workflow_driver.py:2873-2908`, derives fresh from the already-persisted `root_snapshot`, never itself stored). Scope is deliberately blanket, not `cascade_policy`-precise — `PauseSnapshot` carries no `cascade_policy` field at any level, confirmed at authoring time. Property 8's signal, once true, TAKES PRECEDENCE over property 6's §1.1(b) mandatory-delivery outcome (§2.3) — property 6's text is unamended; only the circumstances under which its outcome fires are now conditioned.

A dyadic council convening (C1 + C10) ran the mandatory probe-first check and confirmed `HIERARCHICAL_DELEGATION`'s recursion crosses the CP→Runtime→CP boundary via a fresh `execute_workflow()` call at every level (not same-stack-frame Python recursion), and that two existing sibling values (`hitl_uniform_fallback_eligible_run_id` from `B-39`; `effect_fence_uniform_fallback_eligible_key` from `B-70`) already thread a root-computed signal through the identical channel — confirmed independently at this spec's authoring time via direct grep of `workflow_driver.py`'s `execute_workflow()` signature and `child_workflow_runner.py`'s `ChildWorkflowRunner` Protocol (lines 88-89, 185-186, 258-259). A TENSION over blanket-vs-precise scoping was probe-resolved in favor of the blanket reading (the shipped local rule is itself `cascade_policy`-blind; a precise fix would need a new durable carrier field this spec leg does not authorize).

**Out-of-family `just codex-review-uncommitted` caught 1 real defect in the first draft, before merge.** [P2] The plan-side text claimed "zero cross-axis cascade" for property 8's new threaded parameter — confirmed WRONG: `ChildWorkflowRunner` is a Runtime-owned Protocol (`harness-runtime/src/harness_runtime/lifecycle/child_workflow_runner.py`), not a CP-owned type, so threading a new parameter through its signature IS a cross-axis touch, regardless of whether the parameter's value is CP-computed. Fixed by correcting the claim: no NEW crossing point is introduced (the parameter reuses the SAME established CP→Runtime→CP boundary its two sibling parameters already use), but the touch itself is real. This also surfaced (not fixed, out of this delta's scope) a pre-existing gap: neither sibling parameter is documented anywhere in `Spec_Harness_Runtime_v1.md` today.

Both properties are purely additive — properties 1-6 (v1.106 §1.2, v1.108 §1) are preserved verbatim; property 6's §1.1(b) TEXT is unedited, only its outcome's firing condition is now conditioned on property 8's signal (§2.3). No enum change for either property. Property 7 adds no signature change; property 8 DOES authorize one new additive `execute_workflow` parameter, which also threads through the Runtime-owned `ChildWorkflowRunner` Protocol (same established crossing its two sibling parameters already use).
