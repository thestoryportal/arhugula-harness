# Clearance — `Spec_Control_Plane v1.49`

v1.49 is a behavioral delta over v1.48 absorbing the **R-FS-1 standalone arc `B-HITL-PLACEMENT-PER-STEP-OVERRIDE-FOLD`**. It specifies at **C-CP-06 §6.2** how the singular per-step `StepOverride.hitl_placement` override composes with the workflow-level `WorkflowManifestEntry.hitl_placements` tuple (C-CP-17 §17.3) onto the per-step `StepExecutionContext.hitl_placements` (the v1.41 producer field) so the runtime wrap-time HITL gate composer (runtime §14.8.2 step 1) reads the **effective** placement set. It resolves the silence the v1.41 producer arc explicitly registered as this follow-on, and makes the previously-DEAD `StepEffectiveBinding.hitl_placement` resolution load-bearing.

**The fold semantic — ADD-only (workflow wins on a same-`position` collision) — is genuinely monotone; NO operator gate.** The reasoning + the decorrelated catch that corrected it:

1. **The singular type forecloses position-level set-removal.** `StepOverride.hitl_placement` is singular (`HITLPlacement | None`); the workflow source is a tuple. A singular field cannot represent a replacement of the workflow set, so a per-step **removal** of a workflow gate position is structurally unrepresentable (root `CLAUDE.md` §4 illegal-states).
2. **But the singular type does NOT foreclose attribute-level loosening (the advisor's pre-push catch).** `HITLPlacement` carries `tool_filter` ("limits which tools trigger the gate"), `cascade_policy`, `timeout`. *Replacing* a same-`position` workflow placement with the per-step override could **loosen** the §17.1 "all cells" floor at the attribute level while the position stays present — e.g. a workflow `PRE_ACTION(tool_filter=None)` (gates all tools) replaced by `PRE_ACTION(tool_filter=("git_push",))` leaves every other tool **ungated** at that step. The interim "union-by-`position`, tune-in-place" impl was therefore a SILENT loosening shipped under "no operator gate" — the X-AL-3 silent-absorption shape.
3. **ADD-only is the genuinely-monotone fix.** On a same-`position` collision the **workflow placement wins** (the override is a no-op); the override can ADD an absent position but can neither remove a position NOR weaken an existing one. This is honestly monotone (overrides only TIGHTEN) — the placement-set analogue of the §19.1 `max()`/floor-only gate-level posture — and keeps the no-gate autonomous outcome. ALL per-step tune/replace of an existing position (which can reduce coverage) folds into the operator-gated `B-HITL-PLACEMENT-PER-STEP-LOOSEN` arc (a committed-invariant relaxation — the operator's call per the v1.38 precedent).

So this is **impl-to-cleared-spec** on the existing C-CP-06 contract (the field + resolution + field-by-field discipline all pre-exist; v1.17 §6.2 already described the effective field's source as "manifest_entry hitl_placements per §6.1 + per-step override"). It mints **no** new contract / ADR / enum / fail-class / manifest field / §5.2 hash-recipe / §16.5.4 idempotency key / CXA edge. No committed invariant is sacrificed → **no operator gate**.

**Mechanism — the v1.38 Option-B composition-time fold (single dispatch-read source PRESERVED).** A pure helper `fold_step_hitl_placements(workflow_placements, override)` (ADD-only: append an absent position; on a collision return the workflow tuple unchanged) is wired at the per-step / per-branch composition sites across all 6 topology paths — linear, evaluator-optimizer, the orchestrator step (via the `_per_step_hitl_placement_override` read helper, mirroring `_per_step_role_override` where the binding isn't yet resolved), the orchestrator-worker + parallelization-worker branch contexts (via `.model_copy`), and the hierarchical/handoff stage context. Each fold is keyed from `manifest_entry.hitl_placements` (the workflow base), so an override on one cell never leaks to a sibling or parent. The runtime dispatch read (`step_context.hitl_placements`) is byte-unchanged; only the produced tuple is the effective set. Zero runtime impl change.

**Per-step tune/replace OR removal is the separate operator-gated arc `B-HITL-PLACEMENT-PER-STEP-LOOSEN`.** Modifying an existing workflow placement (tune/replace — which can loosen attributes) OR removing a workflow gate position both reduce coverage → a committed-invariant relaxation (the monotone HITL posture) plus a typed-shape change (a tuple-valued, replace/removal-capable per-step carrier). Registered (not built) at the spine ledger.

Reviewed during clearance (verified by execution): the fold helper unit tests (ADD-new-position appends; same-`position` collision is a NO-OP / workflow wins, a narrowing `tool_filter`+short-`timeout` override is IGNORED — no loosening; `None` → workflow tuple verbatim); the by-execution linear path (a NEW-position override on step-0 → step-0 context = workflow ∪ override, step-1 = workflow tuple, not leaked; a SAME-position narrowing override → workflow placement preserved verbatim); and the by-execution fan-out anti-leak (an override on worker-1 → only worker-1's context adds it, siblings + orchestrator carry the workflow tuple only; an override on the ORCHESTRATOR step → the orchestrator context adds it but the workers re-fold from `manifest_entry` so it does NOT leak to them). harness-cp 1162 passed / 1 xfailed; pyright 0/0/0; the runtime HITL gate composer suite (83) unaffected (it reads `step_context.hitl_placements` unchanged).
