# Clearance — Implementation_Plan_Memory_Substrate_v1 v1.2 (B-92 spec leg, plan delta)

v1.1 → v1.2 adds ONE new atomic unit, **U-MEM-27 — Gate promotion of cross-family-captured records behind review**, decomposing the impl leg of `Spec_Memory_Substrate_v1.md` v1.2. Contracts C-MEM-03, C-MEM-10; requirements R-MEM-05, R-MEM-09; **axis information substrate plus runtime plus operational discipline; depends on U-MEM-01, U-MEM-07, U-MEM-08, U-MEM-09, U-MEM-16, U-MEM-26.**

The unit carries five coupled parts. **Write side:** the tri-state `MemoryRecordEnvelope.captured_cross_family` field on `harness-is`, and its derivation at a **single central site** — `EpisodicMemoryCapture._record` (`harness-runtime/src/harness_runtime/memory_capture.py:1015-1046`), which already receives both inputs (the call's raw `provider` at `:1025`; the resolved scope from `_scope_for_record` at `:1038-1042`). The unit is explicit that **no `capture_*` signature changes and no per-method threading is owed**: all seven methods already pass `provider` to `_capture`, which passes it to `_record`. Prescribing a seven-signature refactor would repeat the exact falsehood the fork's R9 pass corrected, and the unit body forecloses it. One mechanical consequence is pinned instead: `_scope_for_record` is today called inline at the envelope's `scope=` argument, so the resolved scope must be bound to a local before the envelope is constructed. **Read side:** the `cross_family_capture` value admitted into the closed implementation-side `PromotionRiskFlag` enumeration (the only enum edit the unit makes), and the review-required / never-auto-promotable gate at **both** promotion entry points — the hint path's `_candidate_from_hint` and the tool path's `_propose_promotion`. The flag is the **single gate authority**: the provenance value is read from the envelope exactly once, at the existing flag-derivation site, and the four decision predicates are widened to receive **that flag set** rather than a second independent read — the correction Codex round 1 [P2] forced, since parallel derivations would leave the flag advisory and free to diverge. **Two-surface authority model (Codex rounds 2 and 3, reconciled at round 3):** a `PromotionCandidate` model validator rejects the **disagreeing pair** at every *validating* constructor — a consistency guarantee, explicitly **not** an unreachability claim, since `model_copy(update=...)` bypasses after-validators by design and overriding it is forbidden — and the **activation boundary** carries the real obligation: `approve` / `edit_and_approve` **re-derive** the condition from the stored source records named by `source_memory_refs` — **once per service call, carried as a frozen snapshot** that the gate test and every durable write of that call both consume, the gate being a pure projection of it (the round-7 [P1] correction: two independent reads could disagree across a legitimate same-identity rewrite, admitting an activation on one reading while persisting another) — and, irrespective of what the candidate asserts, **override its `auto_promote_allowed` claim to False** on a re-derived `true` / `unknown` — which withholds the **automatic path only**, since `operator_approved` is a disjunct of the pre-existing gate and an operator-approved activation must still succeed (the round-4 [P1] correction: the round-3 wording read as an unconditional refusal, i.e. reading C). Any unresolvable source is treated as `unknown` on the same terms. The identical re-derivation normalizes the reserved flag before **every** durable write taken from such a candidate — implemented at the single choke point `_persist_decision`, which has **four** callers (`propose_for_review`, `approve`, **`deny`**, `edit_and_approve`), so no artifact of any status can carry an omitted or spoofed mark (the round-5 generalization; round 4 had covered the proposal write alone, leaving the operator-approved `ACTIVE` record — the pipeline's longest-lived artifact — persisting whatever the candidate asserted). That closes the two cases no value-level check can (a candidate that **omits** the mark while claiming auto-promotability, and a copied illegal pair) and it requires widening the `PromotionDecisionStore` Protocol with a read method — real work, since it has none today, but an **internal seam**: the Protocol appears nowhere under `design-substrate/` and the widening is satisfied by the existing `MemoryStore.read_record`. Plus the **reserved-flag re-derivation**, which discards a caller-supplied `cross_family_capture` and re-derives it from the source envelope in both directions, so the gate authority cannot be written by its own input. **Durable carrier:** the flag is persisted into the promotion-written record's **content** (`_semantic_record_content` / `_procedural_record_content`), so the durable `PROPOSED` record review actually reads records why the candidate was held; the C-MEM-08 ledger row is deliberately untouched, and the accepted cost is that promotion records written after the unit lands carry one more content key and hash accordingly — forward-shape only, no existing record moved. **Witnesses:** per-arm, per-layer, biconditional, and mutation-probed (below).

**The gate is specified as unconditional on policy, and the unit carries a vacuity-defeating witness for it.** `ReviewMode.AUTOMATIC` is already the sole production setting while the promotion decision is pinned to `PROPOSE_SEMANTIC`, which makes every candidate review-required today for reasons unrelated to this gate. A test that only ran under that pin would pass with no gate implemented at all. The unit therefore requires a paired assertion under `PROMOTE_SEMANTIC` + `AUTOMATIC`: a `false`-provenance candidate **is** auto-promotable there (the positive control, proving the configuration really does permit automatic promotion) while a `true`- or `unknown`-provenance candidate is not.

**Witness discipline, following U-MEM-26's layer-independence precedent.** A five-cell write-side matrix — `true`, `false`, and `unknown` reached independently through each of its three inputs (`provider=None`, an unregistered key, a `null` composed family), because each arrives via a different authority and a fix to one can silently break another. A registered-key canonicalization witness, guarding the key-vs-value defect `_family_escapes_source` already documents. A hash-inertness witness asserting `content_hash` **and** `memory_id` are unmoved and the store's own consistency check still passes. An `EPISODIC_RUN` multi-writer witness asserting the stored envelope describes the **stored version** (run-close), not the run's writer history. Read-side witnesses kept **separate per entry point**, since one aggregate test passes over whichever point is still ungated. An **eligibility-preserved** witness proving an approved cross-family-captured candidate still reaches `ACTIVE` — the anti-reading-C assertion, which fails if the unit implements refusal instead of a gate. A **flag-independence** witness in both directions, so `cross_family_capture` and the pre-existing `cross_scope` cannot be collapsed. **Two direct-construction witnesses** (Codex round 2), deliberately separate because the model-level one passes over the copy route: a hand-built flagged-plus-auto-promotable candidate is refused at construction, and one reached via `model_copy(update=...)` is refused by `approve` / `edit_and_approve` with neither store written. **Reserved-flag witnesses in both arms** — a spoof arm (a hint carrying the flag against a `false` source yields neither flag nor gate) and a suppression arm (a hint omitting it against a `true` / `unknown` source yields both); an implementation that only strips, or only adds, satisfies exactly one. A legacy-record witness in **two arms** — a read arm, and a redaction/tombstone **transition** arm asserting the transition succeeds and the transitioned record still reads `unknown` (the arm a pure read cannot cover, added at Codex round 1 [P2]). A **durable-carrier** witness that reads the `PROPOSED` record back from the store, with a ledger-unchanged control confirming C-MEM-08 was not amended. And **two mutation probes**: with the gate reverted, the `unknown`-arm witnesses must FAIL; with the content-side flag write removed, the durable-carrier witness must FAIL while every in-memory witness still passes. The second probe's asymmetry is the point — it is the exact shape of the [P1] defect out-of-family review caught in this unit's first draft, and only a probe distinguishes a real carrier from a claim of one.

**Dependency and axis rationale, including two deliberate omissions.** U-MEM-26 is the load-bearing edge: it landed the composed-scope writer repair the derivation compares the dispatch `provider` **against**, so without it the record's `provider_family` is a per-turn raw key and the predicate is meaningless. **U-MEM-25 is deliberately NOT declared** — unlike at U-MEM-26 — because it is reached transitively through U-MEM-26, which declares it, so the ordering behind the closeout packet this unit also refreshes is already satisfied; the omission is stated in the plan so it reads as a decision. Information substrate is claimed because the field is added to `harness-is`'s `MemoryRecordEnvelope`, and axis-scoped execution must not skip IS isolation tests — the same reasoning round 14 applied to U-MEM-26. **Control plane is deliberately not claimed** (the gate is unconditional on policy and adds no C-MEM-09 decision value), and **action surface is deliberately not claimed** (no telemetry member, no new tool). R-MEM-12 is likewise deliberately **not** extended in the §4.1 coverage map: the field is provenance, not partition, and the unit adds no scope-enforcement obligation.

Back-reference reconciliation inside the plan: §3 axis placement (information substrate, operational discipline, runtime rows), §4 dependency edges (six new), §4.1 coverage map (R-MEM-01 range plus R-MEM-05 and R-MEM-09 membership), §7 grouping (new G7 review boundary, ordered after G6), and §9 completion range. Every U-MEM-01..26 unit body, §1, §2, §6, §8, and the whole v1 → v1.1 change-note are preserved verbatim; the seven pre-existing lines touched are all range or membership extensions.
