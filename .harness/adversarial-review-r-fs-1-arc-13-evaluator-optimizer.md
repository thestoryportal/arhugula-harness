## Findings + dispositions

**Codex [P2] — `step_context.step_index` drift (REAL BUG → FIXED).** The first cut set `StepExecutionContext.step_index = entry_index` (the monotonic ledger row, 2,3,…). But downstream dispatchers read that field as the **declared** step ordinal (0=generate, 1=evaluate) for per-step policy / override selection + audit context — so after iteration 1 a policy keyed to the declared step stops matching. **Fix:** two distinct indices kept apart — `step_index` = declared ordinal (0/1); the unique monotonic `entry_index` stays on the ledger `action_id` + idempotency key only. Regression test `test_evaluator_optimizer_step_context_carries_declared_ordinal_not_ledger_row` asserts `seen_step_indices == [0,1,0,1,0,1]` while the ledger action_ids are `…:step:0..5`. **`parent_action_id`/`parent_idempotency_key` divergence-safety grep:** the only `parent_action_id` consumers are the `compose_branch_*` fan-out helpers (never invoked by sequential EO) + `sibling_ledger_entry_composition` (takes `parent_action_id` and `step_index` as *independent* sha256 inputs, no consistency assumption, also not in the EO path); no code parses a step ordinal out of `parent_action_id` to compare with `step_index` → Option A (parent_action_id on `entry_index`, step_index on declared) is safe.

**Codex [P1] — the evaluator can't see the generate draft (SCOPE — NON-BLOCKING; data channel tracked forward).** Codex flagged that the evaluate dispatch gets only the static `evaluate_step` + `StepExecutionContext`, never `last_generate_output`, so a real evaluator can't judge the draft → "non-functional." **Decorrelated disagreement** (Codex vs advisor + adversarial agent, who called it an honest scope boundary). **Tie-break (empirical + contract):**
- **Empirical:** the harness has **no driver-level inter-step data flow for ANY topology** — the `SINGLE_THREADED_LINEAR` path builds `accumulated` but **never threads it into `dispatch(...)`**, and the `dispatch(binding, step, step_context)` signature carries no prior-output parameter across any runtime dispatcher. Threading the draft would require a `StepDispatcher` Protocol change or a `StepExecutionContext` schema extension — an **X-AL-3 silent design extension** forbidden at Phase-7, AND inconsistent with the linear path.
- **Contract:** the plan defines "non-hollow" explicitly as *the per-step-prompt distinction* ("distinguished by per-step prompt — non-hollow without B4"), NOT "the evaluator receives the draft." U-CP-87 implements + tests exactly that bar (distinct-step dispatch). The **cleared U-CP-86 precedent** already shipped the first non-linear topology with zero inter-step data threading through P5-CK — so threading-the-output is not a bar this contract family sets; a fork against U-CP-87 would equally indict merged-and-cleared U-CP-86.
- **Disposition:** **non-blocking; control-flow-scoped per the plan's explicit non-hollow definition.** BUT per the FULL-SPEC directive (`[[feedback-full-spec-beyond-mvp-nothing-deferred]]`), "deferred to runtime" must have a **tracked owner** — and B4 is scoped as per-role *selection* (`AgentRole` + per-step override threading), which does **not** cover the generate-*output* → evaluate-*input* data channel. So a one-line forward item is filed at `.harness/beyond-mvp-capability-boundary-ledger.md` (the inter-step DATA-flow channel is a cross-topology runtime/dispatcher capability, currently untracked → forward arc). This converts a silent "runtime's job" defer into an honestly-tracked one.
