# Graft integration — known limits and the decisions taken

Registered 2026-08-16 alongside PR #1388. These are behaviours of **upstream
`@nanonets/graft` 0.10.1**, not of anything this repo authored. They are recorded here
rather than patched, because every file graft generates (`.claude/helpers/*.cjs`,
`.claude/skills/graft/SKILL.md`, the `.gitignore` entry, the marker-fenced `AGENTS.md`
block) is rewritten by the next `graft init` / `graft build`, so a local patch would be
silently reverted and then silently drift.

Do not "fix" any of these by editing a generated file. Fix them upstream, or re-decide
here.

---

## 1. `timeout` is read by two consumers, in two different units — DECIDED

`.claude/settings.json` hook entries carry one `timeout` field. Two things read it:

| Reader | Interprets it as | Consequence |
|---|---|---|
| Claude Code | **seconds** — the hook kill deadline | `15000` = 4.2 hours before a hung hook is killed |
| graft `promptAskTimeout()` (`dist/claude/hooks.js:59`) | **milliseconds** — its own child budget | `max(4000, installed − 2000)` |

Graft ships `15000` and its source comment states the assumption outright: *"every repo
wired before that change keeps `"timeout": 8000` … Reading the installed number keeps the
child strictly inside whatever budget this repo really has."* That reasoning is only sound
if the field were milliseconds. It is not — this repo's own long-standing hooks use
`12 / 20 / 45`, which are plainly seconds.

**Decision: the field is seconds. Graft is wrong, and we keep `8 / 10 / 15`.**

The cost is real and is accepted: `promptAskTimeout()` now computes
`max(4000, 15 − 2000)` → the **4000 ms floor** instead of graft's intended 13000 ms. A
cold `graft ask` that takes longer than ~4 s is discarded and that turn gets no retrieval
pack.

Why that trade: the `UserPromptSubmit` context pack is a convenience whose worst failure
is a missing suggestion, and it already misfires on weak name matches. The alternative
failure is a hung hook wedging an interactive session for over four hours. A degraded
convenience beats a wedged session, and CI never runs these hooks at all.

There is no env override for the child budget — `dist/claude/hooks.js` exposes only
`GRAFT_TEST_*` seams. Recovering the 13 s budget requires an upstream change that reads
the field as seconds (or a separate ms-valued field).

## 2. `graft` must be on `PATH`, and nothing here guarantees it

`.mcp.json` (and the Gemini / Kiro / OpenCode equivalents) declare a bare
`command: "graft"`. Verified: under a clean environment
(`env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin`) `graft` does not resolve — on this machine
it lives only at `~/.local/share/mise/installs/node/24/bin/graft`.

So on any host without that mise shim on `PATH`, the graft MCP server fails to start and
every `graft …` instruction in the skills is unrunnable.

**Not bootstrapped deliberately.** A wrapper or a vendored dependency would be a real
piece of installation machinery, and this integration is meant to stay additive. Treat
graft as a **local operator prerequisite**, the same way `codex` and `agy` already are:
`npm i -g @nanonets/graft`, then `graft --version` to confirm.

Nothing in CI depends on it — `.mcp.json` is not read there, and
`tools/graft_reachability.py`'s tests are fixture-based. The tool itself fails loud
(exit 2) when the graph is absent, rather than reporting an empty result.

## 3. The hook helper swallows its own load failures

`.claude/helpers/graft-hooks.cjs` catches a failure to load `@nanonets/graft` and exits
**0 with no stdout and no stderr**. If the package is absent, moved, or throws at startup,
every graft lifecycle hook silently does nothing and the session looks identical to one
where graft simply had nothing to say.

This is the `[[gate-cannot-tell-empty-from-unlooked]]` shape in vendored code: "could not
run" is indistinguishable from "ran, found nothing". It is upstream's file and is
regenerated by `graft init`, so it is registered, not patched.

Practical guard: if graft context stops appearing, do not assume the graph is empty — run
`graft check` directly and read its exit status.
