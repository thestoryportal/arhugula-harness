# Architectural Tensions in Multi-Tenant Deployment Units

Here is the missing T3 tension, formatted to composite cleanly into the architectural tensions synthesis from our previous discussion:

**Per-Task vs Per-Company Deployment Unit (Catalog T3)**

- **The Tension:** What is the fundamental unit of deployment and isolation? This axis measures whether the architecture scales by horizontally replicating ephemeral, stateless task sessions (optimizing for massive concurrent throughput), or whether it instantiates an enduring organizational structure—spanning companies, roles, strict data boundaries, and multi-tenant budgets—as the core deployment primitive.
- **How Sources Address It:** The vast majority of the cataloged harnesses—including **DeerFlow, kilocode, deepagents, OpenHands, Cline, and OpenHarness**—anchor firmly at the per-task/session pole, treating the deployment unit as a transient job. **Optio** moves slightly along the spectrum by expanding the boundary to the repository, deploying one long-lived Kubernetes pod per repo. **Paperclip** sits at the absolute opposite pole: it defines the deployment unit as the "company" itself, managing organizational goals and multi-tenant isolation rather than individual pull requests.
- **Displacement vs. Honest Absorption:**
  - *Displacing the tension* occurs when developers adopt a per-task framework (like LangGraph or a standard single-process harness) but attempt to bolt on enterprise multi-tenancy later by merely tagging database rows with user IDs. This displaces the immense complexity of inter-tenant data leaks, cross-session financial budget enforcement, and runaway compute isolation back onto the application developer.
  - *Honest absorption* is demonstrated by **paperclip**, which accepts the heavy architectural overhead of true multi-tenancy—such as requiring an embedded Postgres database per deployment, enforcing strict per-agent financial hard-stops, and treating governance with rollback as a core mechanism—to guarantee complete data isolation between companies. Conversely, **kilocode** honestly absorbs the limitations of its per-task pole by relying on concurrent git worktrees for session isolation, accepting that this provides fast local orchestration but cannot satisfy true enterprise multi-tenancy.
- **Phase 2 Persona-Surfacing Resolution:** This tension cannot be resolved by technical preference; it is strictly gated by the target user persona (Cluster 5 V2 specifically marks "multi-tenant identity" as a Derivative Decision deferred to persona definition). If Phase 2 surfaces a solo developer or a single internal team, the systems architect can safely commit to the lightweight per-task pole. However, if the persona is an enterprise SaaS provider or an agency serving multiple clients, the architecture must resolve to the per-company pole, because simple horizontal task replication cannot satisfy the strict data isolation, RBAC, and budget gating that enterprise deployments demand.
