## NEW §21.2.2 (C-OD-21) — backend-aware signature verification API

*Appended under §21.2, sibling of §21.2.1. Closes v1.33's explicit verification out-of-scope: with real KMS signatures durably persisted (`B-47` sidecar), there was no spec-committed way to VERIFY them — `verify_hash_chain_integrity` (:320) and the B-49 per-family verifier (`harness-od/src/harness_od/per_family_audit_verification.py`) check content + linkage only and never touch `signature_attrs`, and the CP-side `verify_audit_entry_signature` (`f5_signing_key_resolution.py:381`) has zero production callers. | # | Property | Contract |
|---|---|---|
| 1 | **Verification surface + resolver parameter** | The OD verification API (extending the B-49 per-family verifier surface over `Sequence[AuditLedgerEntry]`) gains an OPTIONAL verification-backend RESOLVER parameter — a per-row backend resolution keyed on each entry's STORED `(audit_signature_algorithm, audit_signature_key_id)` — NOT a single `SigningBackend | None` parameter: one backend exposes one `.algorithm` and cannot verify mixed multi-algorithm history (a ledger legitimately holds rows under multiple permitted algorithms after an operator algorithm change). Absent resolver → current behavior (hash-chain + content integrity only) PRESERVED VERBATIM — subject to row 8's MTC disposition. Present → per-entry backend verify over the reconstructed canonical message, with `"DEPLOYMENT_BOUND"` projected to `key_period=0` exactly as signing does. |

Era membership is NEVER inferred from the signature value or any mutable row field. |
| 4 | **Authenticated tenant-bound cutover-gated legacy exemption** | Legacy exemption (pre-backend `unsigned:*`-era rows and pre-v1.34 four-tuple-era rows) is gated EXCLUSIVELY on an operator-recorded cutover record that is: (a) **AUTHENTICATED** — signed by a trusted key or anchored outside the rewritable ledger (a plain sidecar row is mutable at exactly the adversarial tier under discussion); (b) **CONTENT-BOUND** — it binds the exact legacy entry hashes (or a digest/root over them), never a date/version/row-position (a monotonic-position boundary authenticates a boundary, not the contents before it — the adversary rewrites an exempt pre-boundary row in place); (c) **TENANT-BOUND with a per-row DISPOSITION** — the record binds signed `(tenant_scope, entry_hash, verification_disposition)` TRIPLES: `tenant_tag` is mutable and absent from `entry_hash`, so a bare entry-hash record would still let an authenticated legacy row be moved between tenants, and a bare pair cannot tell the verifier which mode a listed row takes (placeholder-exempt vs four-tuple-real) without inspecting `signature_attrs` — which reintroduces the forbidden downgrade. authoring timestamp; the signing `(algorithm, key_id)`), with `verification_disposition` an ENUM of exactly `{placeholder_exempt, four_tuple_real, quarantined}` and carrier validation keyed on the EXPLICIT SOURCE identity (codex rounds 11/15/16): each row carries a `source_tag` (default `"_single"` for migration rows;
