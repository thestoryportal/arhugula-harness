# Spec: Control Plane — v1.98 (delta over v1.97)

*Delta-only file. The v1.97 body + the entire C-CP-01 … C-CP-29 contract body are PRESERVED VERBATIM (delta-only-spec-file convention). This delta records the `B-22` standalone arc: an additive, optional composition-root injection seam for §20.2 signing-key resolution, so `sign_audit_entry` / `verify_audit_entry_signature` can consume a real deployment-bound signing backend once one is wired, instead of having no possible call shape to ever accept one.*

## Change-note (v1.97 → v1.98)

**Scope of revision.** One additive, optional `SigningBackend` composition-root-injection seam at §20.2 — no new carrier, no new persona-tier behavior, no change to the signing-key residence table (§20.2's per-persona-tier residence rows, the F5 prod-tech-vault deferral, and the `ed25519`/`ecdsa-p256`/`rsa-pss-2048` algorithm enum are all PRESERVED VERBATIM):

- **`SigningBackend` Protocol (NEW §20.2.1)** — a minimal two-method composition-root-injected surface: `sign(message: bytes, key_id: str, key_period: int) -> bytes` and `verify(message: bytes, signature: bytes, key_id: str, key_period: int) -> bool`, plus an `algorithm` attribute naming which of the three §20.2 algorithms the backend implements. `key_period` is threaded to both methods, not merely embedded in `message` — a single stable `key_id` per §20.2's residence scheme cannot by itself distinguish a key across a rotation boundary (out-of-family Codex round-4 P1 finding), so the Protocol carries the parameter a rotation-aware backend needs to select the historical key valid at that period. The protocol carries no key-custody logic itself, and this delta does NOT itself implement rotation-boundary key selection or verification (that composition is `B-33`'s scope, gated on both this seam and the concrete backend) — it is the seam a deployment-time composition root (per the same "live signing backend ... wired at a deployment-time composition root" shape ADR-D5 v1.3 §1.4 already establishes for the OD-local sibling `sign_audit_entry`) implements once a concrete prod-tech backend (HSM / KMS / vault) exists.
- **`sign_audit_entry` / `verify_audit_entry_signature` gain an OPTIONAL `backend: SigningBackend | None = None` keyword parameter.** Absent (the default) — **the existing `AuditSigningBackendUnavailableError` fail-loud raise is PRESERVED VERBATIM, byte-for-byte, including for the zero production callers that exist today** (confirmed by repo-wide grep at both this delta's authoring and at the prior `B-22` register entry). Present — `sign_audit_entry` computes `audit_signature_sha256 = SHA-256(entry.model_dump_json())` per the same canonical-payload-hash convention ADR-D5 v1.3 §1.4.1's v1.4 tightening already establishes for the OD-local sibling, calls `backend.sign(message, key.key_id, key_period)` for the signature bytes, and returns a real `CPSignedAuditLedgerEntry`; `verify_audit_entry_signature` recomputes the hash, rejects on hash mismatch (`SIGNATURE_MISMATCH` — the tamper-evident content-integrity check), and otherwise calls `backend.verify(...)` for a genuine single-entry cryptographic verdict against the key/period the entry itself claims. **Scope-narrowed claim (round-4 reconciliation):** this delta closes generic single-entry sign/verify against whatever key a caller-resolved `SigningKeyHandle` names, at whichever `key_period` the caller supplies — it does NOT itself implement §20.3.1's two-row rotation-PAIR verification protocol (walking a ledger, locating a sibling pair, verifying each under its own period's key); that composition remains `B-33`'s scope, which this seam is a prerequisite for, not a substitute for.

**This is the `B-22` standalone arc** (registered at `.harness/post-phase-8-forward-register.md`, surfaced at the 2026-07-13 F5-real-audit-signature-backend preflight follow-on). It closes exactly the "no possible way to ever wire a backend" half of the gap: before this delta, `sign_audit_entry` / `verify_audit_entry_signature` had no call shape capable of accepting real key material at all — every future arc wiring a concrete backend would have had to first author this same seam from scratch. It does NOT close the other half — the concrete prod-tech backend (which vault/KMS a `multi-tenant-compliance` deployment actually uses) remains genuinely deferred; see Status below.

**Why this is additive, not a security-posture change.** The 2026-07-13 operator-ratified disposition ("fail loud instead of fabricating `VERIFIED`") is preserved exactly for the only case that exists today — no backend. The seam only ever activates when a caller supplies a real, typed backend; there is no path by which this delta causes an existing or future absent-backend caller to receive anything other than the identical raise it receives today. The seam is what makes it POSSIBLE for a future arc to satisfy §20.3.1's requirement for genuine verification — it does not itself claim that requirement is satisfied for `multi-tenant-compliance` deployments today.

**Deferred — NOT resolved by this delta (Council: ⚖️ conditional per the `B-22` register entry, C10 blast-radius ⊥ C11 operator-loop/local-deployment).** The concrete prod-tech secrets/signing backend a `multi-tenant-compliance` composition root would inject through this seam — HSM / AWS Secrets Manager / HashiCorp Vault / Azure Key Vault / GCP Secret Manager / Doppler / 1Password Connect — is explicitly deferred per ADR-F5 §Deferred D-ADRs ("D-ADR on bootstrap-token issuance protocol per prod-tech") and per ADR-D5 v1.3 §1.4's own signing-key-residence table (row 3: "F5 prod-tech (deferred to D-ADR ...)"). This delta neither picks a backend nor provisions credentials; it is a mechanical, reversible, zero-regression seam only. A concrete backend selection remains a genuine operator + design-phase (D-ADR) + credential-provisioning decision, out of Phase-7-execution scope per X-AL-3.

**Note on the already-landed `harness_runtime` provider-secrets precedent.** `harness_runtime.config.provider_secrets` already implements an analogous two-backend composition (`KeyringSecretResolver` for `LOCAL_KEYRING_ENV_FALLBACK`; `GcpSecretManagerResolver` for `GCP_SECRET_MANAGER`, R-421) for LLM-provider API keys — a real, working precedent for what a future `SigningBackend` composition-root implementation could look like (fetch raw key-material bytes via `GcpSecretManagerResolver`-style access, then sign locally via a library such as `cryptography`'s Ed25519 primitives). This delta does not wire that precedent to audit-signing — CP must not import `harness_runtime` (axis-layering: `harness_runtime` composes CP, not the reverse) — it is cited here only as forward-work orientation for whoever authors the eventual composition-root arc.

**v1.97 + prior body PRESERVED VERBATIM.** All v1.97 content — the entire C-CP-01 … C-CP-29 body incl. §20.x / §25.x / §26.x — is PRESERVED VERBATIM per the delta-only-spec-file convention; the **only** change is the additive `SigningBackend` protocol + the optional `backend` parameter on the two §20.2 functions.

## §1 — NEW §20.2.1 composition-root injection seam (additive)

> **`SigningBackend` (NEW §20.2.1).** A minimal Protocol, implemented by a deployment-time composition root once a concrete prod-tech signing backend exists:
>
> ```
> class SigningBackend(Protocol):
>     algorithm: str  # ∈ {ed25519, ecdsa-p256, rsa-pss-2048} per §20.2
>     def sign(self, *, message: bytes, key_id: str, key_period: int) -> bytes: ...
>     def verify(self, *, message: bytes, signature: bytes, key_id: str, key_period: int) -> bool: ...
> ```
>
> `sign_audit_entry(entry, key, *, key_period, backend: SigningBackend | None = None)` and `verify_audit_entry_signature(signed, key, *, backend: SigningBackend | None = None)` consume it. `backend=None` (default) preserves the existing `AuditSigningBackendUnavailableError` raise verbatim. `backend=<real backend>` performs genuine single-entry SHA-256-then-sign / recompute-then-verify, over a message that **binds the hash to its own `key_id` / `algorithm` / `key_period` metadata** (out-of-family Codex round-1 P1 finding — without this binding, a valid signature could be relabeled onto different metadata post-signing and still verify), with `key_period` ALSO threaded to `backend.sign`/`backend.verify` directly (round-4 P1 finding — a rotation-aware backend cannot select the historical key valid at a period from `key_id` alone, since §20.2's residence scheme keeps `key_id` stable across rotation). `sign_audit_entry` also validates `backend.algorithm` against the closed 3-value enum, `key_period` non-negative, and `key_period` a plain `int` (not `bool`/`float`, which sign a different textual message than what the entry's Pydantic `int` field coerces to) before signing (round-1 + round-3 P2 findings); `verify_audit_entry_signature` repeats the algorithm/period-contract checks against the STORED entry before ever consulting the backend (round-3 P2 finding — an externally-constructed entry may not have passed through `sign_audit_entry`'s validation at all). No new persona-tier behavior, no new CP-importable exception type beyond the pre-existing `AuditSigningBackendUnavailableError`, no change to the §20.2 residence table or the §20.2 algorithm enum. **This is single-entry sign/verify only — it does not implement §20.3.1's two-row rotation-PAIR verification protocol; see `B-33`.**
>
> **Out-of-family Codex review, 4 rounds, 11 findings total (8 fixed, 1 empirically confirmed a no-op, 2 registered as `B-34`).** Round 1: [P1] the verifier accepted a signature after `audit_signature_key_id` / `audit_signature_algorithm` / `audit_signature_key_period` were relabeled on an already-signed entry (the signed message covered only the content hash, not its own metadata) — fixed by binding all four values into the signed message via a length-prefixed canonical encoding (mirrors the B-23 `compose_cost_f2_entry_core` segment-injectivity fix), so tampering with any of the three metadata fields now breaks verification cryptographically. [P2] `sign_audit_entry` accepted any `backend.algorithm` string, including values outside the §20.2 closed enum (e.g. a typo'd `"edd25519"`) — fixed with an explicit enum-membership check before signing. [P2] `sign_audit_entry` accepted a negative `key_period`, violating the §20.3.1 non-negative-monotonic contract — fixed with an explicit non-negative check before signing. Round 2: [P1] `verify_audit_entry_signature` still returned `VERIFIED` when the caller's `key.key_id` (used for backend-side key selection) disagreed with the entry's stored `audit_signature_key_id`, or when `backend.algorithm` disagreed with the entry's stored `audit_signature_algorithm` — a backend that ignores its `key_id` selector (or is bound to a different algorithm) could otherwise attest a verdict for the wrong key/algorithm; fixed with explicit equality checks before ever calling `backend`. [P2] the round-1 `key_period` non-negative check ran BEFORE the backend-presence check, so a caller with `backend=None` and a negative `key_period` received `ValueError` instead of the documented `AuditSigningBackendUnavailableError` — a real regression against this delta's own additivity claim; fixed by reordering the check to run only once a backend is confirmed present. Round 3: [P2] `key_period=True` or `key_period=1.0` (both pass Python's `int` type hint by subtyping/duck-typing, though neither is a plain `int`) signed a different textual message (`"True"` / `"1.0"`) than the value `CPSignedAuditLedgerEntry`'s Pydantic `int` field coerces to (`1`), producing a self-inconsistent entry that immediately failed its own verifier — fixed with an exact `type(key_period) is not int` check before signing. [P2] the read path (`verify_audit_entry_signature`) never validated a `signed` entry's OWN stored `audit_signature_algorithm` / `audit_signature_key_period` against the §20.2 contract before consulting the backend — an entry constructed outside `sign_audit_entry` (e.g. read from persisted storage) with out-of-contract metadata could still verify if a rogue backend happened to agree with that same invalid value; fixed by repeating the write path's two checks at the read path. Round 4 (finding-count trend 3→2→2→4 — the convergence signal `advisor()` flagged, drifting from seam-contract into concrete-signature-representation territory): [P1] `SigningBackend.sign`/`verify` took only `key_id`, making a rotation-aware backend structurally unexpressible against §20.3.1's "key valid at ... key_period" rule — fixed by widening both methods to also take `key_period`, proven with a `_RotationAwareBackend` test double keying off period (a signature relabeled onto a different period now fails, proving genuine per-period key selection). One candidate finding (Pydantic `model_validate` coercing `key_period=True`/`1.0` to canonical `int(1)`, allegedly defeating the round-3 strict-typing check) was empirically probed rather than reasoned about — confirmed a no-op: the coercion produces a value byte-identical to the honestly-signed record (no distinct forgery), and a genuinely type-distinct relabel via `model_copy` is already caught by the round-1 message-binding fix. Two remaining round-4 findings (ECDSA-P256 DER-vs-64-byte signature encoding; `CPSignedAuditLedgerEntry.audit_signature_value` not JSON-serializable for real signature bytes) are concrete-backend-representation concerns — exactly what §20.4 defers to "implementation discretion / the concrete backend" — registered as `B-34` at `.harness/post-phase-8-forward-register.md` rather than fixed inline (no real backend exists yet to hold to a wire format; the second finding is also pre-existing on the shared `CPSignedAuditLedgerEntry` type, out of this seam's blast radius). All landed fixes mutation-probed individually (each guard/binding/ordering change reverted in isolation, confirmed exactly the corresponding test(s) fail, then restored). Convergence criterion applied: "all open findings are in the deferred-representation bucket" — not "Codex returns empty" — so round 4 is the last round; a round 5 would only re-state `B-34`'s already-registered representation-layer residue.

The existing §20.2 signing-key residence table, §20.3 / §20.3.1 rotation + verification semantics, and §20.4 seven-attribute declaration are PRESERVED VERBATIM — this seam is purely a call-surface addition at the two functions that already existed to consume the residence + verification contract.

## §2 — Status

One additive `SigningBackend` Protocol + one optional `backend` keyword parameter on `sign_audit_entry` / `verify_audit_entry_signature`, absorbing the `B-22` standalone arc's first close-out step (registered at `.harness/post-phase-8-forward-register.md`) — a real, single-entry key-material-resolution seam into `harness-cp`, rotation-period-aware at the Protocol level, so a future composition root has a call shape to wire a real signing backend into. **The concrete prod-tech backend remains genuinely deferred** (ADR-F5 §Deferred D-ADRs; ADR-D5 v1.3 §1.4 row 3) — this delta does not select one, does not provision credentials, and does not claim `multi-tenant-compliance` deployment-readiness for audit-signature tamper-evidence. **Two concrete-representation gaps** (ECDSA-P256 DER-vs-64-byte signature encoding; `CPSignedAuditLedgerEntry.audit_signature_value` not JSON-serializable) are registered forward at `B-34`, not fixed here — they are properties of a concrete backend/the shared audit-entry type, not of this seam. **§20.3.1's two-row rotation-PAIR verification protocol is NOT implemented by this delta** — see `B-33` for that residual, which this seam is a prerequisite for.

**No operator gate on this delta itself** (additive, opt-in, zero regression for the zero existing callers — operator already selected this scope via the `B-22` seam-now-vs-hold-fully AskUserQuestion). The concrete backend selection remains its own, separate, genuinely operator + D-ADR + credential-gated decision, out of scope for this delta.
