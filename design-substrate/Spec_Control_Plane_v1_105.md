## Change-note (v1.104 → v1.105)

**The CP rider of the ratified B-33 arc's spec leg** (fork §2 item 4 + §3 sequencing — a genuinely 3-axis amendment, CP + OD + Runtime, not CP-only as the fork's top-level framing might suggest at a glance; the OD-side per-correlation-id accessor is load-bearing and lives at the same-arc `Spec_Operational_Discipline_v1_35.md` §24.8). Division of authority: where this file names the evidence LOOKUP semantics (crypto/consecutive-period/hash-chain checks over a specific correlation id), OD v1.35 §24.8 is the definition site and this file only cross-references; where this file declares the CP-OWNED injection Protocol, typed evidence DTO, and the boundary-attestation comparator, THIS file is the definition site.

**Grounding (verified at filing time, 2026-07-23).** `verify_rotation_6_steps` (`harness_cp/five_axis_composition.py:330`) currently runs six named steps (`RotationVerificationStep`: `STAGE_NEW_KEY` / `WRITE_DUAL_VERIFY_ENTRY` / `PROBE_VERIFY_AT_READ` / `VERIFY_HASH_CHAIN_LINK` / `ROTATE_SIGNING_TO_NEW` / `RETIRE_OLD_KEY`); only `VERIFY_HASH_CHAIN_LINK` performs real work (the generic IS `harness_is.chain_verification.verify_chain` check against caller-supplied `audit_ledger_entries`) — the other five, including `WRITE_DUAL_VERIFY_ENTRY` and `PROBE_VERIFY_AT_READ`, are hardcoded `succeeded=True` SIMULATED narration ("[simulated narration — no real signing backend wired from CP yet]"). The function's own docstring already registers the gap this delta closes: *"Even a genuinely intact non-empty chain does NOT confirm that a rotation boundary ... is present among the supplied entries — registered as `B-33`"*. §20.3.1 row 7 (`Spec_Control_Plane_v1_101.md` §3) currently reads: *"Steps 3-6 ... are PRESERVED VERBATIM; their backend-aware IMPLEMENTATION remains `B-33`'s scope per v1.98's own scope-narrowed claim."* This delta is that implementation, at the spec layer.

**The extension (three of the six steps gain real behavior; three are unaffected).**

1. `WRITE_DUAL_VERIFY_ENTRY` gains a REAL presence/uniqueness check over `audit_ledger_entries`, when a `rotation_correlation_id` is supplied: it consumes the ALREADY-LANDED `harness_is.rotation_window_verification.verify_rotation_window` (IS spec v1.12 §7.7, U-IS-20) — non-emptiness → presence (every entry in the window carries a non-`None` `rotation_correlation_id`) → uniqueness (exactly one distinct value spans the window) — replacing the step's simulated "first new-key-signed entry written" narration with a real IS-side structural check when the caller opts in.
2. `PROBE_VERIFY_AT_READ` gains a REAL OD-anchored evidence check: it consults the injected `RotationPairEvidenceProvider` (NEW below) for the supplied `rotation_correlation_id`, replacing the step's simulated "both keys verify the new entry successfully" narration with the actual OD-side dual-signature/consecutive-period/hash-chain-continuity proof this step's narration always CLAIMED but never checked.
3. `VERIFY_HASH_CHAIN_LINK` is UNCHANGED (already real, IS-side generic chain-link check — untouched by this delta).
4. `STAGE_NEW_KEY`, `ROTATE_SIGNING_TO_NEW`, `RETIRE_OLD_KEY` are UNCHANGED (still simulated — the real-signing-backend gap these narrate is `B-22`'s deployment-surface scope, unrelated to the OD-join gap this delta closes; `ROTATE_SIGNING_TO_NEW`/`RETIRE_OLD_KEY` remain gated on the SEQUENTIAL-halt discipline, now extended to gate on ALL THREE of {hash-chain-link, presence/uniqueness, OD-anchored evidence} succeeding, not just the hash-chain-link check alone).

**Byte-compatibility posture (deliberately NOT preserved — justified).** `evidence_provider` and `key_identity_resolver` are NEW optional keyword-only parameters (both default `None`) — no existing call SIGNATURE breaks. However, the BEHAVIOR when they are supplied is new and, when EITHER is ABSENT, `PROBE_VERIFY_AT_READ` now reports an EXPLICIT INCOMPLETE result rather than the pre-v1.105 simulated `succeeded=True` (§2 row 5 — `key_identity_resolver` absence is NOT a silent skip) — mirroring the §20.2.1/§20.3.1 injected-verifier precedent's own posture ("invoked WITHOUT the backend-aware verification mechanics returns an EXPLICIT INCOMPLETE/UNVERIFIED result — never a passing audit," `Spec_Control_Plane_v1_101.md` §3 row 1b). This is deliberately NOT a byte-compatible no-op for absent-parameter callers, because `verify_rotation_6_steps` has ZERO production callers today (confirmed at the function's own docstring: "no real signing backend wired from CP yet"; `f5_signing_key_resolution.sign_audit_entry`/`verify_audit_entry_signature` raise `AuditSigningBackendUnavailableError` pending B-22) — there is no existing caller whose behavior this silently changes, and preserving the simulated `succeeded=True` narration by default would perpetuate exactly the vacuous-pass gap the arc exists to close.

**Downstream absorption owed (same arc; flagged per spec-writer discipline, NOT edited here).** The CP plan delta (`Implementation_Plan_Control_Plane_v2_41.md`, U-CP-44 + U-CP-45 amendment) + the OD plan delta (`Implementation_Plan_Operational_Discipline_v2_30.md`, NEW U-OD-56) + the Runtime plan delta (`Implementation_Plan_Harness_Runtime_v2_53.md`, NEW U-RT-147) — all enumerated at the same-arc riders' change-notes, not repeated here.

## §2 — NEW §20.3.2 (C-CP-20) — `RotationPairEvidenceProvider` injection seam + physical-key-distinctness boundary attestation

*NEW subsection under C-CP-20, sibling to §20.2.1's `SigningBackend` Protocol (`Spec_Control_Plane_v1_98.md`) and to the §20.3.1 `AuditWalkVerifier` mediation (`Spec_Control_Plane_v1_101.md` §3 row 1). Declares the CP-owned Protocol/DTO/exception surface §1 above consumes, plus a physical-key-distinctness comparator.*

**Mediation (mirrors the §20.3.1 `AuditWalkVerifier` precedent — a DIFFERENT injected verifier for a DIFFERENT query shape, not a reuse of the same Protocol).** `harness-cp` MUST NOT import `harness-od` (the OD→CP canonical direction per CXA §2.3.3; `harness-od` already imports `harness-cp` for `SigningBackend`). `verify_rotation_6_steps`'s `evidence_provider` parameter is therefore a CP-OWNED `Protocol`:

```
class RotationPairEvidenceProvider(Protocol):
    def evidence_for(self, correlation_id: str) -> RotationPairEvidence: ...
```

| # | Property | Contract |
|---|---|---|
| 1 | **`RotationPairEvidence` (CP-owned mirror DTO)** | Structurally mirrors OD v1.35 §24.8's `RotationPairEvidence` (same field set: `correlation_id: str`; `pair_present: bool`; `outgoing_key_period: int \| None`; `incoming_key_period: int \| None`; `outgoing_key_id: str \| None`; `incoming_key_id: str \| None`) but is its OWN CP-owned Pydantic type — `harness-cp` never imports the OD type, per the same no-cross-import discipline `WalkVerificationOutcome` already established for the audit walk. |
| 2 | **`RotationPairIntegrityBreach` (CP-owned exception, same name as OD's, distinct type)** | The adapter (Runtime-owned; composition-root wiring per the same-arc Runtime rider) catches OD's `RotationPairIntegrityBreach` (a genuine cryptographic/structural tamper signal — OD v1.35 §24.8 row 5) and RE-RAISES this CP-owned same-named type, message-preserving. A tamper signal is NEVER folded into a `RotationPairEvidence` field — it always raises, mirroring OD's own fail-loud posture for this exact failure class. |
| 3 | **`RotationPairEvidenceUnavailableError` (CP-owned availability discriminator)** | The EXPLICIT availability signal (mirrors `AuditWalkVerifierUnavailableError`'s role at §20.3.1 row 1): the adapter wraps an OD-side ledger-load/lookup infrastructure failure (NOT a tamper signal, NOT pair-absence) in this type. Availability is NEVER a verdict — `PROBE_VERIFY_AT_READ` reports this as a re-runnable infrastructure failure distinct from both "pair absent" (fails the step, but not as tamper) and "pair invalid" (`RotationPairIntegrityBreach`, tamper). ANY OTHER raise from the injected `evidence_provider` (a `TypeError`/`KeyError`/programming error) PROPAGATES UNWRAPPED as a defect. |
| 4 | **Composition-root wiring** | The Runtime-owned adapter (NEW at the same-arc Runtime v1.104 → v1.105 rider §13.6) supplies the concrete `RotationPairEvidenceProvider` over OD v1.35 §24.8's `find_rotation_pair_evidence` — the SAME `harness-runtime` composition-root pattern §20.3.1's `AuditWalkVerifier` adapter already established (a distinct adapter instance for a distinct Protocol; the two injected verifiers are NOT the same object and are wired independently). |
| 5 | **Physical-key-distinctness boundary attestation (NEW comparator, C-CP-20) — REQUIRED, not skippable (out-of-family review [P1] correction)** | A caller-injected `key_identity_resolver` (a minimal CP-owned Protocol: `physical_identity_for(key_id: str) -> str`) is a REQUIRED sibling parameter to `evidence_provider` — `verify_rotation_6_steps`'s `PROBE_VERIFY_AT_READ` step confirms an evidence-confirmed pair's `outgoing_key_id` and `incoming_key_id` resolve to genuinely DIFFERENT physical key material, not merely different string labels aliasing the SAME underlying key (e.g. two `key_id` aliases both resolving to the same KMS key ARN under `AwsKmsSigningBackend.key_arns`, ADR-D8). A same-physical-identity resolution RAISES a NEW `RotationBoundaryPhysicalKeyCollisionError` — DISTINCT from `RotationPairIntegrityBreach` (OD-detected structural tamper): the OD-side pair may be perfectly well-formed (consecutive periods, differing `key_id` LABELS, valid chain continuity) while STILL failing this CP-owned boundary attestation if the deployment's key-identity mapping reveals the "rotation" never actually changed the physical signing key. **`key_identity_resolver` ABSENT is NOT a silent skip** (the original v1.105 draft's "absent → skip" posture was corrected on review: it would let two labels aliasing one physical key pass as a genuine rotation — precisely the false-boundary failure this comparator exists to catch): `PROBE_VERIFY_AT_READ` reports the SAME EXPLICIT INCOMPLETE disposition as an absent `evidence_provider` when `key_identity_resolver` is absent. A deployment whose configured `SigningBackend` exposes no physical-identity mapping (ADR-F5 concrete-backend-selection deferral) therefore cannot reach a `succeeded=True` `PROBE_VERIFY_AT_READ` at all — this is the intended, honest consequence, not a gap to work around. |
