## Change-note (v1.107 → v1.108)

**Trigger.** `B-72`'s empirical rounds (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md`) confirmed a `SUB_AGENT_DISPATCH` branch's own `SUB_AGENT_BOUNDARY` gate can pause the run BEFORE any child run is dispatched — before `child_run_id` exists at all. Per `Spec_Control_Plane_v1_106.md` §1.2 property 5's own test ("it never itself dispatched into a HITL gate" — the container/ancestor exclusion), such a branch IS gate-owning (it DID dispatch into its own gate). But properties 1 and 4 are written entirely in terms of `child_run_id`-keyed identity — a vocabulary that cannot describe a branch with no child run yet. Round 7 confirmed this is not a contrived edge: `compose_child_run_id_seed`'s deterministic pre-dispatch minting path is gated on `subagent_child_recoverable` and does not cover `PURE_PATTERN_NO_ENGINE` — the exact engine class `B-72`'s own reproduction test uses.

**The defect (confirmed by direct grounding, not reasoning).** Two independent instrumentation passes against the real `B-72` round-3 reproduction (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md` §2, reverted after each check — no code change): (1) `compute_hitl_uniform_fallback_eligible_run_id` returns `None` for the reproduction's own captured `PauseSnapshot`, not the sole branch's identity — `PeerFanOutResumeState.branches` and `.paused_child_branches` are both empty; (2) `terminal_dispositions={}` for that branch's ordinal at the `workflow_driver.py:9698` capture site, confirming the branch's pause is never recorded through EITHER existing per-branch carrier. Property 4's Safety clause ("every gate-owning branch paused this cycle whose own `child_run_id` is NOT a key in `hitl_responses`") therefore has nothing to count this branch as — the uniform fallback it should be eligible for (it is the SOLE gate-owning branch this cycle) never applies, and the gate re-fires on every resume indefinitely (confirmed: `resumed.status == "paused"`, `RuntimeSubAgentDispatcher.dispatch` never reached, the delivered answer never consumed).

**Why this needs a new spec property, not a pure impl-to-cleared-spec fix.** Extending what property 4's resolver must count as "gate-owning" is an observable CONTRACT change to a currently-shipped, P5-CK-cleared mechanism — the same class of change properties 1-5 themselves were at v1.106. Per workspace `CLAUDE.md` §4.4 (X-AL-3), silently stretching property 4's existing text to cover a case its own authors did not contemplate (the round-3/4/5 correction history of this exact section shows they were reasoning about ALREADY-DISPATCHED children throughout) would itself be an uncontrolled design extension — see the tension record's §5 tiebreaker check, which confirms this reading directly against the verbatim text before authoring this delta.

**Why property 6 needs neither property 1's key widened nor a separate delivery path.** Property 1's `run_id`-shaped `hitl_responses` key is required ONLY for the case of 2+ DISTINCT concurrently-paused gate-owning branches needing DISTINCT, individually-addressed resolutions. Property 4's Safety clause needs an identity for exactly two INTERNAL purposes — set-membership counting and a SOLE-member comparison — neither of which requires external addressability or a `run_id` shape. A pre-dispatch gate-owning branch can therefore be made countable for property 4's purposes using an implementation-discretion internal identity, WITHOUT ever entering `hitl_responses`, WITHOUT needing `B-71`'s exposure fix, and WITHOUT depending on engine recoverability — closing exactly the SOLE-branch case `B-72`'s round-3 reproduction pins. The harder case — 2+ concurrently-unaddressed gate-owning branches where at least one is pre-dispatch — genuinely has no externally-knowable identity to key by and stays open, explicitly named as such below, forward-dependent on `B-71` (confirmed narrower in round 7: `B-71` only proposes exposing an ALREADY-DISPATCHED child's `run_id`, not minting one for a not-yet-dispatched branch).

## §1 — Pre-dispatch gate-owning branch counting (property 6, closes `B-72` item 1)

**§1.1 The property (CONTRACT — binding on the impl leg; wiring is NOT specified here, mirrors v1.106 §1.3's own discipline). Scoped to the topologies whose branch-pause state is captured via the `PeerFanOutResumeState`/`FanOutResumeState` carrier family (codex out-of-family review [P1] x2, 2026-07-25, caught before merge — see §1.2b).** A gate-owning branch (per `Spec_Control_Plane_v1_106.md` §1.2 property 5's test — it dispatched into its own HITL gate) under one of the three topologies that materialize branch-pause state via `PeerFanOutResumeState`/`FanOutResumeState` (`TopologyPattern.PARALLELIZATION`, `TopologyPattern.ORCHESTRATOR_WORKERS`, and `TopologyPattern.HIERARCHICAL_DELEGATION` — the last of which is a recursive reuse of `_execute_orchestrator_workers` per U-CP-88/89, not a separate implementation, and therefore shares the identical carrier path) that has not yet produced a child run — its own `SUB_AGENT_BOUNDARY` (or equivalent) placement fired and paused the branch BEFORE any child `run_id` was created — is a **pre-dispatch gate-owning branch**. The replacement mechanism's resolver MUST:

- **(a) Count it.** A pre-dispatch gate-owning branch MUST be a member of property 4's Safety-clause "unaddressed gate-owning set" for the current resume cycle (it is, definitionally, always unaddressed — no `child_run_id` exists for `hitl_responses` to key against it).
- **(b) Never key it, but DELIVER when sole (codex out-of-family review [P1], 2026-07-25, caught before merge — counting alone does not close the livelock).** A pre-dispatch gate-owning branch MUST NEVER be resolvable via `hitl_responses`/`hitl_response_for(child_run_id)` — no `child_run_id` exists to key by; inventing a differently-shaped key for this purpose would itself change property 1's normatively-fixed key shape, which this property does NOT do. Property 4's existing Safety-clause text phrases its uniform-fallback mechanism AS a `hitl_response_for(child_run_id)` call — a call this branch structurally cannot make — so satisfying (a) and this prohibition alone would let an implementation correctly count and never-key the branch while STILL never delivering it a resolution, leaving the round-3 reproduction's livelock unclosed. This property therefore additionally, explicitly REQUIRES: when property 4's SOLE-member rule determines this branch is the sole member of the unaddressed gate-owning set this cycle, the resolver MUST deliver the operator-supplied uniform `hitl_response` value to this branch's own gate through SOME delivery mechanism appropriate to a branch with no `child_run_id` (impl discretion on the wiring — e.g. a delivery-cell-equivalent construction mirroring the LINEAR path's `HITLDeliveryCell`, per `Spec_Control_Plane_v1_106.md` §1.3's own discipline of leaving wiring to the impl leg). This delivery is a REQUIRED OUTCOME of this property, not a plan-level implementation suggestion — an impl leg that counts the branch correctly but never constructs any delivery for it does NOT satisfy property 6.
- **(c) Accept the liveness limit.** When the unaddressed gate-owning set has 2+ members and at least one is pre-dispatch, EVERY member (per property 4's existing text, unamended) MUST re-pause INERT — this MAY mean a pre-dispatch gate-owning branch among peers with no available keyed path ever converges via this property alone. This is a STATED, ACCEPTED forward limitation, not a defect this delta claims to close — see §1.2's scope note.
- **(d) Internal identity, impl discretion — but MUST be unique across the WHOLE resume tree, not merely among local siblings.** WHICH internal representation identifies a pre-dispatch gate-owning branch for purposes of (a)'s counting and any subsequent SOLE-member comparison — a branch ordinal, a composition-derived string, or any equivalent — is impl discretion, exactly as properties 1-4 already defer their own resolver mechanism. **Codex out-of-family review [P1] (2026-07-25, caught before merge):** an unqualified "branch ordinal" is NOT sufficient by itself — under nested fan-out (e.g. a `PARALLELIZATION` barrier nested inside a `HIERARCHICAL_DELEGATION` recursion, or two independent fan-out barriers at different tree positions), two DIFFERENT pre-dispatch gate-owning branches at different nesting levels can each locally compute the SAME local ordinal (e.g. both "branch 0" of their own respective barrier). If the chosen identity is only locally unique, property 4's set/SOLE-member comparison can collapse two genuinely distinct branches into one — reporting a SOLE unaddressed member when the true unaddressed set has 2, and delivering the uniform `hitl_response` to BOTH, the exact cross-branch misattribution property 4 exists to prevent (a correctness violation, not merely an edge case). The chosen identity therefore MUST be unique across the ENTIRE resume tree for the current cycle (e.g. an ancestry-qualified path — the local ordinal composed with every ancestor barrier's own position — or any equivalent scheme achieving the same tree-wide distinctness), mirroring how property 1's `run_id`-based keying is already tree-wide-unique by construction. The impl leg's chosen mechanism MUST include a collision witness (a test asserting two pre-dispatch gate-owning branches at different tree positions produce DISTINCT internal identities) before this property can be considered satisfied. The ONLY additional constraint: this internal identity MUST NOT be placed in, or treated as compatible with, `hitl_responses` (which remains exclusively `child_run_id`-keyed per property 1, unamended).

**§1.2 Scope.** This property closes ONLY `B-72`'s net-position item (1) — the round-3 reproduction's SOLE pre-dispatch gate-owning branch case. It does NOT close: `B-72`'s net-position item (2) (keyed multi-peer addressing across 2+ concurrently-unaddressed gate-owning branches where at least one is pre-dispatch — genuinely gated on `B-71`, confirmed narrower in round 7 to cover only already-dispatched children, and possibly a further Runtime-side early-minting extension `B-71` does not currently cover); item (3) (property 4's general resolver set-membership mechanism, already deferred to the impl leg at v1.106); or item (4) (`B-72`'s own original round-1 "hybrid case" — a branch already-gate-owning once, now resume-forwarded toward its self-dispatched deeper-paused descendant — property 5 does not settle it and it stays untested by any reproduction). All three remain open forward work, unchanged by this delta.

**§1.2b Topology scope (codex out-of-family review, 2026-07-25, caught before merge across TWO rounds — round 5 caught the initial topology-agnostic overclaim; round 6 caught that the round-5 fix itself under-scoped, naming only the two topologies the reproduction directly exercises and missing a THIRD topology that shares the identical carrier path).** §1.1's property is bound to the topologies whose gate-owning-branch pause state is captured via the `PeerFanOutResumeState`/`FanOutResumeState` carrier family this delta's §1.3a durable-carrier authorization names — `PARALLELIZATION`, `ORCHESTRATOR_WORKERS`, and `HIERARCHICAL_DELEGATION`. The round-3 reproduction (`harness-runtime/tests/integration/test_b72_fanout_sub_agent_dispatch_hitl_gate_resume.py`) exercises `TopologyPattern.PARALLELIZATION` exclusively, but `HIERARCHICAL_DELEGATION` is included on carrier-identity grounds, not reproduction grounds: direct code read (`workflow_driver.py:13745-13849`, `_execute_hierarchical_delegation`) confirms it is a RECURSIVE REUSE of `_execute_orchestrator_workers` per U-CP-88/89 ("reuses ORCHESTRATOR_WORKERS at each level — NOT a parallel re-implementation") — it takes the identical `crash_fan_out_resume: FanOutResumeState | PeerFanOutResumeState | None` parameter and threads it through the same helper, not a separate code path. Property 6's counting/delivery requirement, once satisfied at `_execute_orchestrator_workers`'s own carrier-construction and delivery-cell sites, therefore applies at every `HIERARCHICAL_DELEGATION` recursion level for free — excluding it from this property's stated scope while its own mechanism already covers it would leave the CONTRACT text inconsistent with the runtime call graph it constrains, exactly the class of defect this delta exists to close, not perpetuate.

A `SUB_AGENT_DISPATCH` step carrying its own `SUB_AGENT_BOUNDARY` placement under `EVALUATOR_OPTIMIZER` or `DECENTRALIZED_HANDOFF` (captured into `EvaluatorOptimizerResumeState`/`HandoffResumeState` instead — a DIFFERENT carrier family, not a recursive reuse of this one) was, AT THE TIME OF THIS DELTA'S ORIGINAL v1.108 AUTHORING, an ungrounded, unreproduced gap explicitly out of this delta's scope — this delta itself did NOT authorize or require any fix there, per this arc's own round-3/4/5/6/7 discipline (verify before claiming closure), since extending property 6 to a topology nothing had empirically grounded — and whose carrier is genuinely distinct, not a reuse — would have been exactly the uncontrolled-breadth error this arc repeatedly caught and corrected in itself.

**CORRECTED at v1.109 (2026-07-26, stale-carry-text fix — see this file's own v1.108 → v1.109 change-note above):** that gap has since BEEN reproduced and closed. The `B-78` impl leg (PR #1117, 2026-07-26) constructed real `EVALUATOR_OPTIMIZER`/`DECENTRALIZED_HANDOFF` workflows exercising this exact scenario, confirmed the defect was worse than the re-fire-livelock hypothesis (a genuine uncaught `HITLPauseRequestedSignal` `BaseException` crashed the run outright), and fixed it by mirroring the LINEAR delivery-cell mechanism named two paragraphs below — WITHOUT any new CP-spec carrier field, since `EvaluatorOptimizerResumeState`/`HandoffResumeState` have no branch-ordinal ambiguity (unlike the fan-out topologies property 6's new field was built for). This was therefore plain Phase-7 impl work, not a property-6-shaped or any other CONTRACT amendment — property 6's own text above is unaffected and remains scoped to the three fan-out topologies named in §1.1/§1.2b. `.harness/forward-register.yaml`'s `B-78` row reflects the closure; its residual finding (an unanswered `HITL_PENDING` resume proceeding to dispatch rather than staying inert) is a separate, pre-existing gap tracked at `B-79`, reachable at this site and at the already-shipped LINEAR/fan-out sites alike.

`TopologyPattern.SINGLE_THREADED_LINEAR` — the 6th and final member of the closed `TopologyPattern` enum (C-CP-10 §10.1) — is out of scope for a THIRD, distinct reason: it is not ungrounded, it is not broken. The LINEAR path already has a working delivery mechanism for exactly this case — `HITLDeliveryCell` construction at `workflow_driver.py:4766-4777`, the very mechanism property 6's §1.1(b) explicitly mirrors for the fan-out paths. Property 6 exists to close a gap that does not exist under `SINGLE_THREADED_LINEAR`.

**§1.3a Durable-carrier authorization (codex out-of-family review [P1], 2026-07-25, caught before merge — the carrier's EXISTENCE and byte-compat treatment cannot be left to impl discretion, only its exact shape).** `PeerFanOutResumeState`/`FanOutResumeState` (and their parent `PauseSnapshot`) are frozen `extra="forbid"` C-CP-26 types whose serialized contents participate in `snapshot_hash` — the durable hash `api.resume(resume_handle=...)` reloads after a crash. Leaving a NEW field's existence entirely to impl discretion would give the impl leg no contract-authorized basis for adding one without risking rejection of pre-existing durable snapshots (which lack it) or a second design back-flow just to authorize the addition. This spec leg therefore explicitly AUTHORIZES: `PeerFanOutResumeState`/`FanOutResumeState` MAY gain ONE new field to record pre-dispatch gate-owning branches' internal identities, following the SAME established byte-compat scoping convention this carrier family already uses for additive fields — drop-when-empty/`None` hash-strip scoping, mirroring `Spec_Control_Plane_v1_97.md`'s `PeerFanOutResumeState.paused_child_branches` precedent and `Spec_Control_Plane_v1_99.md`'s `PausedChildBranchResumeState.child_workflow_id` precedent (both additive fields whose absence/default state leaves prior snapshots' hash unchanged). A pre-existing durable snapshot with the new field absent/empty MUST hash identically to how it hashed before this delta; a resumed run with 0 pre-dispatch gate-owning branches MUST likewise be unaffected. This authorizes the field's EXISTENCE and hash-compat TREATMENT only — its exact name, type, and internal shape remain impl discretion per §1.3 below.

**§1.3 What is explicitly NOT specified here (impl discretion, mirrors v1.106 §1.3).** The new carrier's exact field name and type (existence + byte-compat treatment now pre-authorized at §1.3a above); the internal identity's exact shape (§1.1(d), beyond the tree-wide-uniqueness requirement already fixed there); which call site constructs it and which call site consults it for property 4's counting. A prior fork-doc draft (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md` §4, before this tension-resolution pass) initially sketched a concrete field name and type — corrected before filing, per the same CONTRACT-altitude discipline v1.106 §1.3 itself states, and per this arc's own four-round history of prescribing wiring that turned out false against the real call graph.
