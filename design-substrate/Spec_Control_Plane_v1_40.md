**Mechanism — the buffered-branch path (the §6.6 note's own named option), ADR-F2-safe.** The v1.38 note named both valid closure mechanisms: "emitting the override entry through the buffered-branch path / on the driver thread." The **buffered-branch path** is adopted (the thread-model-agnostic one): a new `append_branch_override_ledger_entry` (`harness-cp/src/harness_cp/workflow_driver.py`) buffers the override entry into the branch's `BufferingLedgerWriter` (C-CP-25 §25.12 D1.b), so the single barrier drain (`drain_branch_buffers`) serializes it through the one real writer on the driver thread in branch-index order — **realizing ADR-F2 v1.2's single-threaded-write boundary** without a synchronous per-worker write (the same discipline the §25.13 step/terminal branch entries already ride). Each of the 5 non-linear strategies (PARALLELIZATION / EVALUATOR_OPTIMIZER / ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION / DECENTRALIZED_HANDOFF) buffers the override at its branch-plan / sequential-dispatch site, gated on `binding.override_applied` — the non-linear sibling of the `_execute_workflow_body` linear guard. HIERARCHICAL_DELEGATION inherits it (its recursion re-enters `_execute_orchestrator_workers`). Both write paths compose the payload through the shared `compose_override_entry_payload` (factored out of the async `emit_override_state_ledger_entry` composer), so the persisted entry is **byte-shape-identical** across all topologies.

**Idempotency-key identity — the §16.5.4 per-`(step, outcome)` key, PRESERVED VERBATIM (NOT branch-scoped).** The override entry reuses the §16.5.4 idempotency-key 3-tuple `(workflow_id, step_id, sha256(outcome_canonical_bytes))` exactly as the linear path does — **not** branch-scoped (unlike the §25.13 step/terminal branch entries, whose `compose_branch_path` scoping prevents the IS dedup from dropping a legitimately-repeated step *execution*). An override is a **static property of the resolved binding**, not a per-execution event, so a `(step, outcome)` repeated across non-linear iterations (EVALUATOR_OPTIMIZER re-dispatching `generate`) or recursion levels idempotently **dedups at the IS writer to one entry** — the spec's designed §16.5.4 semantic. Branch-scoping the key would *change* the cleared §16.5.4 formula (an X-AL-3 spec change) and is foreclosed.

**No change to the §5.2 hash recipe; no IS-spec change; no CXA change.** The override entry's IS-anchored payload is the existing 5-field shape (C-IS-05); this delta changes neither the §5.2 procedural-tier hash recipe nor the §16.5.4 idempotency-key formula. The provenance stays at the per-step override state-ledger entry, never the run-level §5.2 hash. No new typed cross-axis edge (the override entry rides the already-landed CP→IS §16.5 composer seam). CXA v2.20 UNCHANGED; IS spec UNCHANGED.

## §1 — Amended §6.6 topology-scope note (the per-step override-ledger entry now fires on all topologies)

The §6.6 provenance reasoning (paragraph 1, v1.37/v1.38 — per-step prompt/role provenance at the per-step override state-ledger entry, not the run-level §5.2 hash) is **PRESERVED VERBATIM**. The v1.38 **topology-scope note** (paragraph 2) is refreshed to reflect the `B-NONLINEAR-OVERRIDE-PROVENANCE` closure:

> **Topology-scope of the override-ledger entry (v1.40 — CLOSED for all topologies).** The override-ledger entry (`emit_override_state_ledger_entry` / `append_branch_override_ledger_entry`, gated on `binding.override_applied`) fires on **all six** topology patterns for **every** per-step override dimension (model, since v1.6; prompt, since v1.37; role, since v1.38):
>
> - `SINGLE_THREADED_LINEAR` emits it inline at the `_execute_workflow_body` per-step site, written through the real ledger writer on the driver thread.
> - The 5 non-linear strategies (`ORCHESTRATOR_WORKERS` / `PARALLELIZATION` / `HIERARCHICAL_DELEGATION` / `DECENTRALIZED_HANDOFF` / evaluator-optimizer) emit it **through the buffered-branch path**: `append_branch_override_ledger_entry` buffers the entry into the branch's `BufferingLedgerWriter`, and the single barrier drain (`drain_branch_buffers`) serializes it through the one real writer on the driver thread in branch-index order — realizing the ADR-F2 v1.2 single-threaded-write boundary (C-CP-25 §25.12 D1.b) without a synchronous per-worker write.
>
> The persisted entry is **byte-shape-identical** across all topologies (both paths compose it via the shared `compose_override_entry_payload`): same `action_id` (`cp.per-step-override-application`) and the same §16.5.4 idempotency key `(workflow_id, step_id, outcome_hash)`. Because that key is per-`(step, outcome)` (NOT branch-scoped), a `(step, outcome)` repeated across non-linear iterations / recursion levels idempotently **dedups at the IS writer to one entry** — an override is a static binding property, not a per-execution event. The §6.6 provenance claim (paragraph 1) is therefore now **exact for every topology**. *(This supersedes the v1.38 honest-scope note's "the non-linear topologies do not emit a per-step override-ledger entry"; the gap it registered as a forward item is closed at `B-NONLINEAR-OVERRIDE-PROVENANCE`.)*

The run-level per-**role** / per-**prompt** catalog stays hashed at §5.2 v1.9 (`routing_manifest_sha` / `prompt_selection_manifest_sha`); the per-**step** override is recorded at the override ledger entry. The two scopes compose; no C-IS-05 §5.2 recipe change is owed.
