# ADR-F4: Adopt graduated-isolation as a four-tier sandbox tier-set with `max()`-composed per-tool tier assignment and tier × deployment-context tech-commitment split

## Status
Accepted
Date: 2026-05-09
Revision: v1.1 — Adv-2 revision pass per Path 4 session
Revision date: 2026-05-09

## Context

The project commits to multi-LLM-by-design with local-development as design-time deployment target (V3 system prompt §project_context). Persona_Document_v1 §10.1 records the operator-confirmed F4 principle as locked: graduated-isolation (sandbox-strength-by-trust-level), sourced to Persona_Document_v1 §5 operator phrasing. Persona_Document_v1 §10.3 leaves two F4 sub-aspects open for Phase 3a deliberation: F4-tier-set (process / container / microVM composition — which tiers the harness exposes; how tiers compose; the per-tool tier-assignment policy across the four primary workload classes) and F4-tech (Firecracker / gVisor / Kata / Docker / bubblewrap / Seatbelt / E2B / Modal / Daytona / Sprites / Runloop / etc.). Persona_Document_v1 §5.1 names the in-scope action surface explicitly: code execution, computer-use / browser-driving (at both design-time AND production-time, with stronger sandbox tier at production-time per operator phrasing), API / SaaS / MCP integrations all first-class. Persona_Document_v1 §8.1 [HIGH] names software engineering as code-execution-dominant with "LLM-generated code execution requires F4 sandbox per synthesis §9 Q13." Persona_Document_v1 §9 [HIGH] records the deployment-surface implication: "Computer-use-at-production with stronger sandbox tier (§5) → microVM-class isolation availability required." Persona_Document_v1 §10.2 records production-time deployment surface as persona-constrained — the option space narrows but no specific surface is picked.

The two sub-aspects have asymmetric coupling to persona constraints. F4-tier-set is largely workload-shape-bound and can be settled at the F4 layer with workload-class-tunable tier-assignment policy. F4-tech is **deployment-surface-bound** in a way F4-tier-set is not — Firecracker availability depends on bare-metal-or-KVM hosting; gVisor depends on Linux kernel; Kata on container-host capabilities; Seatbelt only on macOS; bubblewrap only on Linux. Committing specific F4-tech for tiers where deployment-surface coupling is tight would either pre-empt the production-time deployment surface decision or commit to tech that may not be available at the eventual production surface. F4 deliberation must therefore separate the **tier-set commitment** (which tiers exist; how they compose; the per-tool tier-assignment policy) — settleable now — from the **tech commitment** (which specific technology fills each tier) — settleable now per tier where deployment-surface coupling is loose, deferred to D2 D-ADRs per tier where coupling is tight. This is F4's analogue of the F3 capability-requirement-vs-engine-commitment split (ADR-F3 closure shape).

Pattern Reference Catalog v1.0 §10.3 P-AS-1 (sandbox isolation with per-tool trust tiers) documents corpus convergence on per-tool tiering, divergence on mechanism — OpenHands Docker-based agent-server, DeerFlow `LocalSandboxProvider` + `AioSandboxProvider`, deepagents `CompositeBackend` (Modal / Daytona / Deno), dify-sandbox under separate license, kilocode git-worktree via Agent Manager, oh-my-pi worktree / fuse-overlay / fuse-projfs, disler E2B agent-sandboxes, Kode-Agent OpenSandbox. Pattern Reference Catalog v1.0 §11.3.1 F4 enumerates the candidate set for tier-mechanism reference. Pattern Reference Catalog v1.0 §11.3.2 D2 ("Specific sandbox provider — *deployment-surface-dependent*; derived from F4") records tech selection as a downstream derivative decision surface. Cluster 3 §3.4(d) [SPECULATIVE] documents an isolation-by-tool-surface ordering — pure data-read (no sandbox), data-write-bounded (typed + RBAC), code-execution (microVM mandatory), computer-use (full VM, ephemeral, network-egress-restricted); triangulating against Cluster 4 §2.3 documented incidents and Cluster 3 §2.2 [HIGH] sandbox-stack tradeoff table promotes the ordering to [MODERATE]. Cluster 3 §2.2 [HIGH] documents the per-mechanism tradeoff axes: language-level (escape risk high if no language sandbox), container + seccomp (shared kernel, escape risk medium — kernel CVE class), gVisor (user-space kernel, escape risk low, ~10–30% I/O overhead), Firecracker microVM (hardware-virt, escape risk very low, ~150ms cold start), full VM (escape risk very low, seconds cold start). Cluster 4 §2.3.2 [HIGH] documents the lethal-trifecta architectural constraint (Willison): any execution path reaching private-data + untrusted-content + exfil-capability is structurally vulnerable, filter-based mitigations top out near 97% (Anthropic transparency hub: Sonnet 4.5 + detection prevented 94% MCP / 82.6% computer-use / 99.4% bash); architectural cut-of-leg via tier composition is the only reliable mitigation. Cluster 4 §2.3.3 [HIGH] documents the four-level MCP server trust posture (Level 0 refuse-remote / Level 1 signed-pinned / Level 2 sandbox-all / Level 3 allow-with-audit) and the MCP authorization spec 2025-06-18 [HIGH] making OAuth 2.1 Resource Servers + RFC 8707 + RFC 9728 + PKCE mandatory but **explicitly excluding STDIO transports** ("retrieve credentials from environment") — STDIO MCP servers carry zero protocol-level auth and sandbox is the only boundary. Cluster 4 §2.3.5 [HIGH] catalogs in-the-field failures sharing the under-tiering pattern: CVE-2025-53773 (GitHub Copilot RCE via prompt-injected `~/.vscode/settings.json` flipping `chat.tools.autoApprove: true`), CVE-2025-54132 (Cursor IDE Mermaid exfil), Anthropic Cowork file-API exfil (PromptArmor demonstration on Claude Opus 4.5), Oasis Security Claude.ai prompt-injection vulnerability via URL-param.

ADR-F1 (Proposed, 2026-05-09) is a load-bearing prior at the **tool/MCP exposure across providers seam**. ADR-F1 Consequences §(c) explicitly named: "D-ADR on tool/MCP exposure across providers must declare which providers expose which tool-calling shapes (server tools vs client tools vs MCP) — capability introspection extends to action surface." F4's per-tool tier-assignment policy composes against that exposure surface — every tool, regardless of which calling shape it runs through, carries a tier requirement; the per-MCP-server-trust-tier_floor (the second half of T-perm-1's tunable parameter) is settled at that downstream MCP exposure D-ADR rather than at F4. ADR-F2 (Proposed, 2026-05-09) is a load-bearing prior at the **substrate-derived isolation seam**. ADR-F2's worktree-isolation primitive (kilocode pattern, opt-in per workload class) sits at F4's process-tier boundary as one process-tier instance available wherever filesystem + git is. ADR-F2's combined git tier (versioning + state-ledger via commit stream + JSONL event ledger + opt-in shadow-Git checkpoint + worktree-isolation) is the substrate F4 sandbox tiers compose against, not displace. ADR-F3 (Proposed, 2026-05-09) is a load-bearing prior at the **lifecycle-observability seam for sandboxed tool execution**. ADR-F3's capability-requirement floor includes "observable lifecycle exposing workflow-start, step-boundary, fallback-trigger, retry-attempt, breaker-trip, lease-acquired/released, and resumption events"; sandboxed tool executions emit step-boundary + fallback-trigger + breaker-trip events that compose with F4's per-tool tier policy. ADR-F3's lease-coordination capability names "substrate-derived (kilocode-style worktree-isolation per ADR-F2)" as one valid lease implementation — F4's tier-set decision affects which lease implementations are available per workload class. T-perm-3 (C1 ↔ C9) was formally accepted as permanent at ADR-F3 with workload-class-tunable engine selection per D-ADR + capability-requirement floor + manifest-declaration invocation default + per-step annotation opt-in + pattern committed P-CP-8 as the F3-layer resolution shape; F4 sandbox tier composes against that resolution rather than relitigating it.

## Decision

Commit at the F4 layer to a **four-tier sandbox-isolation tier-set** (process / container / microVM / full-VM) with **per-tool tier assignment computed as `max(contract.minimum_tier, blast_radius_floor, mcp_server_trust_tier_floor, operator_policy_floor)`** per call site; commit **process-tier tech now** (Seatbelt on macOS, bubblewrap+socat on Linux/WSL, language-level + filesystem-ACL on Windows-native, with kilocode-style git-worktree-isolation per ADR-F2 as a cross-platform filesystem-bound process-tier composable) and the **container-tier abstraction now** (Docker-on-OCI as the design-time default, with specific container-runtime + image-policy deferred); **defer microVM-tier and full-VM-tier tech selection to per-deployment-surface D2 D-ADRs** constrained to candidates meeting the per-tier capability requirements stated in this ADR.

## Rationale

**(a) Pattern this decision follows.** The four-tier tier-set commitment follows Pattern Reference Catalog v1.0 §10.3 P-AS-1 (sandbox isolation with per-tool trust tiers) at its converged variation point — corpus convergence on per-tool tiering as the principle (OpenHands, DeerFlow, deepagents, Dify, kilocode, oh-my-pi, disler, Kode-Agent), divergence only on mechanism. The per-tier blast-radius mapping follows Cluster 3 §3.4(d) [MODERATE — promoted from SPECULATIVE via triangulation against Cluster 4 §2.3 incident catalog and Cluster 3 §2.2 [HIGH] tradeoff table]: pure data-read (process tier; language-level + filesystem-ACL adequate); data-write-bounded (process or container tier per egress-shape; typed + RBAC); LLM-generated code execution (microVM tier mandatory per Persona §8.1 [HIGH] + synthesis §9 Q13); computer-use / browser-driving (full-VM tier, ephemeral, network-egress-restricted, per Persona §5.1 stronger-sandbox-at-production-time and Cluster 4 §2.3.5 attacker-controllable-URL exfil class). The `max()`-composed per-tool tier-assignment policy follows the Cluster 4 §2.3.3 [HIGH] taint-tracking gate composed with Cluster 4 §2.3.3 [HIGH] four-level MCP server trust posture: contract-attached `minimum_tier` (the C4-side capability-introspection extension that ADR-F1 §(c) flagged as the action-surface analogue of provider capability introspection) plus call-time blast_radius_floor (taint state, lethal-trifecta cut) plus per-MCP-server-trust-tier_floor (set at the downstream MCP exposure D-ADR named in ADR-F1 §(c)) plus operator-policy-override entries in the audit ledger (Pattern Reference Catalog v1.0 §10.4 P-OD-3 [HIGH]). The tier × deployment-context tech-commitment split follows the F3 capability-requirement-vs-engine-commitment-split precedent (ADR-F3 closure shape) — same flexibility-preservation discipline, different axis: tier-set committed at the principle layer where workload-shape coupling is dominant; tech committed selectively where deployment-surface coupling is loose (process tier at design-time has clear cross-platform tech availability; container tier has design-time-universal Docker-on-OCI), deferred per tier where coupling is tight (microVM tier and full-VM tier both deployment-surface-bound per Pattern Reference Catalog v1.0 §11.3.2 D2). The process-tier tech commitment specifically reuses the Anthropic Claude Code sandboxing pattern (anthropic.com/engineering/claude-code-sandboxing) [HIGH] verbatim: Seatbelt on macOS, bubblewrap+socat on Linux/WSL — the only modification is naming a Windows-native fallback (language-level + filesystem-ACL) and the kilocode-style git-worktree composable for cross-platform filesystem-bound subset per ADR-F2.

**(b) Failure mode this decision prevents.** Two failure modes, dual sides of the T-perm-1 axis. **(i) Capability erasure on over-tiered sandbox shape.** If every code-execution tool runs at microVM tier by default — including in-house deterministic helpers whose code we authored — the action surface's per-call cost (Cluster 3 §2.2 [HIGH] documents Firecracker ~150ms boot, gVisor ~10–30% I/O overhead) inflates without proportional capability gain, violating Persona §6 per-class cost ceiling on cache-friendly workloads (§8.1 software engineering, §8.3 pipeline automation) and contradicting Pattern Reference Catalog v1.0 §10.3 P-AS-1's corpus convergence on per-tool tiering. The contract-attached `minimum_tier` in the `max()` policy expresses the C4-side capability_introspection_floor — tools are allowed to declare a low tier when their contract genuinely permits it. **(ii) Blast-radius unbounded on under-tiered sandbox shape.** Cluster 4 §2.3.5 [HIGH] documents the in-the-field pattern: configuration files the agent itself can write are the universal soft target — CVE-2025-53773 (GitHub Copilot RCE via prompt-injected `~/.vscode/settings.json` flipping `chat.tools.autoApprove: true`), CVE-2025-54132 (Cursor IDE Mermaid exfil), Anthropic Cowork file-API exfil, Oasis Security Claude.ai URL-param injection. All share the under-tiering pattern: a tool surface exists at a tier where blast-radius is not contained. The blast_radius_floor and per-MCP-server-trust-tier_floor entries in the `max()` policy express the C10-side trust enforcement — the harness applies a safety floor at call time regardless of what the contract declares. The lethal-trifecta architectural cut (Cluster 4 §2.3.2 [HIGH]) becomes structurally available because the four-tier set with Level 2 MCP composition (microVM tier with allow-listed upstream domains per Cluster 4 §2.3.3 [HIGH]) lets the harness cut a leg by tier elevation: any tool reachable only from inside a microVM with egress allow-listing cannot exfil to attacker-controlled destinations. Filter-based mitigations top out near 97% per Anthropic transparency hub [HIGH] — insufficient for unsupervised lethal-trifecta-positive deployment per Persona §6 architectural posture; structural cut via tier-set composition is the F4-layer mitigation.

**(c) Condition under which this decision stops being worth the cost.** Two conditions, neither current. **(i)** When the workload mix becomes uniformly trusted (no LLM-generated code, no untrusted-content ingest, no computer-use, no remote-MCP exposure), the four-tier set collapses to process tier alone and the `max()` policy becomes vestigial — every floor evaluates to `process`. Persona §5.1 in-scope items (code execution, computer-use at design-time AND production-time, MCP-as-first-class) make this not current. **(ii)** When the workload mix becomes uniformly untrusted (every tool LLM-generated-and-untrusted; no in-house deterministic helpers; no third-party tools we author at install-time), the contract-attached `minimum_tier` becomes vestigial because every tool-contract declares the same value. Persona §3.1 heterogeneous primary task classes (software / web engineering, content creation, pipeline & automation, research / analysis / knowledge work) plus the pragmatic-mixed ecosystem affinity (§7) make this not current and not in design horizon [SPECULATIVE].

## Consequences

**(a) What becomes possible.**

- Per-tool tier declaration at authoring time via contract-attached `minimum_tier` (the C4 capability-introspection extension that ADR-F1 §(c) flagged for the action surface), composing with ADR-F1's call-site capability-introspection API.
- Safety-floor enforcement at call time via blast_radius_floor (taint-state-aware per Cluster 4 §2.3.3) and per-MCP-server-trust-tier_floor (set at downstream MCP exposure D-ADR) without re-touching tool contracts when policy changes.
- Lethal-trifecta architectural cut via Level 2 MCP composition (microVM tier with egress allow-listing per Cluster 4 §2.3.3 [HIGH]) — the four-tier set's structural ability to express Level 2 is the F4-layer enabler of the only reliable mitigation Cluster 4 §2.3.2 [HIGH] documents.
- Persona §5.1 computer-use-at-production-with-stronger-sandbox-tier requirement met via the full-VM tier (ephemeral, network-egress-restricted) as a distinct tier separate from microVM, preventing the conflation Alternatives §1 below names as a structural failure.
- Per-tool tier-assignment policy expressible across the four primary workload classes per Persona §8: software engineering (process tier for filesystem ops; container tier for build/test; microVM mandatory for LLM-generated code per §8.1), content creation (process tier dominant; container tier for media-tool integration), pipeline automation (process tier for API/SaaS/MCP; container tier for occasional code execution), research/analysis (container or full-VM tier for browser-driving; process tier for document parsing).
- Span schema discipline that survives tech swap: `sandbox.tier` as structural attribute (stable across query and dashboard surfaces), `sandbox.tech` as discriminator attribute (swap-friendly without schema migration), `sandbox.fail.class` for failure-class taxonomy (escape / egress-denied / timeout / oom / signal / exit-nonzero) per C7 contribution composing with ADR-F3 lifecycle event set.
- Cost-attribution-per-span across tier overhead (Persona §10.2 constraint) via `sandbox.cost.tier_overhead_usd` and `sandbox.cost.tier_overhead_ms` — per-class cost ceiling enforcement (Persona §6) accurate by per-call attribution rather than amortized tier rate.
- Worktree-isolation per ADR-F2 reusable as a cross-platform filesystem-bound process-tier composable, preserving the ADR-F2 substrate principle into F4 without requiring container or microVM at the filesystem layer.

**(b) What becomes harder.**

- Every tool-contract authored from this point forward must declare `minimum_tier ∈ {process, container, microvm, fullvm}` alongside `input_schema` and idempotency posture; tools without a declared tier require a default-tier policy (proposal: default to `microvm` for fail-closed, with per-tool override required to lower).
- The harness must implement four floors and the `max()` composition at call-time, not just authoring-time: contract.minimum_tier (read from contract registry), blast_radius_floor (computed from call-time taint state), mcp_server_trust_tier_floor (read from MCP exposure D-ADR registry), operator_policy_floor (read from policy ledger).
- Process-tier tech requires three host-OS cases at design-time: Seatbelt on macOS, bubblewrap+socat on Linux/WSL, language-level + filesystem-ACL on Windows-native; the Windows-native case is structurally weaker than the other two and operator awareness is required if Windows-native is the design-time host.
- OTLP collector reachability per tier is non-trivial: process-tier (localhost socket by default); container-tier (explicit network-config for collector reachability); microVM-tier (per-microVM agent OR egress allow-list entry for collector endpoint); full-VM-tier (typically vendor-managed, OTLP egress per provider's egress policy).
- Persona §10.2 compliance-readiness primitive (hash-chained audit ledger) interacts with operator-policy-override entries: every override must produce an audit ledger entry per Pattern Reference Catalog v1.0 §10.4 P-OD-3 [HIGH], with downstream D-ADR specifying entry shape composing with ADR-F2 §(c) `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)` plus tier-override-specific fields.

**(c) What is now constrained downstream.**

- **D2 (specific sandbox provider) deferred by tier.** Per Pattern Reference Catalog v1.0 §11.3.2 D2, microVM-tier tech (Firecracker / gVisor / Kata / vendor-managed E2B / Modal / Daytona / Sprites / Runloop / Anthropic Code Execution / OpenAI Code Interpreter) and full-VM-tier tech (Anthropic Computer Use VMs / OpenAI Operator-class VMs / self-hosted ephemeral VM stack) selection deferred to per-deployment-surface D-ADRs constrained to candidates meeting per-tier capability requirements stated in this ADR. Container-tier tech beyond the Docker-on-OCI abstraction (specific container-runtime + image-policy + seccomp profile) similarly deferred to D2. Process-tier tech committed at design-time per the host-OS-case mapping above; production-time process-tier tech committable to D2 conditional on production deployment surface (Persona §10.2 still persona-constrained).
- **D-ADR on tool/MCP exposure across providers (ADR-F1 §(c))** carries the per-MCP-server-trust-tier_floor — the second half of T-perm-1's tunable parameter `per_tool_gate_level × per_mcp_server_trust_tier`. F4 settles the gate-level half; that D-ADR settles the trust-tier half.
- **F5 (secrets) closes T-perm-2 at the secrets-in-sandbox-environment seam.** F4 commits to permitting both shapes the F5 deliberation may choose: host-keychain-access at process tier (direct read into sandbox at startup) and in-sandbox-secrets-client at microVM tier (JIT-fetch via in-sandbox HTTP client over network). The two shapes have different threat models; F5 chooses, F4 enables.
- **D-ADR on sandbox lifecycle span schema** carries the tier/tech attribute discipline per C7 contribution: `sandbox.tier` (structural, tech-agnostic), `sandbox.tech` (discriminator), `sandbox.fail.class` (failure-class taxonomy), `sandbox.cost.tier_overhead_*` (cost-attribution-per-span), `sandbox.policy.assigned_tier_reason` (audit surface for which `max()` floor won). Composes with ADR-F3 observable-lifecycle requirement.
- **D-ADR on HITL eleven-trigger catalog** composes with sandbox failure-class taxonomy: escape-detection, network-egress-denied, cross-trifecta-leg-attempt (taint + private-data-read or taint + exfil-capability per Cluster 4 §2.3.3 taint-tracking gate) are sandbox-related triggers. The four-response palette (allow / deny / modify / escalate) composes with tier-elevation as one modify response (operator approves at higher tier for this invocation only).
- **D-ADR on OTLP-collector-reachability-per-tier** carries the per-tier collector-reachability mechanism — per-microVM agent vs egress allow-list entry vs container network config.
- **D-ADR on contract-default-tier policy** specifies the default `minimum_tier` for tool-contracts that omit declaration — proposed default: `microvm` (fail-closed); operator-override required to lower.

**Permanent tensions engaged.** This decision **engages T-perm-1 (C4 ↔ C10 — capability vs gating)** structurally at the action-surface layer. F4-layer resolution shape: the gate-level half of the tunable parameter `per_tool_gate_level × per_mcp_server_trust_tier` is settled here at F4 via the `max()` composition across `contract.minimum_tier` + `blast_radius_floor` + `mcp_server_trust_tier_floor` + `operator_policy_floor`; both C4's capability-introspection-floor and C10's safety-floor-by-blast-radius are expressed simultaneously without suppression because the higher tier always wins by construction. The MCP-server-trust-tier half is settled at the downstream MCP exposure D-ADR named in ADR-F1 §(c). Status: *formally accepted as a permanent tension* — surfaced as known-permanent in this session's TENSION block per orchestrator discipline.

This decision touches but does not resolve **T-perm-2 (C2 ↔ C3 — within-turn vs across-turn)** at the secrets-in-sandbox-environment seam — whether secrets are read into sandbox at startup vs JIT-fetched within sandbox is a F4-tier-shape-dependent question. F4 commits to permitting both shapes; F5 (secrets) deliberation closes the seam. T-perm-2's F2-layer resolution shape (read/write contract pair at state-ledger seam per ADR-F2) stands; F4 sandbox tier composes against that resolution rather than relitigating it.

This decision touches but does not re-open **T-perm-3 (C1 ↔ C9 — control-flow vs reliability)**. ADR-F3 closed T-perm-3 at the durable-execution-engine seam with workload-class-tunable engine selection per D-ADR + capability-requirement floor + manifest-declaration invocation default + per-step annotation opt-in + pattern committed P-CP-8. F4 sandbox tier composes against that closure: sandbox failure → fallback-trigger → breaker-trip events compose with ADR-F3 observable-lifecycle requirement and C9 retry/breaker mechanics; F4 exposes the failure-class taxonomy so C9 mechanism can route by class without altering the F3-layer T-perm-3 settlement.

## Alternatives considered

**Alternative 1: Three-tier set (process / container / microVM) with computer-use folded into microVM.** Candidate as the common simplification — vendor-managed microVM (E2B Operator-class workloads, Anthropic Code Execution containerized browser-driving) blurs the boundary between microVM and full-VM at the implementation layer, and a three-tier set reduces tier-assignment complexity. Rejected because Persona §5.1 explicitly names computer-use at production-time with stronger sandbox tier (ephemeral, full-VM, network-egress-restricted) as a distinct requirement separate from arbitrary-code-execution per Cluster 3 §3.4(d) [MODERATE], and Cluster 4 §2.3.5 [HIGH] documents the attacker-controllable-URL exfil class (image rendering with attacker URL, link rendering, DNS lookup, file write to shared/synced location) that requires ephemeral disposability — microVM without disposability is structurally inadequate. Conflating the tiers either over-tiers code execution (forcing every microVM call to assume full-VM-equivalent disposability and egress restriction, inflating the cost surface) or under-tiers computer-use (missing the ephemeral-disposability requirement). The four-tier set with full-VM as a distinct tier preserves the structural distinction at the cost of one additional tier in the policy table — the cost is small and the structural correctness is foundational.

**Alternative 2: Single-tier microVM-everywhere — maximal-safety-floor simplification.** Candidate because it eliminates the per-tool tier-assignment policy entirely (every tool runs at microVM tier; the safety floor is uniform; no `max()` composition needed). Rejected because Cluster 3 §2.2 [HIGH] documents Firecracker ~150ms cold start and gVisor ~10–30% I/O overhead per call; running every pure data-read tool (RAG, DB query) and every in-house deterministic helper at microVM tier inflates per-class cost and per-call latency without proportional capability gain — violates Persona §6 per-class cost ceiling on cache-friendly workloads (§8.1 software engineering, §8.3 pipeline automation) and contradicts Pattern Reference Catalog v1.0 §10.3 P-AS-1's corpus convergence on per-tool tiering. The capability erasure failure mode (Rationale §(b)(i) above) becomes structural rather than avoided.

**Alternative 3: Tier-set committed but tech committed for ALL tiers now — no D2 deferral.** Candidate because it produces a fully-specified F4 ADR with no downstream D-ADR work for tech selection. Rejected because microVM-tier tech (Firecracker / gVisor / Kata vs vendor-managed E2B / Modal / Daytona / Sprites / Runloop / Anthropic-Code-Execution / OpenAI-Code-Interpreter) and full-VM-tier tech (Anthropic Computer Use VMs / OpenAI Operator-class VMs / self-hosted ephemeral VM stack) couple deployment-surface-bound to production-time deployment surface, which Persona §10.2 records as persona-constrained but not picked. Committing microVM-tier tech now pre-empts the production-time deployment surface decision per the F3 capability-requirement-vs-engine-commitment-split precedent (ADR-F3 closure shape) — same flexibility-preservation discipline, different axis. The tier-set commitment without tech commitment for deployment-surface-bound tiers preserves the design-phase flexibility Persona §9 [SPECULATIVE→MODERATE] requires.

**Alternative 4: Tier-assignment via single-floor-only policy — contract-attached `minimum_tier` only OR harness-policy-only.** Candidate as the simplest single-source-of-truth for tier assignment. Rejected because either single-floor shape suppresses one voice's concern in the C4↔C10 dynamic of T-perm-1: contract-only forfeits call-time taint-state and operator-override (C10's blast_radius_floor and operator_policy_floor); harness-only loses authoring-time capability declaration and contract-level auditability (C4's contract.minimum_tier as the action-surface analogue of ADR-F1's call-site capability-introspection). The `max()` composition is the F4-layer resolution of T-perm-1 per the council's TENSION block — both layers express their concern; the higher tier always wins; neither voice is suppressed; capability and gating are reconciled by composition rather than choice.
