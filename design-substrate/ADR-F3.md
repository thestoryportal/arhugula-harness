# ADR-F3: Adopt the stateless-reducer / launch-pause-resume durable-execution pattern with capability-requirement floor and per-workload-class engine selection

## Status
Accepted
Date: 2026-05-09
Revision: v1.1 — Adv-2 revision pass per Path 4 session
Revision date: 2026-05-09

## Context

The project commits to multi-LLM-by-design with local-development as design-time deployment target (V3 system prompt §project_context). Persona_Document_v1 §10.2 records F3 (durable-execution-as-coordination-spine) as **persona-constrained** rather than persona-answered: coarse classification — workload-class dependent; capability requirement set by the long-running subset; detail in §8 (sourced from Persona_Document_v1 §3 and the F3 review pass during Phase 2). Persona_Document_v1 §10.3 enumerates two F3 sub-aspects open for Phase 3a deliberation: F3-engine (Temporal, Restate, DBOS, LangGraph checkpointing, custom-on-Postgres, filesystem-journal, etc.) and F3-invocation-discipline (manifest declaration, auto-inferred, per-invocation operator choice, per-step annotations).

Persona_Document_v1 §10.1 already records the **durable-execution capability requirement** (long-running survives-restarts as workload class) as persona-answered, sourced from §3. The deliberation surface at F3 is therefore narrower than for a fully-open foundational decision: the capability requirement that durable execution must exist as a harness primitive is already locked; F3 deliberates its *shape* — pattern, invocation discipline, capability-requirement floor, and engine selection scope. Persona_Document_v1 §3 names long-running survives-restarts as a workload class; §4 sets the 99.9%+ completion SLO at tens-concurrent scale, which Persona §4 itself notes is "mathematically incompatible with operator-in-loop-on-every-failure HITL — HITL must be selective, with the deterministic outer harness absorbing most recovery"; §8.1 names software engineering as F3-mixed; §8.3 names pipeline automation as "F3 durable-execution-spine territory par excellence" with "Retry / breaker discipline most rigorous of all four classes; idempotency keys non-negotiable"; §8.5 surfaces the cost × reliability × capability cross-class coupling that constrains engine candidate selection per workload class.

Pattern Reference Catalog v1.0 §11.3.1 F3 enumerates the corpus's durable-execution candidate set (deepagents on LangGraph runtime; agentcontrolplane on K8s CRDs with infrastructure-layer durable async/await; VoltAgent Workflow Engine; Dify visual workflow; 12-Factor Agents Factors 6 and 12; optio auto-resume reconciler; Kode-Agent seven-segment resume with WAL); Pattern Reference Catalog v1.0 §11.3.2 D1 records "Specific durable-execution substrate — *deployment-surface-dependent*; derived from F3" — the catalog itself anticipates engine selection as a downstream derivative decision and Brainstorm_Synthesis_For_Phase_2 §6 [MODERATE — synthesis cap] explicitly identifies F3 as the F-decision where committing the *engine* early loses flexibility while committing the *pattern* preserves it. Pattern Reference Catalog v1.0 §10.1 P-CP-8 (stateless reducer / launch-pause-resume control flow) is the converged corpus pattern: agent function is `(context, event) → next_step`; durability lives below the agent; runs are interruptible operations exposed over standard APIs (12-Factor Factors 6, 8, 12; ACP CRDs persist agent state across restarts; Cluster 5 V2 F3). Cluster 2 V2 §2.3.2 [HIGH] establishes the canonical engine-tradeoff frame: LangGraph durable execution & checkpointing as "save points" requiring application-owned failure detection / lease coordination / dedup / resumption (Diagrid Feb 25 2026 critique [HIGH]: "What they actually give you is a save point... That's a far cry from production-grade durability"); Temporal as event-sourced replay where "every workflow API call sends a Command to the Temporal Service... on crash, Worker replays Event History to reconstitute state to immediately-before-crash, then resumes" with the deterministic-workflow-non-deterministic-activity programming-model cost; Cluster 2 V2 §2.3.4 tradeoff table documents the cost / reliability / RPO / RTO axes across the candidate engine families. Cluster 2 V2 §2.3.5 [HIGH] documents the failure modes the F3 capability-requirement floor must prevent — concurrent-resume corruption ("two workers picking up the same `thread_id` after a partial failure each re-execute from the same checkpoint, causing duplicate external-API calls and divergent state writes"), CrewAI conditional-skip-everywhere on `@persist`, ADK tool exception killing entire workflow. Cluster 4 §2.2.1 [HIGH] frames durable execution as a reliability primitive composition site (in-process / gateway / durable-executor); Cluster 4 §2.2.7 [HIGH] documents the per-`{provider, model}` circuit-breaker placement and Stripe-style idempotency-key construction `sha256(conversation_id || step_index || tool || canonical_args)`; Cluster 4 §2.4 [HIGH] establishes that HITL interrupt/resume is structurally identical to durable-execution checkpoint (12-Factor Factor 6; LangGraph `interrupt()` as a special case of the same checkpoint substrate).

ADR-F1 (Proposed, 2026-05-09) is a load-bearing prior at the **routing-chain-advancement seam**. ADR-F1 Consequences §(c) explicitly named: "D-ADR on routing-strategy implementation must specify per-layer time budgets, breaker placement (per `{provider, model}` pair per Cluster 4 §2.2.7 [HIGH]), and chain-advancement coordination with C9 retry mechanics. Engages T-perm-3 directly." F3 closes the durable-execution side of that seam: the engine-and-invocation-discipline F3 settles is the substrate that ADR-F1's chain-advancement coordination runs on. ADR-F1 §"Permanent tensions engaged" already accepted T-perm-3 (C1 ↔ C9 — control-flow vs reliability) as a permanent tension with the per-layer time-budget shape as the F1-layer resolution; F3 engages the same permanent tension at the durable-execution-engine seam and must specify the F3-layer resolution shape, which differs from F1's because F3 is persona-constrained (workload-class-dependent) where F1 was persona-answered (principle locked).

ADR-F2 (Proposed, 2026-05-09) is a load-bearing prior at the **state-ledger substrate seam**. ADR-F2's combined git-tier (versioning + state-ledger via commit stream + JSONL event ledger + opt-in shadow-Git checkpoint) is the substrate any F3 engine layers on top of. Per Brainstorm_Synthesis_For_Phase_2 §6 pattern-vs-engine decoupling, F3-engine choices that *require* a different substrate (DBOS binding Postgres-as-canonical-store; Temporal requiring its own event history) compose against F2's filesystem + git rather than displacing it; this composition is itself an F3 deliberation surface. ADR-F2 §(c) records the downstream D-ADR on state-ledger schema with idempotency-keyed entry shape `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)` as the contract surface F3 composes against. ADR-F2 §"Permanent tensions engaged" formally accepted T-perm-2 (C2 ↔ C3 — within-turn vs across-turn) as permanent with the read/write contract pair as the F2-layer resolution; F3 touches but does not re-open T-perm-2 — engine choices compose against F2's resolution rather than relitigating it.

## Decision

Commit at the F3 layer to the **stateless-reducer / launch-pause-resume durable-execution pattern** (Pattern Reference Catalog v1.0 §10.1 P-CP-8) with a non-negotiable **capability-requirement floor** of (i) durable replay across restart, (ii) idempotency-keyed exactly-once semantics composed against ADR-F2's state-ledger entry shape, (iii) lease coordination preventing concurrent-resume corruption, and (iv) observable lifecycle exposing workflow-start, step-boundary, fallback-trigger, retry-attempt, breaker-trip, lease-acquired/released, and resumption events; commit to **manifest-declaration as the F3-invocation-discipline default** with per-step annotation as opt-in for fine-grained durability cadence; defer **F3-engine selection to per-workload-class D-ADRs** constrained to candidates meeting the capability-requirement floor.

## Rationale

**(a) Pattern this decision follows.** The pattern commitment follows Pattern Reference Catalog v1.0 §10.1 P-CP-8 (stateless reducer / launch-pause-resume control flow) at its converged variation point — corpus convergence on the principle (12-Factor Factors 6, 8, 12; ACP CRDs persist agent state across restarts; Cluster 5 V2 F3); divergence only on substrate (12-Factor methodology-only; ACP K8s-bound). The capability-requirement floor follows Pattern Reference Catalog v1.0 §10.4 P-OD-13 (append-only event stream / WAL — observed across Kode-Agent SDK seven-segment resume, learn-claude-code minimal append-only lifecycle event stream + JSONL mailbox protocol, pi-mono JSONL session) for the durable-replay primitive; ADR-F2 §(c) state-ledger entry shape for the idempotency-key dedup composition; Cluster 2 V2 §2.3.5 [HIGH] LangGraph concurrent-resume corruption documentation for the lease-coordination requirement; ADR-F1 §(c) and Cluster 4 §2.1 / Cluster 4 §2.2 [HIGH] for the observable-lifecycle requirement (chain-advancement subscription, breaker-trip event emission, fallback-trigger span). The manifest-declaration invocation-discipline default follows the same authoring-substrate composition that ADR-F1 established (manifest-as-auditable-default routing) and ADR-F2 settled (manifest-as-file in git, atomic-deploy with prompts and Skills) — F3 reuses the substrate rather than authoring a parallel one. The engine-deferral shape follows Brainstorm_Synthesis_For_Phase_2 §6 [MODERATE — synthesis cap] pattern-vs-engine decoupling, reconciled against Pattern Reference Catalog v1.0 §11.3.2 D1 ("Specific durable-execution substrate — *deployment-surface-dependent*; derived from F3"), which the catalog already records as a derivative decision surface.

**(b) Failure mode this decision prevents.** Five failure modes, each documented. **(i) Restart-survival collapse on the durable workload pole** — Persona §3 names long-running survives-restarts as a workload class and §4 sets the 99.9% SLO; an F3 layer that does not commit the capability-requirement floor allows downstream D-ADRs to select engines that do not meet it (raw filesystem-journal without lease + dedup discipline; LangGraph-without-application-level-coordination per Cluster 2 V2 §2.3.5 [HIGH]), which would forfeit the 99.9% SLO on the durable pole. The capability-requirement floor enforced at F3 is the architectural property that downstream engine selection cannot evade. **(ii) Flexibility-loss from premature engine commitment** — DBOS binds Postgres-as-canonical-store, Temporal requires a cluster, Bedrock AgentCore is cloud-bound, LangGraph-only adoption forfeits restart-survival without external durable backend (per ADR-F2 Alternative 1 rejection) — committing on engine at F3 mismatches at least one workload pole given Persona §3 / §8 heterogeneity (pipeline automation needs spine-grade durability; content creation runs ephemeral; software engineering is mixed; research is mixed). Brainstorm_Synthesis_For_Phase_2 §6 [MODERATE] explicitly names F3 as the F-decision where committing the engine early *loses* flexibility — opposite framing from F1 / F2 / F4 / F5. **(iii) Silent re-execution corruption from CrewAI-style conditional-skip-everywhere** — Cluster 2 V2 §2.3.5 [HIGH] documents `@persist` saving state but resume requiring `if self.state.step_completed >= N: return` on every method, "easy to forget; produces silent re-execution." The capability-requirement floor of idempotency-keyed exactly-once semantics composed against F2's state-ledger entry shape makes this failure mode structurally impossible — the dedup is at the harness layer, not application layer. **(iv) Concurrent-resume corruption** — Cluster 2 V2 §2.3.5 [HIGH] documents two workers resuming the same `thread_id` causing duplicate external-API calls and divergent state writes. The lease-coordination capability-requirement makes this a non-negotiable architectural property; the implementation can be engine-native (Temporal placement primitive), application-level (Redis lease, DB unique constraint per Cluster 2 V2 §2.3.5 [MODERATE]), or substrate-derived (kilocode-style worktree-isolation per ADR-F2 [HIGH]) — the *capability* is fixed at F3. **(v) Observability blackout on the failure path** — without the observable-lifecycle capability, fallback-trigger events, breaker-trip events, and lease-collision events are unobservable to downstream C7 instrumentation, defeating the cost-attribution-per-span persona constraint (§10.2) and the 99.9% SLO measurability (Persona §4 + §10.4 compliance-readiness primitives Persona names as foundational).

**(c) Condition under which this decision stops being worth the cost.** Two conditions, neither current. **(i)** When workload distribution stabilizes to a uniform durability requirement (the §3.2 workload-class extensibility flag becomes vestigial, or workloads converge to a single F3-shape pole), per-workload-class engine selection collapses to a harness-wide engine choice and the F3 ADR can be superseded by a single-engine commitment. The bridging-arc persona (Persona §2) and the §3.2 operator-asserted workload-class-extensibility flag make this not current. **(ii)** When local-deployment ceases to be a design-time constraint (V3 framing changes) and a single production-time deployment surface dominates such that engine selection becomes deployment-surface-bound rather than workload-class-bound, the F3-layer deferral can be re-shaped against the deployment surface. Persona §9 leaves production-time deployment surface narrowed but not picked; the bridging-arc keeps multiple production surfaces in scope; this condition is not current and not within design horizon [SPECULATIVE].

## Consequences

**(a) What becomes possible.**

- **Per-workload-class engine selection at D-ADR** with the capability-requirement floor as the engine candidate filter. Pipeline automation (Persona §8.3 spine territory) selects against the engines meeting the floor with native primitives (Temporal-class with event-sourced replay [HIGH]; DBOS with Postgres-as-canonical-store [MODERATE]; or LangGraph + checkpointer + explicit composition discipline meeting the floor with application-level lease + dedup). Software engineering (§8.1 mixed) selects lighter-weight options compatible with evaluator-optimizer / Reflexion-style validation loops (LangGraph + SQLite + composition discipline; filesystem-journal + SQLite + worktree-isolation lease). Content creation (§8.2 mostly ephemeral) and research quick-lookup subset (§8.4) can run engine-less under F2's substrate alone.
- **Manifest-declared durability boundaries auditable in git** by composition with ADR-F2's manifest-as-file principle — the F3 manifest extension specifies which steps are durable, retention windows, and per-step engine binding (when adopted), atomic-deployable alongside prompts, Skills, and the F1 routing manifest.
- **HITL primitive composes with durable-execution lifecycle by construction** — Cluster 4 §2.4 [HIGH] establishes interrupt/resume as structurally identical to durable-execution checkpoint; the F3 pattern commitment makes the four-response palette (approve/edit/reject/respond) operate against the same lifecycle events that retry, fallback, and breaker subscribe to. Selective HITL (Persona §10.2 constraint) becomes mechanically expressible at the F3-lifecycle layer.
- **Capability-requirement floor as architectural property** enforceable at the engine-candidate-set filter layer — D-ADRs cannot select engines that fail any of the four capabilities; the floor is a structural invariant that the harness preserves across engine choices.
- **Lifecycle event substrate for compliance-readiness** — the observable-lifecycle capability emits events that compose with ADR-F2's hash-chained audit ledger primitive (Persona §10.4 compliance-readiness foundational primitive), producing tamper-evident lifecycle records via git's content-addressable substrate plus the engine event history (when adopted).
- **F2 ↔ F3 substrate composition contract** — F2's state-ledger remains canonical for action side-effects (the idempotency-keyed JSONL entries from ADR-F2 §(c)); engine event history (when adopted) is canonical for lifecycle replay state specifically; the two ledgers are joined on idempotency_key. This makes the pattern-vs-engine decoupling load-bearing at the substrate layer too — F2's substrate principle is preserved across the engine selection space.
- **Local-deployment design-time engine candidate set** is well-defined: filesystem-journal + SQLite + worktree-isolation lease (Anthropic Nov 26 2025 long-running-harness pattern composed with Cluster 4 §2.2.7 reliability primitives [HIGH]); LangGraph + SqliteSaver + explicit composition discipline; embedded durable executor (DBOS-as-library [MODERATE], Restate-as-process [MODERATE]) at workload classes genuinely demanding engine-native primitives.

**(b) What becomes harder.**

- **D-ADR per workload class for engine selection** — engine choice becomes a per-class deliberation rather than a single architectural commitment; four primary workload classes (Persona §3.1) each potentially producing a distinct engine binding.
- **Composition discipline between F2 state-ledger and engine-native event history** when an engine demanding its-own-event-history-as-canonical (Temporal, DBOS) is adopted — two ledgers must be kept consistent via shared idempotency_key, and the harness must enforce the join at write time and verify at replay time. The "best-effort 2PC by convention" pattern Cluster 2 V2 §2.3.5 [MODERATE] documents becomes structural rather than aspirational.
- **Manifest authoring per workload class** — the F3 manifest extension (which steps are durable, per-step retention, per-step engine binding) requires authoring effort proportional to workload-class count; mitigated by manifest-as-file in git making the authoring auditable and reviewable per ADR-F2.
- **Capability-requirement floor enforcement at engine binding** — at every D-ADR for engine selection, the floor must be verified against the candidate; engines meeting the floor only with explicit composition discipline (LangGraph + application-level lease + dedup; raw filesystem-journal + custom coordination) require the composition discipline authored as part of the D-ADR.
- **Engine-incompatibility surfacing at production-time** — the bridging-arc persona (Persona §2) means production-time deployment surface remains live; engines incompatible with V3 local-development design-time framing (Temporal Cloud, Bedrock AgentCore, Vertex Agent Engine) may be in-scope at production-time deployment, requiring re-evaluation of the candidate set at the production-time surface choice.

**(c) What is now constrained downstream.**

- **D-ADR on engine selection per workload class** (Pattern Reference Catalog v1.0 §11.3.2 D1) — pipeline automation likely selects Temporal-class or DBOS-class for native lease + event-sourced replay; software engineering likely selects LangGraph + SQLite + composition discipline or filesystem-journal + worktree-isolation; content creation likely engine-less; research per-task selection. Each per-class D-ADR verifies the capability-requirement floor against the chosen engine.
- **D-ADR on lease primitive** — when the engine does not provide native lease (LangGraph, filesystem-journal), the lease implementation must be specified (kilocode-style worktree-isolation per ADR-F2; Redis lease at multi-process per Cluster 2 V2 §2.3.5 [MODERATE]; SQLite UNIQUE-constraint at single-machine multi-process). Composes with Persona §11.10 multi-tenant tenant-isolation specifics at the bridging-arc multi-tenant binding.
- **D-ADR on F2 ↔ F3 substrate composition** when an engine is adopted — the consistency-enforcement contract (idempotency_key as the join key; write-to-both-on-action; verify-on-replay) authored against ADR-F2's state-ledger entry shape (`action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash`).
- **D-ADR on F3 lifecycle span schema** (C7 owner) — workflow-start, step-boundary, fallback-trigger, retry-attempt, breaker-trip, lease-acquired, lease-released, resumption events emitted as spans with attribute schema authored per OTel GenAI semconv extensions; cost-attribution-per-span (Persona §10.2 constraint) registers against the per-step span hierarchy.
- **D-ADR on routing-chain-advancement coordination** (ADR-F1 §(c) — already flagged as engaging T-perm-3 directly) — the chain-advancement subscribes to F3's fallback-trigger and breaker-trip lifecycle events; per-`{provider, model}` breaker placement composes with the engine's retry-attempt event emission.
- **D-ADR on local-deployment substrate specifics** (C11 owner) — SQLite schemas for in-flight state at engine-less workloads; in-process OTLP collector trace storage composing with F3 lifecycle spans; OS-keychain integration with engine-native secrets fetch (when adopted); fresh-on-restart contracts composing with engine resumption.
- **D-ADR on validator-fail × retry × durable-execution composition** (C5 owner) — the validator-fail-class taxonomy (s8 §7.5 reconciliation note: five-class taxonomy) maps to F3 lifecycle event types; permanent-fail terminates the workflow; transient-fail composes with retry-attempt + idempotency-key dedup.
- **D-ADR on multi-tenant tenant-isolation at F3** at the bridging-arc multi-tenant binding (Persona §11.10) — per-tenant engine isolation, per-tenant audit ledger composition, cross-tenant-leak prevention; T3 (per-task vs per-company deployment unit per Pattern Reference Catalog v1.0 §10.6) traversal composes with F3's per-workload-class engine binding.
- **D-ADR on object-storage tier for content-creation non-text media** (Persona §11.12) — when adopted, object-storage tier composes with F3 lifecycle event emission for media-write actions (idempotency-keyed against F2 state-ledger).

**Permanent tensions engaged.**

This decision engages **T-perm-3 (C1 ↔ C9 — control-flow vs reliability)** structurally at the durable-execution-engine seam. Status: *known permanent — same Layer-3 tension that ADR-F1 §"Permanent tensions engaged" surfaced at the routing-chain-advancement seam, now engaged at the durable-execution-engine seam*. F3-layer resolution shape: **workload-class-tunable engine selection per D-ADR with capability-requirement floor non-negotiable per F3**, plus **manifest-declaration invocation default with per-step annotation opt-in**, plus **pattern committed (P-CP-8) at F3**. The tunable parameter `topology_fault_handling` (the canonical T-perm-3 parameter per the locked-decisions table) is set per workload class downstream; at the F3 layer, the resolution shape is the candidate-set filter (engines must meet capability-requirement floor) plus authoring discipline (manifest-default + per-step opt-in). The F3-layer resolution differs from ADR-F1's per-layer-time-budget resolution because F3 is persona-constrained (workload-class-dependent, Persona §10.2) where F1 was persona-answered at principle (Persona §10.1).

This decision touches but does not re-open **T-perm-2 (C2 ↔ C3 — within-turn vs across-turn)** at the F2 state-ledger seam. ADR-F2 §"Permanent tensions engaged" formally accepted T-perm-2 as permanent with the read/write contract pair as the F2-layer resolution; F3 engine choices compose against F2's resolution rather than relitigating it. The F2 ↔ F3 substrate composition contract (Consequences §(a) and §(c) above) is the F3-layer composition shape, not a T-perm-2 resolution.

## Alternatives considered

**Alternative 1: Commit on a specific engine at F3 (e.g., Temporal as harness-wide, or LangGraph-with-checkpointer as harness-wide, or DBOS).**
Candidate because it produces architectural simplicity (one engine, one programming model, one operational surface) and would close F3 fully without leaving D-ADR work downstream. Rejected because workload-class heterogeneity (Persona §3 four primary classes; §8.1, §8.2, §8.3, §8.4 with distinct durability profiles) makes a single-engine commitment mismatched on at least one workload pole — Temporal's deterministic-workflow-non-deterministic-activity programming-model cost (Cluster 2 V2 §2.3.2 [HIGH]) is uneconomic for ephemeral content-creation workloads; LangGraph-with-checkpointer's application-owned coordination (Diagrid critique [HIGH]) is below the production-grade bar Persona §4's 99.9% SLO requires on the durable pipeline-automation pole without explicit composition discipline; DBOS binds Postgres-as-canonical-store, contradicting ADR-F2's filesystem + git substrate principle on the design-time deployment surface. Brainstorm_Synthesis_For_Phase_2 §6 [MODERATE — synthesis cap] explicitly identifies this alternative as flexibility-losing for F3 (opposite framing from F1 / F2 / F4 / F5 where early commitment gains flexibility).

**Alternative 2: Commit on engine-family at F3 (durable-executor / framework-checkpointer / filesystem-journal) without specific-engine selection.**
Candidate because it constrains the candidate set more tightly than full deferral, providing some architectural commitment while preserving per-workload-class engine selection. Rejected because the capability-requirement floor (durable replay; idempotency-keyed exactly-once; lease coordination; observable lifecycle) is the same across engine families — what matters is whether a candidate engine *meets the floor*, not which family it belongs to. Filesystem-journal + worktree-isolation + idempotency-key state-ledger meets the floor (Anthropic Nov 26 2025 long-running-harness pattern composed with Cluster 4 §2.2.7 reliability primitives [HIGH]); LangGraph + checkpointer + application-level lease + dedup discipline meets the floor (with explicit composition); Temporal-class engines meet the floor natively. Engine-family commitment adds architectural specificity without adding constraint power; the capability-requirement-floor commitment is the more precise resolution. Brainstorm_Synthesis_For_Phase_2 §6 [MODERATE] flexibility-loss critique applies at the engine-family level too — committing to "filesystem-journal-only" at F3 would forfeit Temporal-class native primitives at production-time deployment surface; committing to "durable-executor-only" at F3 would forfeit local-development design-time compatibility (V3 framing).

**Alternative 3: Defer both pattern and capability-requirement to per-workload-class D-ADRs (no F3-layer commitment beyond persona-answered durable-execution-capability requirement from §10.1).**
Candidate because it produces the minimum F3-layer commitment surface and maximizes D-ADR flexibility. Rejected because ADR-F1's chain-advancement coordination and ADR-F2's state-ledger composition both depend on F3 establishing the lifecycle pattern and capability surface at the F-layer — D-ADRs cannot author against an undefined spine. Specifically: ADR-F1 §(c) names "chain-advancement coordination with C9 retry mechanics" as engaging T-perm-3 directly; without F3 committing to the lifecycle pattern (P-CP-8) and the observable-lifecycle capability, the chain-advancement subscription target is undefined. ADR-F2 §(c) names the state-ledger entry shape with idempotency-key fields; without F3 committing to the idempotency-keyed exactly-once capability and the F2 ↔ F3 substrate composition contract, the state-ledger composition discipline is undefined. Persona §4 names 99.9% SLO as a hard target; without F3 committing to the capability-requirement floor, the SLO is unenforceable at the architectural level — D-ADRs would be free to select engines that fail the floor, and architectural drift would surface only at runtime measurement. The minimum-commitment alternative produces unsafe architectural deferral.

**Alternative 4: Commit on F3 fully (pattern + capability-requirement floor + invocation-discipline + specific engine per workload class) in this session.**
Candidate because it produces maximum F3-layer architectural closure and removes all engine-selection D-ADRs. Rejected because per-workload-class engine selection is genuinely workload-class-bound (Persona §3, §8) and decision-input the council does not yet have — the workload patterns within each class (Persona §11.3 long-tail duration of durable pole; §11.4 throughput rough order-of-magnitude per day) are §11 open items closing only as workloads materialize. Premature engine binding would commit against unmeasured workload-pattern tail. The deferral-to-D-ADR-with-capability-requirement-floor preserves the architectural property (capability floor non-negotiable) while leaving the per-class binding to be decided when workload patterns are observable. This composes with Pattern Reference Catalog v1.0 §11.3.2 D1's own framing of "Specific durable-execution substrate" as a derivative decision derived from F3.

**Alternative 5: Adopt auto-inferred F3-invocation-discipline (harness deduces durability boundaries from code structure or static analysis without explicit author declaration).**
Candidate because it removes the manifest-authoring burden Persona §10.3 named as the F3-invocation-discipline cost — the harness inspects step boundaries, side-effect surfaces, and idempotency-key-bearing tool calls and selects durability boundaries automatically. Rejected because (i) the inferred boundary set is not auditable at authoring time — durability is the spine that the 99.9% SLO (Persona §4) lives on; an inferred boundary set that the operator did not see at authoring time produces architectural drift surfacing only at runtime measurement (the same failure pattern Alternative 3 produces at the F-layer); (ii) the inference must be sound across every engine in the candidate set (Pattern Reference Catalog v1.0 §11.3.2 D1) — Temporal's deterministic-workflow-non-deterministic-activity boundary, LangGraph's checkpoint cadence, DBOS's transaction boundary, filesystem-journal's write barrier are different inference surfaces with different soundness conditions; an inference layer common across all engines is structurally near-impossible without committing on engine at F3 (which Alternative 1 rejected); (iii) it removes the manifest-as-file-in-git authoring substrate that ADR-F2 settled and that the manifest-declaration default reuses — auto-inference produces no auditable artifact in the F2 substrate, contradicting Persona §10.4 compliance-readiness posture (hash-chained audit ledger requires durability-boundary decisions to be observable in git); (iv) it is not subsumed by the manifest-declaration + per-step annotation composition — manifest declaration is an authoring-time decision in the F2 substrate; auto-inference is a load-time deduction outside that substrate; the two are architecturally distinct rather than degenerate cases of one another.

**Alternative 6: Adopt per-invocation operator choice F3-invocation-discipline (operator selects durability boundaries at workflow-start time per invocation).**
Candidate because it preserves maximum operator agency and matches the Persona §4 "selective HITL with deterministic outer harness absorbing most recovery" framing at the durability seam — every invocation is an explicit operator decision. Rejected because (i) Persona §4 is explicit that 99.9% SLO at tens-concurrent scale is "mathematically incompatible with operator-in-loop-on-every-failure HITL" — per-invocation operator choice for durability boundaries is the same mathematical incompatibility extended to the workflow-start gate; the operator cannot make a per-invocation durability decision at tens-concurrent throughput (Persona §11.4 rough order-of-magnitude per day) without becoming the bottleneck; (ii) it forces durability decisions to be made at workflow-start without authoring-time deliberation, contradicting the manifest-as-auditable-default discipline ADR-F1 established and ADR-F2 settled — the durability boundary is a stable architectural property of the workload-class, not a per-invocation parameter; (iii) it produces no auditable per-class default — every invocation begins from operator memory rather than a reviewable manifest, defeating the compliance-readiness posture (Persona §10.4 hash-chained audit ledger requires the durability-boundary decision to be observable per workload-class, not per-invocation); (iv) it is not subsumed by the manifest-declaration + per-step annotation composition — manifest declaration fixes the durability boundary at authoring time per workload-class; per-invocation operator choice shifts the decision point to workflow-start, fundamentally different cadence rather than a degenerate case. The four-response palette (allow / deny / modify / escalate) per ADR-F4 HITL eleven-trigger composition remains the operator's per-invocation surface for HITL-eligible events, not the per-invocation gate for durability-boundary selection.
