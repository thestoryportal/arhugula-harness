## Change-note (v1.66 → v1.67)

**Scope of revision.** Two consumer-side mechanisms in `harness_cp.workflow_driver`, both under the **C-CP-25 §25.12 / §25.15** fan-out crash-resume classification (the `_fence_unrecoverable_maybe_ran_indices` classifier introduced at the v1.62 / v1.65 B-FANOUT-EFFECT-FENCE-BRANCH-PAUSE line) — the build of the registered R-FS-1 standalone arc **`B-FANOUT-CRASH-RESUME-MAYBE-RAN-UNFENCED-EXTERNAL`**. v1.65 §3 registered it as "the maybe-ran MANAGED_AGENTS worker; UNFENCED vendor-session sink → needs the C-RT-31 fence EXTENDED to the managed-agents sink." This delta builds exactly that — the CP half (the classifier relaxation); the runtime half (the fence extension itself) is the paired runtime delta v1.82.

**The capability gap it closes.** Before this arc a maybe-ran fan-out MANAGED_AGENTS worker on a strict-tier (PAUSE / CASCADE_CANCEL) crash-resume FAILED CLOSED: re-dispatching it would create a SECOND billable vendor session + re-send the event (no fence → no at-most-once). The #742 TOOL_STEP slice fence-recovered only TOOL_STEP. MANAGED_AGENTS — the one effect-bearing fan-out kind whose effect reaches NO fence — stayed fail-closed and was named the registered follow-on. This delta makes it fence-recoverable now that its vendor-session dispatch is fenced at its own §14.22 sink (runtime v1.82): a maybe-ran MANAGED_AGENTS branch RE-DISPATCHES into the fence, whose lost-reserve SPLITS — suppress-with-captured-outcome (the session completed; fold the captured outcome verbatim — full result-fidelity), ambiguous-PAUSE (the crash fell in the create→capture window), or fresh-fire (claim absent ⟹ the prior attempt did not reach the reserve).

**The two CP changes.**

1. **MANAGED_AGENTS joins the fence-recoverable set.** `_FANOUT_MAYBE_RAN_FENCE_RECOVERABLE_KIND_VALUES` (the maybe-ran fan-out branch kinds whose re-dispatch re-reaches a fence and is therefore at-most-once-safe) grows from `{TOOL_STEP}` to `{TOOL_STEP, MANAGED_AGENTS}`. TOOL_STEP hits the runtime tool-fence directly; MANAGED_AGENTS now hits the §14.22 vendor-session fence directly (both are LEAF effects). SUB_AGENT_DISPATCH stays OUT (fenced only at its CHILD's tool sinks — a recursive child crash-resume, the separately-registered `B-FANOUT-CRASH-RESUME-MAYBE-RAN-SUBAGENT` follow-on).

2. **A same-kind-equality guard closes the cross-kind hole (the load-bearing correctness conjunct).** `_fence_unrecoverable_maybe_ran_indices` recovers a maybe-ran ordinal iff (a) it is in range AND (b) the DISPATCH-MARKER kind is in the recoverable set AND (c) the RESUMED manifest's kind at that ordinal is in the set AND **(d) the marker kind == the resumed kind**. With the prior singleton `{TOOL_STEP}` set, conjunct (d) was IMPLIED (both could only be TOOL_STEP). With a >1-kind set, (d) becomes load-bearing: a CROSS-KIND swap (marker TOOL_STEP / resumed MANAGED_AGENTS, or the reverse) passes both set-membership conjuncts but would re-dispatch into a DIFFERENT fence sink (a different idempotency-key namespace) → the original effect's fence ambiguity silently abandoned + a fresh effect of the new kind fired. The same-kind equality fails the cross-kind swap closed, so recovery only ever re-reaches the SAME sink the original effect claimed. This is the structural analogue of the v1.62 changed-manifest guard, generalized to a multi-kind set.

**The runtime half (paired delta v1.82) — the fence extension.** The §14.20 `ManagedAgentsStepDispatcher` gains the §14.22 effect fence (mirroring the tool dispatcher): a per-run-gated reserve-before-create_session, capture-after-success, and the lost-reserve directive split (RE_FIRE / SKIP_AS_FIRED → empty-but-keyed outcome / ABORT / suppress / ambiguous). The fence key is **payload-independent** — `H(managed_agents : parent_idempotency_key : step_id)`, NO agent_id — and LEADS with the `managed_agents` domain tag so it is disjoint from every tool key `H(parent : step : tool_id)` by construction (out-of-family Codex [P2]: a trailing tag would collide with a tool whose `tool_id == "managed_agents"`). A resumed agent-swap under the same step_id therefore composes the SAME key → it is SUPPRESSED (accepted-parity-or-stricter vs the cleared TOOL_STEP tool-swap, which keys on `tool_id`). See runtime v1.82.

**Why a spec amendment — and why it carries NO new operator gate.** The change adds a kind to a frozenset + an equality conjunct (CP) and extends an existing fence to a new sink (runtime). It changes NO contract removal, NO closed enum (no enum gains/loses a value — MANAGED_AGENTS is an existing `StepKind`), NO committed invariant. At-most-once is PRESERVED and STRENGTHENED: MANAGED_AGENTS goes from "fail-closed (safe but recovers nothing)" to "at-most-once recoverable" via the same key-bound fence machinery; the non-success / poll-exhausted dispatch paths capture NO output → a resume is genuinely ambiguous → the existing §26.2 EFFECT_FENCE_AMBIGUOUS pause + per-branch resolution (v1.66) handles them. `operator_gated: false` (the arc-ledger registration: additive fence extension, no committed-invariant sacrifice). Co-published with `.harness/clearance/` markers (CP v1.67 + runtime v1.82) per workspace `CLAUDE.md` §11.4.

## §1 — MANAGED_AGENTS fence-recoverable classification + the same-kind guard

> **The build (C-CP-25 §25.12 / §25.15).** `_FANOUT_MAYBE_RAN_FENCE_RECOVERABLE_KIND_VALUES` = `{StepKind.TOOL_STEP.value, StepKind.MANAGED_AGENTS.value}`. `_fence_unrecoverable_maybe_ran_indices(unsafe_indices, dispatched_kinds, resumed_kinds, branch_count)` returns the subset of `unsafe_indices` (re-fire-unsafe maybe-ran ordinals) that STAY fail-closed: an ordinal is fence-recoverable iff in range AND `dispatched_kinds[bi] ∈ set` AND `resumed_kinds[bi] ∈ set` AND `dispatched_kinds[bi] == resumed_kinds[bi]`. The fourth conjunct is the same-kind guard (§ above). A maybe-ran MANAGED_AGENTS branch whose resumed manifest is STILL MANAGED_AGENTS recovers; a cross-kind swap (TOOL_STEP ⇄ MANAGED_AGENTS), a changed-to-non-recoverable kind (e.g. DECLARATIVE), an un-recorded / torn marker kind, or an out-of-range ordinal stays fail-closed.
>
> **The two consume sites are unchanged in shape.** The classifier is shared by the incomplete-recovery + cardinality-only fan-out resume sites (`_determine_fanout_resume` via `_execute_parallelization` / `_execute_orchestrator_workers`) exactly as for the v1.62/v1.65 TOOL_STEP recovery — only the recoverable set + the equality conjunct change. A recovered MANAGED_AGENTS branch is RE-DISPATCHED (the CP driver re-dispatches; the at-most-once suppress/ambiguous/fresh-fire is enforced runtime-side at the §14.22 fence, runtime v1.82); siblings with captured output replay.
>
> **Result-fidelity holds by construction (why this is sound where #746 was not).** The #746 SUBAGENT attempt was reverted because a deterministic-run_id child re-dispatch engages the child's OWN recursive fan-out reconstruction → a suffix-only/empty child `final_state` the parent folds. MANAGED_AGENTS is a LEAF: the dispatch returns a single opaque outcome mapping with NO harness-side reconstruction. A fence suppress returns the CAPTURED outcome verbatim → the parent folds the exact original outcome. At-most-once (effect-fidelity) AND result-fidelity both hold; the recursive-fidelity trap that reverted #746 does not transfer.

## §2 — Runtime-paired fence extension + the disposition matrix (the primary half)

> **The fence extension (runtime v1.82, §14.20 / §14.22).** `ManagedAgentsStepDispatcher` gains an `effect_fence: EffectFenceProtocol | None` + `effect_fencing_explicit: bool`, threaded by the stage-5 factory from the SAME `.harness/effect-fence` claim dir as the tool dispatcher (key namespaces are disjoint — the leading `managed_agents` domain tag). The per-run gate (`effect_fencing_explicit OR step_context.run_engine_class ∈ durable-auto set`) decides whether a reserve fires; the dispatch reserves before create_session, captures the outcome after a validated success, and on a lost reserve applies the key-bound directive (RE_FIRE clears + fires fresh; SKIP_AS_FIRED returns an empty-but-fully-keyed outcome; ABORT raises EffectFenceAbortedError) else the captured-output split (suppress / ambiguous-PAUSE).
>
> **The disposition matrix (the verified risk surface).** A non-success terminal status (FAILED / CANCELED / TERMINATED) and a poll-budget exhaustion both RAISE WITHOUT capturing → the claim is held + no output → a resume is genuinely ambiguous → §26.2 EFFECT_FENCE_AMBIGUOUS PAUSE (NOT a false suppress of a failed outcome). The SKIP_AS_FIRED resolution returns an empty-but-fully-keyed outcome (`status="skipped_as_fired"`, the 6 success keys present with empty/zero values) so an opaque fan-out fold never KeyErrors — parity with the TOOL_STEP SKIP_AS_FIRED empty return (§14.22.9). These cells are witnessed through the REAL fence + a counting vendor port (the #746 lesson: fake the vendor PORT, not the dispatcher).
