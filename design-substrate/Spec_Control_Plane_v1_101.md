**Post-effect catch-ordering contract (leg-2 mechanics, CP-owned half — dyad-2 C1 precision note).** *Homed here rather than as a fifth rider section: it is the same leg-2 fail-closed-propagation surface, and OD v1.34 §21.2.3 row 7 cross-references the CP rider for both halves together.* POLICY is OD-owned (OD v1.34 §21.2.3 row 7: a post-effect signing failure surfaces directly and result-preservingly). The CP-owned MECHANICS statement:

- At EVERY post-effect site class — provider response obtained; tool executed; webhook POSTed; sub-agent workflow completed — `AUDIT_SIGNING_HARD_FAILURES` MUST be caught AHEAD of the generic per-attempt classifier catch, result-preservingly. As-built reference: `_run_per_candidate_attempts` (`retry_breaker_fallback.py:837`) catches `except Exception` (:889) and feeds `_classify_provider_exception` (:265), whose all-other-`Exception` branch returns `TRANSIENT_RETRY` (:291/:302) — without the ordered fence, a signing failure after a successful provider response would re-fire a completed PAID external effect.

- The SAME fence applies at every post-effect site class, not only `_run_per_candidate_attempts` — tools execute before cost attribution, webhooks POST before attribution, sub-agent workflows run before audit composition. The already-obtained result is PRESERVED for the audit-failure report.

## §4 — NEW §20.1.1 (C-CP-20) — narrow cutover-scoped historical exception to per-entry signature at MTC (leg 3, gate item 9)

*NEW subsection under §20.1 (`Spec_Control_Plane_v1_2.md`). The §20.1 per-persona-tier table itself is PRESERVED VERBATIM — row 3's per-entry-signature requirement at `multi-tenant-compliance` stands unrelaxed going forward; this subsection defines the ONLY exception anywhere in this arc, and it is HISTORICAL only.*

| # | Property | Contract |
|---|---|---|
| 1 | **The exception (historical, cutover-bounded)** | At MULTI_TENANT_COMPLIANCE, a row MAY satisfy §20.1 row 3 without a verifiable per-entry signature IFF it is named by the authenticated cutover record's signed content-bound `(tenant_scope, entry_hash, verification_disposition)` triples (OD v1.34 §21.2.2 row 4) — i.e. it is a recorded PRE-CUTOVER row whose disposition the operator attested at cutover (placeholder-exempt or four-tuple-real per the recorded disposition). The exception's extent IS the record's content-bound identity set: the exact legacy entry hashes (or a digest/root over them), never a date, version, or row-position. |
| 2 | **Forward posture UNRELAXED** | Every POST-cutover row at MTC requires a real per-entry signature, without exception. `audit_signing_fail_closed` explicit `false` remains INVALID at MTC (gate item 4; OD v1.34 §21.2.3 row 3) — this subsection is NOT a knob, NOT extensible by configuration, and admits no forward-looking membership: the triple set is fixed at cutover-record authoring, and a new row can never enter it. |
| 3 | **Never keyed on signature-value shape** | Membership in the exception is decided EXCLUSIVELY by the authenticated cutover record. Such a row is a verification FAILURE per §3 row 4, not a legacy row. |
| 4 | **Exempt rows are reported, never silent** | Rows passing under this exception are REPORTED explicitly at verification with their recorded disposition (per §3 row 6 and OD v1.34 §21.2.2 rows 4/6/8) — an audit result over a ledger containing exempt rows names them; silent pass-through is prohibited, mirroring the UNVERIFIED-at-MTC never-silent posture. |
| 5 | **Record trust requirements (OD-defined, cross-referenced)** | The cutover record's AUTHENTICATED / CONTENT-BOUND / TENANT-BOUND requirements, the trusted-source rule for legacy tenant bindings (external authoritative mapping, operator attestation, or declared-TOFU + quarantine), and the per-family transitive-tenant-binding distinction are DEFINED at OD v1.34 §21.2.2 rows 4-5 and §21.2.1 row 5 — cross-referenced, not restated. |
