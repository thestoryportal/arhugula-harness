# ADR-F2: Adopt filesystem + git as the canonical state substrate with files-as-artifacts and a combined git tier

## Status
Accepted
Date: 2026-05-09
Revision: v1.2 — Adv-2 iter-3 revision pass per Path 4 session (F2-iter2-01 resolution)
Revision date: 2026-05-10

## Context

The project commits to multi-LLM-by-design (V3 system prompt §project_context). Persona_Document_v1 §10.1 records the operator-confirmed F2 principle as locked: filesystem + git as the canonical state shape (sourced to Persona_Document_v1 §5 — direct host access, repo + persistent storage as local filesystem and remote git of the GitHub/GitLab class). Persona_Document_v1 §10.3 leaves two F2 sub-aspects open for Phase 3a deliberation: F2-adoption-depth (skills-as-files, prompts-as-files, state-ledger-as-files, artifact-tier layering) and F2-git-tier (versioning vs state-ledger vs checkpoint vs combination). Persona_Document_v1 §11.1 routes the shared-vs-siloed harness infrastructure question explicitly into this F2 deliberation; Persona_Document_v1 §11.12 flags the object-storage-tier need for non-text media in content creation as F2-adoption-depth-adjacent and pending downstream resolution.

The decision is foundational on the information substrate axis. Pattern Reference Catalog v1.0 §10.2 documents P-IS-1 (filesystem-as-shared-substrate) as a strong corpus convergence (C-on-the-substrate-commitment, divergent on schema only) observed across ICM, Meta-Harness, DeerFlow, pi-mono, Trellis, kilocode, and Anthropic's canonical long-running agent harness pattern. Pattern Reference Catalog v1.0 §10.4 documents P-OD-3 (audit ledger / hash-chained provenance) and P-OD-4 (checkpoint + rollback via shadow Git) as the operational-discipline patterns the F2-git-tier sub-aspect must allocate against. Cluster 2 V2 §1.4 [HIGH] establishes Anthropic's Nov 26 2025 long-running-harness pattern (`init.sh` + `feature_list.json` as JSON-not-Markdown + `claude-progress.txt` + git commits) as the canonical state-ledger reference; Cluster 2 V2 §3.4.1 [HIGH] establishes the prompt-versioning-substrate decision rule (git unless ≥3 non-engineer authors or runtime-A/B routing required, neither of which Persona §2 surfaces); Cluster 2 V2 §1.2 [HIGH] establishes the prompt-cache hierarchy (tools → system → messages) whose integrity F2-adoption-depth must preserve.

ADR-F1 (Proposed, 2026-05-09) is a load-bearing prior at two seams. ADR-F1 Consequences §(a) declares "manifest-layer model assignment per agent role, per workflow class, per step — declarative routing as the auditable default" — F2 closes that seam by determining the manifest's residence (file in git, with the same authoring + versioning + atomic-deploy properties as prompts and Skills). ADR-F1 Consequences §(c) flagged the prompt-cache pin discipline at the C2↔C3 within-turn/across-turn seam (T-perm-2) as deferred to a D-ADR on prompt-cache; F2 cannot resolve T-perm-2 (it is structural to the slate) but must specify the substrate shape on which prompts-as-files lives such that the static prefix is cache-pinnable, leaving the breakpoint placement to the downstream D-ADR.

## Decision

Adopt filesystem + git as the canonical state substrate, with skills, prompts, the routing manifest, and the state-ledger all authored as files (artifact-tier layering composing working / episodic / semantic / procedural / durable), and with git serving a combined role of code/spec/prompt/manifest/Skill versioning (foundational) plus append-only state-ledger via commit stream + JSONL event ledger (foundational) plus on-demand shadow-Git checkpointing (workload-class-opt-in) plus worktree-isolation for concurrent sub-agent reads (workload-class-opt-in).

## Rationale

**(a) Pattern this decision follows.** The substrate commitment follows Pattern Reference Catalog v1.0 §10.2 P-IS-1 (filesystem-as-shared-substrate) at its converged variation point — the substrate is the coordination medium, not replaced by an in-memory graph abstraction. The artifact-tier layering follows Pattern Reference Catalog v1.0 §10.2 P-IS-1 (D-on-schema variation: ICM five-layer prescriptive, 12-Factor minimum-viable, Anthropic's progress-file pattern as the loosest viable shape) and P-IS-6 (repo-as-memory) for long-lived project memory. The git-tier combination follows P-IS-1 for versioning, the Anthropic long-running-harness pattern (Cluster 2 V2 §1.4 [HIGH]) for state-ledger via commit stream, P-OD-3 (audit ledger / hash-chained provenance) for the JSONL event-ledger composition, and P-OD-4 (checkpoint + rollback via shadow Git, observed in Cline / kilocode / Roo Code) for the workload-class-opt-in checkpoint role. Skills-as-files follows the agentskills.io open standard — announced by Anthropic on 16 October 2025 ("Equipping agents for the real world with Agent Skills") and ratified as an open standard at agentskills.io on 18 December 2025 [HIGH] — with SKILL.md as a directory with YAML frontmatter (`name`, `description` required; optional `allowed-tools`, `disable-model-invocation`, `license`, `dependencies`) and three-level progressive disclosure (frontmatter → body → bundled resources via filesystem reads). Prompts-as-files follows Cluster 2 V2 §3.4.1 [HIGH] explicit decision rule (git as default unless registry-only conditions hold). State-ledger-as-files follows Anthropic's Nov 26 2025 long-running-harness pattern explicitly [HIGH] — JSON-not-Markdown for structured fields per Anthropic's verbatim guidance ("the model is less likely to inappropriately change or overwrite JSON"), append-only progress logs, deterministic git-commit cadence at session boundaries.

**(a.1) Hash-chain integrity construction as F-layer commitment.** F2 commits at the F-layer to construct the hash-chain integrity primitive at write-time via the following discipline (the construction *discipline* is F-layer; the schema fields and library binding are D-derivative downstream):

- **Per-entry canonicalization.** Each state-ledger entry is canonicalized to a deterministic byte representation prior to hashing — RFC 8785 JSON Canonicalization Scheme (JCS) is the corpus-converged baseline candidate [MODERATE — to be confirmed at the D-ADR on canonicalization library binding].
- **Per-entry hash computation.** SHA-256 of the canonical-JSON byte representation produces the entry's `response_hash` field per the entry shape `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)`.
- **Chain construction at write-time.** The `prior_event_hash` field of entry *N* references the SHA-256 of entry *N−1*'s canonical-JSON byte representation; chain inception entries reference the all-zeros sentinel hash.
- **Chain verification on demand.** Chain integrity is verified by re-canonicalizing each entry, re-computing each per-entry SHA-256, and verifying that every `prior_event_hash` matches the prior entry's recomputed hash; tamper-evidence is the verification's failure mode at any chain position.

The F-layer commitment fixes *that* hash-chain integrity is constructed at write-time via canonical-JSON serialization, SHA-256 per entry, and prior-event-hash chaining; the *specific* canonicalization library binding (RFC 8785 JCS reference implementation per language ecosystem) and any per-workload-class extensions to the entry shape are D-derivative downstream per Consequences §(c).

**(b) Failure mode this decision prevents.** Three failure modes, each well-documented. (i) **Restart-survival collapse on the durable workload pole.** Persona §3 names long-running survives-restarts as a workload class and §4 sets a 99.9% SLO; an in-memory-graph-only substrate (LangGraph-style without filesystem layer) forfeits restart survival without an external durable backend, forcing F3 engine commitment at design phase rather than deferring it (Brainstorm synthesis §6 explicitly identifies this as the flexibility-loss F3 must avoid). Filesystem + git provides restart survival as a foundation, with F3's durable execution engine layering on top rather than replacing it. (ii) **Cache-prefix detonation from naive Skills/prompts loading.** Cluster 2 V2 §1.2 [HIGH] establishes that any change to the `tools` array invalidates the entire cache; preloading SKILL.md bodies or composing the system prompt by string concatenation of multiple prompt files at runtime mutates the cacheable epoch and costs the 0.1× cache-read advantage on Anthropic [HIGH, Anthropic Prompt Caching docs] — the derived input-token cost ratio of cache-bypassed-vs-cache-hit access reaches 4–10× [MODERATE — derived inference] on cache-friendly workloads (§8.1 software engineering, §8.3 pipeline automation), incompatible with Persona §6 per-class cost ceilings. The derivation has four inputs: (1) Anthropic cache-read = 0.1× base input cost [HIGH, Anthropic Prompt Caching docs per Cluster 1 V2 §2.2.2]; (2) `tools`-array invalidation as a cache-detonation trigger [HIGH, Cluster 2 V2 §1.2]; (3) cache-friendly workload assumption — high cache-hit rate (50–95%) on stable system prompts and repeated tool definitions per Persona §8.1 / §8.3; (4) input-token-dominant workload shape on the named classes. The lower bound (~4×) holds where output tokens are non-trivial or cache-hit rate is moderate; the upper bound (~10×) approaches the asymptote 1/0.1 where input dominates and hit rate approaches 100%. The 4–10× range is bounded inference; specific empirical validation per workload class is downstream measurement work, not F2-layer commitment. Skills-as-files loaded via filesystem-read tools and prompts-as-files loaded as stable static-prefix content preserve cache-prefix integrity by construction. (iii) **State-ledger corruption from Markdown-only structured fields.** Anthropic's Nov 26 2025 guidance [HIGH] explicitly diagnoses this — Markdown-only state-ledger artifacts invite the model to inappropriately change or overwrite the ledger; JSON-not-Markdown for structured fields (`feature_list.json`) plus append-only Markdown for free-form progress (`claude-progress.txt`) is the corpus's lived-in resolution. (iv) **Loss of compliance-readiness foundation.** Persona §10.4 names hash-chained audit ledger as a foundational primitive; git provides content-addressable storage natively (every commit and blob is referenced by its SHA-1 / SHA-256 content hash), but content addressing and hash chaining are distinct primitives — content addressing makes objects retrievable by content identity, while hash chaining links sequential entries via prior-event-hash references such that tampering at any chain position is detectable. F2 supplies hash-chained integrity by constructing the chain at write-time per the §Rationale (a.1) discipline, leveraging git's content-addressable substrate as the durable storage but adding the chaining construction at the entry-shape layer; a filesystem-only substrate without git would lose the durable-storage foundation that this construction lives on, forcing the entire chain primitive to be built from scratch.

**(c) Condition under which this decision stops being worth the cost.** Two conditions, neither current. (i) When concurrent multi-writer requirements exceed advisory-locking + git-merge-discipline + worktree-isolation — for example, an enterprise multi-tenant scale where embedded-Postgres-per-deployment becomes the mandatory primitive (paperclip's pattern, P-DS-7) and filesystem semantics become the cache rather than the canonical store — F2 stops being worth the cost on the new pole. The bridging-arc traversal Persona §2 names is in scope and per-tenant git-repo isolation (kilocode worktree-style) is the F2-compatible scaling shape; the Postgres-per-tenant alternative is not currently triggered. (ii) When the workload mix becomes so uniformly multi-process / cross-host distributed that filesystem-as-substrate's host-bound orchestration property (Brainstorm synthesis §2 cost-of-filesystem-substrate) becomes a binding constraint that no available shared-network-storage shim resolves cheaply. The persona's local-development-as-design-time target (V3 §project_context) and the bridging-arc to multi-tenant make this not current and not in design horizon [SPECULATIVE].

## Consequences

**(a) What becomes possible.**

- Skills-as-files via SKILL.md folders, lazy-loaded by filesystem reads, preserving the cacheable epoch by construction (composes with ADR-F1 Consequences §(c) prompt-cache pin discipline).
- Prompts-as-files in git, atomically deployed alongside code and evals (Cluster 2 V2 §3.4.1 [HIGH]).
- Manifest-as-file for the ADR-F1-declared routing manifest — auditable, git-tracked, reviewable, and composing with state-ledger event entries that record routing decisions.
- State-ledger-as-files combining the Anthropic Nov 26 2025 pattern (`feature_list.json` + `claude-progress.txt` + git commits) with a JSONL event ledger (Maestro-style audit.jsonl + decisions.jsonl per P-OD-3) — append-only, restart-survives, hash-chain-integrable via git's content addressing.
- Compliance-readiness foundation: hash-chained audit primitive buildable on git's content-addressable substrate without separate ledger system; encryption-at-rest, retention controls, and granular access controls available via filesystem-and-git tooling at all deployment surfaces.
- Shadow-Git checkpointing as a workload-class-opt-in primitive (P-OD-4) — fine-grained reversal available where the workload supports it (software engineering with reversible edits) without imposing repo-size and latency costs on workloads that don't (pipeline automation with hours-long durable steps).
- Worktree-isolation for the concurrent-sub-agent-read subset that fans out reads while preserving Cognition's single-threaded-write convergence (Brainstorm synthesis §1).
- Per-tenant repo isolation as a clean F2-compatible scaling pattern at the bridging-arc multi-tenant binding (kilocode-style), preserving the substrate principle to the multi-tenant pole.
- T1 (filesystem-as-orchestrator vs framework-orchestration; catalog §10.6) deferral to a downstream D-ADR with the substrate decision settled — the orchestration topology now picks against a known substrate.
- Eval-set residence in git enables atomic prompt+code+eval deploys (Cluster 2 V2 §3.4.1) — the Husain-evals discipline (Cluster 2 V2 §2.1.4 [HIGH]) becomes a substrate-native pattern.

**(b) What becomes harder.**

- **Concurrent writes to substrate.** Filesystem doesn't provide distributed locking; concurrent sub-agents must coordinate via worktree-isolation (kilocode pattern) or single-threaded-write boundary (Cognition convergence per Brainstorm synthesis §1). Multi-writer scale beyond worktree-isolation requires a downstream D-ADR on coordination shape.
- **Bridging-arc to multi-tenant.** Per-tenant repo isolation is the F2-compatible pattern but requires explicit design (paperclip-style embedded-Postgres-per-tenant is precluded by the F2 substrate principle on the durable pole; per-tenant git worktrees / repos are the F2-compatible scaling shape).
- **Object-storage-tier need for non-text media** (Persona §11.12) is not solved by F2; content-creation workload patterns (§8.2 long-form with images / video / audio) will require a downstream D-ADR when patterns mature, potentially layering object-storage tier alongside filesystem + git.
- **State-ledger format authoring.** Anthropic does not publish a canonical schema for `claude-progress.txt` (Cluster 2 V2 §4 explicit open question [HIGH]) — the F2-compliant project must author the ledger's per-event JSONL shape and the progress-file section conventions, with the read/write contract pair (see Permanent tensions below) as the structural constraint.
- **Cross-host distributed orchestration.** The substrate's host-bound orchestration property (Brainstorm synthesis §2) means any cross-host workload must use shared-network-storage shims or accept a substrate boundary at the host edge; not currently in scope but a known constraint shape.

**(c) What is now constrained downstream.**

- **D-ADR on ledger entry schema fields and canonicalization library binding.** Per the §Rationale (a.1) F-layer commitment: the hash-chain construction discipline (canonicalization → SHA-256 per entry → prior-event-hash chaining) is fixed at F2; this D-ADR refines (1) per-workload-class extensions to the entry shape beyond the F-layer minimum `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)`, and (2) the canonicalization library binding — RFC 8785 JSON Canonicalization Scheme (JCS) is the corpus-converged baseline candidate [MODERATE], with reference-implementation selection per language ecosystem chosen. The D-ADR composes C3's append-only-write contract (append-only JSONL, JSON-not-Markdown for structured fields, idempotent writes keyed on `(thread_id, step_id, idempotency_key)` per Stripe-style convention, per-event JSONL with stable indexable shape) with C2's selective-read contract (bounded-window read at session start, navigation primitives as Skills or in-process tools, read into dynamic suffix not static prefix). Engages T-perm-2 explicitly with the read/write contract pair as the F2-layer resolution shape.
- **D-ADR on ledger entry idempotency-key composition fields.** Per C4 consultant refinement: entry shape must capture at minimum `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)` — F-layer minimum per §Rationale (a.1) — to support C9's idempotency-key-keyed retry dedup, C10's hash-chained audit integrity per Persona §10.4 compliance-readiness, and the best-effort-2PC-by-convention pattern (Cluster 2 V2 §2.3.5 [MODERATE]).
- **D-ADR on prompt-cache discipline per provider.** ADR-F1 §(c) flagged this; F2 now sets the substrate that prompts-as-files lives on, leaving cache breakpoint placement to the D-ADR.
- **D-ADR on Skills' wrap-vs-equip-vs-MCP allocation per primitive.** Brainstorm synthesis Permanent Tension T4 (markdown-spec-driven vs code-driven configuration) and the Skills-vs-MCP overlap (Cluster 2 V2 §2.2.7 [HIGH]) are contract-allocation decisions downstream of F2 — F2 commits to the substrate hosting both shapes; the D-ADR allocates which primitives go where.
- **D-ADR on shadow-Git scoping per workload class.** Cline-style fine-grained checkpointing is opt-in; the D-ADR specifies which workload classes activate it.
- **D-ADR on concurrent-writer coordination shape.** Worktree-isolation vs single-threaded-write boundary vs operator-mediated merge — the D-ADR scopes per workload class.
- **C7 span schema for state-ledger writes.** State writes become spans; the substrate shape settled at F2 enables span attribute design at the D-ADR on ledger-schema instrumentation.
- **C10 audit-ledger trust boundary.** Hash-chain integrity verification on startup and trust-boundary discipline on ledger writers belong at C10's D-ADR; F2 settles the substrate the ledger lives on.
- **C11 local-deployment-specific implementation.** Sqlite schemas for in-flight state, in-process OTLP collector trace storage, fresh-on-restart contracts — C11's D-ADRs apply on top of F2's substrate principle.
- **D-ADR on T1 (filesystem-as-orchestrator vs framework-orchestration).** Catalog §10.6 T1 is a topology choice depending on F2 adoption depth; the substrate decision settled enables T1 selection downstream.
- **Future D-ADR on object-storage tier for content-creation non-text media** (Persona §11.12), pending workload-pattern maturity.

**Permanent tensions engaged.**

This decision engages **T-perm-2 (C2 ↔ C3 — within-turn vs across-turn)** structurally at the state-ledger read/write seam. Status: *formally accepted as a permanent tension* with the read/write contract pair as the F2-layer resolution shape — write contract owned by C3 (append-only, structured, idempotent), read contract owned by C2 (selective, bounded, navigation-primitive-mediated), composed at the JSONL-with-stable-indexable-per-event-shape format. Specific schemas live at the downstream D-ADR on ledger schema; the parameter is set per workload class. T-perm-2 surfaced in this session's TENSION block per orchestrator discipline.

This decision touches but does not resolve **T-perm-3 (C1 ↔ C9 — control-flow vs reliability)** at the shadow-Git checkpoint cadence vs retry-mechanics seam — workload-class-opt-in shadow-Git checkpoint selection composes with C9's retry policy and C1's topology, deferred to the D-ADR on shadow-Git scoping.

## Alternatives considered

**Alternative 1: In-memory-graph substrate (LangGraph-style without filesystem layer).**
Candidate because it minimizes per-step IO and integrates cleanly with framework checkpointers (LangGraph + DynamoDBSaver / PostgresSaver), and because the graph abstraction makes structured replay tooling immediate. Rejected because it fails restart-survival without an external durable backend, forcing F3 engine commitment at design phase rather than allowing the pattern-vs-engine decoupling Brainstorm synthesis §6 identifies as the flexibility-preserving F3 path; because Diagrid's Feb 25 2026 critique [HIGH] documents that LangGraph-style checkpointing's application-owned failure detection / lease coordination / dedup / resumption is below the production-grade bar Persona §4's 99.9% SLO requires; and because it contradicts Persona §10.1 F2 principle directly.

**Alternative 2: Filesystem-only without git tier (`claude-progress.txt` and ledger files but no git versioning or commit stream).**
Candidate because it minimizes external-tooling dependency (filesystem is universally available; git is one extra primitive) and because the simplest local-development setup doesn't require git initialization. Rejected because it loses the content-addressable hash-chain primitive that Persona §10.4 compliance-readiness names as foundational; because it loses atomic-deploy of prompts+code+evals (Cluster 2 V2 §3.4.1 explicit decision rule [HIGH]); because it loses shadow-Git as opt-in checkpoint primitive (P-OD-4); and because the corpus convergence at P-IS-1 is filesystem *plus* git in every studied production harness (Claude Code, Aider, kilocode, ICM all combine; the divergence is on git's *role*, not whether to include git).

**Alternative 3: Universal shadow-Git checkpoint per step (Cline pattern as default for all workloads).**
Candidate because it provides fine-grained reversal across the board and standardizes the operational discipline; Cline / kilocode / Roo Code have demonstrated the pattern works in production. Rejected because fine-grained reversal value is workload-class-shaped (Persona §8.1 software engineering with reversible edits benefits substantially; §8.3 pipeline automation with hours-long durable steps gains little); because universal adoption inflates repo size and adds latency without proportional reliability gain on the workloads that don't support it; and because Persona §6 per-class cost ceilings make universal adoption fail the cheapest-deterministic-first discipline ADR-F1 established. Adopted as workload-class-opt-in instead.

**Alternative 4: Lightweight adoption — skills-as-files + prompts-as-files only; state in memory (no state-ledger-as-files).**
Candidate because it minimizes the artifact authoring cost at design phase and defers ledger-schema decisions until ledger-shape needs are clearer. Rejected because it fails restart-survival on the durable workload pole; because it forfeits Anthropic's Nov 26 2025 long-running-harness pattern explicitly recommended for the durable workload pole [HIGH]; because it forfeits the canonical state primitive (`claude-progress.txt` + `feature_list.json`) the corpus has converged on; because the compliance-readiness primitive Persona §10.4 names cannot be foundational without a durable ledger; and because the design-phase cost of authoring a ledger schema is materially smaller than the design-phase cost of architecting around the absence of one.
