## §1 — Non-attested branch-index-keyed fan-out recovery substrate (C-CP-25 §25.12)

> **The durable store is the SOLE which-branches-completed authority on a fan-out crash-resume.** Per §25.12 **D1.b**, concurrent-fan-out branch terminals buffer into per-branch `BufferingLedgerWriter`s and drain at the barrier (ADR-F2 single-threaded-write boundary). The durable F2 ledger is **BINARY at the barrier boundaries** — empty pre-barrier, complete post-barrier — so a mid-fan-out crash before the barrier (the common replay case; post-barrier = fan-out done = a normal `resume_at` skip) leaves the ledger with ZERO branch terminals. (`drain_branch_buffers` is a per-entry serialized append loop, NOT a single atomic transaction, so a crash *during* the drain leaves a PARTIAL ledger; this does not break the store-as-authority recovery — the partial entries are reconciled at re-materialization, §2, via the IS idempotency dedup.) A NEW durable per-branch substrate is therefore required to know which branches completed.

> **The substrate (sibling methods on the existing `EngineOutputStore`).** During fan-out execution, when a branch completes AND the run's `engine_class ∈ {EVENT_SOURCED_REPLAY, WAL_SEGMENT}` AND a store is operator-bound (`ctx.engine_output_store`), the branch's `(step_id, output)` is captured to its OWN per-branch file (`{sha256(run_key)}.branches/branch-{branch_index}.jsonl` — N concurrent branch writers, no shared-file contention), keyed by `run_idempotency_key` + `branch_index`. **RESERVE-before-COMMIT:** the store-write is fsynced BEFORE the branch's terminal ledger-append (the SAME skew discipline as the linear `_record_durable_step_output`), so the store always holds ≥ the (binary) ledger's committed branch set. For `ORCHESTRATOR_WORKERS` / `HIERARCHICAL_DELEGATION` the orchestrator (`steps[0]`) output is ALSO captured (it rides `FanOutResumeState.orchestrator_output` on resume). The `step_id` is recorded at CAPTURE time — the load-bearing identity that lets the existing strategy resume material-diff guard fail closed on a changed body.

> **Not part of the §6 hash chain (D1 preserved literally).** The recovery sidecar is a separate durable store, written BEFORE the attested ledger entry; it is NOT a state-ledger entry and contributes NO §6 `entry_hash` link (the linear `EngineOutputStore` precedent, #665). The attested ledger's append order is UNCHANGED — branch-index-ordered at the barrier drain, on a no-crash run AND on a resumed run. See §4.

> **The gate is SHARED (no skew).** A SINGLE predicate (`_fanout_replay_store`: `engine_class ∈ {EVENT_SOURCED_REPLAY, WAL_SEGMENT}` ∧ store-bound) governs BOTH the capture sites and the consume site, so the two halves of the mechanism can never disagree on which runs are recoverable. Default (no store / not replay-capable) → no capture, no recovery → byte-identical to pre-v1.55.

## §2 — Fan-out crash-resume entry (seeds the existing pause-resume recovery)

> **The recovery REUSES the B-FANOUT-PAUSE recovery path — only the snapshot SOURCE differs.** The 3 concurrent fan-out strategies already recover a `cascade_policy=pause` halt from a `FanOutResumeState` / `PeerFanOutResumeState` (skip terminal branches, recover their outputs, re-dispatch the incomplete). On a crash-resume (`_execute_workflow_body`, replay-capable ∧ store-bound ∧ no explicit pause snapshot), the driver reconstructs that SAME resume state from the durable store (`_determine_fanout_resume`: completed = the store's branch keys; `step_id` from the store; for orchestrator topologies the recovered orchestrator output) and threads it into the strategy through the existing recovery local. The completed branches are skipped (outputs recovered), the rest re-dispatched. **Fail-closed:** a branch the store reports PRESENT but UNREADABLE (corruption / tamper), or a missing orchestrator output when workers completed (an inconsistent store), → `RunStatus.FAILED` (never a silent re-dispatch that would re-fire a possibly-landed effect). Because every recursive `HIERARCHICAL_DELEGATION` child re-enters `_execute_workflow_body`, each recursion level recovers against its own run-keyed store.

> **The orchestrator (`steps[0]`) is the recovery authority for orchestrator topologies (at-most-once).** The orchestrator dispatches FIRST, sequentially, BEFORE any worker. So a crash AFTER the orchestrator output is captured but BEFORE any worker completes must STILL recover the orchestrator — `_determine_fanout_resume` checks the captured orchestrator record BEFORE the empty-worker-set return and reconstructs a `FanOutResumeState` with an EMPTY branch set (every worker re-dispatches fresh). Otherwise re-dispatching `steps[0]` would double-fire the orchestrator effect the sidecar already captured. A present-but-unreadable orchestrator fails closed even with zero workers.

> **The resumed run's ledger is RE-MATERIALIZED (audit completeness, NOT just the aggregate).** Unlike a PAUSE-resume — where the recovered branches' step/terminal ledger entries were already DRAINED durably before the pause halt — a CRASH before the barrier drain lost the buffered branch + orchestrator entries (the binary ledger drained nothing). So on a crash-resume the strategy RE-APPENDS the recovered branches' step+`completed` terminal entries (and the orchestrator's sequential entry) to fresh writers included in the barrier drain, so the resumed ledger carries an entry for EVERY recovered entity and `workflow.step_count` counts them. **This is DEDUP-SAFE in every crash window:** the per-(branch) ledger idempotency keys are deterministic, so `append_ledger_entry` returns `IDEMPOTENT_NOOP` for any entry a mid-drain crash DID persist (the partial-ledger reconciliation) and APPENDS the rest — the binary-ledger premise need not hold mid-drain. The fan-out branch entries carry NO `response_hash` (the C9 finding), so re-materialization is identity + causality only; the recovered output rides the store, folded into the aggregate. Crash-resume ONLY — pause-resume entries are already durable, so its recovered branches are skipped as before (byte-identical).

## §3 — Synthesis-bearing fan-outs remain FAIL-CLOSED on crash-resume (PR1 boundary)

> **A `POST_JOIN_SYNTHESIS` fan-out that crash-resumes is FAIL-CLOSED in this slice.** v1.54 §3/§4's interim guard rejected synthesis-on-resume for the PAUSE-resume path (`post-join-synthesis-on-resume-unsupported`). The crash-resume path (this delta) extends that boundary: when a crash-resume recovery state is reconstructed AND the step sequence carries a terminal `POST_JOIN_SYNTHESIS` step, the run FAILS CLOSED with the SAME `post-join-synthesis-on-resume-unsupported` shape — because a recovered fan-out would otherwise dispatch the synthesis FRESH on `_finish` (a NON-reproducible W3-window aggregate, no captured-synthesis replay). This keeps the half-capability from silently shipping. **Reproducible synthesis-across-crash-resume** — a record-local capture-time synthesis self-hash + the captured-synthesis-output replay that RELAXES this boundary — is the **registered follow-on slice (PR2) of `B-FANOUT-OUTPUT-REPLAY`** (per the #719 C9 residual finding: the synthesis output is the one non-deterministic, no-ledger-digest, sole-authority residual that warrants a record-local self-hash). NOT in this slice.

## §4 — §25.12 D1 — PRESERVED LITERALLY (the v1.54 forward-note superseded)

> §25.12 **Point 1 + D1 are PRESERVED VERBATIM** (append order is deterministic given fixed step outputs; the attested branch-terminal entries drain branch-index-ordered at the barrier on BOTH a no-crash and a resumed run; non-determinism stays confined inside the step per ADD §5.3.3). The v1.55 recovery substrate (§1) is **non-attested** — it commits in physical-completion order to a sidecar that is read back by `branch_index` and is NOT part of the §6 hash chain — so it does NOT alter the attested ledger's append order. **There is NO §25.12-D1 sacrifice.** The v1.54 §1/§4/§5 forward-looking framing of this follow-on as "a SECOND committed-invariant sacrifice (§25.12 Point-1/D1)" was a Class-3 over-claim corrected by the #719 council and superseded by this as-built section (operator-ratified A, #721). The recovery sidecar *serves* determinism: it PINS the completed branch outputs so the resumed aggregate is identical to the no-crash trajectory, AND the resumed ledger is re-materialized to completeness (§2) so the audit trail — not only the aggregate — matches a no-crash run.
