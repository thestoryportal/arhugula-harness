## Change-note (v1.52 → v1.53)

**Scope of revision.** One new closed enum + two additive model fields + the per-step HITL placement-**removal** semantics at **C-CP-06 §6.2 / C-CP-17 §17.1 / C-CP-19 §19.1**: a new `LoosenablePlacementKind` one-member enum (§17.1), an additive `StepOverride.removed_placements: frozenset[LoosenablePlacementKind] = frozenset()` (§6.1), an additive `StepEffectiveBinding.removed_placements` (§6.2) carried by `resolve_step_binding`, and the composer-side application semantics (§19.1 / §14.8.2 step 4c). This is the **CP half** of the R-FS-1 standalone arc **`B-HITL-PLACEMENT-PER-STEP-LOOSEN`** (registered at `.harness/beyond-mvp-capability-boundary-ledger.md`; design vetted at `.harness/r-fs-1-final-closure-plan.md` arc (b), C10⊥C11 dyadic council + advisor). The runtime-side application lands in the co-published `harness-runtime` impl (the `hitl_gate_composer` step-4c removal branch + the `placement-removed` audit shape); no runtime-spec contract changes (the composer is impl, the contract amended is the CP-side §6.2/§17.1/§19.1).

**The committed invariant being amended (operator-ratified 2026-06-22).** This is the **first** per-step override that can REDUCE gating — every prior override (`hitl_placement` fold, v1.49) only TIGHTENS. It relaxes the **monotone-HITL** posture: the §17.1 "all cells" `SUB_AGENT_BOUNDARY` trigger + the §19.1 `max()`-over-rank floor where `PERSONA_TIER_GATE_LEVEL_FLOOR[SOLO_DEVELOPER] = ASK` makes a sub-agent-boundary gate FIRE at solo. The operator **AUTHORIZED** this relaxation in principle (declined "declare build-complete"; full-spec closure) and **RATIFIED the specific mechanism** ("Ratify as designed" AUQ, 2026-06-22), consciously accepting the bounded residual stated honestly below. This is an X-AL-3 **explicit** committed-invariant amendment (the v1.27 §2(d) explicit-extension discipline, mirroring the v1.38 per-step-ROLE §14.5.3-invariant relaxation precedent), NOT a silent absorption — co-published with a `.harness/clearance/` marker per workspace `CLAUDE.md` §11.4.

**The bounded residual (stated honestly, operator consciously accepted).** Removing a `SUB_AGENT_BOUNDARY` gate downgrades that step's human oversight from **PREVENTIVE** (approve-before-handoff) to **DETECTIVE** (audited-after): the parent→child handoff proceeds without a gate, and the only remaining containment is the mandatory fail-closed audit entry. This is a real safety-posture change for the removed cell. It is bounded by: (i) **solo-developer tier ONLY** (team = registered follow-on, multi-tenant-compliance structurally foreclosed — the composer never applies the knob there); (ii) the **hard floors are preserved** — `per_tool` / `mcp_trust` (never override-able per the U-CP-91 commitment) + `blast_radius` ABOVE local-mutation clamp the removal automatically (a removal on a high-blast / deny-tier-tool / untrusted-MCP dispatch is REFUSED, the gate fires); (iii) **opt-in + every applied removal auto-audited fail-closed** (a removed preventive gate NEVER goes live un-audited).

**The mechanism is NARROW (much narrower than "per-step loosen any gate").** (1) The loosenable set is `{SUB_AGENT_BOUNDARY}` ONLY — `PRE_ACTION` is **structurally excluded** (it is the §19.1 `_hitl_required` floor-evaluation call-site; removing it would leave the `mcp_trust`/`per_tool`/blast floors intact-but-UNCONSULTED — the bypass-seam; the §19.5 `HITLAutoApprovePolicy` already provides the safe in-`max()` PRE_ACTION loosening), and `VALIDATOR_ESCALATION` is excluded (it fires via the §14.15 validator-outcome re-entry path, not a wrap-time placement → a wrap-time removal is a wrong-layer no-op). The exclusion is at the TYPE (`LoosenablePlacementKind` is a closed one-member enum), not a runtime guard. (2) **Remove-not-replace** — a typed named-position removal, never attribute-tuning (a `tool_filter`-narrowing replace silently ungates other tools while the position reads "present" — the v1.49 docstring footgun). (3) **Floor-clamp is load-bearing, not vacuous** — the `SUB_AGENT_BOUNDARY` composer genuinely computes `gate_level()` with the blast/`per_tool`/`mcp_trust` floors, so the removal overrides ONLY the persona human-oversight-at-handoff floor (+ the `blast_radius` floor at the LOCAL_MUTATION cell, per the ratified `{read-only, local-mutation}` scope); the hard floors clamp it.

**Additive, default byte-identical, no other invariant sacrificed.** `removed_placements` defaults `frozenset()`; absent the opt-in, `resolve_step_binding` + `fold_step_hitl_placements` (the v1.49 ADD-only fold, UNTOUCHED) are byte-identical + monotone. The removal is a SEPARATE binding-carried directive honoured at the composer — NOT a fold mutation. It mints no new ADR, fail-class, manifest top-level field beyond `removed_placements`, or CXA edge. Provenance rides `binding.model_dump` at the WIRED per-step override state-ledger entry (§6.6, the v1.38 `agent_role` precedent) — **NO new C-IS-05 §5.2 hash field, NO IS-spec change**. OD ingestion unaffected (the new `placement-removed` audit `response` is a free-string `CPAuditLedgerEntry.response`, not a closed-enum).

**v1.52 + prior body PRESERVED VERBATIM.** All v1.52 content + the entire C-CP-01 … C-CP-29 body (incl. §6.1/§6.2/§6.6, §17.1, §19.1, §19.5) is PRESERVED VERBATIM per the delta-only-spec-file convention. The only changes are the additive enum/fields + the §6.2/§17.1/§19.1 removal semantics below.

## §1 — NEW `LoosenablePlacementKind` enum (C-CP-17 §17.1)

> **`LoosenablePlacementKind` (NEW at v1.53).** The closed set of HITL placements a per-step override MAY opt-in to REMOVE. A `StrEnum` with **exactly one member** — `SUB_AGENT_BOUNDARY = "sub-agent-boundary"` (value verbatim equal to `HITLPlacementKind.SUB_AGENT_BOUNDARY.value`). `PRE_ACTION` and `VALIDATOR_ESCALATION` are **STRUCTURALLY unrepresentable** (not a runtime guard): `PRE_ACTION` is the §19.1 floor-evaluation bypass-seam (excluded; the §19.5 policy is the safe PRE_ACTION loosening), `VALIDATOR_ESCALATION` fires via the §14.15 path (a wrap-time removal is a wrong-layer no-op). Extension of the loosenable set is a Workflow §4.1.2 Class-2 D5 revision.

## §2 — Amended `StepOverride` (C-CP-06 §6.1) — additive `removed_placements`

> `StepOverride` gains an additive field `removed_placements: frozenset[LoosenablePlacementKind] = frozenset()`. The opt-in set of HITL placements *this step* removes — the FIRST override field that can REDUCE gating. Default empty preserves the v1.49 ADD-only behavior verbatim (byte-identical + monotone). Validated by Pydantic `extra="forbid"` like every other `StepOverride` field; an absent field inherits the empty default.

## §3 — Amended `StepEffectiveBinding` (C-CP-06 §6.2) — additive `removed_placements`

> `StepEffectiveBinding` gains an additive `removed_placements: frozenset[LoosenablePlacementKind] = frozenset()`. `resolve_step_binding` carries `override.removed_placements` onto the binding (field-by-field, like `agent_role`/`prompt_version_sha`); an override carrying ONLY a removal still applies (the override state-ledger entry fires). Empty for a step with no override OR an override that omits the removal dimension. The composer reads `binding.removed_placements` (the CP→runtime seam — the carrier rides the already-typed binding the composer consumes; no new cross-axis edge).

## §4 — Per-step removal SEMANTICS (C-CP-06 §6.2 / C-CP-19 §19.1 / §14.8.2 step 4c)

> The per-step `SUB_AGENT_BOUNDARY` removal is **NOT a fold mutation** — `fold_step_hitl_placements` stays ADD-only (a destructive pre-composer deletion would prevent the floor-clamp, since the composer could not floor-clamp a gate it never sees). It is a **binding-carried directive honoured at the `SUB_AGENT_BOUNDARY` composer** (the host-less `c_rt_17`), parallel to how §19.5 `HITLAutoApprovePolicy` lowers floor cells at the `PRE_ACTION` composer. At step 4c, when the gate WOULD fire (`hitl_required` true) AND `SUB_AGENT_BOUNDARY ∈ binding.removed_placements` AND `persona_tier == SOLO_DEVELOPER`:
>
> 1. **Floor-clamp recompute.** Recompute `gate_level()` with `persona_floor_override = AUTO` (+ `blast_floor_override = AUTO` at the LOCAL_MUTATION cell, per the ratified `{read-only, local-mutation}` scope). The `per_tool` and `mcp_trust` floors are NEVER override-able (the U-CP-91 commitment), and the `blast_radius` floor ABOVE local-mutation is not overridden — so they clamp the recompute automatically.
> 2. **Effective ⟺ AUTO.** If the clamped gate is `AUTO` → the removal is **EFFECTIVE**: the gate is skipped + a non-vacuous audit entry is emitted (`response = "placement-removed"`, `gate_level = AUTO`, fail-closed `raise_on_failure=True`).
> 3. **Refused otherwise (decline-mirror).** If the clamped gate is still `ASK`/`DENY` — i.e. `blast_radius` is **above** local-mutation, OR `per_tool` forces the gate, OR an untrusted owning-MCP-host (`mcp_trust` ∈ {L0, L1, L2}) forces it — the removal is **REFUSED**: the gate fires normally (its own gate-fired audit records the preserved oversight; the refusal is observable via a `hitl.gate.sub_agent_boundary_removal_*` span attribute, no duplicate ledger entry).
> 4. **Fail-closed.** A `None` gate decision (partial binding — the hard floors cannot be verified) REFUSES the removal.
> 5. **Solo-only.** At `TEAM_BINDING` / `MULTI_TENANT_COMPLIANCE` the removal is a no-op (team = registered follow-on; multi-tenant structurally foreclosed — the composer never applies the knob), mirroring §19.5 `_policy_floor_overrides`.

## §5 — Monotone-HITL floor amendment (C-CP-17 §17.1 / C-CP-19 §19.1) — the committed-invariant relaxation

> The §17.1 `SUB_AGENT_BOUNDARY` "All cells" trigger + the §19.1 monotone `max()`-over-rank posture are **amended** so that, at `SOLO_DEVELOPER` and per an explicit per-step opt-in, the **persona-tier** human-oversight-at-handoff floor MAY be removed for a `SUB_AGENT_BOUNDARY` gate — subject to the §4 floor-clamp. The amendment is **bounded to the persona floor at this one placement**: it does NOT touch the §17.1 `PRE_ACTION` / `VALIDATOR_ESCALATION` rows, does NOT make the `per_tool`/`mcp_trust` floors override-able (U-CP-91 preserved verbatim), and does NOT loosen any non-solo tier. The cross-deployment-monotonicity invariant (C-CP-19 §19.x) is preserved at team/multi-tenant. **Residual:** for a removed cell, oversight is PREVENTIVE→DETECTIVE (the §-change-note residual) — the mandatory audit is the containment; the operator consciously accepted this at ratification.

## §6 — Provenance (C-CP-06 §6.6) — no new §5.2 / IS hash

> `removed_placements` rides `binding.model_dump(...)` into the WIRED per-step override state-ledger entry's outcome-hash (the same provenance surface as `agent_role`/`prompt_version_sha`/`model_binding_override` per §6.6), so a per-step removal opt-in is captured in that entry's hash-chained outcome — **live step-level provenance, NOT the run-level C-IS-05 §5.2 procedural-tier hash** (which stays run-level). No new IS field, no §5.2 change, no IS-spec amendment. The applied-removal audit entry (`response = "placement-removed"`) is the runtime forensic record, distinct from the §19.5 `response = "approve"` auto-approve skip.
