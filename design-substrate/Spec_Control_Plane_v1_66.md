The runtime tool dispatcher's directive consumption (key-bind at the §14.22 fence gate: SKIP_AS_FIRED / RE_FIRE / ABORT) is UNCHANGED — it already keys on the per-`(run, step, tool)` `idempotency_key`. ## §1 — The per-branch-DISTINCT effect-fence resolution map

> **The build (C-CP-26 §26.8).** `ResumeContext` gains an additive field `effect_fence_resolutions: dict[str, EffectFenceResolution] | None` (default `None`) and a pure resolver method `effect_fence_resolution_for(idempotency_key) -> EffectFenceResolution | None`. The resolver is the single source of truth for "what did the operator answer for THIS branch's fence?": the `effect_fence_resolutions` map entry for `idempotency_key` if present, else the uniform `effect_fence_resolution` default; `None` when neither is supplied. It is a pure lookup-with-fallback (no control-flow branch on "which mode"): a `None` map and a map-without-this-key both fall through to the single default, so the v1.65 single-field behavior is preserved byte-for-byte when no map is supplied.
>
> **The consume sites (fan-out only — two sites).** Both fan-out resume sites (`_execute_parallelization` for PARALLELIZATION peers; `_execute_orchestrator_workers` for ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION workers) PEEK (non-consuming — the runtime HITL composer retains its one-shot consume) the `ResumeContext` off the `ResumeContextHolder` and, per fence-paused branch, call `effect_fence_resolution_for(branch_key)` (the branch's held-reserve key, from `effect_fence_paused_branches[*].idempotency_key`). The resulting per-branch `EffectFenceResolutionDirective(resolution=…, idempotency_key=branch_key)` is threaded onto that branch's hash-inert `StepExecutionContext.effect_fence_resolution` — so two fence-paused branches in one pause can carry DIFFERENT resolutions. None for a branch (no map entry AND no uniform default) → that branch re-pauses INERT (the decline-mirror), independent of its siblings.
>
> **The LINEAR path is excluded (and why).** A LINEAR effect-fence pause has exactly ONE held reserve key (one TOOL_STEP), so per-branch-DISTINCT resolution is structurally inapplicable there. The linear resume (`_execute_workflow_body`, §14.22.9) consumes the single `effect_fence_resolution` field VERBATIM (preserved byte-for-byte) — it is not changed to read the map. A map supplied for a linear pause is inert (the linear consume reads only the single field); the resolver method `effect_fence_resolution_for` exists uniformly on `ResumeContext` but is called only at the two fan-out sites. This keeps the cleared/shipped linear effect-fence mechanism untouched (surgical-changes discipline) while the asymmetry is documented here so it is not a future-confusion phantom.
>
> **ABORT keeps its run-level-terminal semantic (the load-bearing interaction).** v1.65 §1(b): an `EffectFenceResolution` of ABORT forces `RunStatus.FAILED` tier-agnostically, BEFORE the pause path. That semantic is UNCHANGED. Consequently a map containing an ABORT entry (e.g. `{k0: RE_FIRE, k1: ABORT}`) does NOT yield independent per-branch dispositions — the ABORT dominates and the run FAILs (consistent with ABORT's meaning: "the operator cannot vouch for at-most-once → stop the run"). The genuinely-independent per-branch dispositions this arc delivers are therefore **SKIP_AS_FIRED vs RE_FIRE** (the two "continue" resolutions), which compose freely across branches. Per-branch-SCOPED abort (fail just ONE branch, let the siblings the operator CAN vouch for resolve) is a genuinely DIFFERENT capability the harness lacks today — it is split off + registered (§2), NOT silently absorbed.
>
> **Partial-map iterative composability.** A map answering SOME paused branches but not others (no uniform fallback) resolves the answered branches terminal in the NEW snapshot while the unanswered branches re-pause INERT carrying their residual — so the operator can resolve a multi-branch fence pause ITERATIVELY across resumes (answer some now, the rest in a later resume). Witnessed by-execution (the answered-SKIP branch becomes terminal, the new snapshot holds only the still-unanswered branch).

## §2 — Decompose-at-open determination + registered follow-on + R-FS-1 closure semantics (FULL-SPEC)

> **Decompose-at-open determination (why this is a WHOLE close of the per-branch-DISTINCT capability).** This arc's registered scope (v1.65 §3) is "resolving two fence-paused branches DIFFERENTLY in one resume" via a key→resolution map + per-branch lookup. That capability is delivered in full for the SKIP_AS_FIRED / RE_FIRE cross-product (the genuinely-independent dispositions). The grounding that makes the close honest: (a) keyed by `idempotency_key` (uniform with the dispatcher's per-`(run, step, tool)` key-bind); (b) `ResumeContext` is constructed DIRECTLY at `api.resume(resume_context=…)` — there is NO hand-listed loader/projection that could silently drop the new field (the #738 `WorkflowManifestLoader` trap is genuinely absent here, verified); (c) DECENTRALIZED_HANDOFF and EVALUATOR_OPTIMIZER are single-owner-sequential (they cannot hold MULTIPLE fence-paused branches in one pause) → no cross-topology residual; the only multi-branch-fence topologies are the two fan-out sites, both covered. The ONE residual grounding revealed is the ABORT-scoping capability (below) — named + registered, so the accounting is net-zero, not an optimistic −1.
>
> This delta CLOSES the parent arc **`B-FANOUT-EFFECT-FENCE-PER-BRANCH-RESOLUTION`** (the per-branch-DISTINCT SKIP/RE_FIRE map) + registers ONE narrower follow-on (NAMED + registered, never silently absorbed):
>
> - **`B-FANOUT-EFFECT-FENCE-PER-BRANCH-SCOPED-ABORT`** (NEW, registered, `operator_gated` decided at open) — per-branch-SCOPED abort. Today an `EffectFenceResolution` of ABORT (in the single field OR a map entry) forces the WHOLE run terminal FAILED (v1.65 §1(b), preserved). A genuinely-distinct capability is to abort just ONE fence-paused branch (record it failed/degraded) while the SIBLING branches the operator CAN vouch for resolve (SKIP_AS_FIRED / RE_FIRE) and the run folds survivors per `cascade_policy`. This is a NEW tier/disposition semantic (a per-branch failure-isolation beyond the shipped run-terminal ABORT) — likely a new `EffectFenceResolution` value or a per-branch abort-scope flag + the cascade reaction; whether it sacrifices a committed semantic (ABORT-is-run-terminal) is decided at open. Surfaced during this build (advisor flagged the ABORT-is-terminal × per-branch interaction).
>
> `closure_gate.py` G1.1 (`standalone_registered + standalone_gated == 0`) was **6 + 0**; after this delta it is **6 + 0** (one closes, one registers — net-zero) → R-FS-1 stays ACTIVE. The R-FS-1 follow-ons keeping the program ACTIVE (still **6**): `B-FANOUT-CRASH-RESUME-MAYBE-RAN-SUBAGENT`, `B-FANOUT-CRASH-RESUME-MAYBE-RAN-UNFENCED-EXTERNAL`, `B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT`, `B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-EFFECT-BEARING`, `B-FANOUT-CRASH-RESUME-ORCHESTRATOR-PROCEED-RESIDUAL`, and the NEW `B-FANOUT-EFFECT-FENCE-PER-BRANCH-SCOPED-ABORT`. This is the honest FULL-SPEC accounting — it does not declare the per-branch-resolution family resolved-whole while the ABORT-scoping capability remains genuinely open.
