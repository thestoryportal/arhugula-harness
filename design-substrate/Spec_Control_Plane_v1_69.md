## Change-note (v1.68 → v1.69)

**Scope of revision.** Three CP surfaces in `harness_cp.workflow_driver`, all on the ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION orchestrator (`steps[0]`) sequential-dispatch path — the build of the registered R-FS-1 standalone arc **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-EFFECT-BEARING`** (registered at v1.64 §3 as the orchestrator analogue of the worker effect-bearing maybe-ran split):
1. `_determine_fanout_resume` (the orchestrator-maybe-ran classifier) — the v1.64 effect-bearing fail-closed (`fan-out-crash-resume-orchestrator-maybe-ran`) is RELAXED for a fence-recoverable orchestrator kind;
2. the orchestrator dispatch site (`_execute_orchestrator_workers`, the sequential `_orch_dispatcher.dispatch(...)` + its `except`) — composes a §26.2 `EFFECT_FENCE_AMBIGUOUS` pause when the orchestrator's own dispatch raises the runtime effect-fence ambiguous error;
3. the orchestrator context construction (the NEW resume→orchestrator application site) — threads the operator's key-bound `EffectFenceResolution` onto the orchestrator's `StepExecutionContext.effect_fence_resolution`.

**The capability gap it closes.** v1.64 (`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-RESOLUTION`) re-dispatched a maybe-ran orchestrator FRESH only when its dispatch-time kind was re-fire-safe (`{DECLARATIVE_STEP, INFERENCE_STEP}` — no external effect), and FAILED CLOSED for an effect-bearing orchestrator (its effect may have landed; re-dispatching `steps[0]` would double-fire). The orchestrator `steps[0]` kind is UNCONSTRAINED (admissibility does not foreclose an effect-bearing orchestrator — a reachable gap confirmed at the parent arc by grep), so a maybe-ran TOOL_STEP / MANAGED_AGENTS orchestrator terminated FAILED. This delta RECOVERS it: those two kinds reach a runtime fence at their OWN sink, so re-dispatching re-reaches the auto-active fence (at-most-once), and the genuinely-ambiguous case (the fence lost the reserve + found no captured output) routes to a §26.2 pause for operator resolution rather than failing closed.

**The mechanism (mirrors the worker `B-FANOUT-CRASH-RESUME-MAYBE-RAN-EFFECT-BEARING` v1.65 two-half shape).**
- **Classification relaxation (the crash-resume half).** A maybe-ran orchestrator whose DISPATCH-MARKER kind is fence-recoverable (`{TOOL_STEP, MANAGED_AGENTS}`) AND whose RESUMED `steps[0].step_kind` is the SAME fence-recoverable kind is NO LONGER failed closed — `_determine_fanout_resume` returns `None` (re-run the whole fan-out fresh in the pristine window), so the orchestrator re-dispatches into the auto-active fence, which SPLITS at the sink: suppress-and-continue (the fence captured the output ⟹ effect completed), ambiguous-PAUSE (below), or fresh-fire (the reserve is absent ⟹ the prior attempt crashed before reserving ⟹ did not fire). The **same-kind guard** (marker kind == resumed kind, both recoverable) is the changed-kind protection inherited from the worker `_fence_unrecoverable_maybe_ran_indices` (v1.65/v1.67): a cross-kind swap (TOOL_STEP ⇄ MANAGED_AGENTS) or a change to a non-recoverable kind would re-dispatch into a DIFFERENT sink (or none) and silently abandon the original effect's ambiguity → fail closed. SUB_AGENT_DISPATCH / un-kinded / orphaned-marker orchestrators STAY fail-closed (unchanged).
- **The ambiguous-PAUSE half (the §26.2 route + the NEW resume→orchestrator application site).** When the orchestrator's own re-dispatch raises the runtime `EffectFenceAmbiguousUncommittedError` (C-RT-31 §14.22; name-matched at the dispatch boundary, since `harness-cp` cannot import `harness-runtime`), and a `PauseResumeProtocol` is bound + the run is pause-resumable + a STRICT tier (`cascade_policy is not PROCEED`), the orchestrator dispatch composes a §26.2 `EFFECT_FENCE_AMBIGUOUS` `PauseSnapshot` carrying the new `orchestrator_effect_fence_resume` carrier (the held reserve's `idempotency_key` + the orchestrator `step_id`/`step_kind` guards). Else it falls through to the existing FAILED return (behaviorally the pre-arc fail-closed; only the disposition differs — the linear path's two-case split). On `api.resume`, `_execute_orchestrator_workers` reads the carrier and threads the operator's `EffectFenceResolution` (key-bound to the orchestrator's reserve) onto the re-dispatched orchestrator's `StepExecutionContext.effect_fence_resolution` — the NEW application site (the linear effect-fence resume threads its directive at the step loop, which the orchestrator-workers strategy does not reach). The runtime fence consumes it: RE_FIRE → clear the claim + re-dispatch fresh (then the workers fan out fresh, none ran); ABORT → the fence raises `EffectFenceAbortedError` → terminal FAILED (never a re-pause).

**SKIP_AS_FIRED is REJECTED for an orchestrator (palette = RE_FIRE / ABORT).** The linear/worker palette includes SKIP_AS_FIRED (proceed with empty output, the effect's data is gone). For an orchestrator that is UNSOUND: the orchestrator's output STRUCTURES the fan-out aggregate (`_aggregate_orchestrator_workers`), so an empty orchestrator output would silently fold into a DEGENERATE aggregate while the workers still run — a silent under-contribution, the no-silent-failure class. The resume site REJECTS SKIP_AS_FIRED for an orchestrator fence pause → FAILED (`fan-out-orchestrator-effect-fence-resume-skip-as-fired-unsupported`), the orchestrator NOT re-dispatched. Fail loud, never silently under-execute.

At-most-once is PRESERVED: the fence makes every re-dispatch at-most-once at the sink, and the same-kind + changed-orchestrator guards close the silent-abandonment hole. `operator_gated: false` (additive; resolve the effect-bearing orchestrator maybe-ran via a §26.2 operator-resolution pause; no committed-invariant sacrifice — the design question was the resolution mechanism, now built). ## §1 — The fence-recoverable orchestrator-maybe-ran relaxation (the crash-resume half, C-CP-25 §25.12)

> At `_determine_fanout_resume`, the orchestrator-maybe-ran classifier (the `orchestrator is None ∧ not orchestrator_present ∧ not branches ∧ orchestrator_dispatched` block, v1.64 §1) gains a SECOND relaxation leg AFTER the re-fire-safe leg:
>
> ```text
> _resumed_orch_kind = steps[0].step_kind  # the resumed manifest's orchestrator kind
> if (
>     not _downstream_artifact_present              # pristine window (no cardinality / worker / synthesis artifact)
>     and store.dispatch_instrumented(run_key)      # the dispatch-instrumented stamp (not orphaned)
>     and orchestrator_marker_kind in {TOOL_STEP, MANAGED_AGENTS}   # fence-recoverable DISPATCH-TIME kind
>     and _resumed_orch_kind   in {TOOL_STEP, MANAGED_AGENTS}       # resumed kind ALSO recoverable
>     and orchestrator_marker_kind == _resumed_orch_kind           # same-kind guard (changed-kind protection)
>     and store.orchestrator_dispatched_step_id(run_key) == str(steps[0].step_id)  # same-step_id guard (the fence key includes step_id — Codex [P1])
> ):
>     return None   # re-run the whole fan-out fresh → the orchestrator re-dispatches into the auto-active fence
> ```
>
> The conjuncts are the orchestrator analogue of the worker `_fence_unrecoverable_maybe_ran_indices` (v1.65 §3 / v1.67): membership in the fence-recoverable set (the original effect reached a fence at its own sink — the runtime tool fence for TOOL_STEP, the §14.20 vendor-session fence for MANAGED_AGENTS) + the same-kind equality guard (a cross-kind swap re-dispatches into a different sink → the original effect's ambiguity is silently abandoned → fail closed). The **same-step_id guard** (out-of-family Codex [P1]) is load-bearing for the effect-bearing case: the runtime fence key INCLUDES `step_id`, so a maybe-ran orchestrator re-supplied at the same kind but a CHANGED `step_id` (rename / reorder) would compose a DIFFERENT fence key, miss the held claim, and double-fire the original effect — the recorded dispatch-time `step_id` (already stored by `record_orchestrator_dispatched`, now read by `orchestrator_dispatched_step_id`) must equal the resumed `steps[0].step_id`. The re-fire-safe leg (v1.64) needs no step_id guard (no external effect to double-fire). The fence is AUTO-ACTIVE because a fan-out crash-resume is reachable ONLY for `_FANOUT_REPLAY_ENGINE_CLASSES` (a subset of the runtime's durable-auto-fence engine classes) and the orchestrator context inherits the run `engine_class`. SUB_AGENT_DISPATCH (recursively fenced at the child's sinks — a larger mechanism), un-kinded markers (presence ≠ validity), and orphaned markers without the dispatch-instrumented stamp STAY fail-closed (`fan-out-crash-resume-orchestrator-maybe-ran`, unchanged).
>
> **Verification provenance (read-verified parity, NOT a real-runtime-fence orchestrator e2e).** The orchestrator introduces NO new fence logic — it reaches the SAME runtime tool / managed-agents fence the worker path uses, via the SAME dispatcher (`run_engine_class` set on the orchestrator context, key = `orchestrator_idempotency_key`, deterministic across the crash — verified by read). The fence's at-most-once suppress / ambiguous-PAUSE / fresh-fire BEHAVIOR is proven by the runtime `test_effect_fence.py` + `test_managed_agents_dispatch_effect_fence.py` + the worker real-fence witnesses; the CP witnesses here exercise the REAL `_execute_orchestrator_workers` driver composition path with the fence error name-matched (the established worker "real-fence witness" convention = real driver path + injected fence error), NOT the real runtime fence reaching the orchestrator. A real-runtime-fence orchestrator crash-resume e2e is the read-verified-parity residual (no new fence behavior to witness, only the same-dispatcher reach, which is structural).

## §2 — The orchestrator §26.2 pause + the NEW resume→orchestrator application site (C-CP-25 §25.12 / C-CP-26 §26.2)

> **The carrier (a 6th `PauseSnapshot` top-level resume carrier).** `OrchestratorEffectFencePausedResumeState(idempotency_key, step_id, step_kind)` is carried on `PauseSnapshot.orchestrator_effect_fence_resume` (default-None; NEVER co-set with the five existing resume carriers). It is the FIRST-step analogue of the linear `effect_fence_resume` (the orchestrator runs first + sequentially, BEFORE any worker and BEFORE its own capture, so its fence pause carries no `FanOutResumeState` — nothing ran), but captured + resumed by the orchestrator-workers strategy, so it additionally carries `step_id`/`step_kind` for the changed-orchestrator guard the key-only linear carrier does not need. It is registered in the `_RESUME_CARRIER_STRATEGIES` topology-mismatch table for `{ORCHESTRATOR_WORKERS, HIERARCHICAL_DELEGATION}` (a snapshot carrying it resumed under any other strategy fails closed). COVERED by `_compute_snapshot_hash` when present (conditional include at the top level); when nested inside a HIERARCHICAL `paused_child_branches[].child_snapshot` it is dropped-when-None by the recursive `_strip_default_fanout_resume_fields` (byte-compat with pre-arc nested snapshots — a brand-new field, so stripping-when-None can only RESTORE byte-compat, never alter an existing non-null nested carrier).
>
> **The pause composition (the dispatch site).** In `_execute_orchestrator_workers`, the orchestrator dispatch `except` intercepts a name-matched `EffectFenceAmbiguousUncommittedError` and composes a §26.2 `EFFECT_FENCE_AMBIGUOUS` `PauseSnapshot` (carrying the carrier built from the error's `idempotency_key` + the orchestrator `step_id`/`step_kind`) when `pause_resume_protocol` is bound ∧ `pause_resumable` ∧ `cascade_policy is not PROCEED`; else it falls through to the existing FAILED. An `EffectFenceAbortedError` (an operator ABORT applied on resume) is NOT name-matched → it falls through to FAILED (terminal, never a re-pause). The pause does NOT drain the orchestrator override buffer (unlike the terminal FAILED path): on resume the orchestrator re-dispatches + re-buffers its per-step override, so draining now would double the entry.
>
> **The resume→orchestrator application site (NEW).** On `api.resume`, before the orchestrator re-dispatch, `_execute_orchestrator_workers` reads `resume_snapshot.orchestrator_effect_fence_resume`. It (a) FAILS CLOSED if the resumed `steps[0]` `step_id`/`step_kind` differs from the captured carrier (`fan-out-orchestrator-effect-fence-resume-changed-orchestrator` — the changed-orchestrator guard; its **empty-body analogue** [out-of-family Codex codex-vs-main] fails closed with the SAME fail-class BEFORE the empty-steps SUCCESS fast path when the resumed body was changed to `[]`, since the dispatch-site guard reads `steps[0]` which an empty body lacks → it would otherwise silently abandon the ambiguous effect + the operator resolution), (b) REJECTS SKIP_AS_FIRED (`…-skip-as-fired-unsupported`, §change-note), and (c) for RE_FIRE / ABORT builds an `EffectFenceResolutionDirective(resolution, idempotency_key)` and threads it onto the orchestrator's `StepExecutionContext.effect_fence_resolution` (the resume-context holder is ALSO peeked when an orchestrator fence resume is present — the orchestrator pause carries no worker fence branches, so the worker peek-gate would otherwise leave the orchestrator resolution unread → an INERT re-pause forever). The runtime tool / managed-agents dispatcher consumes the matching directive at its §14.22/§14.20 fence gate (RE_FIRE → clear + re-fire; ABORT → `EffectFenceAbortedError` → FAILED). None → the fence re-pauses INERT (the decline-mirror, never an auto-re-fire).
