## Change-note (v1.106 → v1.107)

**Trigger.** v1.106 §1.2 property 4 fixed the identical uniform-fallback safety gap for the NEW `hitl_responses`/`hitl_response_for` mechanism, but its own text states: "Deliberately NOT extended to `effect_fence_resolution_for`/`effect_fence_resolutions`... it ships the identical uniform-fallback-to-every-unaddressed-branch safety gap, already SHIPPED and CLEARED prior to this arc... registered as `B-70`." This delta builds exactly that deferred fix.

**The defect (confirmed by direct grounding).** `harness-cp/src/harness_cp/workflow_driver.py`'s LINEAR consume site reads the singular `resume_context.effect_fence_resolution` independently at EVERY `execute_workflow` recursion depth whose own `resume_snapshot.effect_fence_resume is not None`, with no cross-depth/cross-branch uniqueness check. If two or more distinct locations in one resume tree are simultaneously effect-fence-paused (e.g. a nested child's own linear pause co-occurring with a top-level or sibling pause), an operator supplying only the uniform `effect_fence_resolution` (no keyed map) has that single SKIP_AS_FIRED/RE_FIRE/ABORT/ABORT_BRANCH judgment applied to ALL of them — silently wrong for any location whose correct resolution differs. The fan-out-peer `effect_fence_resolutions` map itself already provides correct per-branch addressing (keyed by `idempotency_key`, globally unique); the gap is specifically in the UNIFORM FALLBACK's lack of a "am I the only one waiting" restriction, the identical shape as the pre-B-39 `hitl_response` gap.

**Why this needs a spec property, not a pure impl-to-cleared-spec fix.** Restricting when the auto-fallback applies is an observable CONTRACT change to a currently-shipped, P5-CK-cleared mechanism (whether a given resume auto-resolves or safely re-pauses INERT) — the same class of change v1.106 §1.2 property 4 itself was. Per workspace `CLAUDE.md` §4.4 (X-AL-3), this is design-substrate-gated, not a Phase-7 code fix; `B-70`'s own register row was correctly flipped from `registered_finding` to `design_substrate_gated` at the grounding pass that produced this fork.

## §1 — Multi-branch effect-fence-resolution fallback-safety invariant (closes B-70)

**§1.1 The property (CONTRACT — binding on the impl leg; wiring is NOT specified here, mirrors v1.106 §1.3's own discipline).** For a given resume cycle, let the **"unaddressed effect-fence-pause set"** be every location in the resume tree, across all THREE existing effect-fence-pause carriers — (a) the LINEAR path's own `resume_snapshot.effect_fence_resume` (if set — `EffectFenceResumeState`, which ALREADY carries its own `idempotency_key: str`, per-`(run, step, tool)`, per its existing field); (b) the ORCHESTRATOR's own `resume_snapshot.orchestrator_effect_fence_resume` (if set — `OrchestratorEffectFencePausedResumeState`, the FIRST-step analogue populated by `ORCHESTRATOR_WORKERS`/`HIERARCHICAL_DELEGATION` when the orchestrator's OWN dispatch, not a worker's, fence-pauses; a 6th top-level `PauseSnapshot` carrier, never co-set with the other five per its own docstring); and (c) every fan-out `effect_fence_paused_branches` entry (`PARALLELIZATION` peers or `ORCHESTRATOR_WORKERS`/`HIERARCHICAL_DELEGATION` workers) — at any recursion depth, whose own `idempotency_key` is NOT a key in `effect_fence_resolutions` (an absent map counts every location as unaddressed). **This requires the LINEAR site to become map-addressable** (round-3 correction, below): it MUST consult `effect_fence_resolution_for(effect_fence_resume.idempotency_key)` — reusing the ALREADY-EXISTING `idempotency_key` field, no new carrier — rather than reading `resume_context.effect_fence_resolution` directly, so a LINEAR pause's map entry (if the operator supplies one) genuinely addresses it, symmetric with the ORCHESTRATOR and fan-out sites.

Round-1 correction (out-of-family `just codex-review-uncommitted`, same-day): a first draft of this definition omitted (b) — the ORCHESTRATOR's own fence-pause carrier is a DISTINCT top-level `PauseSnapshot` field from the worker-level `effect_fence_paused_branches` list, and the shipped consume site at `workflow_driver.py` (~line 11044) ALSO calls `effect_fence_resolution_for`, so omitting it would have left exactly the cross-location misapplication this property exists to close.

Round-2 correction (out-of-family `just codex-review-uncommitted`, second same-day pass): a draft after round 1 phrased the safety clause as "MAY resolve a location's `effect_fence_resolution_for(idempotency_key)` call ONLY when...", which is a no-op for the LINEAR site — it never calls that method (per `Spec_Control_Plane_v1_66.md` §1, the map is structurally inert there today) — so a co-existing fan-out/orchestrator pause could correctly re-pause INERT under the rule while the LINEAR site kept consuming the uniform value unconditionally regardless, reproducing the exact hazard on the LINEAR side. That round's fix (making a LINEAR pause UNCONDITIONALLY a member of the unaddressed set, never excludable) over-corrected: it is REPLACED by round 3 below.

**Round-3 correction (out-of-family `just codex-review-uncommitted`, third same-day pass) — round 2's "unconditionally unaddressed" fix was itself defective.** Because round 2 counted a LINEAR pause as unaddressed REGARDLESS of any map entry, TWO simultaneously-paused LINEAR locations (e.g. two independent nested children, each its own simple linear workflow, each hitting its own tool-step effect fence) could NEVER be resolved by ANY operator input — the unaddressed set would always have size ≥2 for that pair, forcing both to re-pause INERT forever, even if the operator supplied a correctly-keyed, distinct `effect_fence_resolutions` entry for each — a genuine LIVENESS violation (unrecoverable resume), worse than the safety gap this property exists to fix. Root cause: the LINEAR carrier `EffectFenceResumeState` ALREADY exposes its own `idempotency_key` (verified by direct read, `pause_resume_protocol_types.py` line 541) — the map is inert TODAY only because the CONSUME SITE chooses to read the raw field instead of calling the resolver method with that key, not because the carrier lacks the key. §1.1 above is corrected accordingly: the LINEAR site becomes genuinely map-addressable (reusing its existing key, calling the existing resolver method) rather than permanently excluded from addressing — the uniform definition above (membership determined by map-key presence, uniformly across all three carriers, per (a) below) replaces round 2's carve-out.

- **(a) Safety.** The uniform `effect_fence_resolution` value MAY be applied at a location — whether via the LINEAR site's (now map-consulting) resolution, the ORCHESTRATOR's `effect_fence_resolution_for(idempotency_key)` call, or a fan-out branch's `effect_fence_resolution_for(idempotency_key)` call — ONLY when that location is the SOLE member of the unaddressed effect-fence-pause set this cycle. When the unaddressed set has 2+ members, EVERY member MUST re-pause INERT rather than receive the uniform default (never an auto-re-fire, never a cross-location misattribution of a SKIP_AS_FIRED/RE_FIRE/ABORT/ABORT_BRANCH judgment intended for a different location). This is a property of the RESOLUTION OUTCOME, not a prescription of implementation technique — HOW the resolver determines set membership across the full resume tree (a tree-walk of `paused_child_branches` collecting every nested `effect_fence_resume`/`orchestrator_effect_fence_resume`/`effect_fence_paused_branches` entry, or any equivalent), and HOW the LINEAR site's map consultation is wired, is impl discretion; the rule only fixes WHAT the outcome must be.
- **(b) Liveness.** A transitively-paused container/ancestor branch (§2 below — never itself gate-owning, and never itself holding an `idempotency_key`) MUST still be traversed/re-entered regardless of the effect-fence-pause set's contents; it is NEVER a member of the unaddressed set above.
- **No property-5 equivalent.** Unlike v1.106 §1.2 property 5 (which formally distinguishes HITL gate-owning branches from transitively-paused containers because BOTH shapes can appear in the SAME `hitl_responses` addressing surface), this mechanism needs no such split — see §2's grounding. Every member of the unaddressed effect-fence-pause set is already gate-owning by construction; the resolver does not need to distinguish container from gate-owning locations the way the `hitl_responses` resolver does.

**Round-4 correction (out-of-family `just codex-review-uncommitted`, fourth same-day pass) — `resume_handle` scope limit, mirroring `B-69`'s already-registered HITL analogue.** For `api.resume(resume_handle=...)` (crash-recovery: the caller supplies only a `workflow_id`; the runtime reads the latest durably-journaled snapshot itself, per `Spec_Harness_Runtime_v1.md` §14.14.8), the caller has NO prior `RunResult.pause_snapshot` to read a paused location's `idempotency_key` from BEFORE `resume_context` must be constructed — identical to `B-69`'s finding for `hitl_responses`. When 2+ effect-fence-pause locations are simultaneously outstanding this cycle, such a caller cannot construct a correctly-keyed `effect_fence_resolutions` map addressing them individually and is limited to the single-pause case (the uniform `effect_fence_resolution` field, valid per (a) above only when exactly one location is paused this cycle). This is a registered, NOT-silently-dropped scope limitation.

**Round-5 correction (out-of-family `just codex-review-uncommitted`, fifth same-day pass) — round 4's `B-69` citation was aspirational, not accurate.** Round 4 claimed the SAME durable-pause-state read accessor `B-69` already registers would close this gap too, generalized to expose any paused location's identity. Out-of-family review found `B-69`'s own registered close-out, as then-written, named only HITL child `run_id`s — a caller building `effect_fence_resolutions` needs `idempotency_key`s, a distinct identity kind `B-69`'s prior text did not commit to exposing. Fixed by widening `B-69`'s own `.harness/forward-register.yaml` row (summary + close_out) to explicitly cover both identity kinds, so this citation is now accurate rather than merely asserted; no new `B-*` row is filed.

**§1.2 Scope.** This property amends ONLY the fallback-safety behavior of the ALREADY-SHIPPED effect-fence resolution mechanism — `effect_fence_resolution_for`/`effect_fence_resolutions` (C-CP-26 §26.8.1, built at `Spec_Control_Plane_v1_66.md` §1, unamended by `Spec_Control_Plane_v1_73.md`'s `ABORT_BRANCH` addition) — extended per (a)'s round-3 correction so the LINEAR site ALSO consults this EXISTING mechanism (reusing its EXISTING `idempotency_key` field) instead of reading `effect_fence_resolution` directly; this is map-consultation wiring, not a new field or method. NO field is added to `ResumeContext`. NO change to `EffectFencePausedBranchResumeState`, `FanOutResumeState`, `PeerFanOutResumeState`, `OrchestratorEffectFencePausedResumeState`, `EffectFenceResumeState`, or any `EffectFenceResolution` enum member. NO change to `hitl_responses`/`hitl_response_for` (v1.106, unamended by this delta) or to `attempt_resume`'s signature (unchanged since v1.16 §26.8.5).

## §2 — Grounding: why no property-5 (gate-owning-vs-container) equivalent is needed

Confirmed by direct read, two ways:

1. **`EffectFencePausedBranchResumeState`'s own docstring** (`harness_cp/pause_resume_protocol_types.py`) states `step_kind` is "always tool-step in production — only a TOOL_STEP's dispatch reaches the runtime tool fence." An ancestor `SUB_AGENT_DISPATCH` branch merely forwarding a nested descendant's pause is captured via the generic `SubAgentChildPausedError` → `PausedChildBranchResumeState` path (any `RunStatus.PAUSED` child, any `pause_reason`) — NEVER via `EffectFencePausedBranchResumeState`, which is populated only at the true fence-holding (tool-step) location.
2. **`Spec_Control_Plane_v1_106.md` §2 (REMOVED at correction pass)** states this canonically: "the effect-fence mechanism does not cross a recursion boundary the way HITL child-pause delivery does" — `idempotency_key` is already globally unique per held reserve, independent of recursion depth, so there is no `branch_path`/`run_id`-style keying collision to fix (the reason v1.106 §1.2 property 5 exists for `hitl_responses` in the first place).

Every captured `effect_fence_resume`/`orchestrator_effect_fence_resume`/`effect_fence_paused_branches` entry is therefore inherently gate-owning by construction — `OrchestratorEffectFencePausedResumeState`'s own docstring confirms it is likewise populated only at the true fence-holding dispatch (the orchestrator's OWN `steps[0]` dispatch, never a forwarded nested pause), the FIRST-step analogue of the LINEAR-path carrier, not a container/ancestor shape. §1.1's safety+liveness invariant is complete without a property-5 analogue.
