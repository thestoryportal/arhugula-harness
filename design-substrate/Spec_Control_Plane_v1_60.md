## §1 — Reserve-before-dispatch strict-tier incomplete-crash recovery (C-CP-25 §25.12 / §25.15)

> **The reserve-before-dispatch marker.** For the strict tiers (PAUSE + CASCADE_CANCEL), the driver writes a durable, fsynced per-(run, branch) DISPATCHED marker (C-RT-32 `record_branch_dispatched`) STRICTLY BEFORE each branch body dispatches — synchronously, atomic with the dispatch scheduling (no yield between the marker write and the `ensure_future` dispatch), so a sibling cascade-cancel cannot land after the marker but before the dispatch (no false-positive marker; the cancel still lands at either the not-yet-dispatched `cancelled` boundary or the in-flight `completed`/`timed_out` boundary). The marker is the fan-out analogue of the §14.22 effect-fence's `try_reserve` at branch granularity: within an instrumented run, **marker-absent ⟺ effect-not-fired**. PROCEED writes NO marker (its recovery is unchanged).

> **The strict-tier incomplete-recovery classification (resume).** On a strict-tier crash-resume (`resume_snapshot is None`, replay-capable ∧ store-bound) with an INCOMPLETE recovered branch set (some declared ordinal absent), the driver classifies the absent branches via the markers:
> - **maybe-ran** = `present_dispatched_indexes − recovered_branch_indexes` — a branch that BEGAN dispatch (marker present) but whose terminal record is absent (the fire→capture window). If this set is non-empty → fail closed (`fan-out-crash-resume-cascade-policy-incomplete-recovery`): the branch's effect may have fired, re-dispatch risks a double-fire on the effect-bearing strict tiers.
> - otherwise (every absent branch is **provably-not-run** — no marker) AND the run is dispatch-instrumented (§2) → CONTINUE: recover the captured branches + re-dispatch ONLY the provably-not-run ones, each first-and-only (the existing pause-resume recovery path).
>
> The classification is index-scheme-agnostic (the `dispatched − recovered` set difference, not a `range(expected)` reconstruction), so it holds identically for the peer (`branch_index = step ordinal`) and orchestrator-workers (`branch_index = 0-based worker ordinal`) carriers.

> **The cardinality-only case.** When NOTHING is readably recovered (`_determine_fanout_resume` → None) but a cardinality marker is present (the fan-out STARTED), the same classification applies: dispatch-instrumented ∧ ZERO dispatch markers → no branch began → re-dispatch all fresh (safe); any dispatch marker → maybe-ran → fail closed.

> **An ERRORED branch is unchanged.** An errored branch (`completed`-no-output) still drives the v1.57 §1 policy semantics FIRST: CASCADE_CANCEL → reproduce FAILED; PAUSE → `pause-trigger-ambiguous`. The reserve-before-dispatch lift applies only to the no-errored-branch INCOMPLETE case.

> **Scope: WORKER/PEER branches only — the orchestrator's own dispatch is OUT.** This slice adds reserve-before-dispatch for fan-out WORKER/PEER branches. The ORCHESTRATOR_WORKERS `steps[0]` orchestrator runs FIRST, sequentially, and is recovered via its own `record_orchestrator` reserve-before-COMMIT capture; its OWN dispatch-before-capture window (the orchestrator fires its effect, then a crash before `record_orchestrator` + the cardinality marker → a fresh re-run re-dispatches `steps[0]`, a potential double-fire on the compliance tier) is a PRE-EXISTING, separate concern (accepted since v1.55/v1.57 — the orchestrator is a sequential dispatch, not a fan-out branch) and is NOT closed by this slice. It is registered as the FULL-SPEC follow-on **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-DISPATCH`** (§4) — named here per FULL-SPEC rather than silently left, since this arc builds "at-most-once for fan-out."

## §2 — Cross-version dispatch-instrumented stamp (the presence-validity guard)

> **The hazard.** The "no marker ⟹ provably not-run" invariant holds ONLY for runs the marker-instrumented code wrote from the start. A crash journal written by PRE-arc code carries NO markers for ANY branch — including a maybe-ran one — so classifying its absent branches "provably not-run" would re-dispatch + double-fire (`[[durable-recovery-presence-validity-scope]]`: presence ≠ validity).

> **The guard.** The driver writes a per-run DISPATCH-INSTRUMENTED stamp (C-RT-32 `record_dispatch_instrumented`) ONCE at fan-out start (co-located with the cardinality marker, before any branch dispatches) on the strict tiers only. The §1 classification trusts the per-branch markers ONLY when the stamp is present; an un-stamped journal (pre-arc, or never-stamped) retains the conservative v1.57 incomplete-recovery fail-closed. This makes the lift forward-safe across the code upgrade that introduces it.
