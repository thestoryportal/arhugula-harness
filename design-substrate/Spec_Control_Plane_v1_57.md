**The key insight (design-vetted: advisor + the §25.15 probe).** The `cascade_policy` governs the run's ON-A-BRANCH-FAILURE semantics. A CRASH is a DIFFERENT event (the host died), so the policy only DIVERGES from "continue the fan-out" when a branch actually FAILED before the crash. A branch failure is captured `completed`-no-output (`output is None`) to the crash-resume store **STRICTLY BEFORE** the `raise` that triggers the `asyncio.TaskGroup` sibling-cancel (the `_cancel_branch` `except Exception` capture precedes the re-raise; the worker analogue mirrors it). The dichotomy is therefore TOTAL — there is no "cancel fired but trigger uncaptured" window:
- crash BEFORE the capture ⟹ no `raise` yet ⟹ no cancel ⟹ the siblings were NEVER cancelled ⟹ re-dispatching them on resume is a FIRST dispatch, not a re-run (no compliance violation; identical to PROCEED's accepted window); AND no errored branch is in the store ⟹ the recovery continues.
- crash AFTER the capture ⟹ the errored branch IS in the store ⟹ the policy's failure semantics apply.

So a single signal — **any recovered branch with `output is None`** (`_determine_fanout_resume` already RAISES on `timed_out`, so in the recovered set `output is None` ⟺ ran-and-errored) — faithfully detects "a branch failure fired the policy." An errored **orchestrator** (`steps[0]`) is NOT a cascade trigger — it returns FAILED directly before any worker dispatches (the §25.12 driver: "cascade_policy governs WORKER failure, not the orchestrator's own dispatch"), so detection over the branch/worker set is complete.

## §1 — Cascade-policy-aware crash-resume recovery (C-CP-25 §25.12)

> On a fan-out crash-resume (replay-capable ∧ store-bound ∧ no explicit pause snapshot), after the branches are recovered, the driver resolves the `cascade_policy` and applies its run-level semantics to the recovered state:
> - **No errored branch recovered** (a clean host-crash mid-fan-out — no policy trigger) → recover + continue (re-dispatch the incomplete branches), for **all three policies**. If a re-dispatched branch then fails, the strategy resolves the policy THEN (the cascade-cancel `TaskGroup` / pause snapshot fires on the actual failure). This LIFTS the v1.55 §2 fail-closed for the common case.
> - **An errored branch recovered** (a branch failure fired the policy before the crash): **`PROCEED`** → PARTIAL (the v1.56 `_recovered_degraded` downgrade, unchanged); **`CASCADE_CANCEL`** → reproduce **`RunStatus.FAILED`** (`fan-out-crash-resume-cascade-cancel`); **`PAUSE`** → fail CLOSED (`fan-out-crash-resume-pause-trigger-ambiguous`, §2).

> **CASCADE_CANCEL reproduces FAILED with NO re-dispatch.** §25.15.1 maps cascade-cancel → FAILED, and obligation 7 forbids re-dispatching a `cancelled` branch. The not-yet-dispatched (cancelled) siblings were NEVER dispatched, so re-dispatching them would RUN their effects (LLM calls / gated tool steps) the `MULTI_TENANT_COMPLIANCE` tier deliberately stopped — "not-yet-dispatched" ≠ effect-free. So the recovery short-circuits to FAILED, re-dispatching nothing. **Audit (the deliberate choice, not inherited):** the recovered branches are NOT ledger-re-materialized on this FAILED path — the §25.12 disposition keystone (the crash-resume store) IS the durable crash-recovery audit substrate (every recovered branch's terminal disposition + output), and a FAILED run produces no aggregate a consumer attests, so the §25.15.2 obligation 3 "no silent landed effect" guarantee is met by the store without a FAILED-only strategy re-materialization mode.

## §2 — PAUSE-trigger-crash stays FAIL-CLOSED (the spec-foreclosed leg)

> A branch failure under `pause` writes a durable `PauseSnapshot` → PAUSED (the pause-resume path, `resume_snapshot is not None`, mutually exclusive with crash-resume). A crash-resume under PAUSE with an errored branch means the pause was triggered but its `PauseSnapshot` write was LOST in the crash. A naive reconstruct from the crash-resume store is **SPEC-FORECLOSED**: §25.15.1 PAUSE is "*Allowed to finish in-flight, then pause*", but a crash-INTERRUPTED store does NOT hold the finished-in-flight branches (the crash cut them mid-flight), so a reconstructed snapshot would resume interrupted-not-finished branches — violating the cleared pause semantics (probe-resolved; advisor). So this leg fails CLOSED (`fan-out-crash-resume-pause-trigger-ambiguous`) → the operator resumes via HITL. A CORRECT reconstruct that honors "finish in-flight, then pause" is the registered **`B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT`** follow-on (a genuine design problem, not a deferral).
