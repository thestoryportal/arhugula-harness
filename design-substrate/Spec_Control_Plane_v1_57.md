For the STRICT tiers — PAUSE (TEAM_BINDING) + CASCADE_CANCEL (MULTI_TENANT_COMPLIANCE) — a crash-resume CONTINUES the fan-out ONLY when the recovery is provably safe: the recovered branch set is **COMPLETE** (every declared ordinal recovered → NOTHING to re-dispatch) AND no branch errored. Every other state fails closed:
- An **errored branch** (a failure fired the policy before the crash — captured `completed`-no-output; `_determine_fanout_resume` already RAISES on `timed_out`, so in the recovered set `output is None` ⟺ ran-and-errored) → the policy's failure semantics: CASCADE_CANCEL → reproduce FAILED (§1); PAUSE → fail-closed-ambiguous (§2).

An absent branch is INDISTINGUISHABLE from one that RAN its effect but crashed BEFORE `_capture_branch_terminal` persisted (the dispatch-before-capture window), so re-dispatching it would risk DOUBLE-FIRING an effect — and branches are effect-**BEARING** (unlike the effect-free synthesis of v1.56). An errored **orchestrator** (`steps[0]`) is NOT a cascade trigger — it returns FAILED directly before any worker dispatches (the §25.12 driver: "cascade_policy governs WORKER failure, not the orchestrator's own dispatch"), so detection over the branch/worker set is complete. The COMPLETE ∧ no-error continue path re-dispatches nothing → it finalizes from the recovered set (trivially safe — VERIFIED by witness, not inferred).

## §1 — Cascade-policy-aware crash-resume recovery (C-CP-25 §25.12)

> On a fan-out crash-resume (replay-capable ∧ store-bound ∧ no explicit pause snapshot), after the branches are recovered, the driver resolves the `cascade_policy`. For the strict tiers (PAUSE + CASCADE_CANCEL) it applies, in order:
> - **An errored branch recovered** (a branch failure fired the policy before the crash): **`CASCADE_CANCEL`** → reproduce **`RunStatus.FAILED`** (`fan-out-crash-resume-cascade-cancel`); **`PAUSE`** → fail CLOSED (`fan-out-crash-resume-pause-trigger-ambiguous`, §2). (`PROCEED` → PARTIAL via the v1.56 `_recovered_degraded` downgrade, the SOLO tier, unchanged.)
> - **Otherwise an INCOMPLETE recovery** (a branch ordinal absent — `len(branches) < worker_count`/`branch_count`) → fail CLOSED (`fan-out-crash-resume-cascade-policy-incomplete-recovery`): an absent branch could be ran-but-uncaptured (the dispatch-before-capture window), so re-dispatching an effect-bearing branch is unsafe for these tiers. Broad incomplete recovery needs at-most-once branch dispatch (reserve-before-dispatch, so an absent branch is provably not-yet-run) — the registered **`B-FANOUT-CRASH-RESUME-STRICT-TIER-INCOMPLETE`** follow-on.
> - **Otherwise (COMPLETE recovery, no error)** → continue: the recovered set is complete, so the strategy finalizes from it, re-dispatching NOTHING (trivially safe). This is the one strict-tier continue path the slice lifts (e.g. a crash after all branches finished but before the run finalized).
>
> Honest scoping: this slice delivers **correct CASCADE_CANCEL→FAILED semantics** (the v1.55 §2 blanket fail-closed becomes the spec-mandated FAILED) + **complete-recovery completion**; the common incomplete-crash recovery for the strict tiers stays fail-closed pending the at-most-once-dispatch follow-on.

> **CASCADE_CANCEL reproduces FAILED with NO re-dispatch.** §25.15.1 maps cascade-cancel → FAILED, and obligation 7 forbids re-dispatching a `cancelled` branch. The not-yet-dispatched (cancelled) siblings were NEVER dispatched, so re-dispatching them would RUN their effects (LLM calls / gated tool steps) the `MULTI_TENANT_COMPLIANCE` tier deliberately stopped — "not-yet-dispatched" ≠ effect-free. So the recovery short-circuits to FAILED, re-dispatching nothing. **Audit (the deliberate choice, not inherited):** the recovered branches are NOT ledger-re-materialized on this FAILED path — the §25.12 disposition keystone (the crash-resume store) IS the durable crash-recovery audit substrate (every recovered branch's terminal disposition + output), and a FAILED run produces no aggregate a consumer attests, so the §25.15.2 obligation 3 "no silent landed effect" guarantee is met by the store without a FAILED-only strategy re-materialization mode.

## §2 — PAUSE-trigger-crash stays FAIL-CLOSED (the spec-foreclosed leg)

> A branch failure under `pause` writes a durable `PauseSnapshot` → PAUSED (the pause-resume path, `resume_snapshot is not None`, mutually exclusive with crash-resume). A crash-resume under PAUSE with an errored branch means the pause was triggered but its `PauseSnapshot` write was LOST in the crash. A naive reconstruct from the crash-resume store is **SPEC-FORECLOSED**: §25.15.1 PAUSE is "*Allowed to finish in-flight, then pause*", but a crash-INTERRUPTED store does NOT hold the finished-in-flight branches (the crash cut them mid-flight), so a reconstructed snapshot would resume interrupted-not-finished branches — violating the cleared pause semantics (probe-resolved; advisor). So this leg fails CLOSED (`fan-out-crash-resume-pause-trigger-ambiguous`) → the operator resumes via HITL. A CORRECT reconstruct that honors "finish in-flight, then pause" is the registered **`B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT`** follow-on (a genuine design problem, not a deferral).
