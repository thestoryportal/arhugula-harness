## Change-note (v1.71 → v1.72)

**Scope of revision.** Two CP surfaces in `harness_cp.workflow_driver`. (1) The `CascadePolicy.PAUSE ∧ _crash_pause_trigger ∧ ¬_crash_complete` crash-resume leg (the v1.71 §1 gate): its classification is widened from "recover ONLY re-fire-safe maybe-ran (omit + re-dispatch fresh)" to "ALSO recover the FENCE-RECOVERABLE maybe-ran (carry into `effect_fence_paused_branches`)". (2) The §25.15 shared classifier `_fence_unrecoverable_maybe_ran_indices`: it gains a marker-`step_id` == resumed-`step_id` conjunct (the #742 crash-time fold-in). This is the build of the registered R-FS-1 standalone arc **`B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT-MAYBE-RAN-FENCE-STEP-ID`** as a WHOLE close.

**The capability gap it closes.** v1.71 lifted the PAUSE-reconstruct fail-closed for re-fire-safe maybe-ran ordinals only; a FENCE-RECOVERABLE (`TOOL_STEP`/`MANAGED_AGENTS`) maybe-ran in the deferred-resume window STAYED fail-closed because the omitted-ordinal re-pause carried NO `step_id` — a same-kind CHANGED-`step_id` `api.resume` would re-dispatch under a DIFFERENT runtime fence key `(parent_idempotency_key, step_id)`, miss the held claim, and DOUBLE-FIRE the maybe-fired effect (out-of-family Codex [P1], #756). This delta recovers that window: the fence-recoverable maybe-ran ordinals are NOT omitted — they are carried into the reconstructed snapshot's `effect_fence_paused_branches`, the disjoint fan-out disposition the v1.65 `B-FANOUT-EFFECT-FENCE-BRANCH-PAUSE` arc built. On `api.resume` the EXISTING material-diff guard validates each carried ordinal's `step_id` + `step_kind` against the resumed manifest (fail-closed on a rename / reorder / kind-swap), then re-dispatches it FRESH into the auto-active runtime effect fence — whose held prior claim makes the re-dispatch at-most-once at the tool sink (suppress-if-captured / ambiguous-PAUSE / fresh-fire-if-claim-absent).

**Why the WORKER carrier is the mirror (the grounding correction to v1.71 §2).** v1.71 §2 registered the follow-on anticipating "a new resume carrier, mirroring the orchestrator's `OrchestratorEffectFencePausedResumeState`". Grounding (advisor full-transcript, BEFORE substantive work) revealed that anticipation is unnecessary: the orchestrator carrier's own docstring names it "the ORCHESTRATOR analogue of the WORKER `EffectFencePausedBranchResumeState`". The orchestrator needed a NEW *top-level* carrier ONLY because `steps[0]` runs FIRST + sequentially, before any worker exists — there is no `FanOutResumeState` to carry, so the absence itself is the ambiguity. That reason does NOT apply to a maybe-ran WORKER ordinal, which lives in the fan-out's `FanOutResumeState`/`PeerFanOutResumeState.effect_fence_paused_branches` tuple. That worker carrier ALREADY holds `(branch_index, step_id, step_kind, idempotency_key)`, and the resume material-diff guard ALREADY validates `step_id` (the `effect-fence-paused-identity-mismatch` fail-class) + `step_kind` (the `effect-fence-paused-kind-changed` fail-class) on BOTH the PARALLELIZATION (`_execute_parallelization`) AND ORCHESTRATOR_WORKERS / HIERARCHICAL (`_execute_orchestrator_workers`) resume paths — verified present on both before the build. So the sound fix is to SYNTHESIZE worker carriers at the reconstruct gate + inject them into the reconstructed snapshot — NO new model, NO new snapshot field, NO new resume guard.

**The mechanism (carry fence-recoverable into `effect_fence_paused_branches`).** At the cascade-policy crash-resume PAUSE leg, the maybe-ran set splits THREE ways via the EXISTING §25.15 classifiers:

```text
_pr_maybe_ran        = store.present_dispatched_indexes(run_key) - recovered
_pr_maybe_ran_unsafe = _refire_unsafe_branch_indices(_pr_maybe_ran, kinds, expected)   # NOT re-fire-safe
_pr_fence_unrecov    = _fence_unrecoverable_maybe_ran_indices(                          # SoT classifier
    _pr_maybe_ran_unsafe, kinds, resumed_kinds, expected,
    dispatched_step_ids=store.dispatched_branch_step_ids(run_key),                      # NEW reader
    resumed_step_ids=resumed_step_ids)
if _pr_instrumented and not _pr_fence_unrecov:                                          # nothing genuinely-unrecoverable
    _crash_pause_reconstruct_no_dispatch = True                                        # re-fire-safe + not-yet-dispatched → OMIT
    _pr_fence_recoverable = _pr_maybe_ran_unsafe - _pr_fence_unrecov                    # TOOL_STEP / MANAGED_AGENTS
    _crash_pause_reconstruct_fence_paused = tuple(                                      # CARRY (NOT omit)
        EffectFencePausedBranchResumeState(branch_index=bi, step_id=marker_step_id[bi],
            step_kind=marker_kind[bi], idempotency_key="") for bi in _pr_fence_recoverable)
else:                                                                                   # SUB_AGENT / un-kinded / out-of-range / crash-time changed-step_id
    return FAILED("fan-out-crash-resume-pause-trigger-ambiguous: … neither re-fire-safe nor fence-recoverable …")
```

The strategy's reconstruct re-pause path APPENDS `_crash_pause_reconstruct_fence_paused` to the reconstructed snapshot's `effect_fence_paused_branches` (empty in a normal pause; the live `effect_fence_paused_dispositions` map is empty in reconstruct mode since no branch dispatched). The re-fire-safe + not-yet-dispatched ordinals are still OMITTED (re-dispatched fresh on resume); the fence-recoverable ordinals are carried (re-dispatched through the guard). The two sets are DISJOINT + bounded by `branch_count`; the resume material-diff guard re-checks disjointness + identity. **NO new strategy code path** — the reconstruct snapshot construction already builds `effect_fence_paused_branches`; this delta only appends the threaded carriers.

**Why `idempotency_key=""` is correct (not a degradation — the derivability finding).** The runtime fence key is `H(domain : parent_idempotency_key : step_id : tool_id)` (runtime §14.9.7 / §14.22) — composed with the opaque `tool_id` living in `step_payload`, which CP CANNOT read (X-AL axis isolation; the same boundary as the v1.65 accepted-parity tool-swap). So CP cannot DERIVE the held reserve's `idempotency_key` at reconstruct time. The carrier therefore holds `idempotency_key=""` (the existing defensive default). This is NOT a degradation: the operator is NEVER asked about a maybe-ran branch at reconstruct time (it was not a pause they saw), so there is no `EffectFenceResolution` to key-bind on the FIRST resume regardless of the key. `api.resume` re-dispatches the branch FRESH into the auto-active fence keyed on the RUNTIME-computed key (not the carried ""); if the prior attempt's claim is held + uncaptured, the fence re-pauses with the REAL key (captured off the runtime `EffectFenceAmbiguousUncommittedError` via the existing v1.65 live path), and a SUBSEQUENT resume key-binds the operator's resolution. At-most-once rides ENTIRELY on (a) the durable fsynced fence reserve (survives the crash) + (b) the resume-side `step_id`/`step_kind` guard — never the carried key.

**§2 — the #742 crash-time fold-in.** The same changed-`step_id` hole exists at LOWER exposure in #742's crash-time `_fence_unrecoverable_maybe_ran_indices` predicate (which recovers a fence-recoverable maybe-ran AT CRASH-TIME): it checked marker-kind == resumed-kind but NOT marker-`step_id` == resumed-`step_id`, so an operator-EDITED crash-resume manifest that kept the kind but renamed the step would re-dispatch under a different fence key. The fix adds the marker-`step_id` == resumed-`step_id` conjunct INSIDE `_fence_unrecoverable_maybe_ran_indices` (the documented single-source-of-truth classifier), fed by the new `dispatched_branch_step_ids` reader + a `_resumed_branch_step_ids_by_ordinal` helper. At the PAUSE-reconstruct the resumed manifest IS the crash manifest, so the conjunct passes trivially (same `step_id`) — it only bites the crash-time edited-manifest case; the deferred `api.resume` timing is covered by the resume-side guard on the carried `effect_fence_paused_branches`. The two timings are DISTINCT, same defect class.

**Why a spec amendment — and why it carries NO new operator gate.** The change relaxes one fail-closed leg for fence-recoverable maybe-ran ordinals + hardens a crash-time predicate; it reconstructs a state shape the harness already produces (a fan-out pause carrying `effect_fence_paused_branches`) and resumes through the existing v1.65 path + guard. It changes NO contract removal, NO closed enum, NO committed invariant; at-most-once is PRESERVED. The arc's registration carried `operator_gated: false` (additive carrier reuse + a same-`step_id` compare; no committed-invariant sacrifice). Co-published with a `.harness/clearance/` marker (CP v1.72) per workspace `CLAUDE.md` §11.4.

## §2 — The #742 crash-time changed-step_id fold-in (C-CP-25 §25.15)

> `_fence_unrecoverable_maybe_ran_indices` (the SoT fence-recoverability classifier shared by the incomplete-recovery + cardinality-only crash-time sites) gains a marker-`step_id` == resumed-`step_id` conjunct: a fence-recoverable ordinal whose dispatch-marker `step_id` (best-effort; `None` on a torn marker → fail closed) differs from the resumed manifest's `step_id` at that ordinal moves to the UNRECOVERABLE set. The fence keys on `(parent_idempotency_key, step_id)`, so a kind-preserving `step_id` change on an EDITED crash-resume manifest would otherwise re-dispatch under a different fence key → double-fire. At reconstruct the resumed manifest IS the crash manifest → the conjunct passes trivially; it only bites the crash-time edited-manifest case. The conjunct is fed by the new runtime `dispatched_branch_step_ids` reader + a `_resumed_branch_step_ids_by_ordinal` helper (the `step_id` sibling of `_resumed_branch_kinds_by_ordinal`).
