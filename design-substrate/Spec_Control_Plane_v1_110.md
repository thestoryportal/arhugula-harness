## Change-note (v1.109 → v1.110)

**Trigger — `B-79`.** The `B-72` impl leg's `_resume_body_mismatch` guard validates a pre-dispatch gate-owning branch's `step_id`/`step_kind`/`child_workflow_id` identity before delivering the operator's resolved response, but does not validate whether the branch's HITL placement (e.g. `SUB_AGENT_BOUNDARY`) or gate-configuration still applies to the resumed step. If a workflow is edited between pause and resume while preserving the branch's `step_id` — e.g. removing its `SUB_AGENT_BOUNDARY` placement — the guard still accepts the resume, and `RuntimeHITLGateComposer`'s Step 0 (`hitl_gate_composer.py:1684-1750`) unconditionally consumes and applies the stored `HITLDeliveryCell` to the now-differently-gated branch. Confirmed pre-existing at the already-shipped LINEAR `resume_at` delivery-cell site too (`workflow_driver.py` ~4748-4777) — which, unlike the fan-out sites, carries NO per-step identity check of any kind today, not even `step_id`. Also confirmed (round-2 codex out-of-family review, caught before merge) at the LATER `EVALUATOR_OPTIMIZER` (`workflow_driver.py:10789-10806`) and `DECENTRALIZED_HANDOFF` (`workflow_driver.py:14803-14820`) delivery-cell construction sites landed by the `B-78` impl leg (PR #1117) — both single-owner sequential topologies whose own inline comments state they mirror the LINEAR site's mechanism EXACTLY, and so share the IDENTICAL gap.

**Why `B-79` needs a new spec property, not a pure impl-to-cleared-spec fix.** The exact same reasoning as property 6's own change-note applies here: extending what `_resume_body_mismatch` validates is an observable CONTRACT change to a currently-shipped, cleared mechanism (every prior addition to these same carriers — `step_kind`; `child_workflow_id` at `B-31`/v1.99; property 6's own pre-dispatch identity at v1.107→v1.108 — went through a CP spec-leg amendment before impl). Silently stretching the guard's coverage without a contract amendment would itself be an uncontrolled design extension per workspace `CLAUDE.md` §4.4 (X-AL-3).

**Why no new cross-axis seam is needed.** A dyadic council convening (C10 + C1) probed the actual call graph before deliberating and falsified the registered finding's own premise that Runtime-owned persona/engine-class placement-resolution logic is opaque to `harness-cp`. ## §1 — HITL placement/gate-configuration material-diff identity (property 7, closes `B-79`)

**§1.1 The property (CONTRACT — binding on the impl leg; wiring is NOT specified here, mirrors v1.108 §1.3's own discipline).** A resumed branch's HITL-relevant gate configuration — the set of `HITLPlacement` objects applicable to its step (per C-CP-17 §17.3, as folded by `fold_step_hitl_placements`) together with any per-step `removed_placements` override (C-CP-06 §6.2) — MUST be validated as UNCHANGED between pause-capture time and resume time, for every resume path that may deliver a previously-resolved HITL response to that step's dispatch. The resolver MUST:

- **(a) Persist an identity at pause-capture time.** Whichever internal representation the impl leg chooses (a content hash, a canonicalized tuple, or any equivalent) MUST deterministically distinguish two gate-configuration states that differ in EITHER the applicable `HITLPlacement` set OR the `removed_placements` override — not merely whether a placement of a given `HITLPlacementKind` still exists, but whether ANY of its 4 fields (`position`, `tool_filter`, `cascade_policy`, `timeout`) or the override set changed. A scheme that only distinguishes placement-kind existence does NOT satisfy this property.
- **(b) Reject on mismatch, fail closed.** If the re-supplied step's current gate configuration does not match the persisted identity, the resume MUST be rejected as a material diff — mirroring the existing `step_id`/`step_kind`/`child_workflow_id` precedent's fail-closed discipline (`_resume_body_mismatch`) — rather than silently delivering a stale resolved response to a step whose gating has changed. This applies symmetrically: a placement REMOVED between pause and resume MUST be rejected (the stored response would otherwise apply to a now-ungated step); a placement ADDED or altered MUST also be rejected (a stored APPROVE would otherwise authorize an action against a gate that was never actually re-evaluated against the new configuration).
- **(c) Report the rejection through the existing failure path (codex out-of-family review [P2], caught before merge — corrected from an initial draft that falsely claimed a C-CP-20 audit-ledger entry).** A resume rejected under (b) MUST compose a `RunResult` failure disposition through the SAME path the existing `_resume_body_mismatch` mismatches already use — confirmed at this delta's authoring, that path returns `RunResult(status=RunStatus.FAILED, fail_class=<mismatch description>)` directly; it does NOT emit a C-CP-20 audit-ledger entry. This property requires ONLY that same `RunResult.fail_class` reporting shape for the new mismatch kind — it does NOT require, and an initial draft incorrectly claimed, a NEW audit-ledger emission beyond what the existing precedent already does.
- **(d) Cover every site that ACTUALLY constructs a stored HITL delivery (codex out-of-family review [P1] x2, caught before merge across two rounds — corrected from an initial draft that both mis-scoped a carrier that never delivers one AND omitted two sequential-topology sites that do).** This property binds: the fan-out closure's pre-dispatch-gate-owning delivery site (`_execute_parallelization`/`_execute_orchestrator_workers`, including `HIERARCHICAL_DELEGATION`'s recursive reuse per §1.2b's own topology-scope discipline) — property 6's `PreDispatchGateOwningBranchResumeState` consult site, confirmed at this delta's authoring, `workflow_driver.py:8036-8045`/`12279-12289`, gated on `branch_index in _recovered_pre_dispatch_gate_owning`; the LINEAR `resume_at` delivery-cell construction site (`workflow_driver.py` ~4748-4777); the `EVALUATOR_OPTIMIZER` construction site (`workflow_driver.py:10789-10806`), whose own inline comment states it "mirrors `workflow_driver.py:4830-4859` EXACTLY — the LINEAR `resume_at` delivery-cell construction site"; and the `DECENTRALIZED_HANDOFF` construction site (`workflow_driver.py:14803-14820`), whose own inline comment states the identical mirroring (round-2 codex out-of-family review caught these last two omissions — both are single-owner sequential topologies, landed by the LATER `B-78` impl leg, PR #1117, after property 6's own authoring, and share the IDENTICAL no-per-step-identity-check gap as LINEAR, confirmed at this delta's authoring). ALL FOUR of LINEAR/EO/DH carry NO per-step HITL-configuration identity check of any kind today — since EO/DH are byte-identical in shape to LINEAR (single-owner sequential, no branch-ordinal ambiguity), the SAME net-new carrier §1.3a authorizes for the LINEAR site MAY serve all three, at impl discretion. Separately, `RuntimeHITLGateComposer`'s own Step 0 short-circuit (`hitl_gate_composer.py:1684-1750`) today computes `resumed_placements`/`resumed_matching` ONLY to compose an audit entry and never gates delivery on whether they changed. **A paused-child branch's own `PausedChildBranchResumeState` (`B-21`/`B-31`) is explicitly OUT OF SCOPE for this property's identity requirement** — confirmed at this delta's authoring (`workflow_driver.py:8016-8058`) that carrier ONLY forwards `child_resume_snapshot` to a recursively-dispatched child's own, separate `execute_workflow()` call; it never itself constructs a `HITLDeliveryCell` or delivers a stored response, so persisting a placement-identity hash on it would neither close a real gap NOR be neutral — it would incorrectly reject a valid resume whenever the PARENT branch's own unrelated placement configuration changed, even though the parent delivers nothing stale. The child's own gate-configuration identity (if the child is itself pre-dispatch gate-owning, or reaches its own sequential/fan-out delivery site) is already covered recursively by this SAME property applying independently at the child's own `execute_workflow()` invocation. Satisfying (a)-(c) at the CP-side pre-dispatch/sequential-site guards is the PRIMARY closure (a rejected resume never constructs a `HITLDeliveryCell`, so a mismatched configuration structurally cannot reach Step 0 with a stale response for the CP-driven dispatch paths this property covers); this property does NOT separately mandate an independent Runtime-side re-check as a REQUIRED second gate — whether the impl leg additionally hardens Step 0 as defense-in-depth is impl discretion, not a contract requirement of this property.

**§1.2 Scope.** This property closes `B-79` as registered — the material-diff gap for a resumed branch's HITL-placement/gate-configuration identity, at the sites that ACTUALLY construct a stored delivery (§1.1(d)). It does NOT specify: the exact hashing/canonicalization algorithm (impl discretion, beyond the full-4-field/`removed_placements` coverage §1.1(a) fixes); the exact new field name(s) or type(s) (§1.3 below); whether the LINEAR site's new per-step identity check is unified with a future general LINEAR resume-identity mechanism or built narrowly for this property alone (impl discretion — no such general mechanism exists today to unify with).

**§1.3a Durable-carrier authorization (mirrors v1.108 §1.3a's own discipline — the carrier's EXISTENCE and byte-compat treatment cannot be left to impl discretion, only its exact shape; codex out-of-family review [P1], caught before merge — corrected from an initial draft that also authorized this field on `PausedChildBranchResumeState`, a carrier §1.1(d) now explicitly excludes).** `PreDispatchGateOwningBranchResumeState` (and its parent `PauseSnapshot`) is a frozen `extra="forbid"` C-CP-26 type whose serialized contents participate in `snapshot_hash`. This spec leg explicitly AUTHORIZES: this type MAY gain ONE new field to record the pause-time HITL-placement/gate-configuration identity, following the SAME established byte-compat scoping convention this carrier family already uses for additive fields — drop-when-empty/`None` hash-strip scoping, mirroring `Spec_Control_Plane_v1_108.md`'s own precedent for this exact type (both additive fields whose absence/default state leaves prior snapshots' hash unchanged). A pre-existing durable snapshot with the new field absent/empty MUST hash identically to how it hashed before this delta. Separately, this spec leg AUTHORIZES a NEW carrier (exact name/type impl discretion) at the LINEAR `resume_at` site to hold a per-step identity for THIS property's purposes — the LINEAR site has no existing per-step resume-identity carrier of any kind to extend, unlike `PreDispatchGateOwningBranchResumeState`, so this is a net-new addition rather than a field added to an existing type; the SAME byte-compat/hash-strip discipline applies (a snapshot captured before this delta's impl leg lands, or a LINEAR run with no HITL placements at all, MUST be unaffected). **This same net-new carrier's existence, at impl discretion, MAY be reused verbatim for the `EVALUATOR_OPTIMIZER` and `DECENTRALIZED_HANDOFF` sites** (§1.1(d), codex round-2 correction) — both are byte-identical in shape to LINEAR (single-owner sequential, no branch-ordinal ambiguity, no existing per-step identity carrier), so this authorization is NOT scoped to LINEAR alone; a distinct carrier per sequential topology is also permitted if the impl leg finds that cleaner, at its own discretion. `PausedChildBranchResumeState` (`B-21`/`B-31`) gains NO new field under this delta — per §1.1(d), it never constructs a `HITLDeliveryCell`, so no material-diff identity is needed there.

**§1.3 What is explicitly NOT specified here (impl discretion, mirrors v1.108 §1.3).** The new fields' exact names and types (existence + byte-compat treatment now pre-authorized at §1.3a above); the exact canonicalization/hashing scheme (beyond the full-coverage requirement fixed at §1.1(a)); which call site constructs the identity and which call site consults it for the material-diff comparison; whether `RuntimeHITLGateComposer`'s Step 0 gains an additional defense-in-depth check (§1.1(d) leaves this to impl discretion, not a contract requirement).

## §2 — Tree-wide effect-fence-abort suppression scope (property 8, closes `B-80`) + property 6 precedence note

**§2.1 The property (CONTRACT — binding on the impl leg; wiring is NOT specified here, mirrors v1.107 §1 + v1.108 §1.1's own discipline).** The effect-fence-abort HITL-delivery suppression guard (the `_any_fence_abort`-gated suppression that both the pre-existing effect-fence-directive peer suppression and property 6's mandatory-delivery outcome must respect) MUST be computed against the TRUE ROOT of the current resume tree — not merely the current fan-out level's own locally-recovered branches — mirroring the SAME root-computed, thread-down-unchanged discipline `Spec_Control_Plane_v1_107.md` §1's `compute_effect_fence_uniform_fallback_eligible_key` and its `B-39` sibling `compute_hitl_uniform_fallback_eligible_run_id` already establish for this exact class of tree-wide safety computation. The resolver MUST:

- **(a) Compute tree-wide, once, at the true root.** A boolean (or equivalent) signal — "does ANY location in the full resume tree resolve to an effect-fence ABORT" — MUST be computed ONCE against the depth-0 `PauseSnapshot` (the caller-supplied snapshot at the true `resume()` entry, BEFORE any recursion narrows it to a subtree) using the SAME tree-wide enumeration `_collect_effect_fence_idempotency_keys`/`compute_effect_fence_uniform_fallback_eligible_key` already perform for the sibling safety computation, and threaded down UNCHANGED through every recursion level — a nested child's own narrowed snapshot cannot see sibling locations elsewhere in the full tree, so recomputing this independently at each level cannot satisfy the safety intent.
- **(b) Widen, not replace, the level-local guard.** The tree-wide signal MUST be combined with (not substituted for) the existing level-local `_any_fence_abort` computation at every consume site — a strict widening of when suppression fires, never a narrowing. Byte-compat with the crash-resume path (where no `resume_context` exists and the level-local term already evaluates false) is a required property of the combination, not merely a convenience.
- **(c) Blanket scope, not `cascade_policy`-precise (deliberately declined refinement — see the change-note's TENSION-resolution rationale).** The tree-wide signal covers ANY effect-fence ABORT anywhere in the resume tree, regardless of the `cascade_policy` of any intervening ancestor fan-out. A `cascade_policy`-aware precise version (suppressing only where an intervening hop is `cascade-cancel`) is EXPLICITLY OUT OF SCOPE of this property — `PauseSnapshot` carries no `cascade_policy` field at any level today, and building the precise version would require a new durable carrier dimension this spec leg does not authorize. This mirrors the ALREADY-SHIPPED local-level rule's own `cascade_policy`-blind "tier-agnostic FAILED" discipline (`workflow_driver.py:8204-8208`, CP spec v1.107 §1.1) — a `cascade_policy`-aware tree-wide extension would be MORE discriminating than the shipped convention it extends, which this property does not attempt.

**§2.2 Scope.** This property closes `B-80` as registered — the tree-wide scoping gap for the effect-fence-abort HITL-delivery suppression guard, at all four fan-out dispatch sites (`_execute_parallelization` and `_execute_orchestrator_workers`, including `HIERARCHICAL_DELEGATION`'s recursive reuse, per §1.2b's own topology-scope discipline, unamended). It does NOT specify: the exact new parameter's name (impl discretion, mirrors the existing `hitl_uniform_fallback_eligible_run_id`/`effect_fence_uniform_fallback_eligible_key` naming convention); the §2.1(c) precise `cascade_policy`-aware refinement, explicitly deferred as a future, separately-scoped fork IF a real production case ever demonstrates non-negligible over-suppression cost under `cascade_policy=proceed` nesting — not a defect this property claims to close.

**§2.3 Precedence over property 6's §1.1(b) mandatory-delivery outcome (the genuine new spec-prose reconciliation this delta owes — NEW, amends property 6's OUTCOME, not its text).** `Spec_Control_Plane_v1_108.md` §1.1(b) states that when property 4's SOLE-member rule determines a pre-dispatch gate-owning branch is the sole member of the unaddressed gate-owning set this cycle, the resolver MUST deliver the operator-supplied uniform response to it. Property 8's tree-wide suppression signal, once it fires, TAKES PRECEDENCE over this mandatory-delivery outcome — a pre-dispatch gate-owning branch that would otherwise qualify for property 6's §1.1(b) mandatory delivery MUST instead be suppressed (re-pause INERT, no delivery this cycle) when the tree-wide abort signal is true, exactly as the pre-existing effect-fence-directive peer suppression already treats the level-local signal. This is NOT a livelock regression: property 6's own §1.2 scope note already accepts that a pre-dispatch gate-owning branch may not converge in every cycle (the liveness limit at §1.1(c)), and suppression under a tree-wide abort delays delivery by at most one resume round (the branch is recoverable at the next round if the run turns out not to be doomed by the abort, and the run terminates `FAILED` via the abort's own path regardless if it is doomed) — never a lost response, never data loss. Property 6's §1.1(a)-(d) text is otherwise PRESERVED VERBATIM; only the circumstances under which its §1.1(b) outcome fires are now conditioned on property 8 §2.1's signal being false.
