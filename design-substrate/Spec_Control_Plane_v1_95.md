## Change-note (v1.94 → v1.95)

**What this materializes.** The v1.87–v1.90 warm-up serialized `branch[0]` only when ALL branches attested ONE identical non-None cohort key (`_same_prefix_cohort()`, v1.88 §25.15) — a heterogeneous fan-out (per-step prompt/model/role overrides per C-CP-06 §6.1 produce per-branch bindings with different `prompt_version_sha`/`model`, hence different cohort keys) received NO warm-up at all, so each multi-member cohort cache-miss-stormed independently (the ADR-F2 §(b)(ii) detonation, per cohort). B-18-EPOCH-PARTITION (registered at v1.87; reshaped at `.harness/u1-slice3b-epoch-partition-design.md` §6) closes this: branches are PARTITIONED by cohort key and each multi-member cohort's first ordinal (its LEADER) performs the cache-write before that cohort's FOLLOWERS release. The §4.1 epoch identity (`prefix_content_hash`) is REALIZED BY the v1.88 `cohort_key()` oracle — no second hash is built (the `fts_bound` sentinel is sufficient within one fan-out because `frozen_tool_superset` is a run-scoped constant on the one capable dispatcher instance the registry resolves per step_kind).

**Scope of revision — NEW §25.19 (heterogeneous cohort partition).** *(§25.18 is the v1.32 impl-discretion + recorded-forks section — the pre-build review's B1 finding corrected this delta's carrier to §25.19, verified zero-hit through v1.94.)*

1. **Partition definition (supersedes the v1.88 §25.15 binary predicate).** `_warmup_phase_split()` groups the LIVE `branch_plan` (post-recovery-seed — a partial-recovery resume re-partitions the remainder with a NEW leader per remaining cohort, the v1.90 item-1 lineage) by `(step_kind, cohort_key)`: `step_kind` participates because equal 16-hex keys are attested-comparable only within one capable dispatcher instance, which the registry resolves per step_kind (behavior-inert at HEAD where only INFERENCE_STEP is capable; forecloses a silent cross-kind collision). Non-`CohortKeyCapable` dispatchers and None keys form NO cohort — they no longer veto sibling cohorts' warm-up (the v1.88 "any None → gate False" collapse was the binary gate's definition, superseded here; a None branch itself is never warmed). **Phase 1** = one LEADER (first ordinal) per multi-member cohort PLUS every non-beneficiary branch (None-key / non-capable / singleton-cohort — cache-neutral, so Phase-2 placement would delay them for zero benefit; Phase-1 placement preserves their baseline immediate dispatch). **Phase 2** = the followers. `_warmup_gate = concurrent_cache_warmup AND phase2 non-empty`. The H3 `len(branch_plan) < 2` short-circuit is kept explicit (zero `cohort_key()` oracle calls on a singleton plan — the v1.90 call-count-exact property), as is gate-off (`concurrent_cache_warmup=False` → the split is never computed).

2. **Degenerate reductions (the byte-preservation contract).** All-same non-None key → phase1 = {first ordinal}, phase2 = rest — the v1.87/v1.90 serialize-branch[0] schedule EXACTLY. No multi-member cohort (all-distinct / all-None / non-capable / <2 plan) → phase2 empty → gate False → the all-concurrent baseline byte-identical. `concurrent_cache_warmup=False` → gate False, split never computed.

3. **PROCEED two-phase (H1 generalized).** `_proceed_fanout` gathers Phase 1 (`return_exceptions=True`), then Phase 2 (same), results reassembled in `branch_plan` ordinal order. A Phase-1 failure still dispatches Phase 2 and drains the failed branch's buffered entries (→ PARTIAL). **Named carve-out (review C1):** a SPONTANEOUS branch CancelledError is captured as a gather result under this shape (→ PARTIAL), aligning the warm-up path with the gate-False baseline gather — the v1.87 solo `except Exception` (which let it escape naked) was the outlier; the DEADLINE CancelledError still propagates (the gather itself is cancelled → TimeoutError at the timeout `__aexit__`), preserving v1.91 M2/ML semantics.

4. **Strict-tier Phase 1 = TaskGroup + MANDATORY result-collection (supersedes v1.90 item 3).** `_cancel_fanout`'s Phase 1 runs the phase-1 branches under an `asyncio.TaskGroup` (per-branch records byte-identical — all handlers live in `_cancel_branch`, ordinal-keyed). The v1.90 item-3 solo R3 guard's obligations are carried natively: (a) the outer deadline CancelledError propagates through the group unwrapped → TimeoutError at `__aexit__` → `BranchBarrierDeadlineExceededError`; (b) a child's bare TimeoutError is wrapped into an ExceptionGroup that `except TimeoutError` does NOT catch (no implicit group unwrap) — a branch FAILURE, never the barrier deadline (W7 retained as the by-execution pin). **NORMATIVE:** after `TaskGroup.__aexit__`, `task.result()` MUST be collected for every Phase-1 task BEFORE Phase 2 releases — CPython's TaskGroup SWALLOWS a child that raises SPONTANEOUS CancelledError (a watchdog-cut future — e.g. an OUTER nested-fan-out barrier's earlier-armed watchdog cutting this inner Phase 1 inside the window where the inner timeout has not fired — or a sub-agent child's naked escape through `dispatch()`): the group exits CLEAN with `task.cancelled()=True`, and without the resurface the followers would dispatch AFTER the cut, inverting the v1.90 item-4 effect-set subset invariant on the tiers that exist to bound effects. `task.result()` re-raises the swallowed CancelledError, byte-matching the Phase-2 collection idiom; the K=1 degenerate case reduces to the pre-arc solo re-raise exactly (witness EP9; empirically verified on the project interpreter, both reviewers independently). One accepted micro-divergence (recorded, not engineered around): a Phase-1 TaskGroup child has one scheduling tick before its synchronous `_mark_branch_dispatched` where a sub-tick deadline could cancel pre-marker — unreachable at the non-injectable 300 s default.

5. **Failure semantics per tier (unchanged classification surface).** Strict tiers: any Phase-1 member failure (leader OR non-beneficiary) raises grouped → `branch_failed = True` → the tier's committed outcome; Phase 2 (followers of ALL cohorts) is withheld — a strictly SMALLER dispatched set than the baseline (the v1.90 item-4 direction; a leader failure does NOT promote a replacement leader — no committed basis, and on PROCEED the followers still release per H1 and may cache-miss within that cohort, today's committed K=1 behavior).

6. **Obligation-4 scan family UNTOUCHED.** `_synthesize_undispatched_terminals()` (all five PARALLELIZATION exits + the O-W counterpart) keys on writer-disposition ABSENCE + the fence/reconstruct dicts — ordinal-keyed, phase-free. Withheld followers at any terminal exit receive exactly the v1.91–v1.94 arms. ZERO store-write changes; ZERO new crash-visible additions; run statuses / fail_classes / step counts byte-unchanged; the PAUSED boundary stays scan-free; §5.2 hash untouched.

7. **Carve-out carried (v1.88).** The `routing_activation` content-sensitive-routing carve-out (equal cohort keys, different promoted models → warm-up without benefit; latency-only) carries forward verbatim — the partition neither fixes nor worsens `cohort_key()` fidelity.

8. **Witness-contract supersession (explicit).** CK-3 (`test_cohort_key_capable.py`) pinned "ANY non-uniformity → all-concurrent" — under the partition its A/B/B reverse-completion fixture fails in ~10 s (PROCEED: both blocked branches' 10 s waits expire concurrently → AssertionErrors captured → Phase 2 dispatches the follower → PARTIAL ≠ asserted SUCCESS; not a live deadlock, not a 300 s hang). RESHAPED to CK-3′ (all-distinct keys → every cohort singleton → gate False → all-concurrent): the surviving half of the old contract. The superseded half is pinned by the EP witnesses.
