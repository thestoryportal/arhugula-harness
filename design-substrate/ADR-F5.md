## Decision

Adopt a single capability-aware secret-fetch abstraction interface — `fetch_secret(name, scope) -> SecretRef` — backed by tier-aware resolution closing T-perm-2 at the secrets-in-sandbox-environment seam (host-keychain-access at process tier reading into the sandboxed process via environment variables at process startup; in-sandbox-secrets-client at microVM and full-VM tiers fetching JIT via in-sandbox HTTP client over network using a sandbox-identity bootstrap token bounded by sandbox lifetime), with dev-tech committed at the cross-platform OS-keyring abstraction layer per host-OS case (macOS Security.framework Keychain, Linux Secret Service / libsecret with `secret-tool` fallback, Windows Credential Manager via wincred.h) and specific keyring-library binding deferred to D-ADR per language ecosystem chosen, prod-tech entirely deferred to D-ADR per Pattern Reference Catalog v1.0 §11.3.2 derivative as deployment-surface-bound, with secret-access events composing against ADR-F2's state-ledger entry shape `(action_id, idempotency_key, actor, response_hash, timestamp, prior_event_hash)` via structure-not-content audit (`outputs_hash = sha256(secret.name || secret.scope || secret.last_rotated_at)` — fingerprint that proves access against a specific secret version without revealing the value), per-tool secret-allowlist (`required_secrets`) as a separate access-control dimension alongside ADR-F4 `assigned_tier`, secret-passthrough-protection as a contract constraint per MCP authorization spec 2025-06-18 directive, and **five cause-attribution refinements of the secret-fetch fail surface within the C5/C9 fail-class taxonomy** (`secret_unknown` — permanent, unprovisioned; `secret_unavailable` — transient, backend-down, per-`{secret_backend, scope}` breaker; `secret_expired` — Reflexion-recoverable, refresh-and-retry with idempotency-key preservation; `secret_locked` — HITL-recoverable, workload-mode-aware operator-input-required; `secret_revoked` — HITL-recoverable, workload-mode-aware rotation-needed) composing with C9 retry/breaker mechanics and ADR-F3 observable-lifecycle requirement.

## Rationale

**Framing on the five-class clause (FM-J cause_attribution + FM-C no-redesign joint compliance).** The five classes named in §Decision (`secret_unknown`, `secret_unavailable`, `secret_expired`, `secret_locked`, `secret_revoked`) are **cause-attribution refinements on the existing C5/C9 fail-class taxonomy**, not a redesigned top-level taxonomy. They map to the C5/C9 reconciled five-class taxonomy (per s14 §7.5(d) reconciliation note) as cause-attribution discriminators on the secret-fetch surface: `secret_unknown` is a permanent-fail (cause: unprovisioned); `secret_unavailable` is a transient-fail (cause: backend-down — per-`{secret_backend, scope}` breaker scope); `secret_expired` is a Reflexion-recoverable fail (cause: token aged out — refresh-and-retry with idempotency-key preservation per ADR-F2 state-ledger entry shape); `secret_locked` is an HITL-recoverable fail (cause: operator-input-required — workload-mode-aware: ephemeral fail-fast, durable pause-and-wait per ADR-F3 lease-coordination); `secret_revoked` is an HITL-recoverable fail (cause: rotation-needed — workload-mode-aware: same shape as `secret_locked` with rotation-specific operator signaling). Each cause attribution determines the recovery path within the existing taxonomy class — the five classes do not introduce a new taxonomy, they specialize the existing one at the secret-fetch surface so C9 retry mechanics, C5 in-loop gates, and ADR-F4 HITL composition can route by cause without ambiguity. This satisfies C5 FM-J (cause_attribution surfaced explicitly) and C9 FM-C (no taxonomy redesign — refinement only) jointly.

**(a) Pattern this decision follows.** The fetch-abstraction commitment follows Pattern Reference Catalog v1.0 §10.4 P-OD-11 (encrypted-secrets-at-rest with OS-keychain abstraction) at its convergence point — the C-on-the-dev-vs-prod-abstraction is settled across the corpus (optio AES-256-GCM at rest; kilocode CA-trust handling; Cluster 5 V2 F5 foundational); the D-on-transit-mechanism is what F5 closes via the tier-aware T-perm-2 resolution. The structure-not-content audit composition follows Pattern Reference Catalog v1.0 §10.4 P-OD-3 [HIGH] (audit ledger / hash-chained provenance) and Cluster 4 §2.3.3 [HIGH] hash-chain ledger schema. The secret-passthrough contract constraint follows the MCP authorization spec 2025-06-18 [HIGH] mandatory directive verbatim. The tier-aware T-perm-2 closure follows the lethal-trifecta architectural-cut-of-leg discipline (Cluster 4 §2.3.2 [HIGH]) — filter-based mitigations top out near 97%, structural cut via tier composition is the only reliable mitigation. The fetch-abstraction-vs-dev-tech-vs-prod-tech split follows ADR-F3's capability-requirement-vs-engine-commitment-split closure shape and ADR-F4's tier-set-vs-tech-commitment split — same flexibility-preservation discipline along the deployment-surface-coupling axis. The cross-platform OS-keyring abstraction layer is documented in the corpus (Architecture deliverable secrets section [MODERATE]: `@napi-rs/keyring`, `keytar`, `zalando/go-keyring`, `python-keyring`).

**(b) Failure mode this decision prevents.** Four failure modes:

(i) **macOS keychain prompts blocking cloud automation** (Brainstorm_Synthesis_For_Phase_2 §6 F5 [MODERATE — synthesis cap]; Architecture deliverable secrets section [MODERATE]) — the canonical local-dev failure where macOS Keychain ACL prompts when an unsigned process tries to read interrupt durable workloads. Prevented at process tier via the long-lived agent-process-with-keyring-handles pattern (C11 implementation surface): the harness daemon holds keyring handles inside the user session and serves them via in-process API to short-lived sub-agents. Headless modes use `pass` / `gpg` or environment-pre-seeded values where a user session is unavailable.

(ii) **Short-lived cloud tokens breaking local dev loops** (Brainstorm_Synthesis_For_Phase_2 §6 F5 [MODERATE — synthesis cap]; Architecture deliverable secrets section [MODERATE]) — vault token expiration mid-agent. Prevented via the rotation-aware retry contract (re-fetch on 401/403 + single retry with same idempotency_key per ADR-F2 state-ledger entry shape, then escalate to `secret_revoked` and HITL) combined with the fresh-on-restart contract (no in-process secret cache across restart boundaries; test-fetch on resumption per ADR-F3 resumption events).

(iii) **Secret-leak as exfil-leg of the lethal trifecta** (Cluster 4 §2.3.2 [HIGH]; Cluster 4 §2.3.5 [HIGH] in-the-field failures: ChatGPT memory exfil via `*.blob.core.windows.net`; Claude.ai prompt-injection exfil via attacker-controlled API key embedded in hidden prompt + own-domain whitelist of api.anthropic.com Files API; Anthropic Cowork file-API exfil PromptArmor demonstration on Claude Opus 4.5). Prevented structurally by four composing primitives: (1) audit-ledger structure-not-content (the secret VALUE never enters the ledger; only the access event does); (2) secret-passthrough contract constraint (tool outputs MUST never include secret material; tool inputs MUST be redacted in span attributes); (3) per-tool secret-allowlist (`required_secrets` declares scope; the harness gates secret access via the contract's allowlist intersected with operator-policy override); (4) tier-aware T-perm-2 closure with sandbox composition per ADR-F4 (microVM/full-VM tiers' network-egress allow-list cuts the exfil leg structurally; filter-based defenses topping at 97% per Anthropic transparency hub are insufficient per Persona §6 architectural posture).

(iv) **Secret-in-git** (categorically incompatible with ADR-F2 git boundary). Prevented by ADR-F2 boundary preservation: F5 secrets reside in OS keychain at dev / vault at prod, never in git. The audit-ledger composition is hash-chained against ADR-F2's state-ledger but contains only fingerprints, never values.

**(c) Condition under which this decision stops being worth the cost.** Two conditions, neither current. (i) When the workload mix becomes uniformly trusted (no LLM-generated code, no untrusted-content ingest, no computer-use, no remote-MCP exposure, no production-time multi-tenant binding) and the action surface no longer carries lethal-trifecta-positive paths, the audit-ledger structure-not-content discipline and per-tool secret-allowlist become vestigial — every tool would access every secret without exfil risk. Persona §5.1 in-scope items (code execution + computer-use at design-time AND production-time + MCP first-class) plus §10.4 compliance-readiness posture (secrets rotation as foundational primitive) make this not current and not in design horizon [SPECULATIVE]. (ii) When the production-time deployment surface and the dev-time deployment surface converge (e.g., uniformly local self-hosted at multi-tenant binding; uniformly cloud-managed at design-time), the cross-deployment bridge principle becomes vestigial — single-tier suffices. Persona §2 bridging arc (sole operator at design-time → multi-tenant binding state later) and §9/§10.2 (production-time deployment surface persona-constrained but not picked) make this structurally not current — the bridging arc is the source dimension of the principle.

## Consequences

**(a) What becomes possible.**

- A single consumer-facing secret-fetch API (`fetch_secret(name, scope) -> SecretRef`) at all call sites, identical across dev and prod deployment surfaces — call-site code unchanged across deployment surfaces, analogous to ADR-F1's capability-aware multi-LLM provider abstraction.
- Tier-aware secret-fetch resolution composing structurally with ADR-F4 sandbox tier-set: process tier within-turn-snapshot via env vars at startup; microVM and full-VM tiers across-turn fresh-fetch via in-sandbox HTTP client over network using sandbox-identity bootstrap token. Both T-perm-2 poles expressed; threat-model alignment preserved per tier.
- Audit-ledger structure-not-content fingerprinting (`outputs_hash = sha256(secret.name || secret.scope || secret.last_rotated_at)`) enables version-precise auditability without value disclosure: two access events for the same secret version produce identical fingerprints (deterministic auditability); rotation produces a different fingerprint (rotation observable in chain); composes with ADR-F2 hash-chain integrity per Pattern Reference Catalog v1.0 §10.4 P-OD-3.
- Per-tool `required_secrets` allowlist as a separate access-control dimension alongside ADR-F4 `assigned_tier` — orthogonal access-control axes; a low-tier tool consuming a low-blast-radius secret is a coherent shape (e.g., a deterministic helper that calls a billing API with a scoped read-only token) without sandbox tier inflation.
- Secret-passthrough contract constraint per MCP authorization spec 2025-06-18 directive — tool outputs cannot include secret material; tool inputs are redacted in span attributes; cross-trifecta exfil leg cut structurally rather than by filter.
- Five cause-attribution refinements on the secret-fetch fail surface (per the §Decision and §Rationale framing paragraph) compose with C9 retry/breaker mechanics and ADR-F3 / ADR-F4 HITL composition by cause: rotation-aware retry on 401/403 with idempotency-key preservation (`secret_expired` — Reflexion-recoverable); per-`{secret_backend, scope}` breaker (analog of ADR-F1 per-`{provider, model}` breaker) with fail-closed-or-fallback-backend-advance behavior on trip (`secret_unavailable` — transient backend-down); workload-mode-aware HITL handling extended **symmetrically across `secret_locked` and `secret_revoked`** — both classes are HITL-recoverable per their cause attribution (operator-input-required vs rotation-needed), and both follow the same workload-mode envelope: ephemeral workflow fails fast at the secret-fetch site (call site receives the fail-class; the topology decides retry-or-abort per ADR-F1 fallback-chain composition); durable workflow pause-and-waits per ADR-F3 lease-coordination (the workflow checkpoints, releases the lease, registers an HITL trigger from the eleven-trigger catalog per ADR-F4, and resumes when the operator-unlock signal lands); the four-response palette (allow / deny / modify / escalate) per ADR-F4 HITL composes with both classes — `allow` resumes with the operator-supplied secret value or rotation event, `deny` permanently fails the workflow at the fetch site, `modify` permits operator-supplied scope adjustment to bypass the lock, `escalate` raises to a higher-authority operator per the multi-tenant escalation chain when bound. `secret_unknown` is permanent (cause: unprovisioned — no recovery path; workflow fails at fetch site).
- OTel `secret.fetch` lifecycle span schema with sensitive-data default-off + structure-not-content discipline: `secret.name`, `secret.scope`, `secret.backend` (discriminator), `secret.fail.class`, `secret.cache.tier_overhead_ms`, `secret.policy.access_decision_reason`; lifecycle events as standalone spans (`secret.rotated`, `secret.expired`, `secret.revoked`, `secret.locked`, `secret.unavailable`, `secret.refreshed`); composes with ADR-F3 observable-lifecycle requirement.
- Cross-deployment bridge with mechanical swap of dev-tech (per host-OS case via the keyring abstraction layer) and prod-tech (deferred to D-ADR per deployment surface) — preserves design-phase flexibility for the production-time deployment surface decision Persona §10.2 requires.

**(b) What becomes harder.**

- A second access-control axis (`required_secrets`) alongside the tier system — tool authoring requires declaring required secrets at contract time; operator policy includes a separate allowlist surface; the audit ledger's `policy.access_decision_reason` must capture which axis denied access (sandbox tier vs secret allowlist).
- The bootstrap-token shape at microVM / full-VM tiers requires concrete protocol selection per prod-tech (AWS STS AssumeRoleWithWebIdentity for AWS Secrets Manager; Vault wrapped token; GCP Workload Identity; Azure Managed Identity; Doppler service token; 1Password Connect API token) — the abstraction is uniform but the bootstrap-token issuance protocol is prod-tech-specific, deferred to D-ADR.
- Secret rotation triggers harness-side reactive paths: the `secret.rotated` event must propagate to running tool invocations holding stale tokens (refresh-required pattern); long-running durable workloads holding pre-rotation tokens require explicit pause-and-refresh per ADR-F3 lease-coordination — not transparent.
- The fresh-on-restart contract (no in-process secret cache across restart boundaries; test-fetch on resumption) imposes a startup latency cost proportional to the number of `required_secrets` declarations across loaded tool contracts.
- The long-lived agent-process-with-keyring-handles pattern at process tier requires careful lifecycle management — daemon crash invalidates handles; daemon-replacement requires keychain re-prompt; this is C11's local-deployment D-ADR territory.
- The cross-deployment bridge principle creates a permanent coupling between design-time (OS keychain) and production-time (vault) that the harness must keep observable: degraded-mode at production (e.g., file-fallback when vault unreachable) must be auditable per the provider-discriminator (`secret.backend`) attribute.

**(c) What is now constrained downstream.**

- **D-ADR on specific keyring library binding per language ecosystem** (Pattern Reference Catalog v1.0 §11.3.2 derivative; F5-tech-dev specific library) — `python-keyring` / `keytar` / `@napi-rs/keyring` / `zalando/go-keyring` selection per language ecosystem chosen; conditional on language-ecosystem D-ADR.
- **D-ADR on specific secrets provider for production deployment** (Pattern Reference Catalog v1.0 §11.3.2 derivative; F5-tech-prod) — Vault / AWS Secrets Manager / Azure Key Vault / GCP Secret Manager / Doppler / 1Password Connect selection deployment-surface-bound; depends on production-time deployment surface decision per Persona §10.2.
- **D-ADR on bootstrap-token issuance protocol per prod-tech** — AWS STS / Vault wrapped / GCP Workload Identity / Azure Managed Identity / Doppler service / 1Password Connect API; depends on F5-tech-prod D-ADR.
- **D-ADR on secrets-registry SQLite schema** (C11 owner; local-deployment D-ADR) — `secrets_registry(name, scope, backend, last_accessed_at, last_rotated_at, status, required_by)` per C11 contribution; metadata only, never values.
- **D-ADR on `secret.fetch` span attribute schema** (C7 owner) — `secret.name`, `secret.scope`, `secret.backend`, `secret.fail.class`, `secret.cache.tier_overhead_ms`, `secret.policy.access_decision_reason` plus lifecycle-event span types; composes with ADR-F3 lifecycle span hierarchy and OTel GenAI semconv extensions; cost-attribution-per-span aggregates at workload-class boundary per C7 refinement.
- **D-ADR on per-`{secret_backend, scope}` breaker placement** (C9 owner) — analog of ADR-F1 per-`{provider, model}` breaker; trip-on-repeated-`secret_unavailable`-rate threshold; trip behavior advance-fallback-backend-or-fail-closed.
- **D-ADR on tool/MCP exposure across providers (ADR-F1 §(c))** carries the per-MCP-server-trust-tier_floor — the second half of T-perm-1's tunable parameter; F5's per-tool secret-allowlist is independent of that surface and composes alongside `assigned_tier`, not within the `max()`.
- **D-ADR on local-deployment substrate specifics** (C11 owner) — long-lived agent-process-with-keyring-handles pattern; daemon lifecycle; in-process IPC contract for sub-agent fetch; `pass` / `gpg` headless fallback; TUI surfacing of secret-rotation and secret-fetch lifecycle composing with structure-not-content discipline.
- **D-ADR on HITL eleven-trigger catalog** (per ADR-F4) composes with F5 fail-class taxonomy: `secret_locked` and `secret_revoked` are HITL-trigger candidates; the four-response palette (allow / deny / modify / escalate) composes with operator-unlock signaling.
- **D-ADR on multi-tenant tenant-isolation at F5** at the bridging-arc multi-tenant binding (Persona §11.10) — per-tenant secret namespace; per-tenant audit-ledger composition; cross-tenant-secret-leak prevention; T3 (per-task vs per-company deployment unit) traversal composes with the F5 bridge principle when the binding materializes.

T-perm-2's F2-layer resolution shape (read/write contract pair at state-ledger seam per ADR-F2) stands; F5 closure is at a different seam (sandbox environment) and composes against the F2-layer resolution rather than relitigating it. This decision **touches but does not re-open T-perm-3 (C1 ↔ C9 — control-flow vs reliability)**. ADR-F3 resolved T-perm-3 at the durable-execution-engine seam with workload-class-tunable engine selection per D-ADR + capability-requirement floor + manifest-declaration invocation default + per-step annotation opt-in + pattern committed P-CP-8. F5's secret-token-expiration is a fail-class composing with ADR-F3 observable-lifecycle (secret-rotation event + secret-expiration event as new event classes) and C9 retry/breaker mechanics; F5 specifies the fail-class so C9 mechanism can route by class without altering the F3-layer T-perm-3 settlement. The workload-mode-aware `secret_locked` handling (ephemeral immediate-HITL; durable pause-and-resume) composes with ADR-F3 lease-coordination but does not relitigate the F3-layer resolution.

## Alternatives considered

**Alternative 1: Single-backend abstraction — environment variables only, both at dev and prod.** Candidate as the simplest minimal abstraction (no keyring, no vault; the operator manages secrets in a `.env` file or shell-exported variables; the harness reads them at startup). Rejected because: (i) it forfeits the ADR-F2 git-boundary preservation as a categorical guarantee — `.env` files routinely leak into git via developer error and standard `.gitignore` discipline is not a structural prevention; (ii) it provides no rotation discipline — short-lived cloud tokens require operator intervention to refresh, breaking the local dev loop and contradicting Persona §10.4 secrets-rotation foundational primitive; (iii) it has no audit-ledger composition surface — secret access is not observable, contradicting Persona §10.4 hash-chained audit ledger requirement; (iv) it has no rotation-aware retry primitive — an expired token surfaces as an arbitrary upstream 401/403 to the call site, with no taxonomic distinction from other transient failures, contradicting the persona-answered cross-deployment bridge principle. The `.env`-only shape is appropriate for individual scripts but inadequate for a production-grade harness with the persona's scale and SLO commitments (Persona §4: tens-concurrent + 99.9%).

**Alternative 2: Single-shape T-perm-2 closure — within-turn-snapshot at all tiers (env vars at sandbox creation everywhere).** Candidate as the simplest tier-uniform shape and consistent with the MCP authorization spec STDIO-transport directive at face value. Rejected because: (i) it forces microVM and full-VM tiers to snapshot secrets at sandbox creation, broadening blast-radius across the sandbox lifetime — Cluster 4 §2.3.5 [HIGH] in-the-field failures show that long-lived sandbox handles holding stale credentials are a documented exfil pattern (the ChatGPT Operator string-combination tool exfil shape, the Anthropic Cowork file-API exfil); (ii) it precludes rotation-aware refresh within sandbox lifetime — long-running tool executions in microVM/full-VM tiers cannot refresh tokens without sandbox restart, contradicting the per-class cost ceiling for cache-friendly long-running workloads; (iii) it suppresses C3's across-turn discipline at the very seam where the threat model HAS network-egress-restricted boundaries that JIT-fetch is consistent with; (iv) the MCP authorization spec STDIO-transport directive is explicitly tier-bound to STDIO transport (process-tier shape) and does NOT generalize to network-bound transports — the spec's posture is precisely that env-var-at-startup is the right shape WHERE the threat model is filesystem + syscall, not network. The tier-aware closure expresses both poles per their threat-model alignment.

**Alternative 3: Single-shape T-perm-2 closure — across-turn fresh-fetch at all tiers (no env-var snapshot, all JIT).** Candidate as the most rotation-aware shape and consistent with cloud-native security postures. Rejected because: (i) it forces process-tier sandboxes to require network access for credential fetch — incompatible with the Anthropic Claude Code sandboxing pattern's network-egress-restricted process-tier shape (Anthropic, "Claude Code Sandboxing," anthropic.com/engineering/claude-code-sandboxing [HIGH]) which explicitly prevents network egress at this tier; (ii) it inflates per-fetch latency for the fast-path (process-tier keychain access is functionally free; JIT-network-fetch adds 50–200ms per fetch + bootstrap-token issuance overhead); (iii) it suppresses C2's within-turn discipline at the very seam where the threat model does NOT include network-egress concerns (process tier's threat model is filesystem + syscall isolation; env-var snapshot at startup is consistent and cheaper); (iv) the MCP authorization spec STDIO-transport directive ratifies env-var-at-startup at this tier explicitly. The tier-aware closure preserves the fast-path at process tier without sacrificing the rotation-aware shape at deployment-surface-bound tiers.

**Alternative 4: Per-tool secret-allowlist as fifth floor in ADR-F4 `max()` policy (instead of separate access-control dimension).** Candidate as a single-source-of-truth tier-assignment policy where all access controls compose into one parameter. Rejected because secrets and sandbox tier are structurally orthogonal access-control axes: a tool's required tier is a function of *what its execution can affect* (filesystem writes, network egress, computer-use); a tool's required secrets are a function of *what authorities its execution requires* (a billing API token, a GitHub PR-creation token). Folding the allowlist into the `max()` would force tier-promotion for tools consuming secrets even when the secret's blast radius is bounded (e.g., a read-only token for a public API); this would inflate sandbox cost without proportional security gain — contradicting Persona §6 per-class cost ceiling. The orthogonal-dimension framing is also consistent with ADR-F4's `max()` policy operating over tier-promoting floors only — sandbox tier is the access-control axis the `max()` composes; the allowlist is a separate access-control axis evaluated in parallel.

**Alternative 5: Commit prod-tech now — single specific secrets manager (e.g., commit Vault).** Candidate as a definitive production posture and the most opinionated F5 closure. Rejected because committing prod-tech now pre-empts the production-time deployment surface decision per the F3 capability-requirement-vs-engine-commitment-split precedent (ADR-F3 closure shape) and ADR-F4's tier-set-vs-tech-commitment split — same flexibility-preservation discipline applied to F5's deployment-surface-bound dimension. Vault requires self-hosted infrastructure; AWS Secrets Manager requires AWS; Azure Key Vault requires Azure; GCP Secret Manager requires GCP; Doppler is SaaS with network dependency; 1Password Connect is hybrid. Persona §10.2 records production-time deployment surface as persona-constrained but not picked. Committing Vault (or any specific candidate) at this session would either pre-empt the production-time deployment surface decision or commit to tech that may not be available at the eventual production surface. The fetch-abstraction commitment without prod-tech commitment preserves the design-phase flexibility Persona §9 [SPECULATIVE→MODERATE] requires; the prod-tech D-ADR closes the binding when the production deployment surface decision binds.
