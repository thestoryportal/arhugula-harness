## §1 — The live effect-fence ambiguous-pause composed through the fan-out barrier

> **The build (C-CP-26 §26.2 + C-CP-25 §25.15).** A fan-out branch (PARALLELIZATION peer worker OR ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION worker) whose OWN dispatch raises the runtime effect fence's `EffectFenceAmbiguousUncommittedError` (C-RT-31 §14.22 — the fence lost a reserve to a prior uncommitted attempt of a non-idempotent effect AND found no captured output, so whether the branch's effect fired is genuinely ambiguous) NO LONGER becomes a generic branch error. Pre-arc the generic `except Exception` recorded the branch `completed` (ran-and-errored) → cascade → the run FAILED or proceeded, silently discarding the ambiguity. This slice catches it (name-matched — harness-cp cannot import harness-runtime — the same discipline as the LINEAR path's `workflow_driver.py` effect-fence branch) and COMPOSES the ambiguous-pause THROUGH the fan-out barrier: the branch is recorded as a NON-terminal **effect-fence-paused** disposition (NOT a `completed` terminal — a terminal branch would be SKIPPED on resume, dropping the pause), the worker TaskGroup halts at the pause boundary, and the run returns `RunStatus.PAUSED` with a `PauseSnapshot` carrying the new `effect_fence_paused_branches` carrier (§3). The in-flight (sibling-cancelled) case is symmetric: when a sibling raises first, a branch whose own in-flight dispatch raised the fence lands in `inflight.exception()` (the shield suppresses + re-raises `CancelledError`) and is captured as effect-fence-paused, NOT mislabeled `cancelled`. This is the fan-out analogue of the LINEAR-path `B-EFFECT-FENCE-HITL-ROUTE` (v1.51 §26.2) / `B-EFFECT-FENCE-PAUSE-RESOLUTION` (v1.52 §26.8).
>
> **The resume re-entry (C-CP-26 §26.8 directive threading).** On `api.resume` (`execute_workflow(pause_snapshot_input=...)`) of an effect-fence-paused fan-out, an effect-fence-paused branch is re-entered WITH the operator's resolution — NOT skipped (like a terminal branch) and NOT re-dispatched fresh (like an absent one). The driver PEEKS (non-consuming — the runtime HITL composer retains its one-shot consume) the single operator `EffectFenceResolution` off the `ResumeContextHolder`, and threads an `EffectFenceResolutionDirective(resolution=…, idempotency_key=…)` — KEY-BOUND per branch to that branch's held reserve `idempotency_key` (read by name off the runtime error, carried in the carrier) — onto the re-dispatched branch's hash-inert `StepExecutionContext.effect_fence_resolution`. The runtime tool dispatcher applies the matching directive at the §14.22 fence gate (SKIP_AS_FIRED → empty-output success; RE_FIRE → clear the claim + re-fire; ABORT → fail), key-bound so a stale resolution can never mis-apply. Absent the holder / resolution / key, the branch re-pauses INERT (never an auto-re-fire — the #701 decline-mirror). Under `CascadePolicy.CASCADE_CANCEL` an effect-fence-paused branch is recorded `completed` (dispatch-boundary — its effect may have landed; it MUST NOT be mislabeled `cancelled`) and the run FAILs (the resolution is discarded, not resumed).

## §2 — The fence-recoverable TOOL_STEP maybe-ran crash-resume relaxation + the changed-kind guard

> **The build (C-CP-25 §25.12 / §25.15 strict-tier crash-resume classification).** The v1.62 `B-FANOUT-CRASH-RESUME-MAYBE-RAN-RESOLUTION` re-dispatched a maybe-ran branch of a re-fire-safe kind (`{DECLARATIVE_STEP, INFERENCE_STEP}` — no external effect) and failed CLOSED on ANY effect-bearing maybe-ran branch (the conservative "branches are effect-BEARING" blanket). This slice narrows that blanket: a maybe-ran **TOOL_STEP** is now FENCE-RECOVERABLE — re-dispatching it re-reaches the AUTO-ACTIVE runtime effect fence (the fan-out crash-resume engine classes `{EVENT_SOURCED_REPLAY, WAL_SEGMENT}` are a SUBSET of the durable-auto-fence set, and the worker child context inherits `run_engine_class`), which makes the re-dispatch at-most-once AT THE TOOL SINK (suppress-if-captured / ambiguous-PAUSE [routed via §1] / fresh-fire-if-claim-absent). Applied at BOTH the incomplete-recovery and cardinality-only strict-tier classification sites via one shared helper. The remaining effect-bearing kinds STAY fail-closed: SUB_AGENT_DISPATCH (fenced only at its child's tool sinks → registered §3) and MANAGED_AGENTS (unfenced vendor sink → registered §3).
>
> **The changed-kind guard (at-most-once — the load-bearing correctness condition).** Fence-recovery of a maybe-ran TOOL_STEP requires BOTH (a) the DISPATCH-MARKER kind is TOOL_STEP (the v1.62 changed-manifest guard — the ORIGINAL effect was a fenced tool effect) AND (b) the **RESUMED** manifest's `step_kind` at that ordinal is ALSO TOOL_STEP. Conjunct (b) is essential: a maybe-ran TOOL_STEP re-supplied at the same ordinal as a NON-TOOL kind (e.g. DECLARATIVE) would re-dispatch a step that reaches NO tool sink → NO fence to make the re-dispatch at-most-once → the original tool effect's ambiguity would be silently abandoned. Keying fence-recovery on the marker kind ALONE re-opens the exact v1.62 changed-manifest hole; requiring the resumed kind to ALSO be TOOL_STEP closes it. The CP driver knows `step_kind` (a typed `WorkflowStep` field — C-CP-25 §25.2) without reading the opaque `step_payload`, so conjunct (b) is computable CP-side at no axis-boundary cost. An out-of-range / stale-store ordinal, an un-recorded / `None` marker kind (presence ≠ validity), or a changed-to-non-TOOL resumed kind all STAY fail-closed.

## §3 — Accepted-scope notes + registered follow-on status + R-FS-1 closure semantics (FULL-SPEC)

> **The carrier (`effect_fence_paused_branches`, additive, drop-when-empty).** A NEW field on `FanOutResumeState` + `PeerFanOutResumeState` (C-CP-26 §26.2), each element an `EffectFencePausedBranchResumeState{branch_index, step_id, idempotency_key}`. It is DISJOINT from `branches` (a terminal branch never enters it), from `paused_child_branches` (a SUB_AGENT child-pause), and from absent ordinals (re-dispatch fresh) — the illegal-states-unrepresentable split. Resume validates each entry's bounds + step_id-identity + no-overlap with the other dispositions (fail-closed on a corrupt snapshot). Additive + default-empty: `_compute_snapshot_hash` DROPS the field from the canonical serialization when empty (the `synthesis_step_id` / `paused_child_branches` drop-when-default discipline), so every pre-existing snapshot hashes byte-identically. NO §5.2 IS-hash change (the carrier rides the C-CP-26 `PauseSnapshot` hash, NOT the IS six-field hash).
>
> **ACCEPTED PARITY — tool-swap (NOT a registered arc).** A tool-SWAP under the same `step_id` (marker TOOL_STEP, resumed TOOL_STEP, but a DIFFERENT `tool_id`) composes a DIFFERENT fence key (the §14.22 key is per-`(run, step, tool)`) → fires the new tool fresh; per-key at-most-once is PRESERVED (each tool key fires ≤once). This is the SAME structural consequence as the cleared LINEAR effect-fence path (which likewise re-dispatches the resumed manifest's step into the fence keyed on `tool_id`) — the CP driver cannot distinguish it because `tool_id` lives in the opaque `step_payload`. This is CORRECT PARITY with linear, not a missing capability — so it is DOCUMENTED, not registered. (A stricter-than-linear fail-closed-on-tool-swap is *possible* — record `tool_id` runtime-side in the marker — but is a policy stricter than the cleared linear path, not a deferred capability.)
>
> This delta CLOSES the parent arc **`B-FANOUT-CRASH-RESUME-MAYBE-RAN-EFFECT-BEARING`** as the **TOOL_STEP slice** + registers THREE narrower follow-ons (each NAMED + registered, never silently absorbed):
>
> - **`B-FANOUT-CRASH-RESUME-MAYBE-RAN-SUBAGENT`** (NEW, registered, `operator_gated: false`) — the resolution of a maybe-ran **SUB_AGENT_DISPATCH** worker. Unlike TOOL_STEP, a sub-agent's own dispatch does NOT hit the effect fence directly — its non-idempotent effects are its CHILD sub-workflow's tool calls, fenced at the CHILD's tool sinks. Resolving a maybe-ran sub-agent worker is recursive child crash-resume (compose the child's own fence/pause state through the parent barrier), a larger, separately-verified mechanism than the direct-tool-sink TOOL_STEP slice.
> - **`B-FANOUT-CRASH-RESUME-MAYBE-RAN-UNFENCED-EXTERNAL`** (NEW, registered, `operator_gated: false`) — the resolution of a maybe-ran **MANAGED_AGENTS** worker. The managed-agents dispatcher performs an UNFENCED vendor-session external effect (create_session + send_event), so there is no held reserve to make a re-dispatch at-most-once. Resolving it needs the C-RT-31 effect fence EXTENDED to the managed-agents sink (a runtime-side change), then the same barrier-composition as the TOOL_STEP slice.
> - **`B-FANOUT-EFFECT-FENCE-PER-BRANCH-RESOLUTION`** (NEW, registered, `operator_gated: false`) — a per-branch-DISTINCT effect-fence resolution. This slice applies ONE `EffectFenceResolution` TYPE across ALL effect-fence-paused branches in a pause (key-bound per branch, but the same RE_FIRE / SKIP_AS_FIRED / ABORT for all). Resolving two fence-paused branches DIFFERENTLY in one resume needs a `idempotency_key → EffectFenceResolution` MAP on `ResumeContext` (a new contract surface on C-CP-26 §26.8) + the driver lookup keyed per branch — a genuine capability the harness lacks today (surfaced during this build).
>
> `closure_gate.py` G1.1 (`standalone_registered + standalone_gated == 0`) was **4 + 0**; after this delta it is **6 + 0** (one closes, three register) → R-FS-1 stays ACTIVE. The R-FS-1 follow-ons keeping the program ACTIVE (now **6**): `B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT`, the two NEW orchestrator legs (`…-ORCHESTRATOR-MAYBE-RAN-EFFECT-BEARING` + `…-ORCHESTRATOR-PROCEED-RESIDUAL`, from v1.64 §3), and the three NEW legs above. This is the honest FULL-SPEC accounting — it does not declare the worker effect-bearing maybe-ran resolved-whole while the sub-agent + unfenced-external + per-branch-resolution residuals remain genuinely open.
