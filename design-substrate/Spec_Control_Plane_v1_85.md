## Change-note (v1.84 → v1.85)

**Grounding overturned the v1.84 registration anticipation — the SAVE_POINT fan-out substrate is NOT missing.** v1.84 §carrier-segregation registered `…-FANOUT-CHILD-SAVE-POINT-RECONCILER` on the premise that "a SAVE_POINT/RECONCILER fan-out child has NO fan-out replay store." Grounding at open (advisor BEFORE substantive work, `[[grounding-reveals-claude-closeable-slice-close-honestly]]`) shows that premise is over-cautious for SAVE_POINT — the same overturn shape as #779 ("needs an entirely NEW output substrate" → the `EngineOutputStore` is class-agnostic). Three empirical facts settle it:

1. **The branch-capture store is engine-class-AGNOSTIC.** `_fanout_replay_store` binds the SAME `EngineOutputStore` (`record_branch` / `read_branch_records`) the LINEAR `_record_durable_step_output` uses; it binds whenever `RuntimeConfig.engine_output_replay` is on, INDEPENDENT of engine class. The ONLY thing gating fan-out replay to {ESR,WAL} was the `_FANOUT_REPLAY_ENGINE_CLASSES` constant — a CP-side under-extension at #788 (when the SAVE_POINT fan-out composition was unverified), NOT a substrate gap.
2. **The fan-out AGGREGATE reconstruction consumes ONLY that class-agnostic store.** `_determine_fanout_resume` reconstructs from `store.read_branch_records(run_key)` — "the STORE is the SOLE which-branches-completed authority." It does NOT consume the §8.1 cached-output-replay inter-step channel (which IS ESR/WAL-only). So no ESR/WAL-specific dependency leaks into the fan-out path.
3. **The §14.22 effect fence is auto-active for SAVE_POINT.** The runtime `_DURABLE_AUTO_FENCE_ENGINE_CLASSES` includes ALL FOUR durable classes, so an in-flight SAVE_POINT fan-out branch's re-dispatch is at-most-once-safe (fenced) exactly as ESR/WAL.

**Why SAVE_POINT closes but RECONCILER does NOT (the decompose, advisor-directed, mirroring #779→#781).** SAVE_POINT_CHECKPOINT is the C-CP-11 §11.2 **ABOVE_ENGINE** reading — "harness composes lease + dedup + resumption" → the harness branch store is the SOLE aggregate authority, no engine-owned competing substrate, and SAVE_POINT fires NO recovery loop / CAS-claim (no F-1 window). RECONCILER_LOOP is the §11.2 **RECONCILER** reading — "control-loop owns reconvergence" via CRD-resource-version → whether the U-RT-123 reconciler substrate COMPETES with the branch store for the fan-out AGGREGATE authority (the two-authorities question #781 had to ground for the LINEAR slice), PLUS its CAS/F-1 won-claim window under a fan-out of branches, is UNGROUNDED. So RECONCILER is its own registered build arc, not complete-by-construction.

**Representability (FULL-SPEC honesty).** Fan-out + {SAVE_POINT,RECONCILER} is REPRESENTABLE: no load-time topology×engine validator forbids it (the §11.2 overlay is fault-handling, total over `EngineClass`, NOT admissibility), `engine_class` is operator-specified, and the §11.3 20-cell matrix admits every (workload, engine) pair except (PIPELINE_AUTOMATION, PURE_PATTERN) — a fan-out-default workload (RESEARCH → ORCHESTRATOR_WORKERS; SOFTWARE_ENGINEERING / PIPELINE_AUTOMATION permit ORCHESTRATOR_WORKERS) paired with SAVE_POINT or RECONCILER is admissible. So neither leg is a trivial resolve-invalid; SAVE_POINT is a genuine build (this delta), RECONCILER a genuine registered follow-on.

**Scope of revision.** One constant widen under **C-CP-25 §25.15**: `_FANOUT_REPLAY_ENGINE_CLASSES` {ESR,WAL} → {ESR,WAL,SAVE_POINT}. Conjunct 2 of the `_subagent_child_recoverable` predicate now reads:

- **SINGLE_THREADED_LINEAR** → any of `{ESR, WAL, SAVE_POINT, RECONCILER}` (UNCHANGED — the LINEAR auto-resume + the `reconstruct_final_state` seed back all four);
- **fan-out** (`PARALLELIZATION` / `ORCHESTRATOR_WORKERS` / `HIERARCHICAL_DELEGATION`) → `{ESR, WAL, SAVE_POINT}` (the widened `_FANOUT_REPLAY_ENGINE_CLASSES` the `_fanout_replay_store` branch-capture gate backs);
- any other topology (`EVALUATOR_OPTIMIZER` / `DECENTRALIZED_HANDOFF`) → fail closed (no reconstruction substrate). RECONCILER under fan-out → fail closed (the registered `…-FANOUT-CHILD-RECONCILER`).

**Shared-constant widen is the one-source-of-truth move (NOT a carrier-segregation violation).** `_FANOUT_REPLAY_ENGINE_CLASSES` is consumed by BOTH the branch-capture PRODUCER gate (`_fanout_replay_store` → `_capture_branch_terminal` / `record_branch`) AND the recoverability predicate (`_fanout_recoverable`). For SAVE_POINT fan-out recovery to be sound, the capture MUST fire (so the store holds the branches to reconstruct from) AND the predicate must admit it — the two halves of one mechanism MUST share their scope key (`[[durable-recovery-presence-validity-scope]]`). Widening the shared constant moves both in lockstep; a separate set would risk a capture/predicate skew. The v1.84 "must NOT admit SAVE_POINT/RECONCILER" comment described the pre-this-arc state — this delta is precisely the arc that grounds SAVE_POINT into it. The set stays DISTINCT from the four-class LINEAR `_FINAL_STATE_RECONSTRUCT_ENGINE_CLASSES` (RECONCILER is in the latter, not yet the former).

**Scope honesty — the capture gate is RUN-scoped, so this ALSO activates TOP-LEVEL SAVE_POINT fan-out recovery.** `_fanout_replay_store` gates on `manifest_entry.engine_class` of the RUN, and `_capture_branch_terminal` / `_mark_branch_dispatched` fire in the run-scoped concurrent-strategy dispatch path reached by EVERY SAVE_POINT fan-out run at `execute_workflow` — not only a sub-agent child. So widening the constant ALSO makes a top-level SAVE_POINT fan-out run capture its branches and recover its aggregate via `_determine_fanout_resume`, where before it did not. This is INTRINSIC to the mechanism (a run-engine-class gate cannot be scoped to "only when this run is a sub-agent child") and is a strict improvement — the exact engine-class-agnostic B-FANOUT-OUTPUT-REPLAY machinery the {ESR,WAL} top-level feature (#723/#724) already uses, now extended to SAVE_POINT (full suites green). The sub-agent-child case is the arc's NAMED surface; the top-level activation is a beneficial co-effect closing a latent top-level SAVE_POINT fan-out gap, not a scope overreach.

**CAN vs DOES — the by-execution RED-without-fix witness (advisor, the honest-vs-vacuous gate).** Substrate-agnosticism proves the producer CAN fire, not that it DOES. `test_fanout_child_save_point_reconstructs_aggregate_under_deterministic_seed` drives the REAL `compose_child_workflow_runner` → `execute_workflow` for a `SAVE_POINT_CHECKPOINT` PARALLELIZATION child, two-phase (clean capture → delete one in-flight branch → resume under the SAME deterministic seed): **RED before the widen** — `_fanout_replay_store` returned `None` for SAVE_POINT, so Phase-1 captured NOTHING (`present_branch_indexes == set()` ≠ `{0,1,2}`) — empirically confirmed by reverting the constant. **GREEN with the widen** — the class-agnostic store captures the SAVE_POINT branches, `_crash_fan_out_resume` reconstructs the aggregate (committed effect-bearing branches 0+2 recovered fire-once, only in-flight branch 1 re-dispatched, result-faithful to a clean run). This blocks the "green-over-dead-producer" failure (`[[built-but-vacuous-reground-ledger-asis]]`).

**Cross-topology at-most-once swap guard — already covered by the #788 fold (no new hole).** Admitting SAVE_POINT under fan-out opens the same swap surface #788 closed for {ESR,WAL}: a maybe-ran child dispatched LINEAR-SAVE_POINT (recoverable via the LINEAR `reconstruct_final_state` seed) whose resumed manifest swaps ONLY topology to fan-out (recoverable via the SEPARATE `_crash_fan_out_resume` branch store) would reuse the same engine-class-agnostic `child_run_id` against a DIFFERENT substrate. The #788 `_payload_engine_signature` fold ALREADY folds `f"{topology}:{engine}"` for a fan-out child, so a fan-out SAVE_POINT signature `parallelization:save-point-checkpoint` is distinct from the bare LINEAR `save-point-checkpoint` and from every other engine/topology combo → the dual-gate marker==resumed comparison fails closed. Witnessed for the NEW engine at `test_recursive_signature_catches_save_point_topology_swap` (LINEAR-SAVE_POINT ↔ fan-out-SAVE_POINT and fan-out↔fan-out swaps both change the marker). No new identity dimension — `{engine_class, topology_pattern}` remains the complete recovery-selecting pair (#788 *Completeness of the topology fold*); SAVE_POINT simply adds a member to the engine axis already folded.

**At-most-once scope (the honest claim).** The widen introduces NO new at-most-once window versus the {ESR,WAL} fan-out-child slice: a SAVE_POINT fan-out child's in-flight branch at re-dispatch has the SAME tier-governed maybe-ran disposition (re-fire-safe fresh / fence-recoverable fenced / unfenced fail-closed) handled by the EXISTING B-FANOUT-CRASH-RESUME-MAYBE-RAN family, and SAVE_POINT (UNLIKE RECONCILER) fires NO CAS-claim → no F-1 window at all. The by-execution witness proves committed-effect non-re-fire across crash+resume — the load-bearing claim. The PROCEED in-flight-effect-bearing re-fire window is the SEPARATELY-registered, operator-gated `…-ORCHESTRATOR-PROCEED-RESIDUAL`, not this arc.
