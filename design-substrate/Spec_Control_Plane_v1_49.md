## Change-note (v1.48 → v1.49)

**Scope of revision.** A single behavioral specification at **C-CP-06 §6.2**: the per-step `StepOverride.hitl_placement` override **fold** — how the singular per-step placement override (`StepOverride.hitl_placement: HITLPlacement | None`, an existing field since v1.6) composes with the workflow-level `WorkflowManifestEntry.hitl_placements` tuple (C-CP-17 §17.3) onto the per-step `StepExecutionContext.hitl_placements` (the v1.41 producer field) so the runtime wrap-time HITL gate composer (runtime §14.8.2 step 1) reads the **effective** per-step placement set. This is the **R-FS-1 standalone arc `B-HITL-PLACEMENT-PER-STEP-OVERRIDE-FOLD`** (registered at `.harness/beyond-mvp-capability-boundary-ledger.md`), the follow-on the v1.41 producer arc named as the "separate, under-specified add-vs-replace semantic decision." It resolves the v1.41-registered silence and makes the previously-DEAD `StepEffectiveBinding.hitl_placement` resolution load-bearing.

**The fold semantic — ADD-only (an override ADDs an absent `position`; on a same-`position` collision the workflow placement WINS) — is genuinely monotone; NO operator gate.** The discriminator the workspace applies (v1.38 per-step ROLE was operator-gated because it relaxed the §14.5.3 committed "single role source" invariant; v1.37 per-step PROMPT + v1.41 producer were NOT, sacrificing none): an ADD-only fold **sacrifices no committed invariant** and is monotone at BOTH the position level and the attribute level. The reasoning:

1. **The singular type forecloses set-replacement (position-level removal).** `StepOverride.hitl_placement` is **singular** (`HITLPlacement | None`); the workflow source is a **tuple** (`hitl_placements`). A singular field cannot represent a replacement of the workflow set — "replace the workflow's N placements with these M" is structurally unrepresentable (illegal-states-unrepresentable, root `CLAUDE.md` §4). So a per-step **removal** of a workflow gate position is not expressible.

2. **But the singular type does NOT foreclose attribute-level loosening — so a replace/tune on a same-`position` collision is EXCLUDED.** `HITLPlacement` carries `tool_filter` ("limits which tools trigger the gate"), `cascade_policy`, and `timeout`. *Replacing* a same-position workflow placement with the per-step override could **loosen** the §17.1 "all cells" floor at the attribute level while the position stays present — e.g. a workflow `PRE_ACTION(tool_filter=None)` (gates all tools) replaced by a per-step `PRE_ACTION(tool_filter=("git_push",))` leaves every other tool **ungated** at that step. Position-level monotonicity does NOT imply attribute-level monotonicity. Therefore the fold does **not** replace/tune on a collision — the **workflow placement wins** (the override is a no-op for an already-present position).

3. **ADD-only is the genuinely-monotone fold (overrides only TIGHTEN).** An override whose `position` is absent ADDs a gate that did not exist (strictly more gating); an override whose `position` is present is ignored. The fold can neither remove a position NOR weaken an existing one. This is the placement-set analogue of the §19.1 `max()`-over-escalation-rank floor-only gate-level posture (`gate_level_rule.py`: `per_tool_gate_level` + `mcp_trust_tier` "NEVER overridden", U-CP-91; v1.35 `MCP_TRUST_GATE_LEVEL_FLOOR` floor-only). §17.1 is the workflow's declared HITL safety floor; an ADD-only override raises it locally, never lowers it.

The fold is therefore **impl-to-cleared-spec** on the existing C-CP-06 contract (the `StepOverride.hitl_placement` field + `StepEffectiveBinding.hitl_placement` resolution + the §6.2 field-by-field discipline all pre-exist; v1.17 §6.2 already described the effective field's source as "manifest_entry hitl_placements per §6.1 + per-step override"). It mints **no** new contract, ADR, enum, fail-class, manifest field, §5.2 hash-recipe, §16.5.4 idempotency key, or CXA edge. Because the ADD-only fold sacrifices nothing committed, there is **no operator gate** (`[[feedback-gate-only-on-meaningful-architecture-change]]`); FULL-SPEC (`[[feedback-full-spec-beyond-mvp-nothing-deferred]]`) pre-authorizes the build + back-flow.

**Per-step tune/replace OR removal is a separate operator-gated arc.** Per-step *modification* of an existing workflow placement (tune/replace — which can loosen attributes like `tool_filter`) OR *removal* of a workflow gate position (lowering the §17.1 "all cells" floor at a trusted step) is a committed-invariant relaxation (the monotone HITL posture) plus a typed-shape change (a tuple-valued, removal/replace-capable per-step carrier) — a **separate operator-gated ADR/spec request**, registered (not built) at the spine ledger as `B-HITL-PLACEMENT-PER-STEP-LOOSEN`. This v1.49 build is ADD-only / monotone by construction.

**Mechanism — the v1.38 Option-B composition-time fold (single dispatch-read source PRESERVED).** The CP driver folds `binding.hitl_placement` onto the single `StepExecutionContext.hitl_placements` source at the per-step / per-branch composition sites — the exact structural template as the v1.38 `agent_role` fold (`binding.agent_role` → `step_context.agent_role`) and the v1.20 `default_gate_level → StepExecutionContext.parent_gate_level` lift. The runtime dispatch read is **unchanged** (the composer reads `step_context.hitl_placements` verbatim, runtime §14.8.2 step 1); only the produced tuple is now the *effective* set. **Zero runtime dispatch code change.** The fold is performed by a pure helper `fold_step_hitl_placements(workflow_placements, override)` keyed from `manifest_entry.hitl_placements` (the workflow base) at each site, so a per-step override on one cell never leaks to a sibling cell (the orchestrator's own placement override does not propagate to its workers).

**v1.48 + prior body PRESERVED VERBATIM.** All v1.48 content — the §26.2 EO resume carriers + the entire C-CP-01 … C-CP-29 body incl. §6.x / §16.5.x / §25.x / §26.x — is PRESERVED VERBATIM per the delta-only-spec-file convention. Within C-CP-06: §6.1 (`StepOverride` schema, incl. the v1.6 `hitl_placement` field) / §6.3 / §6.4 / §6.5 / §6.6 / §16.5.x are PRESERVED VERBATIM; the **only** change is the §6.2 fold specification below (a behavioral spec of an existing field's resolution + driver composition; no field added).

## §1 — Amended C-CP-06 §6.2 per-step override fold for `hitl_placement`

`resolve_step_binding` continues to resolve `StepEffectiveBinding.hitl_placement = override.hitl_placement` field-by-field (the existing §6.2 `None`-or-override discipline, unchanged — like `prompt_version_sha` / `agent_role`, there is no manifest-entry-level placement default at this layer; `None` ⟹ no per-step override). The **fold** of that resolved per-step override onto the workflow placement tuple is specified here as a CP-driver composition step (the `agent_role` precedent):

> **Effective per-step HITL placements (NEW spec at v1.49).** The effective placement set surfaced on `StepExecutionContext.hitl_placements` for a step is the **ADD-only** fold of the workflow's `WorkflowManifestEntry.hitl_placements` tuple (C-CP-17 §17.3) with the resolved per-step `StepEffectiveBinding.hitl_placement` (when non-`None`):
>
> - When the per-step override's `position` is **not present** in the workflow tuple → the override is **appended** (ADD a gate position at this step — strictly adds gating that did not exist).
> - When the per-step override's `position` **is already present** in the workflow tuple → the **workflow placement WINS** (the override is a no-op for that position). The fold does **not** replace/tune an existing placement, because replacing it could **loosen** the §17.1 floor at the attribute level (`HITLPlacement.tool_filter` narrows which tools trigger the gate; a weaker `cascade_policy` / shorter `timeout`) while the position stays present.
> - When there is no per-step override (`None`, the default) → the workflow tuple is surfaced **verbatim** (byte-identical to the v1.41 producer-only arc; §14.5.3-style invariant-1 non-breaking default).
>
> The fold is **genuinely monotone — overrides only TIGHTEN, never loosen — at BOTH the position level and the attribute level**: the singular per-step override can ADD an absent position but can neither remove a workflow-declared position (the singular `HITLPlacement | None` type makes set-removal unrepresentable) NOR weaken an existing one (a same-`position` collision is a no-op, not a replace). This realizes the §17.1 "all cells" workflow floor as a *floor* the per-step override raises locally, never lowers — the placement-set analogue of the §19.1 `max()`-over-rank monotone gate-level posture. The composer (runtime §14.8.2 step 1) reads the resulting tuple unchanged and filters by its `applicable_placements` set; the ADD-only fold **never introduces a duplicate `position`** (the override never adds a second placement for a position the workflow already declares). It does NOT de-duplicate a workflow that *itself* declares two same-`position` placements — that is a workflow-validation concern (the composer would fire once per matching placement), out of scope for this fold. Per-step tune/replace of an existing position is the separate operator-gated `B-HITL-PLACEMENT-PER-STEP-LOOSEN` arc.

The §6.2 field-by-field-no-field-set-substitution discipline is unchanged; the per-step override `hitl_placement` continues to ride `resolve_step_binding` as before. The **driver composition** folds `binding.hitl_placement` onto `step_context.hitl_placements` at: the `SINGLE_THREADED_LINEAR` per-step site; the `EVALUATOR_OPTIMIZER` per-step site; the `ORCHESTRATOR_WORKERS` orchestrator-step + worker-branch sites; the `PARALLELIZATION` worker-branch site; and the `HIERARCHICAL_DELEGATION` / `DECENTRALIZED_HANDOFF` stage sites — each keyed from `manifest_entry.hitl_placements` (the workflow base), so an override on one cell does not leak to siblings. Branch children inherit the folded tuple from their composed branch context.
