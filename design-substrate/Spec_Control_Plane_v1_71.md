## Change-note (v1.70 → v1.71)

**Scope of revision.** One CP surface in `harness_cp.workflow_driver` — the `CascadePolicy.PAUSE ∧ _crash_pause_trigger ∧ ¬_crash_complete` crash-resume leg (the v1.70 §2 `fan-out-crash-resume-pause-trigger-ambiguous` fail-closed). The gate is widened from "the FULL `_maybe_ran` set must be EMPTY" to "the `_refire_unsafe_branch_indices(_maybe_ran)` subset must be EMPTY" — recovering ONLY re-fire-safe maybe-ran ordinals (`DECLARATIVE_STEP` / `INFERENCE_STEP`). The three fan-out strategies are UNCHANGED (the re-pause-without-dispatch mode already skips every not-yet-recovered ordinal — the re-fire-safe maybe-ran ones now ride that same skip). This is the build of the registered R-FS-1 standalone arc **`B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT-MAYBE-RAN`** as its re-fire-safe slice. v1.70 §2 registered it as "the hard residual … needs the per-kind effect-surface refinement (re-fire-safe / fence-recoverable absent branches) COMPOSED with this delta's obl-5-respecting re-pause mode."

**The capability gap it closes.** Before this arc, a strict-tier (PAUSE / `TEAM_BINDING`) fan-out whose branch failed under `pause` and then crashed before the durable `PauseSnapshot` landed FAILED CLOSED whenever ANY absent ordinal was a maybe-ran (a dispatch marker, no capture) — even a re-fire-safe `DECLARATIVE_STEP`. v1.70's deliberately-strict gate reserved that whole window for this follow-on. But an interrupted-in-flight absent ordinal of a RE-FIRE-SAFE kind has NO external effect to double-fire on re-dispatch — so it is SAFE to OMIT-and-re-dispatch-on-`api.resume` regardless of the resume manifest, exactly like the not-yet-dispatched window. This delta RE-ESTABLISHES the PAUSED state for that window: the operator still gets their HITL boundary, the snapshot OMITS the re-fire-safe maybe-ran ordinals (as it omits the not-yet-dispatched), and `api.resume` re-dispatches them under obl-5.

**Why the fence-recoverable kinds are SPLIT OFF (the Codex [P1] catch, decided at open).** The arc's registration anticipated lifting BOTH re-fire-safe AND fence-recoverable (`TOOL_STEP` / `MANAGED_AGENTS`) maybe-ran ordinals by reusing the §25.15 `_fence_unrecoverable_maybe_ran_indices` predicate. Out-of-family Codex flagged that this is UNSOUND for the PAUSE-reconstruct: the §25.15 incomplete leg re-dispatches a fence-recoverable maybe-ran AT CRASH-TIME with the SAME `_crash_branch_steps` manifest — so the runtime fence key `(idempotency_key, step_id)` matches the maybe-fired effect's held claim, and the re-dispatch is suppressed/folded (at-most-once). But this reconstruct OMITS the ordinal and DEFERS its re-dispatch to `api.resume` (operator-mediated; the manifest may be edited), and the snapshot carries NO `step_id` for the omitted ordinal. A same-kind CHANGED-`step_id` resume would re-dispatch under a DIFFERENT fence key, miss the held claim, and DOUBLE-FIRE the maybe-fired effect. The orchestrator's same-`step_id` guard (`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-EFFECT-BEARING`, CP v1.69) works only because the orchestrator re-dispatches AT classification time / carries its own resume carrier; a deferred-omitted worker has neither. Resolving it SOUNDLY needs the snapshot to CARRY the marker `(idempotency_key, step_id)` per omitted fence-recoverable ordinal + compare at `api.resume` before re-dispatch — a distinct, larger mechanism mirroring the orchestrator's carrier. That is the registered follow-on **`B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT-MAYBE-RAN-FENCE-STEP-ID`** (§2). The SAME hole at LOWER exposure exists in #742's crash-time `_fence_unrecoverable_maybe_ran_indices` predicate (a crash-resume could in principle be handed an edited manifest); it is folded into that follow-on's scope, NOT fixed here (no change to #742's cleared semantics).

**The mechanism (re-fire-safe via the obl-5 re-pause mode).** At the cascade-policy crash-resume classification, the `PAUSE ∧ _crash_pause_trigger ∧ ¬_crash_complete` leg classifies the maybe-ran set by RE-FIRE-SAFETY:

```text
_pr_instrumented   = store.dispatch_instrumented(run_key)
_pr_recovered      = { b.branch_index for b in crash_resume.branches }
_pr_maybe_ran      = store.present_dispatched_indexes(run_key) - _pr_recovered
_pr_maybe_ran_kinds  = store.dispatched_branch_kinds(run_key)
_pr_maybe_ran_unsafe = _refire_unsafe_branch_indices(_pr_maybe_ran, _pr_maybe_ran_kinds, expected)
if _pr_instrumented and not _pr_maybe_ran_unsafe:    # not-yet-dispatched + RE-FIRE-SAFE maybe-ran
    _crash_pause_reconstruct_no_dispatch = True       # fall through to the re-pause mode
else:                                                 # fence-recoverable / SUB_AGENT / un-kinded / un-instrumented
    return FAILED("fan-out-crash-resume-pause-trigger-ambiguous: … not re-fire-safe …")
```

A `True` flag drives the EXISTING v1.70 re-pause-without-dispatch strategy mode verbatim: each fan-out strategy's branch-dispatch loop already `continue`s on every not-yet-recovered ordinal when the flag is set → the re-fire-safe maybe-ran ordinals (which are not-yet-recovered) are SKIPPED alongside the not-yet-dispatched → an empty/partial `branch_plan` → the v1.68 `_crash_pause_reestablish` / `not branch_plan` re-establish block builds the snapshot from the recovered terminals OMITTING the absent, and returns PAUSED. `api.resume` re-dispatches the omitted ordinals — the omitted ordinal is snapshot-absent ⟹ re-dispatched (keyed on `branch_index in _recovered_terminal`, NOT a divergent `terminal_status` read). NO strategy edit — the flag's meaning is unchanged; only the gate that sets it is widened. NOT the §25.15 `_fence_unrecoverable_maybe_ran_indices` (that narrows `TOOL_STEP`/`MANAGED_AGENTS` back IN — correct for its crash-time same-manifest re-dispatch, UNSOUND for this deferred-omitted resume).

**Why this honors obl-5.** The §25.15 incomplete-recovery leg recovers a re-fire-safe maybe-ran by re-dispatching it AT CRASH-TIME; for a PAUSE trigger that would bypass the operator's blast-radius gate. This delta routes the re-fire-safe maybe-ran into the RE-PAUSE mode (omit + defer the re-dispatch to `api.resume`), and the §25.15 leg stays guarded `and not _crash_pause_reconstruct_no_dispatch` so it never reaches its crash-time re-dispatch path.

**Fidelity — re-dispatch faithfulness, NOT a byte-match of a live pause.** v1.70 named the maybe-ran ambiguity as DOUBLY-ambiguous: (a) the effect maybe-fired AND (b) the ordinal maybe-was-a-second-pause-trigger. For a RE-FIRE-SAFE ordinal both are resolved: (a) a re-fire-safe kind has NO external effect to double-fire (the only cost is re-execution non-determinism, already accepted); (b) the pause is ALREADY established by trigger #1, and the omitted ordinal is RE-DISPATCHED on `api.resume`, so its true disposition (including a failure) RE-SURFACES there — never silently dropped (witnessed: a re-fire-safe maybe-ran whose resume re-dispatch FAILS AGAIN is HANDLED). The post-resume PARTIAL state EQUALS the no-crash baseline for a DETERMINISTIC re-fire-safe branch; a NON-deterministic one CAN differ — the §14.8.8.7 invariant-3 re-ask semantic (already-committed; the unfenced linear resume already re-asks per retry), NOT a regression.

**Why a spec amendment — and why it carries NO new operator gate.** The change relaxes one fail-closed leg for re-fire-safe maybe-ran ordinals; it reconstructs a state shape the harness already produces (the v1.70 re-pause mode) and resumes through the existing path. It changes NO contract removal, NO closed enum, NO committed invariant — §25.15.1 + §25.15.2 obl-5/obl-7 are IMPLEMENTED for the re-fire-safe-maybe-ran crash-resume path, not changed (the v1.68/v1.70 impl-to-cleared-spec posture). At-most-once is PRESERVED (a re-fire-safe re-dispatch has NO external effect under ANY resume manifest — the deferred-`step_id` double-fire hazard is fence-effect-only, which is exactly why the fence-recoverable kinds are split off). The arc's registration carried `operator_gated: false (provisional — decided at open)`. **Decided at open: it stays `false`** for the re-fire-safe slice — neither at-most-once nor the pause semantic is sacrificed. Co-published with a `.harness/clearance/` marker (CP v1.71) per workspace `CLAUDE.md` §11.4.
