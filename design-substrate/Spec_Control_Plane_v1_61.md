This delta is ADDITIVE — it CLOSES the v1.60 §1 scope carve-out (the ORCHESTRATOR_WORKERS `steps[0]` orchestrator's OWN dispatch-before-capture double-fire window) by extending the reserve-before-DISPATCH at-most-once primitive to the orchestrator's sequential dispatch. ## Change-note (v1.60 → v1.61)

**Scope of revision.** One mechanism under **C-CP-25 §25.12 / §25.15** (paired with a runtime **C-RT-32 §14.23** store extension): **reserve-before-DISPATCH for the orchestrator's own `steps[0]` dispatch** — the build of the registered R-FS-1 standalone arc **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-DISPATCH`** (registered at v1.60 §1 scope note + §4 as "the ORCHESTRATOR_WORKERS `steps[0]` orchestrator's own pre-existing dispatch-before-capture double-fire window … the sequential-dispatch analogue of the per-branch reserve"). v1.60 added reserve-before-DISPATCH for fan-out WORKER/PEER branches but EXPLICITLY left the orchestrator's own window OUT (§1: "Scope: WORKER/PEER branches only — the orchestrator's own dispatch is OUT"). This delta closes that window. PR flips the arc-ledger `registered → closed`; R-FS-1's resolution is governed by §4 below.

**The pre-existing gap (v1.60 §1 scope note, verbatim premise).** The orchestrator (`steps[0]`) runs FIRST, sequentially, before any worker fans out. It is recovered on a crash-resume via its own `record_orchestrator` **reserve-before-COMMIT** capture (the output captured AFTER it completes). But its OWN dispatch-before-capture window was uncovered: the orchestrator fires its effect, then a crash BEFORE `record_orchestrator` (and before the cardinality marker) leaves NO orchestrator record + no cardinality → `_determine_fanout_resume` returns None → a fresh re-run re-dispatches `steps[0]` → a potential double-fire on the compliance tier. This window has ALWAYS returned None (fresh) — even post-v1.57/v1.60 (the worker markers do not cover it; the orchestrator is a sequential dispatch, not a fan-out branch).

**Why a spec amendment — and why it carries NO new operator gate.** The recovery semantics change (an orchestrator that maybe-ran now FAILS CLOSED instead of silently re-dispatching `steps[0]` fresh; one that provably-not-ran re-runs fresh as before) is enabled by extending the SAME non-attested at-most-once substrate v1.60 introduced — a reserve-before-DISPATCH marker, now at orchestrator granularity. The substrate is a **non-attested sibling extension of C-RT-32 `EngineOutputStore`** (the v1.55 branch-API / v1.56 synthesis-API / v1.60 dispatched-marker precedent — not in the §6 hash chain, consumed via the `cp_is_wiring` getattr idiom). It is **additive**: it changes NO contract, NO enum, and NO committed invariant. At-most-once is PRESERVED — it is the WHOLE point: the orchestrator is re-dispatched ONLY when its marker is ABSENT (provably not-fired), so the change can never introduce a double-fire (`[[disposition-label-is-a-claim-verify-against-spec]]`: the pre-arc unconditional return-None on `orchestrator-None + no-branches` was the conservative IMPL of fresh-run for the ambiguous window, not a committed invariant). `operator_gated: false`. Co-published with a `.harness/clearance/` marker per workspace `CLAUDE.md` §11.4.

**The mechanism (design-vetted: advisor full-transcript + the §25.15 / §26.2 at-most-once probe + out-of-family Codex [P2]; no council — no nameable cross-domain tension, the design is dictated by the v1.60 reserve-before-dispatch precedent + the cleared §25.15 contract).** THE NAMED INVARIANT: the driver writes a durable, fsynced per-run orchestrator dispatch marker (C-RT-32 `record_orchestrator_dispatched`) STRICTLY BEFORE the orchestrator body dispatches, so within an instrumented run **marker-absent ⟺ the orchestrator's effect did NOT fire**. The orchestrator dispatch is **SYNCHRONOUS** (no `ensure_future` / yield between the marker write and the dispatch), so unlike the worker path there is no atomicity dance — no false-positive marker is possible. On an ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION crash-resume where nothing is recovered (orchestrator output absent + no worker), the driver classifies the orchestrator by the marker's **presence alone** (presence-only, like `present_dispatched_indexes`):
- **provably-not-run** (no dispatch marker) → safe to re-run fresh (the orchestrator + workers re-dispatch, first-and-only — the marker is the at-most-once proof);
- **maybe-ran** (the dispatch marker is PRESENT but NO terminal-capture record) → the narrow fire→capture window; its effect MAY have fired → fail closed (`fan-out-crash-resume-orchestrator-maybe-ran`). Its resolution is the registered follow-on **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-RESOLUTION`** (§4).

The cross-version guard is **INHERENT in the new-file marker** (`[[durable-recovery-presence-validity-scope]]`): `orchestrator.dispatched` is a NEW file written ONLY by this arc's instrumented code, so a pre-arc journal carries no orchestrator marker → it classifies as provably-not-run → the unchanged fresh re-run. The marker's presence is therefore self-proving — the classifier needs NO dispatch-instrumented stamp gate. Critically, an **orphaned marker WITHOUT the stamp still fails closed** (out-of-family Codex [P2]): the stamp is written before the marker, so a marker-without-stamp is an INCONSISTENT store (corruption / tamper / partial loss), NOT a legitimate pre-arc journal — gating maybe-ran on the stamp (an earlier draft) would have let an orphaned marker fall through to a fresh re-dispatch (a latent double-fire); the marker-presence-alone rule closes that. PROCEED is UNCHANGED — it writes no orchestrator marker and consumes none (its recovery accepts the orchestrator dispatch-before-capture window per the v1.56 PR2-round-4 precedent; see §4 for the PROCEED residual).

**The PARALLELIZATION changed-topology guard is widened to the marker.** v1.60's `_determine_fanout_resume` already failed a PARALLELIZATION resume closed when the store held an orchestrator RECORD (a changed-topology resume of an ORCHESTRATOR / HIERARCHICAL run). A maybe-ran orchestrator leaves no record, only the marker — so the guard is widened to also fail closed on the orchestrator DISPATCH marker (a peer fan-out never writes it, so this only fires on a genuine changed-topology resume of a maybe-ran orchestrator).

**v1.60 + prior body PRESERVED VERBATIM.** All v1.60 content (the WORKER/PEER reserve-before-dispatch markers + strict-tier incomplete-recovery classification) + the entire C-CP-01 … C-CP-29 body (incl. §5.2, §25.10–§25.18, the §25.15 cascade contract, §25.12 D1 + D1.b, the §3/§4 opt-in synthesis amendment, C-CP-26 §26.2 PauseSnapshot envelope) is PRESERVED VERBATIM. The only additions are §1–§3 + the §4 follow-on accounting. No enum, no contract, no committed-invariant change.

## §1 — Reserve-before-dispatch for the orchestrator `steps[0]` (C-CP-25 §25.12 / §25.15)

> **The orchestrator reserve-before-dispatch marker.** For the strict tiers (PAUSE + CASCADE_CANCEL), the driver resolves the dispatcher FIRST (a PURE registry lookup — no effect), then writes a durable, fsynced per-run ORCHESTRATOR DISPATCHED marker (C-RT-32 `record_orchestrator_dispatched`) + the dispatch-instrumented stamp STRICTLY BETWEEN the lookup and the orchestrator (`steps[0]`) `dispatch()`. Writing the marker AFTER the lookup is load-bearing: a lookup failure (unknown `step_kind`) raises BEFORE any effect could fire, so it must leave NO marker — else a false marker would poison a later same-run-key recovery into a spurious fail-closed (out-of-family Codex [P2]). The lookup → marker → dispatch sequence is SYNCHRONOUS — no `ensure_future` / yield — so the marker still strictly precedes the effect with no interleave; no false-positive marker is possible (the worker path's `ensure_future`-atomicity reasoning is unnecessary here). The marker is the sequential-dispatch analogue of the v1.60 per-branch reserve: within an instrumented run, **marker-absent ⟺ the orchestrator's effect did NOT fire**. PROCEED writes NO orchestrator marker (its recovery is unchanged).

> **The orchestrator-dispatch classification (resume).** On an ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION crash-resume (`resume_snapshot is None`, replay-capable ∧ store-bound) where the orchestrator output is ABSENT and no worker was recovered (the `_determine_fanout_resume` `orchestrator is None ∧ no branches` case), the driver classifies the orchestrator by the marker's **presence alone**:
> - **maybe-ran** = the orchestrator dispatch marker is PRESENT → the orchestrator BEGAN dispatch (its effect may have fired) but its terminal record is absent (the fire→capture window). Fail closed (`fan-out-crash-resume-orchestrator-maybe-ran`): re-dispatching `steps[0]` risks a double-fire on the effect-bearing strict tiers. (An orphaned marker without the dispatch-instrumented stamp ALSO fails closed — it is an inconsistent store, never a pre-arc journal, per the cross-version note above; out-of-family Codex [P2].)
> - **provably-not-run** = no marker → return the unchanged fresh re-run (the orchestrator + workers re-dispatch, first-and-only). A pre-arc journal (no orchestrator marker ever written) classifies here too — the new-file marker is the inherent cross-version guard.
>
> The `orchestrator is None ∧ workers-completed` case is UNCHANGED (an inconsistent store — the orchestrator completes BEFORE any worker dispatches → fail closed, v1.55).

> **Changed-topology guard widened.** A PARALLELIZATION resume whose store holds an orchestrator dispatch MARKER (output absent) is a changed-topology resume of a maybe-ran orchestrator → fail closed (the v1.55 orchestrator-record topology-mismatch guard, widened to the marker). A peer fan-out never writes the orchestrator marker, so this only fires on a genuine topology change.

## §2 — The dispatch-instrumented stamp (orchestrator path)

> The dispatch-instrumented stamp (C-RT-32 `record_dispatch_instrumented`, v1.60 §2) is the WORKER classifier's cross-version guard (it distinguishes "no worker markers because none dispatched" from "no markers because pre-arc"). This delta also writes it in the orchestrator block STRICTLY BEFORE the orchestrator dispatch (idempotent, last-wins) for consistency with the worker fan-out-start stamp + to record the run instrumented from the orchestrator dispatch onward. **The orchestrator-dispatch classification (§1) does NOT gate on it** — the orchestrator marker is a NEW file (a pre-arc journal carries none), so the marker's presence alone is the fail-closed signal and its absence alone is the fresh-run signal. The stamp ordering (stamp before marker) is what makes a marker-without-stamp provably an inconsistent store rather than a legitimate state (§1 cross-version note).

The v1.60 §1 scope-note prose stands as the historical record of the WORKER/PEER-only slice; this §3 supersedes its "the orchestrator's own dispatch is OUT … is NOT closed by this slice" as the standing rule — the orchestrator dispatch-before-capture window is now closed for the **provably-not-run** case (fresh re-run) and **maybe-ran** case (fail closed), per the workspace stale-carry-text discipline.

## §4 — Registered follow-on status + R-FS-1 closure semantics (FULL-SPEC)

> This delta CLOSES `B-FANOUT-CRASH-RESUME-ORCHESTRATOR-DISPATCH`. It REGISTERS one new FULL-SPEC follow-on: **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-RESOLUTION`** — the orchestrator analogue of the registered worker `B-FANOUT-CRASH-RESUME-MAYBE-RAN-RESOLUTION`: a maybe-ran orchestrator (dispatched, but its effect crashed before its terminal capture) still fails closed; resolving it (a post-dispatch output capture that distinguishes completed-and-captured from genuinely-ambiguous, then suppress-and-continue or a §26.2 pause — the fan-out analogue of the B-EFFECT-FENCE-HITL-ROUTE / B-EFFECT-FENCE-PAUSE-RESOLUTION family) is a genuine design problem, not a deferral. **This follow-on ALSO carries the PROCEED-orchestrator pre-capture residual** (named here per FULL-SPEC rather than silently absorbed): under PROCEED (SOLO_DEVELOPER), the orchestrator's pre-capture window still re-dispatches `steps[0]` fresh on a crash — a potential double-fire. It is folded into this follow-on rather than left silent.

PR flips the arc-ledger `registered → closed` (ORCHESTRATOR-DISPATCH) + registers ORCHESTRATOR-MAYBE-RAN-RESOLUTION; `closure_gate.py` G1.1 (`standalone_registered + standalone_gated == 0`) stays **4 + 0** → R-FS-1 stays ACTIVE.
