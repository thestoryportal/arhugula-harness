## §1 U-CP-45 amendment — `verify_rotation_6_steps` OD-anchored rotation-boundary extension (CP v1.105 §1)

The v2.38 U-CP-45 body (`Implements: … C-CP-20 §20.3, §20.3.1`; the §3 row-7 acceptance criterion "Rotation-pair steps 3–6 PRESERVED VERBATIM; their backend-aware implementation remains B-33's scope — not this arc") is PRESERVED VERBATIM as a HISTORICAL record of the prior deferral; v2.41 SUPERSEDES that ONE criterion (retiring the deferral it named) and adds:

**Implements (addition):** + C-CP-20 §20.3.1 row 7 (AMENDED at CP v1.105 §1 — retires the B-33 deferral) + C-CP-20 §20.3.2 (NEW at CP v1.105 §2 — the `RotationPairEvidenceProvider` Protocol + `RotationPairEvidence` DTO + `RotationPairIntegrityBreach` + `RotationPairEvidenceUnavailableError`, consumed by this unit's extension).

**Superseded criterion:** the v2.38 acceptance row *"(§3 row 7.) Rotation-pair steps 3–6 PRESERVED VERBATIM; their backend-aware implementation remains B-33's scope — not this arc"* is RETIRED — this IS that implementation, at the two named steps below (steps 3-6's OTHER members — `STAGE_NEW_KEY`, `ROTATE_SIGNING_TO_NEW`, `RETIRE_OLD_KEY` — remain simulated per `B-22`'s unrelated deployment-surface scope; only `WRITE_DUAL_VERIFY_ENTRY` and `PROBE_VERIFY_AT_READ` gain real behavior).

**Acceptance criteria (v2.41 additions):**

1. **(CP v1.105 §1 — `WRITE_DUAL_VERIFY_ENTRY` presence/uniqueness + id derivation over the DEDICATED window parameter.)** `verify_rotation_6_steps` gains TWO new optional keyword-only parameters: `evidence_provider: RotationPairEvidenceProvider | None = None` and `rotation_window_entries: Sequence[StateLedgerEntry] = ()` — deliberately NO separate `rotation_correlation_id` parameter (out-of-family review round-1 [P1]: an independently-supplied id could diverge from the window's own id, letting the verifier join two UNRELATED rotation events). `WRITE_DUAL_VERIFY_ENTRY` calls the ALREADY-LANDED `harness_is.rotation_window_verification.verify_rotation_window` (IS spec v1.12 §7.7, U-IS-20) over `rotation_window_entries` — **NOT `audit_ledger_entries`** (out-of-family review round-2 [P1] correction: `audit_ledger_entries` remains the full genesis-anchored chain required by `VERIFY_HASH_CHAIN_LINK`'s `verify_chain` inception-sentinel check, a CONFLICTING shape from the sparse window `verify_rotation_window` needs — the two parameters are never the same collection). A `VALID` result (non-empty, every entry's `rotation_correlation_id` present and identical) makes the step succeed AND extracts the single distinct id as the ONLY id used downstream; any `INVALID` result (empty window / presence failure / uniqueness failure), including an empty/absent `rotation_window_entries`, makes the step FAIL with the specific `RotationWindowFailureType` named in the detail, and NO id is available for `PROBE_VERIFY_AT_READ`. Witness: `test_write_dual_verify_entry_valid_window_extracts_the_single_correlation_id` (the extracted id used downstream is asserted to equal the window's own value, never a separately-threaded one — mutation probe: accepting a caller-supplied id parameter instead of deriving it fails this test by construction, since no such parameter exists to supply) + `test_write_dual_verify_entry_rejects_full_chain_passed_as_window` (mutation probe: passing the full `audit_ledger_entries` fixture as `rotation_window_entries` must fail presence/uniqueness on the non-rotation entries it contains — a regression guard against re-conflating the two parameters).
2. **(CP v1.105 §1/§2 — `PROBE_VERIFY_AT_READ` OD-anchored evidence + id-echo check + required physical-key attestation + required signature-verification gate.)** When `evidence_provider` AND `key_identity_resolver` (U-CP-44 below) are BOTH supplied AND `WRITE_DUAL_VERIFY_ENTRY` derived a valid id, `PROBE_VERIFY_AT_READ` calls `evidence_provider.evidence_for(<the window-derived id>)`. It FIRST asserts the returned `evidence.correlation_id` equals the window-derived id (out-of-family review round-2 [P2] correction) — a mismatch raises `RotationPairEvidenceUnavailableError` with an explicit correlation-id-mismatch detail, never silently accepted. It THEN requires `pair_present=True AND signatures_verified=True` (out-of-family review round-2 [P1] correction — CP spec v1.105 §2 row 4b: structural evidence alone is NOT sufficient) → the physical-key-distinctness comparator (U-CP-44) runs next; all three passing → step succeeds with an "OD-anchored structural pair evidence AND per-period signature verification confirmed" detail naming the returned `outgoing_key_period`/`incoming_key_period`. `pair_present=False` → step FAILS with an EXPLICIT "no OD-anchored evidence for this rotation boundary" detail — distinct wording from a `RotationPairIntegrityBreach` raise (criterion #4). `pair_present=True AND signatures_verified=False` → step FAILS with an EXPLICIT "structural evidence present, signature verification not available" detail — distinct from BOTH the absence case and a tamper raise; since every `RotationPairEvidenceProvider` in this delta returns `signatures_verified=False` unconditionally (OD spec v1.35 §24.8 row 8a), this is the ONLY reachable disposition for a structurally-valid pair in this delta, and that is the intended, registered consequence (§0.4 leg-iii dependency note), not a test gap. Witness: `test_probe_verify_at_read_pair_present_and_signatures_verified_true_succeeds_with_full_wording` (constructs a stub provider returning `signatures_verified=True` to prove the success path is real and reachable in principle, even though no shipped provider can produce it yet) + `test_probe_verify_at_read_pair_present_true_signatures_verified_false_reports_explicit_incomplete_not_success` (mutation probe: treating `pair_present=True` alone as sufficient for `succeeded=True` fails this test) + `test_probe_verify_at_read_pair_present_false_fails_with_explicit_absence_detail` + `test_probe_verify_at_read_evidence_correlation_id_mismatch_raises_unavailable_error` (mutation probe: skipping the id-echo assertion lets a mismatched-id evidence object silently pass through, failing this test).
3. **(Sequential-halt gate extended.)** `ROTATE_SIGNING_TO_NEW` and `RETIRE_OLD_KEY` are gated on ALL THREE of `{VERIFY_HASH_CHAIN_LINK, WRITE_DUAL_VERIFY_ENTRY, PROBE_VERIFY_AT_READ}` succeeding (extended from the pre-v1.105 single-gate-on-hash-chain-link discipline) — any one of the three failing blocks both downstream steps with the existing `blocked` detail shape. Witness: `test_write_dual_verify_entry_failure_blocks_rotate_and_retire` + `test_probe_verify_at_read_failure_blocks_rotate_and_retire` (mutation probe: removing either from the gate lets `ROTATE_SIGNING_TO_NEW` succeed despite the upstream failure).
4. **(Fail-loud tamper propagation.)** A `RotationPairIntegrityBreach` raised by the injected `evidence_provider` (OD-detected structural tamper, translated by the Runtime adapter per Runtime plan v2.53 U-RT-147) PROPAGATES as a raised exception out of `verify_rotation_6_steps` — it is NEVER caught and folded into a `StepResult(succeeded=False)`, mirroring the codebase's existing fail-loud discipline for `RotationPairIntegrityBreach`/`HashChainBreach`/`AuditSignatureInvalid` elsewhere. A `RotationPairEvidenceUnavailableError` (infrastructure availability, never a verdict) likewise PROPAGATES unwrapped. A `RotationBoundaryPhysicalKeyCollisionError` (U-CP-44) ALSO propagates unwrapped, distinct from both — three distinct raise types for three distinct failure classes, never conflated. Witness: `test_evidence_provider_integrity_breach_propagates_uncaught` + `test_evidence_provider_unavailable_error_propagates_uncaught` + `test_physical_key_collision_error_propagates_uncaught` (mutation probe: wrapping any in a try/except that returns a failed `StepResult` instead of re-raising fails the corresponding test).
5. **(Absent-parameter posture — deliberately not byte-compatible, per CP spec v1.105's own justification.)** When `evidence_provider` is absent, OR `key_identity_resolver` is absent (U-CP-44 — absence is NOT a silent skip, per out-of-family review [P1] correction), OR `WRITE_DUAL_VERIFY_ENTRY` did not derive a valid id, `PROBE_VERIFY_AT_READ` reports `succeeded=False` with an EXPLICIT incomplete detail — NEVER the pre-v1.105 simulated `succeeded=True`. Witness: `test_absent_evidence_provider_or_key_identity_resolver_reports_explicit_incomplete_not_simulated_true` (parametrized over both absences independently — mutation probe: reverting either to a silent-skip/simulated-pass default fails the corresponding case).
6. **(Scope fence — explicit non-goal, per fork §3; leg-iii dependencies REGISTERED not silently deferred, out-of-family review round-2 [P1].)** This unit does NOT build a real production caller of `verify_rotation_6_steps`/`execute_key_rotation`, a real `rotation_window_entries` producer, or the OD §21.2.2 rotation-period signature-verification extension `signatures_verified=True` requires — `execute_key_rotation`'s own `rotation_complete`/`rotation_state_partial` computation (`all(s.succeeded for s in steps)`) is UNCHANGED and automatically reflects the extended step set; no new call site is wired in this arc. All three deferred dependencies are named explicitly at §0.4 above and at the fork's own progress note — this criterion is a scope boundary, not a claim that `verify_rotation_6_steps` genuinely passes anywhere yet.

**Tests (mutation-probed per PD-8):** the 11 witnesses named at criteria #1-#5 above.

## §2 U-CP-44 amendment — physical-key-distinctness boundary attestation (CP v1.105 §2)

The existing U-CP-44 body (F5 signing-key resolution, `Implements: C-CP-20 §20.3.1`) is PRESERVED VERBATIM; v2.41 adds:

**Implements (addition):** + C-CP-20 §20.3.2 (NEW at CP v1.105 §2 — the physical-key-distinctness comparator).

**Acceptance criteria (v2.41 additions):**

1. **(CP v1.105 §2 row 5 — the comparator.)** A NEW `key_identity_resolver` Protocol (`physical_identity_for(key_id: str) -> str`) is declared alongside the existing F5 signing-key resolution surface. `verify_rotation_6_steps`'s `PROBE_VERIFY_AT_READ` step (U-CP-45 above) confirms an evidence-confirmed pair's `outgoing_key_id` and `incoming_key_id` resolve to DIFFERENT physical identities — a same-identity resolution RAISES `RotationBoundaryPhysicalKeyCollisionError` (a NEW, DISTINCT failure mode from `RotationPairIntegrityBreach`: the OD-side pair may be well-formed while the physical keys are the same underlying material under two labels). Witness: `test_physical_key_distinctness_different_identities_passes` + `test_physical_key_distinctness_same_identity_raises_collision_error` (mutation probe: comparing key_id STRINGS instead of resolved physical identities passes the collision case and fails the second test).
2. **(Resolver absent — REQUIRED, out-of-family review [P1] correction: NOT a skip.)** `key_identity_resolver` defaults `None` at the Python parameter level (so `evidence_provider`-only callers don't get a `TypeError` at import time), but its ABSENCE at call time makes `PROBE_VERIFY_AT_READ` report the SAME EXPLICIT INCOMPLETE disposition as an absent `evidence_provider` (U-CP-45 criterion #5) — it is NEVER treated as "attestation skipped, step still succeeds." A deployment whose `SigningBackend` exposes no physical-identity mapping (ADR-F5 concrete-backend-selection deferral) cannot reach `succeeded=True` on this step; this is the intended, honest consequence (the original draft's "absent → skip" posture would let two labels aliasing one physical key pass as a genuine rotation — exactly the false-boundary failure this comparator exists to catch). Witness: `test_physical_key_distinctness_resolver_absent_reports_explicit_incomplete_never_silent_skip` (mutation probe: reverting to "resolver absent → skip, step still succeeds" passes a stale assertion and fails this one).
3. **(Reference implementation shape, non-binding home decision.)** `AwsKmsSigningBackend.key_arns` (ADR-D8, B-36) is the reference `key_identity_resolver` implementation available today (ARN as physical identity) — this criterion does not mandate a specific module location for the concrete adapter; the Protocol is the binding contract.

**Tests (mutation-probed per PD-8):** the 3 witnesses named above.
