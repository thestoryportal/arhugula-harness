# Specification — Harness Runtime v1.133 (delta over v1.132)

**Status:** Proposed for PR #1616 Class 1 backflow. Runtime v1.132 remains the cleared head until this delta is independently reviewed and cleared. Every v1.132 and earlier contract term is preserved except the C-RT-03 audit-signing configuration rule stated below.

## §0 Change-note (v1.132 → v1.133)

[HIGH] This delta applies ADR-D8 v1.1's bounded local-signing choice to C-RT-03. `AuditSigningConfig.backend="local-ed25519"` is admissible only when `RuntimeConfig.persona_tier` is `SOLO_DEVELOPER` or `TEAM_BINDING`. It remains an explicit opt-in; existing defaults and the lower-tier `audit_signing_fail_closed` tri-state behavior are unchanged. `backend="aws-kms"` remains admissible at `MULTI_TENANT_COMPLIANCE` with all existing MTC inputs and checks. The read-only `local-ed25519-public` historical key-map entry used by audit inspection is not a private signing backend and is not prohibited by this rule.

[HIGH] At `MULTI_TENANT_COMPLIANCE`, a configured `backend="local-ed25519"` is an **invalid v2 value**. The Runtime audit-signing config-shape validator MUST raise `AuditSigningConfigInvalidError` / `RT-FAIL-CONFIG` naming `persona_tier` and `local-ed25519` before backend construction, private PEM loading, KMS SDK/credential discovery, protected-store or cutover-record mutation, and global tracer registration. This occurs after bootstrap stages 1–3, which may create the state root, path registry, and ledger. The rule promises pre-signing-effect refusal, not a whole-bootstrap no-I/O outcome. A local backend is never silently replaced by KMS or `none`. The invalid-value classification takes precedence over simultaneously missing MTC inputs, following C-RT-03 v1.101's existing two-pass discriminator. The bootstrap stage-4 OD path and any mutating administrative path that uses a `RuntimeConfig` to construct its selected signing backend must run the same pure validation authority before that construction. Direct use of the low-level backend factory without a `RuntimeConfig` is a library primitive, not an MTC deployment admission.

[HIGH] A solo/team config that selects `local-ed25519` continues to use the existing absolute-path, key-map, key-identity, and record-key-distinctness checks. The local backend's private-key residency in the harness OS user bounds the claim: no compliance-tier key isolation, compromised-user resistance, or installed restart/tamper success is inferred from source tests. The operator chose solo/team for the first Omarchy release, while retaining tenant isolation and redaction and deferring MTC; the signer remains disabled until the B1/B2 and installed evidence gates pass. The shipped lower-tier Runtime composition strips content attributes by default, honors the session override only at solo, and binds no MTC recoverable token map. An OD library caller can narrow the explicit attribute set below MTC, so installed redaction needs its own acceptance proof; tenant-isolation acceptance likewise remains independent of this signer guard.

**Acceptance discriminator.** With a syntactically valid local backend map and `persona_tier=MULTI_TENANT_COMPLIANCE`, the pure validator emits `RT-FAIL-CONFIG` and the backend factory is not called. With the same map and either lower tier, this new persona rule does not reject it. With MTC and `backend="aws-kms"`, the new rule does not change the existing validation result. The mutating record-migration entry point exhibits the same pre-construction refusal. These are source witnesses; an installed operator run remains a separate gate.

**Scope.** No new contract number, fail class, configuration field, signature algorithm, wire format, audit-chain rule, CXA row, or cross-axis edge. This is a C-RT-03 invariant and an ordered validation boundary only. The PR #1616 fork record is `.harness/class_1_fork_pr1616_local_signer_and_runtime_plan.md`; the design authorities are `ADR-F5_v1_2.md`, `ADR-D8_audit_signing_backend_v1_1.md`, and `ADR-D5_v1_7.md` §1.4. [SPECULATIVE] A separate-principal local signer would require a future design arc and is not an allowed configuration under this delta.

**Deployment boundary.** The first-release solo/team configuration must be provisioned with its private PEM outside every Git checkout and with owner/mode controls. The current source loader checks owner/mode but does not detect Git checkout residence; the installed release gate must verify the actual key path. This C-RT-03 delta enforces only the MTC-local backend mismatch. It does not detect a pre-existing local-signed ledger when a future MTC+KMS configuration is opened; MTC activation and in-place upgrades remain outside this release and require a separate source admission guard and installed continuity review.
