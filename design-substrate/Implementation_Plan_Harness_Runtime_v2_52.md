## §1 New unit

### §1.1 U-RT-146 — cross-bootstrap capacity-authority continuity (v1.104 §14.8.10.6)

**Implements:** Runtime spec v1.104 §14.8.10.6 (process-lifetime capacity-authority continuity — adoption across sequential `api.run()` invocations, adopt-new-budget-carry-occupied reconciliation, every-admission-surface rider) + the v1.104 change-note's NEW §14.8.10.5 taxonomy row `RT-FAIL-CAPACITY-AUTHORITY-BUDGET-SHRINK`. The CP-side admission-guarantee span clarification (CP spec v1.104 §1) is cross-referenced, never restated — it changes no CP-owned code, only the reading of the existing `occupied + N + S ≤ cap` formula.

**Depends on:** [U-RT-141 (prior-landed — the grow-on-demand `SubAgentDispatchExecutor` + shared frame budget this unit makes process-lifetime instead of per-bootstrap; Runtime plan v2.50 §1.2 lineage)].

**Files affected (logical):** `lifecycle/sub_agent_dispatch_executor.py` (the frame-ledger accounting — `_budget`/`_available`/its lock — is factored out of `SubAgentDispatchExecutor` into a separately-adoptable ledger object that the executor DELEGATES to for `reserve`/`reserve_fanout`/`submit`'s admission checks; the DELEGATION preserves the existing single-critical-section shape — the executor's `_draining` check and the ledger's capacity decision happen under the SAME lock as ONE combined operation, never two separately-locked steps; the ledger gains a lock-guarded budget-reconciliation method used by the adopt path); `bootstrap/stage_5_loop_init.py` (the construction at lines ~620-622 gains an adopt-existing-ledger-or-construct-first-time branch — the LEDGER is adopted; a FRESH `SubAgentDispatchExecutor`/worker-pool is still constructed every bootstrap, bound to the adopted ledger); a new process-lifetime ledger holder (module-global or composition-root-held registry — carrier shape implementation-discretion); a conftest reset/replace fixture for test isolation.

**Acceptance criteria:**

1. **(Adopt the ledger; construct a fresh executor.)** Stage 5 checks for an already-adopted process-lifetime frame ledger BEFORE constructing the bootstrap's `SubAgentDispatchExecutor`; on a process's FIRST bootstrap it constructs a fresh ledger and adopts it; on every SUBSEQUENT bootstrap it ADOPTS the existing ledger instead of constructing a new one, while the `SubAgentDispatchExecutor` object itself (worker pool + `_draining` flag) is FRESHLY CONSTRUCTED every bootstrap and bound to the adopted ledger. **Never reuse the same executor object across a bootstrap boundary** — `drain()` (§14.8.10.1) unconditionally and permanently flips `begin_draining()`, after which `reserve`/`reserve_fanout`/`submit` reject ALL admission on that object forever (`sub_agent_dispatch_executor.py:164`/`:204`/`:266`); reusing it would zero out every subsequent bootstrap's admission (mutation probe: adopting the executor object itself instead of only the ledger must make the cross-bootstrap admission witness fail with permanent rejection, not over-admission).
1c. **(Drain-check and admission stay ONE atomic operation, codex round-2.)** The pre-existing invariant — ONE lock guards both the `_draining` check and the `_available` decrement inside `reserve`/`reserve_fanout`/`submit` — is PRESERVED after the ledger split: the per-bootstrap executor's `_draining` check and the shared ledger's capacity decision execute under the SAME lock (the ledger's lock) as ONE combined operation. A two-lock implementation (draining checked unlocked or under a separate executor-local lock, THEN the ledger's lock acquired separately for the capacity decision) is an acceptance FAILURE — it reopens a window where `begin_draining()` flips the flag between an admission's draining-check and its capacity reservation, admitting a branch after shutdown began.
2. **(Adopt-new-budget-carry-occupied, ATOMIC with lease release.)** On adoption, if the newly-configured `sub_agent_dispatch_max_workers` differs from the adopted ledger's current `frame_budget`, the ledger's budget is RECONCILED against its CURRENT occupied count (`occupied = old_budget - old_available`; `new_available = new_budget - occupied`) UNDER THE SAME LOCK the ledger uses for every `reserve`/`release` call — never reset to `new_budget` outright, and never computed via an unsynchronized read-then-write that a concurrent straggler release could race. Growing the budget is honored immediately (`new_available` increases). Shrinking the budget to AT OR ABOVE the current occupied count (`new_budget >= occupied`) is ALSO honored immediately at the new, smaller-but-still-sufficient budget — exactly like growth, never rejected outright and never silently retaining the old larger budget. Shrinking the budget BELOW the current occupied count (`new_budget < occupied`) is REFUSED TYPED at bootstrap with the NEW `RT-FAIL-CAPACITY-AUTHORITY-BUDGET-SHRINK` error naming the configured budget and the current occupied count — bootstrap does NOT proceed with a negative or silently-clamped `_available`.
3. **(Every admission surface.)** The adopted ledger backs BOTH the CP fan-out adapter's `reserve_fanout` path AND the direct non-fan-out `reserve(1)` path identically — a single direct offload in a later bootstrap sees the SAME `occupied` a fan-out would (fork §3 rider 4; fork §4 item 1b's direct-dispatch twin).
4. **(Lease-release path byte-unchanged.)** The `add_done_callback` → `release_unless_job_bound` lease-release path is UNCHANGED — a draining worker's eventual release lands in the SAME adopted ledger the next bootstrap reads, regardless of which bootstrap's executor object originally admitted it; no double-release, no phantom frame.
5. **(Per-run isolation preserved.)** ONLY the frame-ledger object is process-lifetime; every other run-scoped ContextVar/lease (the existing B-48 isolation discipline — `INTER_STEP_CHANNEL_VAR`, `_BRANCH_INFLIGHT_DISPATCHES`, pause-flag/resume-context isolation) remains per-run. The existing B-48 isolation witnesses re-run GREEN unmodified.
6. **(Interpreter-exit posture unchanged.)** No new join is introduced anywhere in the adopt/reconcile path; daemon workers remain unjoined at interpreter exit.
7. **(Test isolation.)** A conftest fixture resets or replaces the process-lifetime authority between test cases, so no test's occupied/budget state leaks into another's.

**Tests (mutation-probed per PD-8):** **Fork §4 item 1 — the defect's direct witness:** `test_cross_bootstrap_fanout_admission_sees_residual_not_full_budget` — two sequential `api.run()` invocations in ONE process; run 1 leaves a worker draining past its shutdown deadline (occupying frames); run 2's fan-out admission is asserted against `budget - occupied`, never the full configured budget (mutation probe: reverting stage 5 to unconditional fresh-construction must make this witness fail — over-admission reproduces). **Ledger-vs-executor-object witness (codex round-1 on this rider):** `test_reusing_executor_object_across_bootstrap_permanently_rejects_admission` — a NEGATIVE control proving why the ledger/executor split is required: adopting the PRIOR bootstrap's `SubAgentDispatchExecutor` object itself (not just its ledger) after that object's `drain()` ran makes EVERY subsequent admission on it fail permanently, distinguishing this failure mode from the over-admission the primary witness guards against (mutation probe: an implementation that adopts the executor object instead of a separately-adoptable ledger must fail THIS witness with permanent rejection, not over-admission). **Item 1c (atomicity, codex round-4 sharpened — structural, not timing-dependent):** `test_reserve_and_begin_draining_share_the_identical_lock_object` — a live timing-based race cannot DETERMINISTICALLY force the split-lock failure window (round-3's barrier-before-either-starts attempt was itself non-deterministic: both threads still race non-deterministically for their own separately-acquired locks, so the forbidden interleaving is rarely hit and the witness can pass against a genuinely broken implementation). The DETERMINISTIC fix is structural: assert that the object `reserve()`/`reserve_fanout()`/`submit()` acquire for their draining-check-plus-capacity-decision critical section IS THE SAME lock object `begin_draining()` acquires to flip `_draining` (e.g. `executor._admission_lock is ledger._lock`, exact attribute names implementation-discretion) — identity, not merely "both synchronized." Two DISTINCT locks (even if each individually held during its own operation) permit the forbidden interleaving nondeterministically under real thread scheduling; identical-lock-object is the only structural guarantee that forecloses it entirely, independent of scheduling. Mutation probe: an implementation using two separate `threading.Lock()` instances — one for the executor's `_draining` flag, one for the ledger's `_available` — passes any test that only checks final outcomes under lucky scheduling, but fails THIS witness immediately (the two lock objects are not identical) and is the exact bug class this item exists to catch. **Fork §4 item 1b — the direct-dispatch twin:** `test_cross_bootstrap_direct_dispatch_admission_sees_residual` — same two-run setup, but run 2 issues a single non-fan-out `reserve(1)` offload instead of a fan-out; asserts it too sees `budget - occupied` (mutation probe: an implementation that globalizes ONLY the fan-out adapter's accounting while leaving direct `reserve(1)` on a fresh per-bootstrap budget must fail THIS witness while item 1's witness still passes — pins that both surfaces, not just one, back onto the shared ledger). **Fork §4 item 2 — straggler release correctness:** `test_straggler_done_callback_releases_into_adopted_ledger` (the run-1 draining worker's eventual completion releases its frame into the SAME ledger run 2 read; a subsequent admission after the release succeeds at the now-correct residual; mutation probe: routing the release into a stale/discarded ledger object leaves run 2 permanently under-admitted and fails) + `test_no_double_release_across_bootstrap_boundary` (mutation probe: a release path that fires twice — once at hypothetical bootstrap teardown and once at the real done-callback — must be caught; this test asserts occupied count arithmetic stays consistent, not merely non-negative) + `test_straggler_release_races_budget_reconciliation_under_same_lock` (fork §4 item 2 sharpened, codex round-1: run 2's bootstrap reconciles the budget concurrently with run 1's straggler done-callback releasing its lease; both operations MUST serialize under the ledger's single lock so neither the release nor the reconciliation's read of `occupied` is lost — mutation probe: an implementation that reconciles via an unsynchronized `occupied = old_budget - old_available` read outside the ledger's lock must fail this witness under a forced interleaving that lands the release between the read and the write). **Fork §4 item 3 — budget reconfiguration:** `test_budget_grow_across_bootstraps_honored_immediately` (run 2 configures a LARGER `sub_agent_dispatch_max_workers`; the adopted ledger's available capacity reflects the growth immediately) + `test_budget_shrink_below_occupied_refused_typed_at_bootstrap` (run 2 configures a budget below run 1's still-occupied count; bootstrap raises `RT-FAIL-CAPACITY-AUTHORITY-BUDGET-SHRINK` naming both the configured budget and the occupied count; mutation probe: silently clamping `_available` to 0 instead of raising, or proceeding with a negative `_available`, must fail this witness) + `test_budget_shrink_at_or_above_occupied_honored_immediately` (codex round-2: run 2 configures a budget SMALLER than run 1's original budget but still AT OR ABOVE run 1's current occupied count; asserts the shrink is honored immediately at the new smaller budget — `available` becomes `new_budget - occupied`; mutation probe: an implementation that rejects every shrink regardless of the occupied count, OR that silently retains the old larger budget instead of applying the configured smaller one, must fail THIS witness while `test_budget_shrink_below_occupied_refused_typed_at_bootstrap` still passes — distinguishes valid-shrink-honored from invalid-shrink-refused, since a "reject everything" implementation would pass the refusal witness alone). **Fork §4 item 4 — per-run isolation:** the EXISTING B-48 isolation witness suite (`INTER_STEP_CHANNEL_VAR` sibling isolation, `_BRANCH_INFLIGHT_DISPATCHES` cross-thread-safe handle, pause-flag/resume-context isolation) re-run GREEN with no modification required — a regression here would mean the adopt mechanism leaked run-scoped state, which is an acceptance FAILURE distinct from this unit's own new tests. **Fork §4 item 5 — interpreter-exit posture:** `test_no_new_join_introduced_at_adopt_path` (static/behavioral assertion: the adopt-or-construct branch and the reconciliation method perform no blocking join; existing shutdown-drain-with-deadline coverage from U-RT-141 is unaffected).

**Rollback boundary:** revert to unconditional fresh-construction-per-bootstrap at stage 5; the process reverts to the fork §1 defect (a still-draining prior worker's occupied frame becomes invisible to the next bootstrap, permitting a transient over-cap breach of the C-RT-03 single-shared-cap promise across the bootstrap boundary) — the new `test_cross_bootstrap_fanout_admission_sees_residual_not_full_budget` witness is the canonical regression guard.
