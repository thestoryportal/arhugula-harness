### §0.2 Revision context — CP spec v1.106 absorption, CONTRACT-altitude correction pass

Per `Spec_Control_Plane_v1_106.md` §0/§1: the `ResumeContext` carrier (§26.8.1) gains `hitl_responses`/`hitl_response_for` (U-CP-64's own carrier, per its v2.21 authoring); `DriverContext.resume_context_holder` is retired as a ctx-level binding, with the exact replacement propagation mechanism left to impl discretion (spec §1.3).

**Round-1 correction note (same-day, this arc).** A first draft of this plan delta additionally amended U-CP-86 (`PARALLELIZATION`), U-CP-88 (`ORCHESTRATOR_WORKERS`), and U-CP-89 (`HIERARCHICAL_DELEGATION`) with ACs asserting that these functions' own worker re-dispatch sites directly thread new parameters into a recursive `execute_workflow(...)` call. Out-of-family review (`just codex-review-uncommitted`) plus an `Explore` grounding pass found this call graph EMPIRICALLY FALSE: `_execute_parallelization`/`_execute_orchestrator_workers` do not recursively call `execute_workflow` for a paused-child re-dispatch — they stamp `StepExecutionContext.child_resume_snapshot` and hand off to `harness-runtime`'s `RuntimeSubAgentDispatcher.dispatch()`, which reads that field and invokes an injected `ChildWorkflowRunner` closure (`harness-runtime/lifecycle/child_workflow_runner.py`) that itself calls back into `harness_cp.workflow_driver.execute_workflow`. The propagation-mechanism wiring this arc's spec-leg contract (spec §1.2) obligates therefore crosses the CP↔Runtime package boundary at a DIFFERENT seam than this plan delta assumed, and may touch U-CP-86/88/89, may touch Runtime-owned units (`sub_agent_dispatch.py`, `child_workflow_runner.py`), or both — this is genuine scope-discovery work belonging to the impl leg, not something this spec-leg plan delta can responsibly assert today. §2-§4 (the U-CP-86/88/89 amendments) are THEREFORE REMOVED from this delta rather than re-authored against a fourth unverified call graph; see §5 below for the deferred-scope note.

**Round-2 correction note (same-day, second out-of-family pass).** After round 1 landed, a second `just codex-review-uncommitted` pass found the round-1-corrected `hitl_responses` key shape — `branch_path` (CP spec v1.106 §0, `compose_branch_path`) — is ALSO wrong: it derives from a workflow_id-scoped `action_id` with NO run-instance component, so it collides when two peer branches dispatch the SAME `child_workflow_id` (an explicitly supported scenario). The fix keys `hitl_responses` by the paused child's own `run_id` instead (`PausedChildBranchResumeState.child_snapshot.run_id` — an EXISTING `PauseSnapshot` field, genuinely unique across recursion depth AND repeated same-`child_workflow_id` dispatch, per the `compose_child_run_id_seed` derivation chain CP spec v1.106 §0 traces). This requires NO new field on `PausedChildBranchResumeState` — the round-1 draft's `branch_path` field addition is REMOVED as unnecessary. §1 below (U-CP-64's amendment) is updated accordingly.

**Round-3 correction note (same-day, branch-vs-main `just codex-review` against open PR #1092 — the correct pre-merge review mode, distinct from rounds 1-2's `-uncommitted` mode).** Two defects, both in this plan file (a third, addressability-safety defect landed entirely in the spec file — see `Spec_Control_Plane_v1_106.md`'s own round-3 note): (a) AC #8 (below) asserted `DriverContext.resume_context_holder` field removal as a STANDALONE, independently-completable unit test — out-of-family review found this breaks the 3 CURRENTLY-WORKING effect-fence peek-reader consumption sites (`workflow_driver.py`, `getattr(ctx, "resume_context_holder", None)`) if landed alone, before their replacement delivery mechanism exists, since those readers would then unconditionally receive `None`, causing effect-fence resume to ALWAYS re-pause INERT — a regression. AC #8 is revised below to fold physical field removal into the SAME deferred bucket as §5's delivery-mechanism row: it may only land atomically with re-pointing all 3 sites, at the impl leg, never as a standalone unit-testable AC of this spec-leg plan. (b) The Files (EXTEND) row's `DriverContext` Protocol file citation left the 3 sites' migration entirely unassigned ("out of scope... impl-leg scope-discovery work") with no atomicity requirement stated — revised below to state the co-landing constraint explicitly, so a literal reading of this plan cannot land a broken intermediate state.

**Round-4 correction note (same-day, branch-vs-main `just codex-review` against the round-3 fix commit — the round-3 fix ITSELF introduced 2 new defects, the `[[non-convergent-adversarial-hardening-arms-race]]` discriminator's "did my fix cause this finding?" test answering yes).** Round 3's AC #7 addition (a resolver mechanism: "count HITL-paused children, gate the uniform fallback to the single-paused-child case, else force INERT re-pause") was found DOUBLY defective: (a) the mechanism itself is wrong — it would strand a transitively-paused container/ancestor branch (one blocked only because an unresolved DESCENDANT exists below it, never itself gate-owning) by forcing INERT re-pause instead of unconditional recursion toward the actually-addressed gate-owning descendant, breaking traversal for any nested multi-branch pause; (b) the obligation was assigned to U-CP-64, but U-CP-64 only owns the `ResumeContext` carrier — the counting/traversal logic is resolver-internal, and the resolver is itself deferred to the impl leg (§5), so no declared unit could implement or test it. Fix (advisor()-recommended): CP spec v1.106 §1.2 property 4 is CONVERTED from a mechanism to a black-box safety+liveness invariant and MOVED to §5's deferred bucket alongside properties 1-3 — no longer owned by U-CP-64. A NEW property 5 formally distinguishes gate-owning branches (subject to `hitl_responses` addressing) from transitively-paused container/ancestor branches (never subject to it). AC #7 below reverts to testing ONLY carrier-level behavior; the multi-branch mutation-probe test is removed from it.
