## Change-note (v1.107 → v1.108)

**Trigger.** `B-72`'s empirical rounds (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md`) confirmed a `SUB_AGENT_DISPATCH` branch's own `SUB_AGENT_BOUNDARY` gate can pause the run BEFORE any child run is dispatched — before `child_run_id` exists at all. Per `Spec_Control_Plane_v1_106.md` §1.2 property 5's own test ("it never itself dispatched into a HITL gate" — the container/ancestor exclusion), such a branch IS gate-owning (it DID dispatch into its own gate). But properties 1 and 4 are written entirely in terms of `child_run_id`-keyed identity — a vocabulary that cannot describe a branch with no child run yet. Round 7 confirmed this is not a contrived edge: `compose_child_run_id_seed`'s deterministic pre-dispatch minting path is gated on `subagent_child_recoverable` and does not cover `PURE_PATTERN_NO_ENGINE` — the exact engine class `B-72`'s own reproduction test uses.

**The defect (confirmed by direct grounding, not reasoning).** Two independent instrumentation passes against the real `B-72` round-3 reproduction (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md` §2, reverted after each check — no code change): (1) `compute_hitl_uniform_fallback_eligible_run_id` returns `None` for the reproduction's own captured `PauseSnapshot`, not the sole branch's identity — `PeerFanOutResumeState.branches` and `.paused_child_branches` are both empty; (2) `terminal_dispositions={}` for that branch's ordinal at the `workflow_driver.py:9698` capture site, confirming the branch's pause is never recorded through EITHER existing per-branch carrier. Property 4's Safety clause ("every gate-owning branch paused this cycle whose own `child_run_id` is NOT a key in `hitl_responses`") therefore has nothing to count this branch as — the uniform fallback it should be eligible for (it is the SOLE gate-owning branch this cycle) never applies, and the gate re-fires on every resume indefinitely (confirmed: `resumed.status == "paused"`, `RuntimeSubAgentDispatcher.dispatch` never reached, the delivered answer never consumed).

**Why this needs a new spec property, not a pure impl-to-cleared-spec fix.** Extending what property 4's resolver must count as "gate-owning" is an observable CONTRACT change to a currently-shipped, P5-CK-cleared mechanism — the same class of change properties 1-5 themselves were at v1.106. Per workspace `CLAUDE.md` §4.4 (X-AL-3), silently stretching property 4's existing text to cover a case its own authors did not contemplate (the round-3/4/5 correction history of this exact section shows they were reasoning about ALREADY-DISPATCHED children throughout) would itself be an uncontrolled design extension — see the tension record's §5 tiebreaker check, which confirms this reading directly against the verbatim text before authoring this delta.

**Why property 6 needs neither property 1's key widened nor a separate delivery path.** Property 1's `run_id`-shaped `hitl_responses` key is required ONLY for the case of 2+ DISTINCT concurrently-paused gate-owning branches needing DISTINCT, individually-addressed resolutions. Property 4's Safety clause needs an identity for exactly two INTERNAL purposes — set-membership counting and a SOLE-member comparison — neither of which requires external addressability or a `run_id` shape. A pre-dispatch gate-owning branch can therefore be made countable for property 4's purposes using an implementation-discretion internal identity, WITHOUT ever entering `hitl_responses`, WITHOUT needing `B-71`'s exposure fix, and WITHOUT depending on engine recoverability — closing exactly the SOLE-branch case `B-72`'s round-3 reproduction pins. The harder case — 2+ concurrently-unaddressed gate-owning branches where at least one is pre-dispatch — genuinely has no externally-knowable identity to key by and stays open, explicitly named as such below, forward-dependent on `B-71` (confirmed narrower in round 7: `B-71` only proposes exposing an ALREADY-DISPATCHED child's `run_id`, not minting one for a not-yet-dispatched branch).

## §1 — Pre-dispatch gate-owning branch counting (property 6, closes `B-72` item 1)

**§1.1 The property (CONTRACT — binding on the impl leg; wiring is NOT specified here, mirrors v1.106 §1.3's own discipline).** A gate-owning branch (per `Spec_Control_Plane_v1_106.md` §1.2 property 5's test — it dispatched into its own HITL gate) that has not yet produced a child run — its own `SUB_AGENT_BOUNDARY` (or equivalent) placement fired and paused the branch BEFORE any child `run_id` was created — is a **pre-dispatch gate-owning branch**. The replacement mechanism's resolver MUST:

- **(a) Count it.** A pre-dispatch gate-owning branch MUST be a member of property 4's Safety-clause "unaddressed gate-owning set" for the current resume cycle (it is, definitionally, always unaddressed — no `child_run_id` exists for `hitl_responses` to key against it). This closes the round-3 reproduction's own SOLE-branch case: once correctly counted, property 4's existing uniform-fallback rule already applies — no new resolution mechanism, no new fallback rule, no amendment to property 4's text itself.
- **(b) Never key it.** A pre-dispatch gate-owning branch MUST NEVER be resolvable via `hitl_responses`/`hitl_response_for(child_run_id)` — no `child_run_id` exists to key by; inventing a differently-shaped key for this purpose would itself change property 1's normatively-fixed key shape, which this property does NOT do. It is resolvable ONLY via property 4's uniform `hitl_response` fallback, and ONLY under property 4's existing SOLE-member rule.
- **(c) Accept the liveness limit.** When the unaddressed gate-owning set has 2+ members and at least one is pre-dispatch, EVERY member (per property 4's existing text, unamended) MUST re-pause INERT — this MAY mean a pre-dispatch gate-owning branch among peers with no available keyed path ever converges via this property alone. This is a STATED, ACCEPTED forward limitation, not a defect this delta claims to close — see §1.2's scope note.
- **(d) Internal identity, impl discretion — but MUST be unique across the WHOLE resume tree, not merely among local siblings.** WHICH internal representation identifies a pre-dispatch gate-owning branch for purposes of (a)'s counting and any subsequent SOLE-member comparison — a branch ordinal, a composition-derived string, or any equivalent — is impl discretion, exactly as properties 1-4 already defer their own resolver mechanism. **Codex out-of-family review [P1] (2026-07-25, caught before merge):** an unqualified "branch ordinal" is NOT sufficient by itself — under nested fan-out (e.g. a `PARALLELIZATION` barrier nested inside a `HIERARCHICAL_DELEGATION` recursion, or two independent fan-out barriers at different tree positions), two DIFFERENT pre-dispatch gate-owning branches at different nesting levels can each locally compute the SAME local ordinal (e.g. both "branch 0" of their own respective barrier). If the chosen identity is only locally unique, property 4's set/SOLE-member comparison can collapse two genuinely distinct branches into one — reporting a SOLE unaddressed member when the true unaddressed set has 2, and delivering the uniform `hitl_response` to BOTH, the exact cross-branch misattribution property 4 exists to prevent (a correctness violation, not merely an edge case). The chosen identity therefore MUST be unique across the ENTIRE resume tree for the current cycle (e.g. an ancestry-qualified path — the local ordinal composed with every ancestor barrier's own position — or any equivalent scheme achieving the same tree-wide distinctness), mirroring how property 1's `run_id`-based keying is already tree-wide-unique by construction. The impl leg's chosen mechanism MUST include a collision witness (a test asserting two pre-dispatch gate-owning branches at different tree positions produce DISTINCT internal identities) before this property can be considered satisfied. The ONLY additional constraint: this internal identity MUST NOT be placed in, or treated as compatible with, `hitl_responses` (which remains exclusively `child_run_id`-keyed per property 1, unamended).

**§1.2 Scope.** This property closes ONLY `B-72`'s net-position item (1) — the round-3 reproduction's SOLE pre-dispatch gate-owning branch case. It does NOT close: `B-72`'s net-position item (2) (keyed multi-peer addressing across 2+ concurrently-unaddressed gate-owning branches where at least one is pre-dispatch — genuinely gated on `B-71`, confirmed narrower in round 7 to cover only already-dispatched children, and possibly a further Runtime-side early-minting extension `B-71` does not currently cover); item (3) (property 4's general resolver set-membership mechanism, already deferred to the impl leg at v1.106); or item (4) (`B-72`'s own original round-1 "hybrid case" — a branch already-gate-owning once, now resume-forwarded toward its self-dispatched deeper-paused descendant — property 5 does not settle it and it stays untested by any reproduction). All three remain open forward work, unchanged by this delta.

**§1.3 What is explicitly NOT specified here (impl discretion, mirrors v1.106 §1.3).** Which carrier (an amendment to `PeerFanOutResumeState`/`FanOutResumeState`, or an equivalent) records a pre-dispatch gate-owning branch's presence; the internal identity's exact shape (§1.1(d)); which call site constructs it and which call site consults it for property 4's counting. A prior fork-doc draft (`.harness/class_1_fork_b72_gate_ownership_missing_carrier.md` §4, before this tension-resolution pass) initially sketched a concrete field name and type — corrected before filing, per the same CONTRACT-altitude discipline v1.106 §1.3 itself states, and per this arc's own four-round history of prescribing wiring that turned out false against the real call graph.
