**The grounding correction (why the slice is per-kind re-dispatch, not a new pause).** The arc was registered (v1.61 §4) anticipating *"a post-dispatch output capture that distinguishes completed-and-captured … from genuinely-ambiguous (route to a §26.2 pause)."* HEAD grounding refines this exactly as the v1.62 worker arc refined its identical registration language (`[[grounding-reveals-claude-closeable-slice-close-honestly]]` + `[[cleared-spec-resolves-it-before-first-principles-fix]]`): the post-dispatch capture ALREADY exists (`record_orchestrator` writes the orchestrator's terminal record the moment its output is in hand — a completed-and-captured orchestrator is therefore recovered via `read_orchestrator_output`, never maybe-ran), so maybe-ran ⟺ *genuinely fire→capture-ambiguous*. The actionable distinction is not capture-vs-no-capture (already made) but **whether re-dispatching the ambiguous orchestrator can double-fire**, which is determined by its **dispatch-time step kind's external-effect surface**. Anchored to the runtime per-step blast-radius one-source-of-truth (`step_blast_radius.py:13-22` `_READ_ONLY_KINDS`: *"INFERENCE_STEP / DECLARATIVE_STEP — no external effect"*): an orchestrator that is an LLM inference (the common ORCHESTRATOR_WORKERS shape — `steps[0]` farms sub-tasks via an LLM) has no external side-effect (cost + output non-determinism only, which crash-resume ALREADY tolerates), and a DECLARATIVE_STEP orchestrator is a pure transform. Re-firing either is *a fresh at-most-once-external execution*, never a double-fire.

**Why a spec amendment — and why it carries NO new operator gate.** The recovery semantics change (a maybe-ran orchestrator of a re-fire-safe kind now re-dispatches fresh instead of failing the strict-tier crash-resume closed) is enabled by reading the orchestrator's **dispatch-time kind** off its existing reserve-before-dispatch marker (the §2 paired runtime extension). This is sound: the maybe-ran orchestrator case fires only when no worker completed (`not branches`) AND no cardinality marker exists yet (the cardinality marker is fsynced AFTER the orchestrator terminal capture, so a crash in the orchestrator fire→capture window leaves none) — so the fresh re-run re-dispatches an empty-progress fan-out, and a re-fire-safe orchestrator re-runs as a fresh at-most-once-external execution.

## §1 — Re-fire-safe relaxation of the orchestrator maybe-ran fail-closed (C-CP-25 §25.12 / §25.15)

> **The orchestrator-maybe-ran re-fire-safety classification (resume).** On an ORCHESTRATOR_WORKERS / HIERARCHICAL_DELEGATION crash-resume (`resume_snapshot is None`, replay-capable ∧ store-bound) where the orchestrator output is ABSENT, no worker was recovered, and the orchestrator dispatch marker is PRESENT (the v1.61 §1 maybe-ran case), `_determine_fanout_resume` no longer unconditionally raises. **It first applies the cardinality corruption guard, then** partitions on the **dispatch-time** kind recorded in the orchestrator marker (`orchestrator_dispatched_kind(run_key) → str | None`, §2):
>
> - **DEFAULT-DENY downstream-artifact guard (precondition).** The relaxation re-runs the WHOLE fan-out fresh, so it is admissible ONLY in the pristine pre-everything maybe-ran window — the orchestrator runs FIRST + sequentially, so its dispatch marker + the dispatch-instrumented stamp are the ONLY durable artifacts the writer (`_execute_orchestrator_workers`) emits in that window. **Every** artifact the writer emits AFTER the orchestrator marker proves the run advanced past orchestrator capture → an absent capture is then a LOST capture (corruption), NOT the fire→capture window → fail closed (`_FanOutStoreCorruptError`). Tied to the WRITER's full durable-artifact list (a default-deny ALLOWLIST, NOT a per-finding denylist): the orchestrator capture (already excluded by `orchestrator is None ∧ not orchestrator_present`), the **cardinality marker** (presence-only `fanout_cardinality_present` — NOT `read_fanout_cardinality`, which returns `None` for BOTH an absent AND a present-but-TORN marker; both the readable [R2] and torn [R3] cases are corruption), a **worker dispatch marker** (`present_dispatched_indexes` non-empty — written only after the orchestrator+cardinality phase [R4]), a **worker branch capture** (`present_branch_indexes` non-empty, readable OR corrupt — defensive; the readable case hits the workers-completed-but-orchestrator-absent guard and the corrupt case the present-but-unreadable guard first), and a **post-join synthesis capture** (`synthesis_present`, written last). ONLY when ALL are absent (∧ the stamp present ∧ a re-fire-safe kind) does the relaxation re-run; anything else — including unknowns — fails closed (`[[durable-recovery-presence-validity-scope]]`; the equivalence is "re-fire-safe-maybe-ran ≡ provably-not-run EXCEPT the orchestrator marker" — assert-absent everything the no-marker fresh path assumes absent).
> - **re-fire-safe kind ∧ dispatch-instrumented** (`{DECLARATIVE_STEP, INFERENCE_STEP}` AND the per-run dispatch-instrumented stamp present) → return `None` → the unchanged fresh re-run (the orchestrator + workers re-dispatch, first-and-only). A re-fire-safe orchestrator has no non-idempotent external effect, so a fresh re-run cannot double-fire (the same reading the v1.62 §1 worker machinery applies to a maybe-ran branch — and the unfenced linear-resume path already re-dispatches an INFERENCE_STEP, the §14.8.8.7 invariant-3 re-ask-per-retry posture). The **dispatch-instrumented stamp is a required co-condition** (mirroring the worker `_instrumented ∧ ¬unsafe` gate): the stamp is written STRICTLY BEFORE the marker, so a marker-WITHOUT-stamp is an INCONSISTENT store (corruption / tamper / partial loss) whose recorded kind cannot be trusted — it falls through to fail-closed regardless of the recorded kind.
> - **effect-bearing, un-kinded, or orphaned-marker** (any kind not in the re-fire-safe set, OR a missing / unreadable / pre-v1.64 marker whose `step_kind` is absent, OR a re-fire-safe-kinded marker with NO dispatch-instrumented stamp) → raise `_FanOutStoreOrchestratorMaybeRanError` (fail closed, byte-identical to v1.61). Its effect may have landed (or the store is corrupt); a re-dispatch would double-fire. A pre-v1.64 orchestrator marker (written by the v1.61 build, which recorded only `step_id`) reads `None` → fail closed; an orphaned marker without the stamp fails closed even with a re-fire-safe recorded kind — the conservative cross-version + presence-vs-validity reading, never a wrongful re-dispatch (`[[durable-recovery-presence-validity-scope]]`; out-of-family Codex [P2]).

> **At-most-once is the gate, not the kind.** The relaxation expands recovery ONLY where it is provably safe — a re-fire-safe (no-external-effect) orchestrator. An effect-bearing orchestrator's resolution is NOT supplied here (it stays fail-closed); there is no fail-open path. The classification keys on the **dispatch-time** kind in the marker, NOT the resumed manifest's current kind — the at-most-once changed-manifest guard (v1.62 §3): an orchestrator dispatched as an effect-bearing kind that crashed before terminal capture, then re-supplied at `steps[0]` as a re-fire-safe kind on a same-shape resume, STAYS classified effect-bearing → fail closed.

> **Sound only when no progress was recovered.** The orchestrator-maybe-ran case fires exclusively under `orchestrator is None ∧ not branches` (no worker completed) — the `orchestrator is None ∧ workers-completed` case is an inconsistent store and fail-closes unchanged (v1.55), and a captured orchestrator is recovered via `read_orchestrator_output` and never reaches this branch. So returning `None` re-dispatches an empty-progress fan-out: nothing is double-dispatched, and the cardinality-only fail-closed path is not tripped (the cardinality marker is fsynced AFTER the orchestrator terminal capture, so a crash in the orchestrator fire→capture window leaves no cardinality → `read_fanout_cardinality` is `None` → the `_cardinality is not None` guard is False → fall through to the fresh re-run).

## §2 — Reuse of the dispatch-time-kind marker substrate for the orchestrator (paired runtime delta)

> The re-fire-safety gate reuses the v1.62/v1.80 substrate pattern, extended to the orchestrator's single marker. The runtime **C-RT-32 `EngineOutputStore`** orchestrator dispatched-marker (v1.61/runtime-v1.79 `record_orchestrator_dispatched(run_key, step_id)`) gains the **dispatch-time step kind**: `record_orchestrator_dispatched(run_key, step_id, step_kind)` records `{step_id, step_kind}` (exactly the v1.80 worker `record_branch_dispatched` shape), and a NEW read method `orchestrator_dispatched_kind(run_key) → str | None` exposes it (the single-orchestrator analogue of the worker `dispatched_branch_kinds`; `None` for a missing / torn / pre-v1.64 marker). The CP driver writes the kind at the `_execute_orchestrator_workers` orchestrator-block reserve site (`str(orchestrator_step.step_kind.value)`, mirroring the worker `record_branch_dispatched` caller) and the `_determine_fanout_resume` orchestrator classifier consumes it via the `cp_is_wiring` getattr idiom. **Paired runtime delta `Spec_Harness_Runtime_v1.md` v1.80 → v1.81** (the §14.23 C-RT-32 sibling-method-signature extension + read method — non-attested, not in the §6 hash chain; no new contract, no `StepDispatcher` widening, no new CXA edge).

> **No new fail-class, no closed-enum change.** The effect-bearing / un-kinded orchestrator raises the EXISTING `_FanOutStoreOrchestratorMaybeRanError` (`fan-out-crash-resume-orchestrator-maybe-ran`, v1.61). The re-fire-safe orchestrator re-runs fresh (no fail-class). `_FANOUT_MAYBE_RAN_REFIRE_SAFE_KINDS` is the existing v1.62 frozenset, not a change to a closed/cardinality-asserted enum. No §5.2 IS-hash / §16.5 key change (the marker is a non-attested recovery sidecar; `run_idempotency_key` composes `run_id` + `workflow_id` + `entry_version` only, unchanged).

## §3 — Registered follow-on status + R-FS-1 closure semantics (FULL-SPEC)

> This delta CLOSES the parent arc **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-RESOLUTION`** as the **re-fire-safe slice** (the orchestrator analogue of the v1.62 worker `B-FANOUT-CRASH-RESUME-MAYBE-RAN-RESOLUTION` close). Grounding the arc at open revealed it is genuinely **three** sub-problems; the re-fire-safe case is the Claude-closeable, no-gate slice, and the other two are split to their own registered legs per `[[spec-leg-split-on-ratification-boundary]]` (a split, NOT a defer — each is NAMED + registered, never silently absorbed; FULL-SPEC `[[feedback-full-spec-beyond-mvp-nothing-deferred]]`):
>
> - **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-MAYBE-RAN-EFFECT-BEARING`** (NEW, registered, `operator_gated: false`) — the resolution of a maybe-ran orchestrator of an **effect-bearing** dispatch-time kind (TOOL_STEP / SUB_AGENT_DISPATCH / MANAGED_AGENTS — the orchestrator `steps[0]` kind is **unconstrained**; topology admissibility does not foreclose a non-re-fire-safe orchestrator, so this is a reachable gap). It stays fail-closed today. Its resolution is the orchestrator analogue of the worker `B-FANOUT-CRASH-RESUME-MAYBE-RAN-EFFECT-BEARING` (which is explicitly worker-branch-scoped and does NOT cover the orchestrator): a §26.2 `EFFECT_FENCE_AMBIGUOUS` pause routing the ambiguous orchestrator to operator resolution (RE_FIRE / ABORT — SKIP_AS_FIRED degenerates for an orchestrator, whose absent output the workers consume). This requires a NEW resume-side application site in the orchestrator dispatch path — the linear effect-fence resume threads its directive at step composition (the linear loop), which `_execute_orchestrator_workers` does NOT reach — a genuinely larger mechanism than this slice.
> - **`B-FANOUT-CRASH-RESUME-ORCHESTRATOR-PROCEED-RESIDUAL`** (NEW, registered, **`operator_gated: true`**) — under `CascadePolicy.PROCEED` (SOLO_DEVELOPER) the orchestrator writes NO reserve-before-dispatch marker (v1.61 §1, strict-tier-only) and its pre-capture window still re-dispatches `steps[0]` fresh on a crash → a potential double-fire of an effect-bearing orchestrator. Closing it changes PROCEED's **committed** tier semantic — the deliberate, repeatedly-documented (v1.56/v1.57/v1.60/v1.61/v1.62) "PROCEED accepts the dispatch-before-capture window per the v1.56 PR2-round-4 precedent" — into a fail-closed / pause for the effect-bearing orchestrator. That carries a nameable **C10 ⊥ C11 tension** (action-safety/blast-radius wanting at-most-once even at SOLO vs operator-loop/local-deployment wanting SOLO to never-block) → a **dyadic council + operator AUQ at open** (per workspace `CLAUDE.md` §10.9 + §13.4); NOT convened in this slice. (The v1.56 "no correctness gain" justification for PROCEED's window does NOT transfer to an effect-BEARING orchestrator — v1.61 §4 named this residual rather than silently absorbing it; the same tension generalizes to worker-branch PROCEED, to be considered when that leg opens.)
>
> `closure_gate.py` G1.1 (`standalone_registered + standalone_gated == 0`) was **3 + 0**; after this delta it is **4 + 0** (one closes, two register) → R-FS-1 stays ACTIVE. The remaining R-FS-1 follow-ons keeping the program ACTIVE (now **4**): the worker `B-FANOUT-CRASH-RESUME-MAYBE-RAN-EFFECT-BEARING`, `B-FANOUT-CRASH-RESUME-PAUSE-RECONSTRUCT`, and the two NEW orchestrator legs above. This is the honest FULL-SPEC accounting — it does not declare the orchestrator maybe-ran resolved-whole while the effect-bearing orchestrator + the PROCEED residual remain genuinely open.
