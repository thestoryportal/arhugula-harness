## Class 2 findings (moderate — current-phase spec revision)

### F2-01 — C-IS-03 sub-role count contradiction: prose says "four", the §3 table and both upstream artifacts say "five"

- **Location:** `Spec_Information_Substrate_v1_PREFIX_tension001.md` §3 C-IS-03 — four prose sites contradict the §3 table:
  - Line 178 `**Contract surface.**` — "**Four-sub-role** git tier composition"
  - Line 182 `**ADR commitment(s) honored.**` — "ADR-F2 v1.2 §Decision (combined git tier serving **four-sub-role** composition)"
  - Line 188 `**Specification content.**` lead-in — "The combined git tier serves **four sub-roles** within a single git repository"
  - Line 198 `**Sub-role co-residence contract.**` — "All **four sub-roles** share the same git repository identity"
  - Line 206 `**Cross-sub-role consistency invariant.**` — "the **four sub-roles** share that ledger"
  vs. the §3 table at lines 190–196, which enumerates **five** rows: Versioning · State-ledger via commit stream · JSONL event ledger · Shadow-Git checkpointing · Worktree-isolation for concurrent sub-agent reads.
- **Defect:** The contract is internally self-contradicting on its own central cardinality. The section title is "Four-sub-role git tier composition" and the prose repeats "four" in five distinct places, but the normative table enumerates five sub-roles. The §[traceability] matrix at line 657 compounds the error a sixth time: it grades C-IS-03 as a "**4-sub-role** schema (enum)" — so the contradiction has propagated into the spec's own self-attestation that it is contract-grade. A reader cannot determine the committed cardinality from the artifact: the prose says one number, the enum says another.
- **Discriminator that classifies as Class 2:** (a) only — affects the substantive content of the current-phase (Phase 5) artifact and requires a spec revision (not a typo fix; the count is the contract's load-bearing claim). Discriminator (b) does *not* fire: resolution does **not** require upstream revision. The cross-check below shows the upstream artifacts are correct and it is the spec prose that drifted — fixing the prose to "five" is self-contained to the Phase-5 spec. Discriminator (c) does not fire.
- **Evidence:** The §3 table (lines 190–196) is unambiguously five rows. The spec's *own* ADR-commitment citation at line 182 quotes ADD §2.2 Synthesis verbatim and that quote itself enumerates five elements: "code/spec/prompt/manifest/Skill versioning (foundational) **+** append-only state-ledger via commit stream **+** JSONL event ledger (foundational) **+** on-demand shadow-Git checkpointing (workload-class-opt-in) **+** worktree-isolation for concurrent sub-agent reads (workload-class-opt-in)" — five `+`-joined roles. The upstream `design-substrate/ADR-F2.md` §Decision (line 19) is identically five-element: "git serving a combined role of code/spec/prompt/manifest/Skill versioning (foundational) plus append-only state-ledger via commit stream + JSONL event ledger (foundational) plus on-demand shadow-Git checkpointing (workload-class-opt-in) plus worktree-isolation for concurrent sub-agent reads (workload-class-opt-in)." Both upstream artifacts and the spec's own table say five; only the C-IS-03 prose says four. The "four" almost certainly originates from an authoring stage where commit-stream and JSONL-event-ledger were treated as a single "state-ledger" role and were later split into two table rows (note line 193's composition-contract text — "commit-stream-as-coarse-grain-ledger pairs with JSONL-as-fine-grain-ledger" — which reads as a post-split annotation), with the surrounding prose never updated to follow.
- **Anti-fabrication attack engaged:** A2 (silent scope narrowing) — adjacent: the prose under-counts the contract surface relative to what ADR-F2 §Decision commits. Here it surfaces as an intra-artifact count contradiction rather than a true narrowing, because the table does carry all five.
- **Axis-domain attack engaged:** IS — durable-vs-transient / tier-survival enumeration precision. The combined-git-tier sub-role enumeration is the C-IS-03 contract's entire substance; an ambiguous cardinality means a downstream implementer (IS atomic-unit cluster) cannot determine whether four or five sub-roles must be built, and which posture (foundational vs workload-class-opt-in) attaches to each.
- **Decision-claim label:** *decided.* The artifact's text supports a single reading of the defect: the table and both upstream artifacts agree on five; the prose is wrong. There is no second reading in which "four" is the correct count.
- **Resolution path:** Current-phase (P5-CK) spec revision. Reconcile the C-IS-03 prose and the §3 section title to the five-row table count, and correct the §[traceability] matrix line-657 entry to match. The reviewer does not supply the replacement count-words; the spec-writer reconciles all six sites (§3 title, lines 178/182/188/198/206, traceability line 657) to a single consistent cardinality, with the §3 table treated as canonical since it agrees with ADR-F2 §Decision and ADD §2.2. C-IS-03 must not be locked until this is resolved — a contract that contradicts itself on its own cardinality has not met the §2.5 exit criterion that "every ADR commitment is honored by at least one spec element" in a verifiable way.

### F2-02 — Posture-of-sub-role count is also miscounted: §3 declares "foundational-vs-opt-in posture per sub-role" but the posture split is 3 foundational / 2 opt-in, not derivable from a four-count

- **Location:** `Spec_Information_Substrate_v1_PREFIX_tension001.md` §3 C-IS-03 line 178 `**Contract surface.**` — "Four-sub-role git tier composition **with foundational-vs-opt-in posture per sub-role**"; cross-reference the §3 table Posture column (lines 192–196).
- **Defect:** The §3 table assigns posture per row: Versioning = Foundational; State-ledger via commit stream = Foundational; JSONL event ledger = Foundational; Shadow-Git checkpointing = Workload-class-opt-in; Worktree-isolation = Workload-class-opt-in — a **3 foundational / 2 opt-in** split across five sub-roles. The Contract-surface line frames the contract as "four-sub-role ... with ... posture per sub-role", which under the erroneous four-count cannot reproduce the table's 3/2 split (a four-count would imply some 2/2 or 3/1 partition). This is the F2-01 contradiction's second-order consequence: a reader using the Contract-surface line as the contract's abstract cannot reconstruct the posture distribution, because the abstract's cardinality is wrong. It is listed separately because even after F2-01's count is fixed, the Contract-surface line should explicitly state the posture *split* (3 foundational / 2 opt-in) rather than only "posture per sub-role" — the per-sub-role posture is the contract's discriminating commitment and the abstract currently leaves it to be reconstructed from the table.
- **Discriminator that classifies as Class 2:** (a) only — affects substantive content of the Phase-5 artifact; the Contract-surface abstract is a contract element and currently misrepresents the posture distribution. Not a typo (it is a semantic under-specification of the posture split). Discriminators (b) and (c) do not fire.
- **Evidence:** §3 table Posture column, lines 192–196: three rows tagged "**Foundational** (always-on; no opt-out)", two rows tagged "**Workload-class-opt-in** (per workflow manifest declaration ...)". ADR-F2 §Decision (line 19) confirms the 3/2 split — three roles marked "(foundational)", two marked "(workload-class-opt-in)". The Contract-surface line gives no posture count at all and is anchored to the wrong sub-role count.
- **Anti-fabrication attack engaged:** A5 (missing uncertainty / completeness signal) — adjacent: the contract abstract omits a load-bearing distribution (3 foundational / 2 opt-in) that the body commits, leaving the reader to reconstruct it.
- **Axis-domain attack engaged:** IS — foundational-vs-opt-in posture is exactly the "tier-survival ambiguity" attack: which sub-roles are always-on (and therefore always part of the durable substrate) vs. which are conditionally present per workflow-manifest declaration. An abstract that does not state the split forces the implementer to read the table to learn which two sub-roles are absent under an opt-out workload.
- **Decision-claim label:** *decided.* The table and ADR-F2 §Decision agree the split is 3/2; the Contract-surface line's omission of the split is a single-reading defect.
- **Resolution path:** Current-phase (P5-CK) spec revision, folded into the F2-01 fix. The Contract-surface line should be revised to state both the corrected sub-role count and the posture split explicitly. The reviewer does not supply the replacement wording; the spec-writer revises the abstract so the posture distribution is stated, not reconstructed.

## Disposition

C-IS-03 carries **two Class 2 findings; zero Class 3; zero Class 1**. Per `Project_Workflow_v1_8.md` §4.1.2, the disposition is **fork to current-phase (P5-CK) spec revision** — C-IS-03 must not be locked in its present state.

The single root defect: C-IS-03's combined-git-tier contract states "four sub-roles" in its section title and five prose sites (and once more in the §[traceability] matrix), while its own normative §3 table, ADR-F2 §Decision, and ADD §2.2 Synthesis all enumerate **five** (Versioning · State-ledger via commit stream · JSONL event ledger · Shadow-Git checkpointing · Worktree-isolation). The contract contradicts itself on its central cardinality. This is the kind of defect that would have been silently absorbed by the IS atomic-unit implementer — building four sub-roles, or guessing which four, against a spec that commits five — and propagated to every dependent unit. F2-02 is the second-order consequence: the contract abstract cannot reproduce the table's 3-foundational / 2-opt-in posture split under the wrong count.

Recommended revision scope: a single P5-CK spec-revision pass reconciling all six count sites (§3 title; lines 178, 182, 188, 198, 206; traceability line 657) to the §3 table's five-row enumeration, treating the table as canonical since it agrees with both upstream artifacts, and revising the Contract-surface abstract (line 178) to state the posture split explicitly. The reviewer does not author the replacement text — the spec-writer reconciles to a single consistent cardinality and re-attests C-IS-03 as contract-grade.

This is a single-artifact review (C-IS-03 only); no cross-artifact systemic-pattern surfacing applies. Note for the broader P5-CK pass: the same prose-vs-table count-drift shape should be spot-checked at the other multi-element contracts in this spec — C-IS-02's five-tier table and C-IS-05's six-field signature — to confirm the drift is isolated to C-IS-03 and not a recurring authoring-stage artifact across the IS spec.
