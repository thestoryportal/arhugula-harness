## Class 2 findings (moderate — current-phase spec revision)

### F2-01 — §1.3 row-1 forced-tier annotation contradicts the forced tier it labels
- **Location:** `Spec_Action_Surface_v1.md` §1.3, line 162 — forced-tier rules table, row `code-execution-2025-08-25 beta invoked`.
- **Defect:** The "Forced tier" cell reads `` `tier-4-full-vm` (microVM minimum) ``. The parenthetical "microVM minimum" names a different tier than the value it annotates: per §1.1, `tier-3-microvm` is the microVM tier and `tier-4-full-vm` is the VM tier. The cell asserts a `tier-4` forced value while parenthetically describing a `tier-3` floor. A reader cannot determine from §1 alone whether code-execution-beta forces `tier-4-full-vm` (the literal value) or floors at `tier-3-microvm` (the parenthetical's "microVM minimum"). The two readings produce different runtime resolutions for any code-execution-beta call whose other floors land below `tier-4`.
- **Discriminator that classifies as Class 3/2:** (a) — affects substantive content of the current-phase artifact (a forced-tier rule a downstream unit must implement); resolution is self-contained to §1.3, requires no upstream ADR/ADD revision, so does not escalate to Class 3.
- **Evidence:** §1.3 line 162 forced tier cell: `` `tier-4-full-vm` (microVM minimum) ``. Contrast §2.3 line 216, which states the code-execution `sandbox_tier_floor` as `` `tier-4-full-vm` (microVM minimum; E2B Firecracker class) `` — i.e. the spec elsewhere also carries the same ambiguous phrasing, so the defect is not an isolated typo but a recurring phrasing. Downstream confirmation: `Implementation_Plan_Action_Surface_v1.md` U-AS-02 acceptance criterion 2 (line 170) already had to paper over the contradiction: "Code-execution beta forces `TIER_4_FULL_VM` (spec §1.3 row 1 'microVM minimum'; full-VM accepted under tier-monotonicity)." The plan author resolved the ambiguity by appeal to a monotonicity argument the spec §1.3 does not itself state — exactly the implementation-drift this review exists to prevent.
- **Anti-fabrication attack engaged (if any):** A2 (silent scope narrowing — the forcing rule's actual floor is under-specified).
- **Axis-domain attack engaged (if any):** AS — tier-label / mechanism mismatch (the §1.3 forcing rule's tier label does not unambiguously bind a single §1.1 tier).
- **Decision-claim label:** *proposing*. Reading 1: code-execution-beta forces exactly `tier-4-full-vm` and "(microVM minimum)" is vestigial descriptive prose carried from an earlier tier-set draft. Reading 2: the forcing rule establishes a `tier-3-microvm` floor and the `` `tier-4-full-vm` `` token is the error. The artifact text supports both; the skill does not pick. ADR-F4 §Decision and §Rationale (a) speak of "microVM tier mandatory" for LLM-generated code execution, which leans toward Reading 2 — but §1.3's stated forced value is `tier-4`, so the spec's own intent is genuinely indeterminate and the operator must settle it.
- **Resolution path:** Phase-5 spec revision-pass on §1.3 to make the forced tier for code-execution-beta resolve to exactly one §1.1 tier identifier, and to remove or reconcile the contradicting parenthetical. The skill does not supply the corrected value — the operator/spec-writer selects Reading 1 or Reading 2 and the §1.3 cell is rewritten to state it unambiguously. Not a §2.7.6 fork.

### F2-03 — §1.1 escape-risk and cold-start columns carry [HIGH] tags whose source is a non-Action-Surface cluster, with no in-spec confidence-discipline note
- **Location:** `Spec_Action_Surface_v1.md` §1.1 line 141, table header — "Escape risk (per Cluster 3 §2.2 [HIGH])" and "Cold-start (per Cluster 3 §2.2 [HIGH])"; cell values lines 143–146.
- **Defect:** §1.1's escape-risk and cold-start columns present quantitative/comparative claims (`<10 ms`, `10–50 ms`, `100–150 ms`, `Firecracker ~150 ms / full-VM seconds`; "High / Medium / low / Very low") tagged [HIGH] and sourced to "Cluster 3 §2.2". Cluster 3 §2.2 is a design-phase research cluster, not an artifact reachable from the Phase-7 `design-substrate/` filesystem — the skill cannot verify the cited table exists or that the cell values transcribe it faithfully (A4 spot-check is not satisfiable). More substantively: these cold-start figures are mechanism-class-bound (Firecracker, gVisor) yet §1.2's stability invariant explicitly decouples `sandbox.tier` (structural) from `sandbox.tech` (swap-friendly). A [HIGH]-tagged latency figure attached to a tier whose mechanism is by-contract swappable is an over-tagged claim: the figure is [HIGH] only for the named mechanism, not for the tier. The spec gives no note distinguishing tier-stable claims from tech-bound claims in this table.
- **Discriminator that classifies as Class 2:** (a) — the confidence tag is applied to substantive content (latency figures an implementer or cost model may rely on) at a precision the source-binding does not warrant once §1.2's tech-swap decoupling is taken into account. Self-contained to §1.1; no upstream revision required.
- **Evidence:** §1.1 line 141 header tags both columns "[HIGH]"; line 146 `tier-4-full-vm` cold-start cell: "Firecracker ~150 ms / full-VM seconds" — a tech-specific figure inside a tier whose §1.2 line 152 invariant states the mechanism class is swappable and "`sandbox.tech` is the swap-friendly discriminator". ADR-F4.md line 91 confirms the source is "Cluster 3 §2.2 sandbox stack tradeoff table [HIGH]" — a cluster deliverable not present under `design-substrate/`.
- **Anti-fabrication attack engaged (if any):** A5 (uncertainty signal applied at the wrong granularity) and A7 (weak-source escalation — [HIGH] on a figure whose load-bearing precision is tech-bound while the column is labelled tier-stable). A4 spot-check could not be completed because Cluster 3 is not in the workspace filesystem; this is recorded, not fabricated into a finding.
- **Axis-domain attack engaged (if any):** AS — tier-survival ambiguity (a tech-bound figure presented in a tier-stable table without the §1.2 decoupling carried through).
- **Decision-claim label:** *proposing*. Reading 1: the [HIGH] tag and figures are an intentional design-time reference snapshot and the §1.2 decoupling is understood to override them at tech-swap — in which case a one-line in-§1.1 note suffices. Reading 2: the figures are load-bearing for downstream cost attribution (C-AS span schema carries `sandbox.cost.tier_overhead_*`) and the tier/tech tag granularity is a genuine precision defect. The skill cannot determine which from §1 text alone.
- **Resolution path:** Phase-5 spec revision-pass — add a confidence-discipline note to §1.1 distinguishing tier-stable claims (escape-risk *ordering*, cardinality) from tech-bound claims (absolute cold-start figures), and qualify the [HIGH] tag granularity accordingly. The skill does not author the note text or re-tag specific cells.

## Class 1 findings (minor — documentation drift)

### F1-01 — §1.2 "Per-tier capability lower bound" row asserts tier monotonicity by appeal to §1.1's escape-risk ordering, but §1.1's column ordering is not labelled as a monotonic ordering
- **Location:** `Spec_Action_Surface_v1.md` §1.2 line 154 ("Per-tier capability lower bound" row): "higher tiers structurally accommodate lower-tier operations (tier monotonicity per §1.1 escape-risk descending)".
- **Defect:** §1.2 line 154 grounds the tier-monotonicity invariant in "§1.1 escape-risk descending". §1.1's table rows do descend in escape risk (High → Medium → Docker medium/gVisor low/Kata very low → Very low), but §1.1 nowhere labels its row order as a normative ordering, and the `tier-3-microvm` escape-risk cell is itself a *range* ("Docker medium / gVisor low / Kata very low") that overlaps the `tier-2-container` value ("Medium"). Monotonicity-by-escape-risk is therefore not strictly derivable from §1.1 as written — a `tier-3` running Docker has "medium" escape risk equal to `tier-2`. The invariant is correct on tier *identifier* ordering (1<2<3<4) but the stated *justification* ("escape-risk descending") is not clean.
- **Defect class:** Cross-reference / justification imprecision that does not change the invariant's semantics (the four-value ordering is unambiguous from the `tier-N` identifiers). Drift, not a content gap.
- **Resolution:** Inline fix in §1.2 — re-anchor the monotonicity justification to the tier-identifier ordinal (`tier-1 < tier-2 < tier-3 < tier-4`) rather than to the non-strict escape-risk column.

### F1-02 — §1.3 "Deferred to implementation discretion" cites Pattern Reference Catalog v1.0 §11.3.2, a design-phase artifact not present under `design-substrate/`
- **Location:** `Spec_Action_Surface_v1.md` §1.3 line 165 — "Deferred to implementation discretion ... per Pattern Reference Catalog v1.0 §11.3.2 derivative."
- **Defect:** The deferral note cites "Pattern Reference Catalog v1.0 §11.3.2". That artifact is not in the Phase-7 `design-substrate/` filesystem (directory listing confirms no such file), so the citation is non-resolvable from this workspace. The deferral itself is substantively fine (container-runtime selection within `tier-3-microvm` is a legitimate implementation-discretion item, and ADR-D2 §1.10 — which *is* cited alongside — is the operative deferral authority). The Pattern Reference Catalog pointer is a redundant secondary citation that an implementer cannot follow.
- **Defect class:** Non-resolvable secondary cross-reference; the primary citation (ADR-D2 §1.10) carries the deferral, so semantics are unaffected. Drift.
- **Resolution:** Inline fix — either drop the non-resolvable Pattern Reference Catalog pointer or annotate it as a design-phase-archive reference not expected to resolve from `design-substrate/`.

## Disposition

C-AS-01 §1 is **structurally sound and ADR-faithful** — the four-tier set, the stable structural identifiers, the cardinality bound, and the tier × deployment-context tech split all honor ADR-F4 v1.1 §Decision and §Consequences (a). No Class 3 finding was surfaced: no project-commitment violation (discriminator (c)) and no upstream-artifact-revision requirement (discriminator (b)).

However, the contract is **not yet safe to build U-AS-01 / U-AS-02 against without a Phase-5 spec revision-pass.** Three Class 2 findings affect substantive content an implementer must consume:

- **F2-01** is the highest-severity finding and the most build-relevant: §1.3's code-execution-beta forcing rule is internally contradictory (`tier-4-full-vm` value vs "microVM minimum" parenthetical). U-AS-02 (the unit that implements §1.3) has *already* silently resolved the ambiguity in its acceptance criterion 2 by importing a monotonicity argument the spec does not state. This is precisely the spec→plan calibration drift the Phase-7 pre-implementation review exists to catch. It must be resolved in the spec before U-AS-02 lands, so the unit implements a stated rule rather than an inferred one.
- **F2-02** is a dangling intra-document reference (`§1.5.2`) on a load-bearing capability rule; the referent is C-AS-12 §12.2 and the pointer must be corrected.
- **F2-03** is a confidence-tag-granularity defect — [HIGH]-tagged tech-bound latency figures presented in a table whose §1.2 invariant decouples tier from tech.

**Recommended disposition: cleared for build pending a Phase-5 spec revision-pass on C-AS-01 §1.3 and §1.1**, per `Project_Workflow_v1_8.md` §4.1.2 (Class 2 — current-phase artifact revision). This is **not** a §2.7.6 Phase-7 execution fork: all three findings resolve inside the current-phase spec artifact with no ADR/ADD/PRD revision, so no halt-execution (§2.7.6 Class 1) routing is triggered. The two Class 1 findings (F1-01 justification imprecision, F1-02 non-resolvable secondary citation) fold into the same revision-pass as inline fixes.

No systemic cross-artifact pattern is surfaced — this review scopes a single contract section, below the ≥3-artifact threshold for a workflow §7 session-prompt-template recommendation. F2-01 and F2-03 do share a shape (ambiguous/over-precise carry-over phrasing also visible at §2.3 line 216 and §2.3 line 221); the spec-writer should check whether the §1.3 "microVM minimum" phrasing and the §1.5.2 dangling reference recur elsewhere in the Action Surface spec during the revision-pass.
