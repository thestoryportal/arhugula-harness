Apply these runner translations only:

- Root `AGENTS.md` is the Codex instruction entrypoint; targeted `CLAUDE.md` sections remain canonical lineage. The canonical body's §12 citations resolve against `CLAUDE.md` — §12 is unchanged by this skill in either runner.
- A "lane" here is one non-interactive `codex exec --profile arhugula-implementer` leg in its own `.codex-worktrees/<leg-id>` worktree, driven from one orchestrator session per `AGENTS.md:29-31`; two lanes is exactly the standing concurrency cap of 2 on the reference machine (`AGENTS.md:31`), so this recipe never justifies a third.
- The canonical `ship-pr` fixed point maps to this flow's autonomous-loop gates: the merge, post-merge-refresh, local-main-sync and worktree-disposition gates recorded with `just codex-loop-record` and verified by `just codex-loop-check` (`AGENTS.md:25`). The serial constraint is therefore: lane B records no merge gate until lane A's post-merge-refresh gate is recorded and its terminating refresh has actually merged. Gate evidence is branch/HEAD/worktree-fingerprint-bound and `codex-loop-check` compares every precommit gate's branch/head to closeout — so lane B's mandatory replay is a **NEW loop, not a patched one**: initialize a FRESH loop ledger in the replayed worktree (`.harness/codex_loop_state.json` is untracked and absent there — the first `codex-loop-record` against a missing ledger exits `loop_state_missing`, and copying the abandoned worktree's ledger produces `gate order invalid` when new records append after the old ones) and run the **complete ordered gate sequence from `preflight` onward** on the replayed branch/worktree — **bootstrapping the loop FIRST and reapplying the work as UNCOMMITTED changes in TWO stages** — replay the TESTS first so `red` records an honest failure against the not-yet-applied implementation, then apply the implementation at its own gate (`git cherry-pick -n` / `git apply` restricted to test paths, then source paths; never a plain committing cherry-pick, and never the whole patch before `red`: the loop mandates `plan -> red(status=failed) -> implementation`, and its commit gate requires HEAD to change AFTER closeout, so work committed — or a red recorded against an already-green tree — can never honestly complete the lifecycle) — even when the reapplied diff is byte-identical: the old records are bound to the abandoned branch and cannot carry, and a fresh ledger is what points the final `worktree_disposition` gate at the REPLAYED worktree/branch (which merges and prunes normally) instead of demanding the abandoned branch be pruned, whose forced deletion is guard-denied. The abandoned original branch then sits OUTSIDE the loop state: per the canonical abandon rule, leave it in place and record it in the **TRACKED `.harness/two-lane-pending-prunes.md` row shipped in the replacement PR** — that tracked row is the durable reminder. A **DEFERRED-HIL ledger row** (`loop_defer`) may additionally surface it in the CURRENT arc's EXIT REPORT, but the loop ledger is gitignored and worktree-local — it is deleted with the reaped worktree or wiped at the next loop activation, so it is an in-run convenience, never the durable home. (Do NOT rely on the SessionStart hygiene sweep or the session-end branch report either: both list only merged refs, so an unmerged abandoned branch is invisible to them.) One more scoping fact: the `.loop-active` loop-mode marker resolves per worktree root — in a shared-orchestrator setup a single marker can govern both lanes, so never stop loop mode while the other lane is mid-run.
